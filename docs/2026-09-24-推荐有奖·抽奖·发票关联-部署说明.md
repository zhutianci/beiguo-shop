## 二、数据库变更（9 条，全部新增，零 DROP）

`prisma migrate diff`（HEAD → 本版 schema）实际输出：

```sql
ALTER TABLE `balance_logs` ADD COLUMN `order_id` INTEGER NULL;
ALTER TABLE `receipts` ADD COLUMN `show_ai_wording` BOOLEAN NULL;
ALTER TABLE `coupons` ADD COLUMN `source` VARCHAR(20) NULL;
CREATE TABLE `invoice_requests` (...);   -- 开票填写链接
CREATE TABLE `lottery_prizes` (...);     -- 抽奖奖项
CREATE TABLE `lottery_entries` (...);    -- 抽奖资格与结果（order_id 唯一）
CREATE INDEX `balance_logs_order_id_idx` ON `balance_logs`(`order_id`);
CREATE INDEX `invoices_source_key_idx` ON `invoices`(`source_key`);
CREATE INDEX `coupons_source_idx` ON `coupons`(`source`);
```

- 三个 ADD COLUMN 都是可空、追加在末尾 → INSTANT
- 三个 CREATE INDEX → INPLACE / LOCK=NONE（invoices 与 coupons 都是小表）
- 三张新表空表建出，零代价

**新 Prisma Client 会显式点名这些新列，新镜像跑旧库必挂（P2022）。所以必须先 db push、再换镜像。**
`scripts/deploy.sh` 的顺序是反的，这一版**不要直接跑它**。

## 三、部署顺序

照交接文档第十四节「正确的部署顺序」，这里只列要点：

```bash
cd /opt/beiguo/beiguo-shop && git pull origin main

# 0) 回滚标签（build 之前！）
docker tag beiguo-shop-app:latest beiguo-shop-app:rollback-$(git rev-parse --short HEAD@{1})

# 1) 备份并校验（不要管道进 gzip，否则做不了 Dump completed 校验）
docker compose --env-file .env.production exec -T db mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers --set-gtid-purged=OFF beiguo_shop \
  > /opt/beiguo/backups/beiguo_shop_$(date +%Y%m%d_%H%M%S).sql
tail -3 /opt/beiguo/backups/beiguo_shop_*.sql | grep "Dump completed"

# 2) 预览 DDL：输出字节数 > 0，逐条对照第二节那 9 条；出现任何 DROP 立刻停手
#    （用交接文档第五节的临时容器命令，--script）

# 3) db push（旧镜像仍在跑，新增的列与表旧代码不读不写，对线上零影响）
#    然后阳性对照：SHOW TABLES LIKE 'lottery_entries'; 同时查一张必然存在的 orders

# 4) build（后台跑、轮询；前后各打一次 latest 的镜像 ID，相同说明没构建成功）
# 5) 只重启 app：docker compose --env-file .env.production up -d --force-recreate app
#    核对 docker inspect -f '{{.Image}}' beiguo-app 等于新 ID
```

**不需要新环境变量。** 但如果生产 `.env.production` 设置了 `NOTIFY_EVENTS` 白名单，
要把 `lottery.won`（有人中奖）和 `invoice.submitted`（客户通过填写链接提交了开票信息）加进去，
否则这两条企业微信推送会被静默丢弃。

**不需要回填脚本。** 老的内推返现流水 `order_id` 为空，读取时从备注「订单#123 内推返现」解析（`lib/balance.ts`）。

买家侧（测试账号）：

## 六、钱路径上修掉的缺陷（上线后行为会变的地方，逐条写清）

| 缺陷 | 以前 | 现在 |
|---|---|---|
| 后台取消待付款订单后，买家开着的收银台仍能按优惠价付款 | 只放券不关收款单 → 付款照样匹配、发货，券却已放回可再用 | 取消 / 退款 / 人工标已付款时先作废待支付收款单 |
| 券被放回之后钱才到账 | 付款核销找不到 LOCKED 的券 → 券保持可用，优惠被享受两次 | 核销兜底：把这张单的券从 AVAILABLE/EXPIRED 补核销为 USED；券已被别的单占用则记错误日志待人工对账 |
| 兜底清扫放回「正在付款」的券 | 锁券超过 120 分钟就放回，不看买家是不是刚开始付款 | 有活着的收款单就不放；发起付款时刷新锁定时间 |
| 过期关单与到账同时发生 | 无条件把整批收款单置 -1，已到账的也被覆盖 → 已付款 + 已取消，券放回 | 逐条条件更新，只处理真正翻成 -1 的；匹配瞬间被关闭的到账记入「未匹配」并在收款监控页高亮 |
| 后台「标已支付」非原子 | 与支付回调并发时销量加两次 | 条件更新，只有抢到的一方记销量、核销券、落地发票 |
| 撤回「已交付」 | 每次减销量、加库存（自动发货商品凭空多出库存） | 已交付 ↔ 处理中来回改不动销量库存；已付款的单取消 −1、恢复 +1；自动发货商品库存一律由卡密数决定 |
| 内推返现 | 流水的「变动后余额」在事务外计算，并发时写错；未付款的单被标已交付也会结算 | 事务内读回余额；只结算已付款的单；流水写入订单 id |
| 后台扣减余额 | 先查后扣，两次并发提现能扣成负数 | 条件更新（余额 ≥ 扣减额才扣） |
| 同一张站内订单的发票 / 收据 | 订单页只看背书行，另一条外部订单行上的发票看不见 → 可以申请第二张、再付一次 6% | 两条行一起查；订单页、邮箱查订阅、四个申请接口都做跨行查重；收据按任一已付发票出含税额 |
| 已付过税费的发票 | 后台能「重置为未开发票」（=删除）或改回「待支付税费」 | 服务端拒绝，前端不再提供这两个选项；停开请用「不可开据」 |
| 禁用账户 | token 30 天内照常下单、领券 | `getCurrentUser` 把禁用账户当未登录；**全部后台接口**路由内再验一次管理员（查库），被禁用/降级的管理员立即失去权限 |
| 下单接口返回整行订单 | 把 `referrerId` / `referralReward` 发给买家 | 显式白名单 |

## 七、需要站长拍板的事（代码里刻意没替你决定）

1. **退款后的内推返现要不要扣回。** 已入推广人余额的返现，退款时代码不动（余额可能已线下提走）。
   现在的做法是：退款后请在「内推管理 → 提现/调整」里人工处理。
2. **首页右下角「XX 刚刚购买了」的滚动提示用的是编造的城市与时间**（`components/live-order-notification.tsx`、
   `api/orders/recent` 的 `FAKE_CITIES`，不足 5 条时还会补假订单）。这和全站「不编数字」的原则冲突，
   也有被认定为虚假宣传的风险。建议只展示真实订单、去掉城市，或者整块下掉。
3. **会员等级目前只有「等级标识」这一项权益。** 后台「系统设置 → 会员等级」里写什么，买家就看到什么 ——
   只写真正会兑现的。
4. **抽奖合规：** 《反不正当竞争法》要求写明奖项种类、兑奖条件与方式；最高奖不得超过 5 万元。
   请在「抽奖管理 → 活动规则」里写清楚（它原样展示在抽奖弹窗里）。
5. **手机号不再开放买家自助绑定。** 站上没有短信验证，开放了会被人占用别人的号码、并能逐个试出哪些号码是本站客户。
   需要登记请客服在后台改。要开放自助绑定得先接短信验证码。
6. **余额流水的备注不再给买家看。** 后台写备注的输入框从没说过买家看得见，历史备注是按内部备注写的。
