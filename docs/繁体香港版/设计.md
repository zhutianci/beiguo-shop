# 繁体香港版（简 / 繁双版本）设计

> 2026-10-19 · 分支 `feat/zh-hk`（worktree `ai-service-shop-hk`）· 站长需求：「全文支持简繁切换，按所在地自动识别，做香港繁体 SEO」

## 0. 结论先行

| 问题 | 决定 | 理由 |
|---|---|---|
| 繁体版放哪 | **同域子目录 `/zh-hk/…`**，简体地址一个都不动 | 子目录继承主域权重（本站 Google 收录本来就少，不能再分散）；同域 cookie，登录态两版通用；Apple（`/hk/`）、维基百科（`/zh-hk/`）、Microsoft Learn（`/zh-hk/`）都是这个结构 |
| 繁体内容从哪来 | **不写第二份代码 / 第二份内容**：页面照常用简体写，经 `/zh-hk` 访问时在**输出层**逐字转成香港繁体 | 全站 4.2 万行中文直接写在代码里，抽词条要改上千个文件、和 40 个并行分支全面冲突；数据库里 2000+ 篇 AI 学习内容、上千条新闻、商品介绍也无需逐篇翻译，改一处简体，繁体同步。这正是维基百科中文版的做法（LanguageConverter：只存一份底稿，看的时候按地区转换） |
| 转换质量 | OpenCC 词库 + **香港用词表** + **DeepSeek 审校**（模型只报错、人工复核后写进词表） | 机器转繁的错误只出在「一简对多繁」和地区用词上，修在词表里一次，全站上万处同时生效，且不会出现模型改写了价格、事实的情况 |
| 自动识别 | **首次访问**按浏览器语言 / Cloudflare IP 国家跳到对应版本，顶部提示可一键切回，选择记 cookie 一年；**爬虫永不跳转**；另可切成「只提示不跳转」 | 站长要求自动切换；Google 官方更推荐横幅（自动跳转可能让人和爬虫看不到另一版），所以做成环境变量 `ZHHK_AUTO_SWITCH=redirect|banner|off` |
| SEO | 每版独立 URL、canonical 自指、hreflang 双向互指（繁体页 `<head>` + 站点地图）、`x-default` 指简体、香港版标题用实测香港搜索词 | Google 国际化 SEO 的标准做法；香港 Google 份额 90.4%（StatCounter 2026-09），百度可忽略 |
| 收录范围 | **第一期只放核心页**进繁体索引（首页、充值落地页、商品、教程、条款等），提示词 / 新闻的繁体页可看但 `noindex` | 大量机器转换页一次性放量，可能被当成「规模化自动生成内容」（Google 垃圾政策原文举了「翻译等自动变换」的例子），连累简体站。观察 4 周再按类型放开（改 `zhhk/policy.json`） |

## 1. 调研摘要（2026-10-19，来源见各条）

- **Google 官方**（Search Central「本地化版本」「多区域站点」）：子目录 / 子域名 / ccTLD 均可；hreflang 必须双向、含自身、可用 `zh-Hans` / `zh-Hant` 这类文字代码；HTML、HTTP 头、站点地图三种写法等效；**不建议按 IP 自动跳转**、Googlebot 多从美国 IP 抓取且不带 Accept-Language；规模化内容政策点名「翻译等自动变换批量生成页面」。
- **维基百科中文**：一份底稿 + 四层转换规则（内置词表、全站表、公共转换组、条目手工标记），`/zh-hk/` 等变体 URL，hreflang 输出 zh-Hans / zh-Hant / zh-Hant-HK 等，`x-default` 指 `/wiki/`。本设计的「OpenCC + 香港词表 + 审校修正」就是这套分层的简化版；香港 IT 用词直接取自它的公共转换组 `Module:CGroup/IT`。
- **OpenCC**：`s2hk` 只换字形、**不做香港用词**（视频仍是視頻、登录仍是登錄）；`s2hkp` 的香港词组只有约 80 条且多为人名地名。所以香港用词表必须自建。
- **香港搜索词实测**（Google 下拉，hl=zh-TW&gl=hk，原始数据 scratchpad/hk-suggest-raw.json）：帳號（8 条）≫ 賬號（1 条）；登入（10）＞登錄（8，且被「實價登錄」污染）；教學 的联想是通用学习词，教程 的联想几乎全是简体跨境购买词；主词是 **訂閱 / 付款**（「ChatGPT Plus 付款」HK 10 条 vs CN 2 条），充值 5 条，「增值」几乎都是增值稅；「XX 香港」句式（ChatGPT / Claude / Gemini / Codex / Grok 香港）全部满 10 条，核心问题是「香港能不能用、怎么付款」。
- **业务事实（写文案时必须遵守）**：ChatGPT、OpenAI API、Claude 的官方支持地区**都不含香港**（与内地相同），文案不能写「香港官方可用」；Gemini 网页版 2026-03 起官方开放香港。WeChat Pay HK 2025-01 起可扫内地「个人小商户」收款码（需香港身份证认证）；AlipayHK 官方不支持付个人收款码。

## 2. 架构

```
浏览器 ── Cloudflare ── 隧道 ── nginx ──┬─(默认)──────────────────────────────▶ Next :3000（简体，原样）
                                        └─ /zh-hk/…、/_next-hk/…、               ▶ 转换代理 :3001 ──▶ Next :3000
                                           /api/… 且带 x-bg-lang: zh-HK               （zhhk/proxy.cjs，与 Next 同进程）
```

- **简体站的流量完全不经过转换代理**（nginx 按路径 / 请求头分流），转换代理出任何问题只影响繁体页。
- 转换代理处理 `/zh-hk/x`：去掉前缀、加请求头 `x-bg-lang: zh-HK` 转给 Next；把返回的 HTML、RSC（客户端导航数据）、JSON 逐字转繁体。
- 繁体页加载的 JS 分块走 `/_next-hk/<词典版本>/static/…`：代理取 Next 的原件转繁体后返回（内存缓存，长缓存头）。webpack 运行时里的 `publicPath "/_next/"` 一并改成繁体路径，后续按需加载的分块也是繁体——**服务端渲染和浏览器水合拿到的是同一份繁体文字**，不会水合不一致。
- 繁体页里的 `fetch('/api/…')` 由 `auth-fetch-patch` 自动带上 `x-bg-lang: zh-HK`，nginx 据此送转换代理，接口返回的商品名、提示文案同样是繁体。
- 买家在繁体页**填写的内容原样落库**（代理只改响应、不改请求体）：发票抬头、留言、搜索词都保留用户输入。

## 3. 转换器（`zhhk/convert.cjs`）

- 正向最大匹配（与 OpenCC 相同），先词组后单字；只碰汉字，HTML / JSON / JS 语法字符一个不动。
- **硬约束：每条词典项转换前后 UTF-8 字节数相同。** RSC 流里大段文本用 `T<十六进制字节数>,` 做长度前缀，字节数一变 React 就解析错位、整页白屏。词典生成时过滤（丢弃 854 条，基本是扩展 B 区生僻字），加载时再校验一遍、不等就拒绝启动；香港用词表也因此要求「同字数」（如 内存→記憶體 不能收）。
- 流式：在缓冲区最后一个非汉字处切开（词组只由汉字组成，所以切口两侧分别转换 ≡ 整段转换），HTML 不必等整页渲染完。
- 性能：41 万字符 31 毫秒；词典加载 26 毫秒、常驻约 10 MB。

## 4. 词典（`zhhk/dict.json`，由 `scripts/i18n/gen-zhhk-dict.mjs` 生成）

三层，后者覆盖前者：

1. **OpenCC** STCharacters + STPhrases（简 → 标准繁体，Apache-2.0）。
2. **字形调整**：OpenCC 标准繁体里的旧字形换成通行字形（爲→為、衆→眾、覈→核、臺→台…）。刻意**不用** OpenCC 的 HKVariants（説、户、税、衞）：那是《常用字字形表》的字形，而香港网页、银行、税局实际用、香港用户搜索时打出来的是 Big5 一系的 說、戶、稅、衛。
3. **香港用词表 `zhhk/vocab-hk.tsv`**：帳號、登入、教學、電郵、短訊、預設、設定、上載、搜尋、私隱、影片、質素、解像度、聯絡、到賬…；「信息」按意思分三种（默认 資訊；帳號 / 訂單 / 收款等「具体资料」→ 資料；錯誤 / 提示「一句话」→ 訊息）。每条注明依据（kw 实测 / hk 惯用 / cg 维基 CGroup / ds DeepSeek / cl 抢匹配检查），并**写进所有包含它的 OpenCC 长词组**，否则长词组会抢先匹配把覆盖绕过去。

### 4.3 DeepSeek 审校（`scripts/i18n/zhhk-review-candidates.mjs` → `zhhk-deepseek-review.mjs`）

1. 从源码（去注释，后台 / 渠道后台 / 机器人 / 营销邮件不转繁体，不收）+ 数据库导出（2361 篇 AI 学习内容、商品、标签）里找出所有「一简对多繁」的决策点：OpenCC 词组决定 749 个，单字默认窗口取源码全部 + 数据库出现 ≥3 次的，共约 9400 条候选。
2. DeepSeek（deepseek-chat，关思考，JSON 输出）按 100 条一批审校，只回报「哪个词在这个句子里转错了、香港该怎么写」。**实际花费约 0.79 元**（这把密钥同时给 AI圈大事记 用，脚本默认 2 元封顶）。
3. 回报 530 条，自动丢弃「本来就转对了」的，剩下人工复核：大部分是窗口截断造成的误报（裏 / 裡来回改、登入 / 登錄互改），**收录 27 条**（含「信息」按语境分写的 12 条），如 发卡→發卡（OpenCC 给「髮卡」= 发夹）、并发送→並發送（OpenCC 给「併發送」）、联系→聯絡、复核→覆核、到账→到賬、设备→裝置、一目了然、上链→上鏈。词表现共 89 条（kw 4、hk 34、cg 18、ds 27、cl 6）。

### 4.4 抢匹配检查（`scripts/i18n/zhhk-collisions.mjs`）

正向最大匹配的固有毛病：前一个字和后一个词的头先组成不相干的词组——「被复制」里「被复」先匹配成「被複」，结果是「被複制」（OpenCC 本身也有）。检查脚本对语料里每个高频词比较「上下文里转出的样子」与「单独转出的样子」，找出被抢的位置，补更长的词（被复制→被複製、面包屑→麵包屑、下注明→下註明）。

**以后的维护**：新增大量内容后重跑这三个脚本；改词表后 `node scripts/i18n/gen-zhhk-dict.mjs` 重新生成并提交 `dict.json`，随镜像生效（词典版本号变 → 繁体 JS 分块地址变，浏览器与 CDN 不会拿到旧词典的分块）。

## 5. 转换代理（`zhhk/proxy.cjs`，入口 `zhhk/entry.cjs`）

- `ZHHK_ENABLED≠1` 时入口不起代理，与原来的 `node server.js` 完全相同。代理任何异常只回这一个请求 503，不抛到进程层（它和 Next 同进程）。
- HTML 后处理（转繁体之后）：脚本地址换成 `/_next-hk/…`；站内 `href="/x"` 补 `/zh-hk`（给爬虫与水合前的点击用，切换链接 `?hl=` 除外）；`<head>` 里 canonical / og:url 补前缀、香港版标题替换、按收录范围补 `noindex` 或输出 hreflang；JSON-LD 的 inLanguage、og:locale 换成 zh-HK。
- 跳转：Next 的 `redirect('/login')` 等同站页面跳转自动补 `/zh-hk`；middleware 的简繁跳转带标记头，代理不再补（否则「切回简体」会被补回繁体）。
- 不提供繁体的：`/zh-hk/admin`、`/zh-hk/partner` → 404；收据、开票链接、退订、客服回复等带令牌的票据页 → 302 回简体原文（法律凭证不转字）；`/zh-hk/*.xml|txt` → 404（站点地图、robots 只在根路径）。
- 渠道站暂不提供繁体版（`ZHHK_HOSTS`，默认取 `PLATFORM_HOSTS`）。

## 6. Next 这一侧

### 6.1 根布局
读请求头 `x-bg-lang`（总开关关着时一律简体）：`<html lang>`、`og:locale`、**metadataBase 带 `/zh-hk` 路径**——Next 解析相对地址时会把 metadataBase 的路径拼在前面，于是全站 63 处相对 canonical 在繁体页上自动变成 `/zh-hk/…`，一处不用改。

### 6.2 middleware（`src/lib/i18n/middleware-lang.ts`）
matcher 加了「所有前台页面」。规则按顺序：① `?hl=` 切换链接：记住选择、302 到目标版本去参数地址；② 已有选择且与当前版本不同：跳过去（客户端导航的 RSC 请求也跳，Next 的路由按最终地址更新地址栏）；③ 首次访问的整页请求：浏览器语言优先于 IP（在港的内地访客看简体、海外港人看繁体），没有任何中文信号（如 Googlebot）不跳。爬虫只做①的去参数跳转。

### 6.3 链接与路径
- `next.config.js` 把 `next/link` 别名到 `src/lib/i18n/link.tsx`：繁体页上站内链接自动带 `/zh-hk`，简体页上就是原版。全仓 117 个文件一个不改。
- 前台 7 个按路径判断的组件改用去前缀的 `usePathname`（`src/lib/i18n/navigation.ts`），服务端与浏览器算出同一路径（流量埋点仍记带前缀的真实地址，可区分繁体流量）。
- `router.push('/x')`、`<a href>` 这类没经过 Link 的跳转，由 ②「已有选择」规则兜底补到繁体。

### 6.4 切换入口
页头（lg 以上）、手机菜单、页脚底栏。普通 `<a href="/zh-hk/x?hl=zh-hk" rel="nofollow">`：不依赖 JS（iPhone 上水合常晚 10 秒以上，那段时间点按钮也要生效）。自动切换后顶部提示「已按所在地区切换为繁体中文（香港）· 簡體」，12 秒后消失。

## 7. SEO

### 7.1 收录范围（`zhhk/policy.json`，代理与站点地图共用）
第一期可收录的繁体页：首页、`/chongzhi` 及各充值落地页、`/products` 及商品页、`/guides` 及教程、`/learn`、`/news`（仅列表页）、`/jiema`、`/about`、`/support`、`/terms`、`/privacy`。其余繁体页照常可看，但 `noindex,follow`、不进站点地图、不写 hreflang。**建议 4 周后看 Search Console 的繁体页表现，再把 `/prompts/` 加进 indexPrefixes。**

香港版标题（同文件 `titles`）：首页与 7 个充值落地页按实测香港搜索词改写（訂閱、付款、教學、分別），不写「香港官方可用」。

### 7.2 hreflang
- 值：`zh-Hans`、`zh-CN` → 简体；`zh-Hant`、`zh-HK`、`zh-MO`、`zh-TW` → 繁体；`x-default` → 简体。（台湾读者看到的是香港用词，但比简体好；以后要做台湾版再拆。）
- 繁体页：代理在 `<head>` 输出。简体页：不经过代理，靠站点地图（`src/lib/i18n/sitemap-hreflang.ts` 把每个地址展开成简繁两条、各带整组 `xhtml:link`）。Google 认可只用站点地图声明，两处是同一组值。

### 7.3 robots
`/zh-hk/pay/`、`/zh-hk/lookup`、`/zh-hk/learn/search` 与简体同样屏蔽；`?hl=` 切换链接不抓。

## 8. 上线前站长要确认的事

1. **香港买家怎么付款**：收银台只有内地支付宝 / 微信个人收款码，人民币标价。建议用一个真实的 WeChat Pay HK（已做香港身份证认证）扫一次站内收款码，确认能付、且收款手机上的到账通知能被现有系统识别（`lib/vmq.ts` 的解析是按内地通知格式写的）。没验证之前，繁体页不要写「香港可付款」。
2. **自动切换方式**：默认 `redirect`（按你的要求自动跳转）。若担心影响 Google 收录可改 `banner`（只提示不跳），改环境变量重启 app 即可。
3. **Search Console**：繁体页与简体同一个资源，无需新建；上线后重新提交 `sitemap.xml` 与 `sitemap-content.xml`，4 周后看「国际定位」报告有没有 hreflang 错误。
4. **Cloudflare**：确认 Network → IP Geolocation 是开着的（`CF-IPCountry` 头靠它；默认开）。

## 9. 自测与验证

- `npx tsx scripts/check-zhhk.ts`：词典字节数、流式 ≡ 整段、关键词转换、两份路径规则一致、访客识别、站点地图、繁体页 `<head>` 处理（83 项）。
- 本地端到端：生产构建（standalone）+ `zhhk/entry.cjs` + 与线上相同的 nginx 配置，见部署说明第三节。
