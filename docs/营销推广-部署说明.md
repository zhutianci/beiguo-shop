# 营销推广（邮件）· 部署说明

> 设计契约见 `docs/营销推广-设计.md`（先读第 1、12、13 节）。
> 这一版：**9 张新表（全部 CREATE TABLE，零 ALTER、零 DROP）+ 1 个新环境变量 + crontab 两行 + 5 个新 npm 依赖**。
> 顺序照交接文档第十四节「正确的部署顺序」，下面只写本版差异。

---

## 一、这一版做了什么

后台「客户 → 营销推广」：区块编辑器排版推广邮件 → 选受众 → 测试 → 检查（含预计完成时间）→ 发送；
经阿里云批量发信地址 `marketing@mail.bigolab.com` 每秒至多 1 封匀速发出；一键退订、订阅偏好、投诉/退信抑制、
频控、发送时段、预热、每日试探、熔断、回执同步、点击→下单归因报表。

买家侧：个人中心「邮件订阅」卡、注册页告知语、退订页 `/unsubscribe/<token>`、隐私政策改写。
其他：流量分析新增「邮件」来源；邮件落地清除旧推广码（`via=mail`）；优惠券后台能看到「邮件直发」批次。

## 二、数据库变更（9 条 CREATE TABLE，零 DROP / ALTER）

`marketing_consents` `marketing_consent_logs` `marketing_suppressions` `marketing_templates`
`marketing_campaigns` `marketing_messages` `marketing_links` `marketing_events` `marketing_audits`

`coupons.source` 多一个取值 `'CAMPAIGN'`（不改表结构）。`settings` 表会多出 `marketing_config` / `mkt_halt` / `mkt_account` / `mkt_sync` 四行（运行时写入）。

## 三、部署前：站长在阿里云与 Cloudflare 做的事

1. **邮件推送控制台**：确认 `marketing@mail.bigolab.com` 类型「批量邮件」、状态「已验证」
2. **RAM 权限**：AccessKey 所属账号需有 `SingleSendMail / DescAccountSummary / SenderStatisticsDetailByParam / ListBlockSending / QueryInvalidAddress`
   （`AliyunDirectMailFullAccess` 已全部包含）
3. **Cloudflare**：安全规则里给路径 `/api/mkt/*` 加「跳过 Bot Fight Mode / 托管质询」，否则 Gmail/Yahoo 服务器的一键退订 POST 可能被拦
4. **准备一个能收信的联系邮箱**（上线后在后台「发送设置」填，不填不能发送；不要用数字 QQ 号邮箱）
5. **强烈建议**（可上线后再做）：营销改用独立子域，如 `edm.bigolab.com` —— 现在三类发信地址共用 `mail.bigolab.com`，
   阿里云规则下一次投诉可能冻结账户下全部发信地址（含注册验证码）。做法：阿里云加发信域名 → 配 DNS（SPF/DKIM/DMARC/MX）
   → 建批量地址 → 改 `ALIYUN_DM_MARKETING` → 重启 app（纯环境变量，不用重新构建）

## 四、部署顺序

```bash
cd /opt/beiguo/beiguo-shop && git pull origin main

# 0) 回滚标签（build 之前！）
docker tag beiguo-shop-app:latest beiguo-shop-app:rollback-$(git rev-parse --short HEAD@{1})

# 1) 备份并校验（不要管道进 gzip）
docker compose --env-file .env.production exec -T db mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers --set-gtid-purged=OFF beiguo_shop \
  > /opt/beiguo/backups/beiguo_shop_$(date +%Y%m%d_%H%M%S)_premkt.sql
tail -3 /opt/beiguo/backups/beiguo_shop_*_premkt.sql | grep "Dump completed"

# 2) 预览 DDL（交接文档第五节的临时容器命令，--script）：
#    期望恰好 9 条 CREATE TABLE `marketing_*`（外加它们的索引），出现任何 ALTER/DROP 立刻停手

# 3) db push（旧镜像仍在跑，新表没人读写，对线上零影响）
#    阳性对照：SHOW TABLES LIKE 'marketing_%';  → 9 行

# 4) 环境变量：.env.production 追加
#      ALIYUN_DM_MARKETING=marketing@mail.bigolab.com
#    若设置了 NOTIFY_EVENTS 白名单，追加 marketing.started,marketing.finished,marketing.paused
#    ⚠️ 不要在生产加 MARKETING_DRY_RUN（代码也会拒绝：库名不含 dev/test 时不生效）

# 5) 腾空间：docker image prune -f      ⚠️ 绝不跑 docker system df（会把 dockerd 撑爆，两个站一起下线）
#    package.json 变了，这次 build 会全量 npm install（多 ~12MB 的 TipTap）

# 6) build（后台跑、轮询；前后各记一次 latest 镜像 ID）
# 7) 只重启 app：docker compose --env-file .env.production up -d --force-recreate app
#    核对 docker inspect -f '{{.Image}}' beiguo-app 等于新 ID
# 8) crontab 改了，必须重建 cron 容器：
#    docker compose --env-file .env.production up -d --force-recreate cron
#    docker compose exec cron cat /etc/crontabs/root | grep marketing   → 两行
```

**以后每次部署**（模块上线之后）：先在后台「营销推广 → 发送设置」关掉「启用发送」，部署完冒烟通过再打开。
原因：Docker 停容器只给 10 秒，而 worker 单趟最长约 45 秒，部署时正在发的那一封会变成「结果未知」。

## 五、上线后冒烟（含负例）

1. `/admin/marketing` 能打开；「发送设置」页清单：发信地址 ✅、AccessKey ✅、联系邮箱（填好后）✅、
   回执同步（5 分钟内）✅、阿里云账户状态 ✅ 并显示信誉等级与日额度
2. 新建活动 → 套「限时优惠券」模板 → 改几个区块 → 预览桌面/手机/暗色/无图 → 自动保存正常
3. 测试发送给自己的 **QQ、163、Gmail、Outlook** 各一封，逐项核对并记到设计文档第 13 节：
   - 排版（QQ 网页版、QQ 手机 App、163、Gmail 网页+App、Outlook 桌面）
   - 暗色模式可读
   - Gmail「显示原始邮件」：`DKIM-Signature` 的 `h=` 是否包含 `list-unsubscribe`；Gmail 是否出现「退订」按钮
   - 原始邮件是否 `multipart/alternative`（纯文本版生效）；若测试报 TextBody 相关错误，到设置里关「附带纯文本版」
   - 主题以 `(AD)[测试]` 开头；页脚有主体、联系邮箱、退订营销邮件
4. 点测试邮件里的「退订营销邮件」→ 打开的是演示页（不改任何状态）
5. 负例：
   - `curl -X POST -F List-Unsubscribe=One-Click https://bigolab.com/api/mkt/unsubscribe/xxxx` → 200 `ok`（无效 token 也是 200，但什么都不改）
   - `curl -I https://bigolab.com/api/mkt/o/xxxx` → 200 image/gif，`Cache-Control: no-store`
   - `curl -I https://bigolab.com/api/mkt/c/xxxx/0` → 302 到首页
   - 未登录 `GET /api/account/marketing` → 401；`GET /api/admin/marketing/campaigns` 未登录 → 401/403
   - `curl -X POST https://bigolab.com/api/cron/marketing` 不带密钥 → 401/503
6. `docker compose exec cron tail -5 /var/log/cron.log`：每分钟一条 marketing 的小 JSON（没有活动时 sent=0）

## 六、首个正式活动的建议

- 先用「条件筛选：最近 90 天付过款」发第一场（预热第一天本来也只放 200 封，且优先发最活跃的人）
- 至少提前几天发一条站内公告：新增营销邮件、标题带 (AD)、可在个人中心或邮件底部一键退订
- 第一场不要做「限时 48 小时」的活动：预热期全量要 3 个发送日，检查页会显示预计完成时间
- 看 24 小时后的报表：无效地址率 < 3%、没有投诉，再放开到「全部活跃用户」

## 七·五、构建内存（2026-09-25 部署时踩到的坑，以后每次都适用）

第一次构建时 `next build` 把机器内存吃满：机器 swappiness=0 几乎不用 swap，构建进程挂在 dockerd 下被保护（-500），
内核于是先 OOM 杀掉了正在跑的 **beiguo-app、jishi-app 和两个 cloudflared**（约 20 秒后自动拉起，数据库因 -800 未受影响），
构建本身也被连带取消。实测整个项目的类型检查要 1.0~1.1G 堆，超过机器空闲内存（约 840MB）。

处置（已随代码提交）：
- `next.config.js`：`typescript.ignoreBuildErrors: true` —— **服务器构建不再做类型检查**，产物不受影响（SWC 本就忽略类型）
- `Dockerfile`：`RUN NODE_OPTIONS=--max-old-space-size=640 npm run build`（本地实测 512MB 即可编译通过）
- 部署时后台跑一个看门狗，把 `next build` 进程树的 oom_score_adj 调到 1000：万一内存还是不够，内核先杀构建而不是站点

**因此推送前必须本地 `npx tsc --noEmit` 零错误**（这道闸从服务器挪到了本地）。
