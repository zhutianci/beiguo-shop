# 微信机器人（贝果助手）· 设计契约

**版本 v0.3 · 日期 2026-10-05 · 状态：已实施（P0–P2 代码一次写完，开关分批开；未上线），与正文不同的地方见文末「实施偏差记录」；部署见 `docs/微信机器人-部署说明.md`**

> 站长需求（2026-10-03，原话见 §1.1）：一部分代理不会用企业微信推送，要一个**微信机器人**——管理员在群里 @ 它下指令，它把**主站动态推到主站管理群、每个分站的动态只推到绑定该分站的代理群**，每天零点发经营日报；主站管理群里还能补货（一次性网页）、提卡（自动建单发卡、推核销链接）等。
>
> 本文是这个模块的**契约**：架构、数据表、接口、指令、安全口径都以这里为准。调研事实见 §2 与附录 C（2026-10-03～05 核实，带来源）；代码引用一律是 `文件:行号`，基于 HEAD `26c9f90`（之后 `5aa5e32` 合入了渠道品牌与公告，个别行号可能偏移）。
>
> **v0.3（2026-10-05 站长拍板）**：采用**一个微信小号 + 非官方方案**；**机器人放在现有阿里云服务器上**（Q1）；**提卡等指令不要网页确认和口令，只要确认发指令的是管理员本人**，卡密核销链接直接发回群里（Q4、Q5）；**分站群放留言摘要和快速回复链接**（Q10）；**渠道单里需要站长处理的告警也进主站群**（Q7）。由此：服务器上不能跑电脑版微信，接入方式从 Windows 界面自动化改为 Linux 上的 **iPad 协议服务 WeChatPadPro**（它能拿到发消息人的微信内部 ID，「确认是管理员本人」可以做得可靠）；机器人收发直接做进网站进程，不再单独起网关程序；口令与确认页整套去掉。逐条落实见文末「站长决定落实记录（v0.3）」。
>
> **v0.2**：v0.1 的三路对抗评审（62 条）处理记录保留在文末；其中与站长新决定冲突的条目（口令、确认页、分站群不带留言）以 v0.3 为准。
>
> **改动前必读**：§0.2 裁决表、§15 安全模型、附录 B「不能改错的地方」。

## 0. 执行摘要与裁决

### 0.1 执行摘要

1. **普通微信群里放机器人没有官方通道**（企业微信机器人进不了外部群，微信官方 ClawBot 只能本人私聊，§2.1），所以用**一个微信小号 + 非官方方案**（站长 10-05 确认）。这类方案违反微信协议、有封号风险（§2.3），**机器人只是旁路**：现有企业微信与邮件推送一行不改；小号被封，换备用号重新拉群绑定即可恢复（§11.7）。
2. **机器人放在现有阿里云服务器上**（Q1）。服务器是 Linux，跑不了电脑版微信，所以用 **iPad 协议服务 WeChatPadPro**（闭源程序，Docker 部署，本质是模拟一台 iPad 登录小号）。它要一个 Redis（新增小容器）和一个 MySQL 库（用现有数据库里**单独的库和账号**，碰不到业务库）。**两个前提要先落实**（§18.2）：小号的手机要和服务器在**同一个城市**（服务器在北京），否则要配同城代理；免费公开版是 2025-07 的 v860，若已登录不上要去作者的付费群拿新版。
3. **内存**：这台机器 1.8G，本来就紧（本机构建会 OOM）。协议服务和 Redis 合计预计 200–300MB，设内存上限、设成「内存不够时最先被杀」，被杀后自动重启重连，不会连累数据库（§11.4）。长远仍建议升 4G（交接文档的老建议）。
4. **结构**：机器人的全部逻辑做在**网站进程里**（`src/lib/bot/*`）：动态采集、群绑定、指令、日报、补货页、审计；只有「和微信说话」这一层通过 HTTP 调协议服务（发消息）、收协议服务的回调（收消息），这一层是可替换的适配器（以后换别的协议或换回 Windows 方案，业务代码不动，§11.2）。
5. **管理员身份**：协议服务给出每条消息的**发送人 wxid** 和**被 @ 的人的 wxid 列表**，群成员改昵称冒充不了。指令只在「真的 @ 了机器人 + 发送人 wxid 是登记过的管理员 + 会话合适」时执行，其余一律不回（站长原话）（§7.1）。管理员 wxid 的登记：后台生成一个一次性认领码，管理员私聊发给机器人即可（§7.1）。
6. **提卡**：`@机器人 提卡 <货号> <价格> [数量]` → 确认发送人是管理员 → 在主站建一张「机器人提卡」订单、原子领卡 → **把核销链接（如 `https://bigolab.com/redeem/sysa?cdk=…`）直接发回群里**（站长原需求）。不发买家邮件、不触发返现/抽奖/发票，不进首页「实时成交」。保留不增加操作步骤的保护：按消息去重、每日上限、全程审计、每次抄送企业微信、一键锁定（§8）。
7. **补货**：`@机器人 补货 [货号]` → 回一个 5 分钟有效的一次性网页，粘贴卡密提交后即作废；导入逻辑与后台卡密导入同一份代码（§9）。
8. **群与分站绑定**：管理员在代理群 `@机器人 创建 tibo.pw` 即生效（身份已经可靠，不再要确认），也可在后台选群绑定（§4.2）。**推送范围**：主站动态进主站群；分站动态只进它绑定的群；**渠道单里需要站长处理的告警同时进主站群**（Q7）。分站群推送带**留言摘要**和**渠道快速回复链接**（Q10，站长决定放宽多渠道「渠道推送不带留言正文与免登录链接」那条规矩，仅限机器人推送），但仍不带买家邮箱（§5）。
9. **日报**：每天 00:01 统计刚结束的北京时间自然日，00:02 起逐群错峰发出；主站群一份（附各分站汇总、即将到期的订阅、机器人运行情况），分站群一份（渠道视角，不出现站长成本与利润）。分站 PV/UV 要先把埋点开到分站（§6）。
10. **上线顺序**：P0 网站底座（休眠上线）→ P1a 部署协议服务、登录小号、只推送 + 日报 → P1b 开指令 → P2 提卡/补货与更多指令 → P3 增强。现有推送行为全程不变（§16）。站长需要亲自准备的见 §19。

### 0.2 裁决表

| # | 决策 | 选择 | 理由 | 被否方案 |
|---|---|---|---|---|
| D1 | 群里的机器人用什么 | **微信小号 + 非官方方案**（站长 10-05 确认），按「随时可能被封」设计 | 官方途径都进不了普通微信群（§2.1） | 企业微信群机器人 / 智能机器人（不支持外部群）；微信 ClawBot（只能本人私聊） |
| D2 | 架构 | **机器人逻辑做在网站进程里**；「和微信说话」是可替换的适配器 | 机器人与网站在同一台机器（Q1），不需要再隔一层网关；少一个常驻进程，省内存 | v0.2 的独立网关进程（为跑在另一台 Windows 机而设计，Q1 定在服务器后不再需要；接口设计留作备选，附录 D） |
| D3 | 微信接入方式 | **WeChatPadPro（iPad 协议，Linux / Docker）** | 服务器上只能跑这类协议服务；它是 Gewechat 停服后社区的主流替代；能拿到 wxid 与被 @ 列表（§2.2） | Windows 界面自动化（服务器跑不了）；网页协议（新号基本登录不了）；Linux 版微信 + 自动化（没有成熟方案、太吃内存） |
| D4 | 协议服务怎么部署 | 官方 Docker 镜像**锁定版本**；**不对外暴露任何端口**；单独的 Docker 网络；MySQL 用现有数据库里的**专用库和专用账号**（只授权这一个库）；新增一个限内存的 Redis；内存上限 + 内存紧张时最先被杀 | 闭源程序要当作不可信：碰不到业务库、拿不到业务密钥、外网访问不到；机器只有 1.8G | 照它的示例另起一个 MySQL（再吃 200MB+ 内存）；对外开放它的管理端口 |
| D5 | 管理员身份 | **真 @（被 @ 列表里有机器人）+ 发送人 wxid 在管理员登记表里 + 会话合适**；管理员 wxid 用一次性认领码登记 | wxid 是微信内部 ID，群成员改昵称冒充不了；不再需要口令（站长 Q4） | 看显示名（可伪造）；口令（站长不要） |

| D7 | 卡密核销链接 | **直接发回发起提卡的那个会话**（管理群或管理员私聊）（站长 Q5） | 站长原需求 | 只在网页显示 |

| D9 | 分站群推什么 | 订单号、商品、件数、金额、状态；**留言摘要（前 100 字）+ 渠道快速回复链接**（站长 Q10）；**不带买家邮箱**；渠道后台链接 | 站长 10-05 决定：机器人推送放宽「渠道推送不带留言正文与免登录链接」；邮箱不在放宽范围内 | 只推「有新留言」 |
| D10 | 管理群推什么 | 与现有企业微信推送同一组字段，邮箱打码、留言截 100 字；平台快速回复链接照旧附上；**财务台免登录链接不推**（换成要登录的后台链接，Q8） | 财务台链接 3 天内能看全部待开票的抬头与税号，经过闭源协议程序不划算；其它照原样 | 原样转发 |
| D11 | 补货页 | 一次性网页：令牌只存哈希、**GET 只展示、POST 才执行**、5 分钟、**成功提交后作废**；不要口令（站长 Q4） | 微信与安全扫描会预取链接，GET 执行会被提前触发 | GET 即执行 |

### 1.1 站长需求逐条对照

| 2 | 机器人支持获取网站/分站中所有的动态信息，并实现推送 | §5 事件目录：主站 `notify()` 全部事件 + 渠道全部通知 + 新补三类 | 无 |

### 1.2 不做什么

- 不做 AI 聊天、不自动回复普通消息、不主动加好友、不自动通过好友申请、不自动进群、不建群拉人、不群发营销——这些是微信公告点名打击、最容易被封的行为（§2.3）。
- 不保存群里的普通聊天：协议服务的回调里，只有 @机器人 的消息、管理员私聊、管理群的入群退群提示会被处理与记录，其余**直接丢弃、不落库**。
- 不替代现有推送（D20）。
- 分站群里不开放「代理自己可用」的指令（站长原话）。
- 退款、调余额、导出卡密、渠道打款不进机器人，最多给一条需要登录的后台链接（P3）。

## 3. 总体架构

### 3.1 分层

```
┌──────────────────────── 阿里云服务器（docker compose）────────────────────────┐
│ app（Next.js）                                                                │
│   业务代码 ─ notify() 第一行旁路 ─┐                                             │
│           ─ alertPlatform() 旁路 ─┼─▶ bot_events ─路由/渲染─▶ bot_outbox ─┐       │
│           ─ tenant_notices（已落库）◀─按主键水位回扫                       │       │
│           ─ 新补事件（渠道下单/开票/收据，提交后）                          │       │
│   指令中枢 ◀─ /api/bot/wxpad/hook/<密钥>（协议服务回调，仅内网）            │       │
│   发送器（进程内，限速、合并、重试）◀────────────────────────────────────┘       │
│   日报（cron 00:01）· 补货页 /bot/x/<令牌> · 后台 /admin/bot                    │
│        │ HTTP（内网，带 ADMIN_KEY）               ▲ HTTP 回调（内网）           │
│        ▼                                          │                           │
│ wxpad（WeChatPadPro，闭源，独立网络 bot-net，不映射任何端口）── 外网 ──▶ 微信服务器 │
│   ├─ wxpad-redis（新增，限内存）                                               │
│   └─ db 里的专用库 wxpad（专用账号，只授权这一个库）                              │
│ 现有推送（企业微信 webhook / 渠道企业微信与邮件）——原样保留，兼作掉线告警通道        │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 五条原则

- **原则① 网站是唯一的业务大脑**：协议服务只负责「登录小号、收发微信消息」，不碰业务库、不持有任何业务密钥，外网访问不到它。
- **原则② 机器人是旁路**：现有推送一行不改；机器人代码出错一律吞掉并记日志，不向业务抛异常（与 `notify()` 一致，`src/lib/notify.ts:213-215`）；旁路模块只依赖 `db`（它会被 `vmq.ts`、钱包、接码间接引用，防循环依赖）。
- **原则③ 协议服务按不可信处理**：它是闭源的，能看到也能伪造经过它的微信消息；所以它跑在独立网络、用专用数据库账号、回调要带密钥，敏感指令有上限并抄送企业微信（§15）。
- **原则④ 分站隔离在网站侧强制**：出队按「会话 → 分站」过滤；指令执行时数据范围由会话决定；分站群的出队文本再过一道黑名单扫描（§5.4）。
- **原则⑤ 三张注册表**：事件目录、指令表、适配器；新增一项只加一个条目。

### 3.3 一条动态从发生到进群

1. 渠道站买家付款 → `fulfillOrder` 付款赢家写 `tenant_notices`（`src/lib/vmq.ts:1624`，ORDER_PAID）。
2. 回扫（发送器每次唤醒时顺带执行、节流到 10 秒一次；每分钟 cron 兜底）按主键水位读出新提交的 `tenant_notices`，按 `dedupe_key = 'tn:<id>'` 插入 `bot_events`。
3. 路由：找出绑定该分站、`ACTIVE`、订阅了「成交」类别的会话；渲染成文本，插入 `bot_outbox`。
4. 发送器按节奏调用协议服务的「发文本」接口，成功记 `SENT`，失败按退避重试。

### 3.4 一条指令从 @ 到执行

1. 管理员在主站群发「@贝果助手 提卡 GPT1 150」。
2. 协议服务把消息回调到 `/api/bot/wxpad/hook/<密钥>`。中枢先看是不是要处理的消息（@了机器人 / 管理员私聊 / 管理群系统提示），不是就**直接丢弃、不落库**。
3. 三道闸：会话已登记且合适、被 @ 列表里有机器人、发送人 wxid 是登记过的管理员；不过就静默丢弃。
4. 按消息 ID 去重 → 解析指令 → 执行（提卡见 §8）→ 写审计 → 回复写进 `bot_outbox`（高优先级）并立即唤醒发送器 → 抄送企业微信（敏感指令）。

## 4. 会话（群）与绑定

### 4.1 会话类型

| 类型 | 是什么 | 收什么 | 能用哪些指令 |
|---|---|---|---|
| `MGMT` | 主站管理群（站长建，成员只有管理员和小号） | 主站全部动态、渠道单里需要站长处理的告警、机器人自身状态、主站日报 | 全部 |
| `TENANT` | 分站群（站长建，成员：站长、该分站代理、小号） | 只有绑定分站的动态 + 该分站日报 | 管理员可用：帮助、状态、今日 / 昨日（本站）、订单（本站）、推送暂停 / 恢复、订阅、免打扰、解绑、锁定 |
| `DM` | 管理员与小号私聊 | 不推动态（只回指令结果） | 同 MGMT |
| 未登记 | 小号所在但未绑定的群 | 什么都不推 | 管理员的「设为管理群」「创建」，其它一律静默 |

一个分站可以绑定多个群；一个群只能绑定一个分站。管理群可以有多个；「允许提卡、补货」（T3）的开关在后台按群勾选，默认只开第一个管理群。

### 4.2 绑定方式

- **群里绑定（站长原方案）**：站长建群、拉代理和小号进群 → 管理员在该群 `@贝果助手 创建 tibo.pw`（也认「绑定」；`【】` 等括号会被去掉；可写域名、带 `https://` 的地址、分站子域名或渠道代码，解析见 §4.6）→ 过三道闸 → 会话直接 `ACTIVE` → 机器人在该群发欢迎语，在管理群发「群 X 已绑定分站 Y」。
- **设管理群**：在新建的管理群里 `@贝果助手 设为管理群`。
- **后台绑定**：后台「微信机器人 → 会话 → 新建绑定」，从协议服务给出的群列表里选群、选分站（或设为管理群）。
- 改绑：同一个群再 `创建 <别的分站>` 会回「本群已绑定 X，先解绑再绑定」，不会静默改绑。

### 4.3 群标识

`external_id = 群 ID（xxx@chatroom）`，由协议服务给出，群改名不影响。换小号后，新号进的还是同一个群、群 ID 不变，**绑定自动对上**（§11.7）。私聊会话的 `external_id` = 管理员的 wxid。

### 4.4 解绑、暂停与分站状态变化

- 解绑：在该群 `@贝果助手 解绑`，或管理群 `解绑 <群编号>`，或后台 → 会话 `REVOKED`，未发出的消息立即作废。
- 暂停 / 恢复推送、订阅 / 退订、免打扰：管理群、该群或后台都能改；任何让某群「少收」的改动在管理群留一条记录。
- 分站 `SUSPENDED`（暂停营业）照常推；`TERMINATED`（停业）→ 会话自动 `PAUSED`，管理群提示是否解绑；`DRAFT` 允许绑定。主域名切换不影响绑定。
- 小号被移出群：协议服务会给出退群提示，或发送失败 → 会话标 `UNREACHABLE` 并告警。

### 4.5 （v0.2 的「换号迁移不做自动匹配」已不适用）

iPad 协议给的是全局群 ID，换号后自动对上，见 §4.3。

### 4.6 分站解析

输入可能是 `tibo.pw`、`lulu.bigolab.com`、`https://tiboshop.bigolab.com/x`、渠道代码 `mysticboy`、`bigolab.com`。规则：

1. 去掉首尾空白与 `【】[]「」<>` 等括号。
2. 是 URL（带 `://`）→ `new URL(s).host`；否则原样。
3. 含点 → `normalizeHost()`（`src/lib/storefront/hosts.ts:31`）→ 命中主站白名单（`platformHosts()`，`hosts.ts:75`）→ 回「分站群不能绑定主站」；否则 `resolveStorefrontForHost()`（`src/lib/storefront/resolve.ts:353`）。2026-10-01 起未登记的域名形 Host 返回 null，这里另外核对返回的 `kind === 'CHANNEL'`，否则按「找不到」处理。
4. 不含点 → 按渠道代码 `prisma.tenant.findUnique({ where: { code } })`。
5. `TenantDomain.status = 0` 的域名回「该域名已停用」；`TERMINATED` 的分站拒绝绑定。
6. 站名：`(await getTenantBrand(tenantId)).name`（`src/lib/tenant/brand.ts`，`5aa5e32` 已合入；没设品牌的渠道返回「贝果科技」，所以**管理群与后台里写「站名（渠道代码）」**，分站群里只写站名）。

## 5. 动态推送

### 5.1 事件采集：不往业务事务里加写

现状（HEAD `26c9f90`）：主站动态全部走 `notify()`（`src/lib/notify.ts:197`），都在业务事务提交之后、fire-and-forget；渠道动态写 `tenant_notices`（`emitTenantNotice`，`src/lib/tenant/notice.ts:323`），无论渠道配没配企业微信都会写行；渠道里需要站长处理的告警走 `alertPlatform(text)`（`src/lib/tenant/platform-alert.ts:16`），有时在付款事务里面被调用（`src/lib/tenant/ledger.ts:517,570`），没有 tenantId 参数。

| 来源 | 怎么接 | 事务语义 |
|---|---|---|
| `notify(event, rows, opts)` | **函数体第一行**（`webhookUrl()` 判空与 `eventEnabled` 白名单之前，`notify.ts:202-204`）加 `botSink.fromNotify(event, rows, opts)`：异步写一行 `bot_events`，出错只记日志；不改变 webhook 的任何发送条件。`bot.*` 事件不进旁路 | `notify()` 都在提交之后调用（已核验） |
| `alertPlatform(text)` | 同样加 `botSink.fromPlatformAlert(text)`；站点从文本里的 `[code]` 取 | 可能在事务里调、事务回滚了告警也已发出——与现在的企业微信行为一致 |
| `tenant_notices` | **按主键水位回扫**（表上只有 `(tenant_id, read_at, id)` 一个索引、没有清理任务，`prisma/schema.prisma:2185`，按时间扫是全表扫描）：`settings` 里记一串「(时间, 当时的最大 id)」，每次从「15 分钟前记下的最大 id」往后按主键扫，`createMany({ skipDuplicates: true })` 进 `bot_events`（`dedupe_key = 'tn:<id>'`）。**排除** `dedupe_key` 以 `whtest:`（渠道「发送测试」）和 `mailcap:`（邮件超限说明）开头的行 | 只看得到已提交的行 |
| 新补事件（§5.2 标「新增」） | 在业务代码**提交之后**调 `botSink.emit(...)` | 同 `notify()` |

`botSink` 不返回 Promise 给调用方、不抛异常、不阻塞；`BOT_ENABLED` 未开时直接返回。

### 5.3 路由规则

1. `notify()` 且 `site` 为空（主站）：投给所有 `ACTIVE` 的 MGMT 会话中订阅了该类别的。
2. 带 `site` 的 `notify()` 与全部 `alertPlatform()`：投 MGMT（站长 Q7），**永不投分站群**（分站群另有对应的 `tenant_notices`）。
3. `bot_events.tenant_id = X（≠1）`：只投给 `tenant_id = X` 的 `ACTIVE` TENANT 会话中订阅了该类别的；**永远不投别的分站群，也不投 MGMT**。
4. `PENDING` / `PAUSED` / `REVOKED` / `UNREACHABLE` 的会话不入队。
5. 免打扰时段的非紧急事件推迟到免打扰结束，合并成一条「夜间动态汇总」。

出队时再按会话核对一次分站，并对分站群文本做黑名单扫描（§5.4）。

### 5.4 消息格式与脱敏

纯文本。首行「图标 类别名｜站名」，其后每行「标签：值」，最后一行链接。示例见附录 A。

| 规则 | 说明 |
|---|---|

### 5.5 留言的快速回复链接

| 订单 | 推到哪 | 链接 |
|---|---|---|
| 主站单 | MGMT | 现有平台快速回复 `quickReplyUrl(orderId)`（`src/lib/quick-reply.ts:83`，7 天，回复身份「客服」`senderRole='PLATFORM'`） |
| 渠道单 | 该分站群 | **新增渠道快速回复**（站长 Q10）：`{渠道 origin}/partner-reply/<令牌>` |

渠道快速回复的做法：

- 令牌：`deriveKey('tenant-reply')` 签名（`src/lib/tenant/crypto.ts:27` 已预留这个用途），内容是**订单公开编号** + 分站 id + 过期时间（7 天，与平台快速回复一致；`BOT_TENANT_REPLY_TTL_DAYS` 可改）。
- 页面 `/partner-reply/<令牌>`、接口 `/api/partner-reply/<令牌>`，**只在渠道自己的域名上**可用（主站 Host 404）；校验令牌里的分站与当前 Host 的店面一致、订单属于该分站。`/partner-reply` 是独立的一级路径，不被 `middleware.ts` 的 `/partner/:path*` 命中（`src/middleware.ts:118-120`），由路由自己验令牌。
- 能做的事：读这一单的留言（≤ 100 条）、回一条（≤ 1000 字；每令牌 10 分钟 20 条）。回复流程照 `partnerPostMessage`（`src/lib/partner-services/messages.ts:57-90`）：`senderRole='PARTNER'`、把买家留言标为渠道已读、写审计、照现有逻辑给买家发「客服已回复」提醒邮件。
- 要同步改：nginx 渠道 Host 的 `/api` 白名单加 `partner-reply`（`nginx/nginx.conf:124`）；itest T12 路由分类表登记它为「渠道开放」（`scripts/itest-tenant/cross-tenant.ts:998-1012`，现有 `partner(\/|$)` 匹配不到 `partner-reply`）；`scripts/check-tenant-boundary.mjs` 相应规则；**多渠道文档**里「渠道推送不带留言正文与免登录链接」这条，加一句「机器人推送到站长建立的分站群例外（站长 2026-10-05 决定）」。这几处与「多渠道权限分离」会话有交集（§16.3）。

### 5.6 投递：限速、合并、免打扰、过期

| 机制 | 默认值 |
|---|---|
| 每群最小间隔 | 4 秒 + 0–2 秒随机抖动 |
| 全局限速 | 每分钟 ≤ 15 条，每小时 ≤ 300 条 |
| 合并 | 同一会话待发普通事件 ≥ 3 条且最早一条已等 ≥ 60 秒 → 合成「最近 N 条动态」（最多 10 行，其余「另有 M 条，见后台」） |
| 优先级 | 指令回复 > 紧急告警 > 普通动态 > 日报 |
| 免打扰 | 分站群 23:00–08:00（可按群改或关）；主站群不设；紧急事件与日报不受限 |
| 过期 | 普通动态 12 小时、日报 72 小时、指令回复 10 分钟 → `EXPIRED` |
| 重试 | 30 秒、2 分钟、10 分钟、30 分钟，第 5 次失败 → `FAILED` + 告警 |
| 新号保护 | 小号登录未满 48 小时：只发管理群，分站群推送暂缓（§2.3 C4） |

### 5.7 掉线告警

- 发送器每分钟查一次协议服务的在线状态（「获取在线状态」接口）。协议服务连不上、小号已退出登录、或连续 3 条发送失败 → `notify('bot.offline')`（新增 NotifyEvent，走现有企业微信 webhook，紧急）；恢复时 `bot.online`，并在管理群发一条「离线期间 N 条动态已过期，请到后台查看」。
- 新增的 `bot.offline`、`bot.online`、`bot.sensitive` 要加进 `NotifyEvent` 联合与 `EVENT_LABELS`（`src/lib/notify.ts:20-81`）。**生产的 `NOTIFY_EVENTS` 若配了白名单，这三个不在里面就推不出去**（留空才是全开）——上线清单第一步先查。
- 机器人离线期间，分站后台的站内通知照常（`tenant_notices` 本来就写）。

## 6. 每日零时日报

### 6.1 时间、幂等、错峰

- crontab 加一行 `1 0 * * *` → `POST /api/cron/bot-daily`（`x-cron-secret`，写法照 `cron/crontab:1-24`）。现在 00:00 前后没有别的任务。**00:01 统计、00:02 起陆续发出**：给 23:59 付款、零点之后才提交的事务留一分钟。
- 统计窗口 = **刚结束的北京时间自然日** `[bjDayStart(今天) − 1 天, bjDayStart(今天))`，用 `src/lib/marketing/time.ts:28,44` 的 `bjDayStart` / `addBjDays`，不依赖容器时区。
- 锁：`acquireLock('bot:daily', 10 分钟)`（`src/lib/marketing/lock.ts:23`）。
- 幂等：每个会话每条日报一行 `bot_outbox`，`dedupe_key = 'daily:<YYYY-MM-DD>:<第几条>'`（日报分两条，键要带序号）；任务重跑只补缺的。
- 错峰：MGMT 00:02 发；分站群按会话编号依次 `not_before = 00:02 + 序号 × 45 秒 + 0–20 秒随机`（20 个群约 00:17 发完）。日报**不受免打扰限制**；若不想让代理半夜收到，Q15 可选「分站群日报改 08:00 发」。
- 每份日报分两条：「核心数据」一条、「明细与待办」一条，每条 ≤ 900 字。
- 接码成本会被 03:00–03:20 的对账事后修正（`src/lib/jiema/reconcile.ts:9-14`），日报里的接码利润标「预估，以 09:00 接码日报为准」。

### 6.5 分站 PV/UV：要补的改动

现状：`page_views` / `visitors` 没有站点列；渠道站**根本不挂埋点**（`src/app/(shop)/layout.tsx:80` 只在 `isPlatform` 时挂）；`/api/track/view` 第一行 `denyOnChannel()`（`src/app/api/track/view/route.ts:54-55`）；**nginx 渠道 Host 的 `/api` 白名单里也没有 `track`**（`nginx/nginx.conf:124`），请求在 nginx 就被 404；渠道 itest 也把它断言为「渠道关闭」（`scripts/itest-tenant/wp1.ts:380`、`scripts/itest-tenant/cross-tenant.ts:991,1001,1271`）。多渠道设计早有预留：「P1 `PageView.tenantId Int @default(1)`」「P0 不记渠道流量；P1 按店面记」（`docs/多渠道分销-设计.md:667,1859`）。

改法（代码在 P0、开关在 P1a 打开，独立开关 `TRACK_CHANNEL_VIEWS`）：

1. DDL：`page_views ADD COLUMN tenant_id INT NOT NULL DEFAULT 1` + 索引 `(tenant_id, day_key)`；`visitors ADD COLUMN tenant_id INT NOT NULL DEFAULT 1` + 索引 `(tenant_id, first_seen)`。MySQL 8 加带默认值的列是即时操作；历史行自动算主站，**主站历史口径不变**。
2. `track/view`：`denyOnChannel()` 换成 `getStorefront()`（写法同 `src/app/api/auth/register/route.ts:39,97`），写入 `tenant_id = 店面 id`；**渠道站的 `viewer_key` 加站点前缀**再做哈希（`sha256('t<tenantId>|' + 原值)`），IP 兜底的访客在不同站点之间不会撞唯一键 `(path, viewer_key, hour_bucket)`、也不会共用一行 `visitors`；主站公式不变。

## 7. 指令系统

### 7.1 触发与身份：三道闸

协议服务回调来的每条消息，先看要不要处理（@了机器人的群消息、管理员私聊、管理群的入群退群提示）；不要的**直接丢弃、不落库**。要处理的再过三道闸，任何一道不过就静默丢弃（不回复、不产生任何出队消息，只在 `bot_commands` 记一行 `IGNORED`）。

| 闸 | 判定 | 做法 |
|---|---|---|
| ① 会话 | 已登记的 MGMT / TENANT / DM；未登记的群只认「设为管理群」「创建」 | 按群 ID / 私聊对方 wxid 查 `bot_conversations` |
| ② 真 @ | 群消息的被 @ 列表（消息附带的 `atuserlist`）里有机器人自己的 wxid，且不是 @所有人；私聊不需要 @ | 同 WeChatFerry `is_at`；**文本里写的「@贝果助手」不作数** |
| ③ 发送人是管理员 | 发送人 wxid（协议服务给出）在 `bot_admin_identities` 里 | wxid 是微信内部 ID，群成员改昵称、改群昵称都冒充不了 |

**登记管理员（认领）**：后台「微信机器人 → 管理员 → 添加」生成一个 8 位认领码（10 分钟有效、只用一次）→ 管理员用**自己的微信私聊小号**发「认领 <码>」→ 中枢把这条私聊的发送人 wxid 记为该管理员，并在后台显示其微信昵称供核对。认领只认私聊，不在群里做（借鉴 CowAgent godcmd「拒绝在群里认证」）。小号要先加管理员为好友。

**管理群有人进群**：协议服务回调里有入群提示时，在管理群和企业微信各告警一条（陌生人进了管理群会看到之后的提卡核销链接）。

### 7.4 解析规则

- 去掉开头的「@小号昵称」及其后的 U+2005 / 空格；全角空格、全角数字转半角；去掉 `【】[]「」<>` 括号（`@机器人 创建 【分站网站】` 也能识别）。
- 指令名与别名不区分大小写；价格接受 `150`、`150.5`、`¥150`、`150元`；每个指令自己声明参数语法，`check-bot-registry` 校验任意两个指令的语法不会互相吞掉。
- 参数个数不对就报用法，**不猜**。一条消息只执行一个指令。引用、转发、撤回的消息不当指令。
- 同一条消息（协议服务给的消息 ID）只执行一次；协议服务重复回调不会重复执行。

### 7.5 回复规则

- 未过三道闸：什么都不产生（站长原话「其余所有人的信息不回复」）。入站每会话限 10 条 / 分钟。
- 过了三道闸、但指令不存在或格式不对：回「没看懂，发送 @贝果助手 帮助 查看可用指令」。
- 会话不对（如在分站群里提卡）：回「该指令只能在主站管理群使用」。
- 回复不 @ 发起人，首行写明是哪条指令的结果。

### 7.6 扩展方式：三张注册表

```ts
// src/lib/bot/commands/types.ts（示意）
export interface BotCommand<A> {
  name: string                         // 唯一
  aliases?: string[]                   // 与所有指令名、别名都不能重复
  scopes: Array<'MGMT' | 'TENANT' | 'DM' | 'UNBOUND'>
  tier: 0 | 1 | 2 | 3
  allowWhenLocked?: boolean            // 只有「锁定」为 true
  auditAction?: string                 // tier ≥ 2 必填，如 'bot.cmd.unbind'
  grammar: ArgSpec[]                   // 参数语法，check 脚本据此做冲突检查
  parse(args: string[]): { ok: true; value: A } | { ok: false; usage: string }
  run(ctx: BotContext, args: A): Promise<BotReply>
  help: { summary: string; usage: string; example?: string }
}
// BotContext：会话（id、kind、tenantId）、管理员、指令 id、消息 id、now，
// 以及按 ctx.scopeTenantId 收窄过的数据访问函数——处理函数拿不到别的分站
```

- **指令表** `src/lib/bot/commands/index.ts`：每个指令一个文件。模块加载时 `assertRegistry()` 校验：名字与别名全局唯一、T2 以上有 `auditAction`、`UNBOUND` 只允许「创建」「设为管理群」、语法不冲突、每个指令都有帮助；`scripts/check-bot-registry.ts` 再校验一遍。
- **单指令开关**：`bot_config.disabledCommands` 可临时关掉某个指令；每个管理员有 `maxTier`（例如给客服同事只开 T1）。
- **边界检查** `scripts/check-bot-boundary.mjs`（仿 `check-tenant-boundary.mjs`，纯文本扫描）：`src/lib/bot/commands/**` 不许直接 import `prisma`，只能用收窄过的数据访问函数；`src/lib/bot/sink.ts` 只许 import `db`。
- **事件目录** `src/lib/bot/events/catalog.ts`：`Record<NotifyEvent, …>` 与 `Record<TenantNoticeKind, …>` 编译期穷尽；新增一种动态 = 一个条目 + 一处 `botSink.emit()`。
- **适配器** `src/lib/bot/adapters/*`：每种协议服务一个文件（§11.2），中枢只认接口。
- **不冲突**：指令之间不互相调用；写操作经服务函数、按指令 id 幂等；T3 全部经同一把锁（`acquireLock('bot:t3', 60 秒)`，非阻塞，拿不到回「正在处理其他操作，请稍后再试」）串行，上限检查不会被并发绕过。

## 8. 提卡

### 8.1 指令

`@贝果助手 提卡 <货号> <价格> [数量]`，例：`提卡 GPT1 150`、`提卡 GPT1 150 3`（与站长原话一致）。**价格是单价**，订单金额 = 单价 × 数量；数量缺省 1、最多 5。

### 8.2 货号

新增 `products.bot_code`（`VARCHAR(16)`，可空，唯一，只允许字母数字与 `-_`，存大写，后台商品编辑页填）。上线时给所有 `deliveryType = 'AUTO'` 的商品预填 `P<商品id>`（例 `P12`），站长可改成好记的（`GPT1`）。只有 AUTO 且有货号的商品能提卡。不复用 `apiSku`：它同时是「对外共享库存」的开关（`src/lib/dispense.ts:66-89`）。

### 8.3 校验（任一不过就回原因、不执行）

会话允许 T3 → 未锁定且 `bot_config` 读取正常 → 货号存在、商品 AUTO（已下架也允许，回执提示）→ 单价 0 < p ≤ 99,999.99、数量 1–5 → 今日额度（§8.6）→ 未用卡 ≥ 数量。

**价格异常只提示、不拦**（站长 Q4）：单价低于发出那几张卡的成本、低于站价 50%、高于站价 300% 时，回执里加一行 ⚠️ 提醒；真打错了用 `改价`（§8.9）。

### 8.4 执行

全部在一次 `READ COMMITTED` 事务里（`vmq.ts:1707-1734` 的注释：领卡循环在默认的可重复读下会反复拿到同一张已被别人领走的卡）：

1. 拿 T3 锁（非阻塞）。
2. 插 `bot_card_issues`（`command_id` 唯一——同一条消息无论回调几次只成一次）。
3. `createShopOrder(tx, { tenantId: 1, userId: <提卡账号>, productId, productName, productPrice: <站价快照>, quantity, amount: 单价 × 数量, invoiceTaxFee: null, invoiceInfo: null, remark: '机器人提卡 #<issueId>' })`——全仓唯一的建单入口（`src/lib/order/create-shop-order.ts:143`；可以在调用方自己的事务里用）。
4. **先加销量**：`product.sales += 数量`。`syncAutoStock` 那条 `UPDATE products SET stock = (SELECT … FROM card_keys …)` 先锁 `products` 再读 `card_keys`（`src/lib/cardkey.ts:80-84`）；这里若先领卡（锁 `card_keys`）再加销量（锁 `products`），加锁顺序相反，会和并发的付款发卡死锁。
5. 订单 CAS：`UNPAID → PAID`，`paidAt = now`，`payMethod` 留空（已核验：不填支付方式、不写 Payment 不影响现有统计与对账）。
6. 领卡：按 `id` 升序找 `UNUSED`，**排除本次试过的 id**；先试解密，解不开的条件更新成 `DISABLED`（remark「解密失败自动停用」，照 `dispense.ts:94-120`）；能解开的 `updateMany({ where: { id, status: 'UNUSED' }, data: { status: 'USED', orderId, usedAt, soldPrice, profit } })`，`count === 1` 才算抢到——与 `fulfillOrder` 的 `allocateCards`（`vmq.ts:1399-1429`）、外部发卡 `dispense` 同一把 CAS，三条路径不会重复发同一张卡。售价按 `splitAmount`（`src/lib/money.ts:27-39`）分到每张，`profit = soldPrice − cost`。抢不够 → 抛错、整个事务回滚、回「库存不足」。
7. 订单 `DELIVERED`、`deliveredAt = now`；审计 `writeAudit(tx, { actorUserId: <管理员对应的站内用户>, actorKind: 'PLATFORM', action: 'bot.card.issue', targetType: 'order', targetId: orderNo, diff: { productId, quantity, unitPrice, costTotal, cardIds, conversationId } })`（`src/lib/audit.ts:74`，**审计里不写卡密**）→ 提交。
8. 提交后：`syncAutoStock(productId)`；库存低于阈值照现有逻辑推 `stock.low`；抄送企业微信 `notify('bot.sensitive', …)`（不含卡密）；把回执写进发起会话的出队（高优先级）。

### 8.5 回执（发回发起提卡的管理群或私聊）

```
✅ 提卡成功｜ChatGPT Plus 月卡 ×1
单价 ¥150.00 · 成本 ¥120.00 · 利润 ¥30.00
订单号 20261005K3F9Q2AB · 剩余库存 17 张
核销：https://bigolab.com/redeem/sysa?cdk=9D8WA-AVOBY-PJ5P5
```

核销链接规则与「我的订单」一致（`src/app/api/orders/route.ts:190-197`）：卡上的兑换平台已注册（`sysa` / `sysb`，`src/lib/redeem/registry.ts`）→ 站内兑换页 `/redeem/<平台>?cdk=<卡密>`；否则给卡密明文 + 本批兑换地址或商品兑换地址。兑换服务对有订单的卡要求订单已付款且未取消（`src/lib/redeem/service.ts:112-120`），提卡单满足。多张时每张一行。

### 8.6 每日上限

北京时间自然日、按 `bot_card_issues` 统计：张数 ≤ 20、金额 ≤ ¥3,000；单次 ≤ 5 张（Q13，后台可改）。目的不是挡站长自己，而是万一管理员微信被盗、或协议服务被动了手脚时，把损失封顶。

### 8.7 提卡专用账号与统计排除

- 上线时用种子 SQL 建（照 `scripts/ops/*-seed.sql` 的写法，可重复执行；**不在代码里新增 `user.create`**）：昵称「机器人提卡」，邮箱与手机为空，密码哈希是随机生成后丢弃的 bcrypt 值（无法登录），角色 USER；id 写进 `bot_config.issueUserId`。
- **要排除它的地方**：首页「实时成交」（`src/app/api/orders/recent/route.ts:19-25` 加 `userId: { not: issueUserId }`）；日报的新注册、累计用户、下单人数、支付转化、访客下单率。
- **照常计入**：成交单数、成交额、利润、商品销量（Q12）、后台订单列表。

### 8.8 刻意不做

不写 `payments`；不发买家邮件（账号没有邮箱）；不触发返现、抽奖（抽奖资格只在下单接口里建，`src/app/api/orders/route.ts:682-687`）、优惠券、开票；不推 `order.paid`；**不调用 `fulfillOrder`**（它会把支付方式写成支付宝、写 Payment、发邮件，`vmq.ts:1571-1576, 1585-1587`）。

### 8.9 改价与撤销

- `改价 <订单号> <单价>`（P2，T3）：只限提卡账号的、7 天内的订单；同一事务里改 `amount`、按 `splitAmount` 重算该单每张卡的 `soldPrice` 与 `profit`；审计 + 抄送企业微信。
- 撤销：v1 不在群里撤销，后台按现有流程取消订单、停用未兑换的卡；P3 再加 `撤销提卡`。

## 9. 补货（一次性网页）

### 9.1 流程

1. 管理员在管理群：`@贝果助手 补货` 或 `@贝果助手 补货 GPT1`。
2. 机器人回：「📦 补货链接（5 分钟内有效，提交成功后作废）：https://bigolab.com/bot/x/<令牌>」。
3. 管理员用手机打开：选商品（带了货号就预选，只列自动发货商品）、粘贴卡密（每行一张）、每张成本、批次名（默认 `bot-20261005-1432`）、兑换平台（默认沿用该商品最近一批）、兑换外链 → 提交。
4. 页面显示结果；机器人在群里回执「📦 补货完成｜ChatGPT Plus 月卡：导入 20 张（重复跳过 2 张），当前库存 35 张；还有 2 单付了款在等卡，发送 @贝果助手 补发 GPT1 即可补发」，同时抄送企业微信。

### 9.3 共用导入函数

## 10. 锁定与解锁

- **锁定**：`@贝果助手 锁定`——任何已登记会话（含分站群）、任何管理员都能用；后台也能锁。效果：`bot_config.locked = true`；作废全部未使用的补货链接；T2 / T3 全部拒绝（「锁定」除外）；T0 / T1 和推送照常；企业微信告警。用于「发现不认识的提卡记录」「管理员手机丢了」「怀疑协议服务异常」。
- **解锁：只能在后台**（站点后台登录 + 写审计）。理由：没有口令之后，能以管理员身份发消息的「人」（盗号者、被动了手脚的协议服务）同样能发「解锁」；后台登录是独立于微信的另一条认证。
- 管理员手机丢了 / 微信被盗：后台锁定 → 后台停用该管理员身份 → 找回微信后重新认领 → 后台解锁。

### 11.3 收消息：回调接口

- 协议服务的 Webhook 指向 `http://app:3000/api/bot/wxpad/hook/<BOT_WXPAD_HOOK_SECRET>`（走 Docker 内网）。密钥放在路径里（≥ 32 字符，常量时间比较；协议服务若支持自定义请求头或签名，PoC 后改用请求头）；nginx 对外一律 404 掉 `/api/bot/wxpad/`（照 `/api/cron/` 的写法，`nginx/nginx.conf:215-218`，80 与 8080 两个入口都要生效）。

### 11.5 登录与「同城」

- **登录**：后台「微信机器人 → 概览 → 登录小号」：中枢调协议服务的「获取登录二维码」接口（可带代理），后台显示二维码 → 站长用**小号的手机**扫码确认 → 轮询登录状态 → 完成后记录机器人自己的 wxid 与昵称。掉线后先点「唤醒登录」（部署教程：首次掉线不唤醒「会严重提高风控风险」），不行再重新扫码。协议服务的管理端口不对外开放，所以一切登录操作都经过后台（站点后台登录 + 审计）。
- **同城**：部署教程与 Gewechat 指南都要求**小号手机与服务器在同一城市**（服务器在北京）。手机不在北京时，给协议服务配一个出口在手机所在城市的代理（`BOT_WXPAD_PROXY`，登录二维码接口带上它，只有协议服务走这个代理）：A 买一个该城市的静态住宅代理；B 在家里常开的路由器或设备上开代理，经隧道给服务器用。**站长 2026-10-05 答 Q18：小号在手机上一直登着，服务器上是平板 / 电脑形态，不会掉线，不配同城代理**；PoC 观察稳定性，只有扫码后频繁被要求重新登录时才按 A / B 补。
- **新号节奏**：登录后头 48 小时只收不发或少发（发送器自动只发管理群）；每天被拉进的群不超过 3 个；不加好友、不建群。

### 11.6 PoC 验收清单（在服务器上，用真小号）

1. 免费公开版（v860）能否登录；不能就按 Q19 决定是否拿新版。
2. 同城直连或配代理后，24 小时不掉线。
3. 内存与 CPU（空闲、发送时）→ 定 `mem_limit`。
4. 回调：群 ID、发送人 wxid、`atuserlist`、消息 ID、系统消息（入群、退群）的字段；Webhook 是否支持自定义头 / 签名；没有 Webhook 时 WebSocket 怎么接。
5. 发群文本：成功率、900 字、换行、链接能否点。
6. 群列表接口（后台绑定用）。
7. 重启容器后会话是否保持、需不需要重新扫码（决定构建期间要不要停它）。
8. 72 小时稳定性：掉线次数、是否要求手机确认。
9. 补货链接、核销链接在微信内置浏览器里的表现（未备案域名的提示页）。

## 12. 发送器与定时任务

### 12.1 发送器（网站进程内）

- Next.js standalone 是常驻的 Node 进程，发送器是进程里的一个异步循环：取出队 → 按节奏调协议服务发消息 → 记结果。
- **唤醒方式**：写入出队后立即唤醒（同进程，`setImmediate`）；每分钟 cron 兜底唤醒；进程内只跑一个循环，数据库层再加一把锁（`acquireLock('bot:send', 60 秒)` 并续租），防止重启交接时两个循环同时发。
- **取消息**：`status = 'PENDING' AND not_before <= now`，按「优先级降序、id 升序」，同一会话距上次发送不足 4 秒（另加 0–2 秒抖动）的跳过，全局每分钟 ≤ 15 条；取到的那条条件更新成 `SENDING`（`lease_until = now + 90 秒`），以影响行数为准；取的时候顺手做合并（§5.6）。
- **发送与确认**：调用适配器 `sendText` → 成功 `SENT`；失败回 `PENDING`、`attempts + 1`、按退避设 `not_before`；进程在发送途中重启 → 租约过期由 cron 收回（**至少一次**：极少数情况下同一条可能发两次，可以接受）。
- **新号保护**：小号登录未满 48 小时，只发管理群。

### 12.2 定时任务（crontab 新增两行）

| 时间 | 任务 | 做什么 |

| 每分钟 | `GET /api/cron/bot-tick`（`--max-time 55`） | 回扫 `tenant_notices`、路由新事件、过期、收回租约、释放免打扰、查协议服务在线状态并告警、唤醒发送器 |

## 15. 安全模型

**信任边界**：协议服务（闭源）、微信小号、腾讯服务器、群里的其他成员都按不可信处理；管理员身份 = 协议服务给出的发送人 wxid。

**站长 Q4 决定不加口令，意味着**：谁能「以管理员的微信身份发出一条 @机器人 的消息」，谁就能提卡、补货。可能做到的只有三类：① 拿到管理员手机或盗了管理员微信的人；② 协议服务程序本身（它是闭源的，能伪造任何消息——若被作者或别人植入恶意代码，就能冒充管理员提卡，并从核销链接拿走卡密）；③ 控制了服务器的人。群成员、代理、外人改昵称都冒充不了。对这三类，本设计不再试图挡住，而是**封顶、留痕、能及时发现、能一键止损**：每日上限、审计、每次提卡补货抄送企业微信（独立通道，不经过小号）、群里或后台一键锁定、解锁只能在后台。

| # | 威胁 | 对策 | 剩余风险 |
|---|---|---|---|
| S1 | 群成员冒充管理员 | 身份只认 wxid 与被 @ 列表，文本与显示名不作数 | — |
| S2 | 管理员微信被盗 / 手机被人拿到 | 每日上限、抄送企业微信、锁定、后台停用身份 | 上限之内的卡可能被提走 |
| S3 | 协议服务被植入恶意代码 | 锁定镜像版本；不暴露端口；数据库只授权它自己的库；不给它任何业务密钥；上限 + 抄送 + 锁定 | 它能读写全部微信消息；上限之内的卡可能被提走 |
| S4 | 有人伪造协议服务回调 | 回调路径密钥（常量时间比较）；nginx 对外 404；只在 Docker 内网可达 | 能进内网的程序（例如协议服务本身）不受此限 |
| S5 | 小号被拉进陌生群 | 小号只加管理员为好友；未登记群只认管理员的「设为管理群」「创建」 | — |
| S6 | 陌生人进了管理群 | 入群提示告警（管理群 + 企业微信） | 告警之前已发出的核销链接可能被看到 |
| S7 | 补货链接落到别人手里 | 5 分钟、成功提交后作废、只在后台能看到谁导入了什么 | 5 分钟内拿到链接的人能导入卡密（站长 Q4 接受） |
| S8 | 分站数据串群 | 路由按分站投递；出队再核一次；分站群黑名单扫描；itest 断言「A 站事件永不进 B 群」 | — |
| S9 | 推送内容被利用（钓鱼） | 用户文本里的网址中性化并标「买家写：」；链接只由代码拼 | 昵称文字仍会出现 |
| S10 | 渠道快速回复链接外泄 | 7 天有效、只能读这一单留言和回复、只在该分站域名可用 | 拿到链接的人能以「客服」身份回复这一单 |
| S11 | 指令刷屏 | 每会话入站限频；上限；锁定 | — |
| S12 | 事后说不清 | T2 / T3 全部写 `audit_events`；提卡补货与「少收」改动抄送企业微信 | — |

## 附录 B：不能改错的地方

1. **机器人旁路绝不影响业务**：`botSink` 不返回 Promise、不抛异常、不进业务事务、只 import `db`；渠道事件靠按主键水位回扫已落库的 `tenant_notices`；`bot.*` 事件不进旁路。
2. **分站隔离**：路由按 `bot_events.tenant_id` 投递；出队时再核对「事件的分站 = 会话的分站」（管理群收渠道告警是唯一例外，且只来自带 `site` 的 `notify()` 与 `alertPlatform()`）；分站群文本过黑名单扫描；指令处理函数只能拿到按 `scopeTenantId` 收窄的查询函数。
3. **分站群永不出现**：卡密、买家邮箱、平台快速回复与财务台链接、站长成本与利润。（留言摘要与渠道快速回复链接是站长 Q10 的例外。）**管理群不出现财务台链接。**
4. **管理员身份只认协议服务给出的发送人 wxid 与被 @ 列表**；文本里的「@贝果助手」、显示名、群昵称一律不作数；认领管理员只认私聊。
5. **提卡领卡**用 `READ COMMITTED`；只能 `updateMany({ where: { id, status: 'UNUSED' } })` 且 `count === 1` 才算抢到（与 `fulfillOrder`、`dispense` 同一把 CAS），循环排除试过的 id；**先加销量、后领卡**；`syncAutoStock` 放在提交之后；抢不够整单回滚；不调 `fulfillOrder`；不写 `payments`；建单只走 `createShopOrder`；同一条消息只执行一次（`bot_card_issues.command_id` 唯一）。
6. **`importCardKeys` 传了 `tx` 就不能在里面调 `syncAutoStock`**。
7. **补货令牌**：库里只存哈希；GET 不改任何状态；消费用条件更新做 CAS；成功导入才作废。
8. **协议服务**：镜像锁版本；不映射任何端口；数据库账号只授权 `wxpad.*`；不给它任何业务密钥；回调必须验路径密钥；`/api/bot/wxpad/` 对外 404。
9. **非管理员的消息静默丢弃**；群里的普通聊天不落库。
10. **现有推送行为逐字不变**：企业微信 webhook、`NOTIFY_EVENTS`、渠道企业微信与邮件、`noticePrefs`。旁路只在 `notify()` 函数体第一行加一行，不改变 webhook 的发送条件。
11. **加了 `page_views.tenant_id` 之后，后台流量分析默认只看 `tenant_id = 1`**；主站 `viewer_key` 公式不变，渠道站加前缀。
12. **提卡账号**：首页实时成交、注册数、下单人数、转化率都要排除它；建号只用种子 SQL。
13. **日报窗口用北京时间工具函数**（`bjDayStart` / `addBjDays`），不依赖容器 TZ；日报去重键带序号。
14. **解锁只能在后台**；锁定在群里、私聊、后台都能做。
15. **中枢日志与 `bot_commands` 不记卡密、令牌、回调密钥**；核销链接只出现在发给管理群 / 私聊的那条消息里。
