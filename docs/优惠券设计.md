# 优惠券

> 改动券相关代码前先读这份。碰钱的地方，错一分钱就是真实资金差错。

---

## 一、数据模型

| 表 | 是什么 |
|---|---|
| `coupons` | **批次**。后台建一批，生成一条共享领取链接 `/coupon/<code>`，谁点谁领 |
| `coupon_grants` | **用户领到的那张券**。状态机在这一层 |
| `coupon_claims` | 三限去重记录。唯一约束 `[couponId, scope, value]` |

`Order` 上加了三列（都可空）：`couponGrantId` / `couponDiscount` / `originalAmount`。
`amount` 记的是**优惠后**实付价，原价与减免额单独留痕 ——
否则后台看到一个低于商品定价的数字，分不清是内推专属价还是用了券。

### 券实例状态机

```
AVAILABLE ──下单选用──> LOCKED ──支付成功──> USED
    ↑                     │
    └──订单取消/超时/兜底清扫──┘
    
AVAILABLE ──到期──> EXPIRED
AVAILABLE ──批次 ENDED──> VOID
```

**LOCKED 的券在批次被 ENDED 时不动。** 它挂在一张待支付订单上，而那张订单的金额
已经是优惠后的了；作废掉会让买家按优惠价付了款却没有核销记录，对账对不上。
让它跟着订单自然走完。USED 的更不能动，那是历史账。

## 二、三条不可动摇的实现约束

### 1. 一张券只能用一次 —— 靠 CAS，不是靠先查后写

```ts
// 对的
const locked = await prisma.couponGrant.updateMany({
  where: { id, userId, state: 'AVAILABLE' },   // 条件即锁
  data: { state: 'LOCKED', lockedAt: new Date() },
})
if (locked.count !== 1) return error('该券正被另一笔待支付订单占用')
```

**错的写法**是 `findFirst` 查到 AVAILABLE 再 `update`：买家开两个标签同时下单，
两个请求都会查到「可用」，然后各自用掉同一张券。

### 2. 三限靠唯一约束 —— 同样不是先查后插

领取时在一个事务里插三行 `CouponClaim`（USER / IP / DEVICE），
唯一约束 `[couponId, scope, value]` 冲突即判定「已领过」。
先查再插在并发下必然失效，理由同上。

**IP 与设备指纹落哈希不落原文**（都属于个人信息，我们只需要判定「出现过没有」）。

### 3. 优惠后金额必须 > 0

站内收款是 V免签式的**按唯一金额匹配到账**（见 `lib/vmq.ts` 的 `allocateAmount`）：
每张待支付订单分到一个不重复的金额，靠收到的钱数反查是哪一单。

**0 元订单没有「到账」这件事，会永远停在待支付。**
所以 `MIN_PAYABLE = 0.01`：券面额大于订单金额时，减到只剩 0.01，而不是算出 0 或负数。
无门槛券建议设得低于最便宜的商品价。

## 三、券在哪一步参与

**建单时**（`/api/orders`）校验 + 计算 + CAS 锁定，**不是**提交收款监控时。

站长最初的要求是「提交收款监控前验证」，但同时要求「订单记录优惠后的价格」——
`order.amount` 在建单时就必须是优惠价，否则收款监控拿原价去匹配，
买家付了优惠价永远对不上账。

提交收款监控那一步（`/api/pay/vmq/create`）保留**第二道复验**：
确认账户与券一致、且券确实锁在这一单上。两道防的不是同一件事：
建单那道防「用不该用的券」，这道防「订单与券的关联在中途被改坏」。

## 四、券的释放路径（一条都不能少）

买家的券卡在「占用中」是他自己解不开的，只能来找客服。所以释放路径要穷尽：

| 路径 | 触发点 |
|---|---|
| 订单超时取消 | `closeExpired()` 遍历过期 VmqOrder → `releaseCouponForOrder` |
| 后台取消订单 | `admin/orders/[id]` 改成 CANCELLED |
| 建单失败回滚 | `/api/orders` 的 catch |
| **兜底清扫** | `sweepStuckCoupons()`，按时间判定，不依赖订单关联；**有活着的收款单（买家正在付款）时跳过** |

**付款发起时会刷新锁定时间**（`api/pay/vmq/create`），清扫的 120 分钟从买家真正开始付款算起。
**付款到账时如果发现券已经被放回**（后台取消、清扫、补单），`consumeCouponForOrder` 会把它从
AVAILABLE / EXPIRED 补核销为 USED，而不是让它再用一次；券已被别的订单占用则记错误日志待人工对账。

**兜底清扫是必需的，不是优化。** 有两条路径靠前三条永远够不着：

1. 买家下了单但**从未提交收款监控**（没点付款就关了页面）。这种订单没有对应的
   VmqOrder，而 `closeExpired` 是遍历过期 VmqOrder 来关单的 —— 它看不到这张订单
2. 建单时「先锁券、后回填 orderId」两步之间进程崩了。券是 LOCKED 但 orderId 为空，
   没有任何按订单查找的逻辑能定位到它

清扫器挂在 `closeExpired` 里（cron 每分钟调一次）。
**注意 `closeExpired` 开头有个 `if (expired.length === 0) return 0` 的提前 return，
清扫必须在它之前也跑一次** —— 恰恰是上面第 1 类情况根本不产生 VmqOrder，
永远不会有 expired。

## 五、与内推的关系：互斥（2026-09-11 起）

站长拍板，取代了最初的「不叠加，取更优」：

```
① 走内推链接下单 → 一律按推广人的专属价，优惠券不可用（券原样留在账户里）
② 没走内推      → 按定价，可以选券；不选就是定价
```

`lib/coupon.ts` 的 `quoteOrder` 是全站唯一的定价口径，结算页与建单共用；里面没有 min、没有比较。
原因与踩过的坑见交接文档第十八节。

## 五·补 · 系统发放的批次（`Coupon.source` 非空）

`source = 'LOTTERY'` 是「下单有奖」中奖时自动建的**单张批次**（一次中奖一个批次，理由见
`docs/下单有奖-抽奖设计.md` 第三节）。这类批次：

- 领取接口与 `/coupon/<code>` 页一律当作不存在
- 后台券列表默认不显示，筛选「抽奖发放」可以看到；不能加量、暂停，只能作废
- 之后就是一张普通的券：锁定 / 核销 / 放回 / 过期走完全相同的状态机

## 六、风控的真实边界（要诚实）

只做三限：每 IP / 每账户 / 每浏览器各 1 张。**明确拦不住的**：

- 换浏览器、开无痕 → 设备指纹是 localStorage 里的 UUID，清掉就换一个
- 手机流量换 IP → 换一个出口 IP
- 注册小号 → 站长明确不要求注册时长与历史订单

还有一条结构性弱点：nginx 配了 `real_ip_header CF-Connecting-IP` 并信任 Cloudflare
回源段，但 **80 端口是对外发布的**，绕过 Cloudflare 直连服务器 IP 时
`CF-Connecting-IP` 是可以伪造的。走 Cloudflare 的正常流量不受影响。
（2026-09-25 已在代码里修掉：直连入口不再信任该头，见 `docs/nginx-真实IP修复-部署说明.md`。
IP 仍然换起来很便宜，下面「控制敞口」的结论不变。）

**所以真正的止损手段不是加限制条件，而是控制敞口**：
单批发行量、券面额、有效期。后台建券时这三个数就是风险上限。

## 七、发票场景不可用券

站长明确要求。发票税费走的是另一条 `createOrGetVmqOrder`
（`lib/order-billing.ts`，`bizType: 'invoice'`），与商品订单完全分开，
券的逻辑一行都没有接进去 —— 结构上就用不了，不需要额外开关。
