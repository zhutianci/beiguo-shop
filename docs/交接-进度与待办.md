
### 三个必须知道的坑

**① PowerShell 会把命令拆坏。** 带空格、引号、或前导 `--` 的参数会被 PowerShell 重新分词，远程命令直接变形（实际踩过：`git log --format="%H %s"` 被拆成三段）。**所有远程命令一律 base64 传输**：

```powershell
$script = @'
<多行 bash>
'@
$norm = $script -replace "`r`n","`n"
$b64=[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($norm))
& $wb exec -i i-2ze8s6my1msl5q6thpum -r cn-beijing --timeout 600 -c "echo $b64 | base64 -d | bash"
```

**② exec 会话对长输出会中途截断。** 耗时命令（build / db push / 管线）必须后台跑再轮询：

```bash
nohup <命令> > /tmp/x.log 2>&1 &
# 之后另起一次 exec：
for i in $(seq 1 280); do pgrep -f "<关键词>" >/dev/null || break; sleep 3; done
cat /tmp/x.log
```

**③ 本地 sleep 被工具链拦截**，等待逻辑要写在服务器端的 bash 里。

```bash

# 查 MySQL（必须带 --default-character-set=utf8mb4，否则中文全是 ?）
```

## 四、AI圈大事记（最复杂的模块）

**先读 `.claude/skills/ai-news-pipeline/SKILL.md`**，那是契约，改动前必看。

### 定位（这条决定其他所有设计）

**是「行业动态聚合工具」，不是新闻站。** 《互联网新闻信息服务管理规定》要求的许可拿不到，策略是让内容不落入其定义：只做自写摘要 + 外链原文，绝不转载；不碰政策/监管/地缘/裁员等「社会公共事务」选题；作者硬编码「贝果科技 AI 资讯助手」，不署真人名；AI 生成标识必须出现在 6 处（法定义务）。

**为内容质量拆掉这条基础，不划算。** 上一轮用户两次要求「搬运 aihot.virxact.com 的内容」，都按此原则挡下并给了替代方案 —— 见待办。

### 管线（六段，各自独立抢锁，任一段失败不影响其他段）

```
collect  每小时05分  抓 feed（零 LLM、零依赖、单源熔断）
triage   每小时05分  分诊：是否 AI 相关、是否命中黑名单、归类
cluster  每小时15分  同事件聚合（urlHash 免费快路 + 实体指纹 + 小模型判定，不用向量）
compose  每小时25分  抓原文正文 → 写摘要/推荐理由/AI评分（唯一的写作题）
rank     每15分钟    重算热度（明细落 scoreDebug，可解释）
digest   21:00/周一09:00  日报周报
```

### LLM

当前用**智谱 GLM**（`glm-4-flash` 分诊 / `glm-4-plus` 写作）。境内直连实测：GLM 401/55ms、DeepSeek 401/87ms、百炼 401/34ms 全部可达；**`api.openai.com` 超时、`api.anthropic.com` 403，均不可用**。换供应商只改 `LLM_PROVIDER` + `LLM_API_KEY` + model 名。

日预算硬闸 `NEWS_DAILY_BUDGET_CENTS=300`（3 元/天），超支当天降级为「只去重不写摘要」。

### 信源可达性（2026-09-04 从该 ECS 实测，新增源前必须实测）

✅ 机器之心、量子位、36氪、InfoQ、少数派、掘金、AIbase、通义博客、IT之家、**hnrss.org**、TechCrunch:AI、The Verge:AI、Ars Technica:AI、MIT TechReview、The Decoder、微软研究院、OpenAI RSS、Anthropic News、GitHub API、arXiv API、Simon Willison

❌ **X/Twitter、Reddit、HuggingFace（含 hf-mirror）、DeepMind、Meta AI、Mistral、Google News、V2EX、RSSHub 公共实例、CSDN、知乎热榜**

⛔ **开源中国已停用** — 它的 news feed 是码云项目发布流水（「灵界 OS v4.0.0」），题材不符且单次 40 条会刷屏

**媒体源用「AI 专版」RSS 而不是全站版** — 全站版里手机汽车游戏占大头，每条都要花一次分诊调用才能剔除，等于为噪音付费。

### 踩过的坑（都是线上真实发生的）

1. **glm-4-flash 吐裸对象** — 提示词里的 JSON 示例被 `join('\n')` 拆成两行，模型认成内层对象形状，把最外层 `results` 数组整个丢掉。**给模型的 JSON 示例必须完整在同一行**
2. **批量越大越浪费** — 给 8 条只答第一条。`NEWS_TRIAGE_BATCH=3` 后每批答全，延迟反而更低
3. **漏答条目被永久判死** — 原逻辑标 `FAILED` 永不重试，40 条丢了 35 条。已改为留 RAW 重试，7 天陈旧清理兜底
4. **素材被锁死在一句话** — 只用 feed 的 description，摘要写不出细节，换强模型也没用。已加 `lib/news/extract.ts` 抓原文正文（零依赖启发式提取），效果显著：

   > 改前：阿里已发表两篇关于循环Transformer的顶会论文，该技术因GPT-6而受到关注。
   > 改后：…提出 MeSH 和 SpiralFormer 解决方案…MeSH 使模型减少 33% 非嵌入参数的同时，准确率提升 1.06 个百分点，额外计算开销仅 0.014%。

## 六、血泪教训（同一个坑不要踩第二次）

### 1. 我自己造成过两次线上故障

**crontab 被删光字母 r。** 容器命令里写了 `tr -d '\r'` 想防 CRLF，反斜杠被 YAML 折叠 + shell 双引号两层处理吃掉，变成 `tr -d 'r'` —— `curl`→`cul`、`cron`→`con`，**全部定时任务静默失效且 crond 不报错**，连原有的收款单清理和接码轮询一起挂。现已改用 `.gitattributes` 强制 LF，容器命令里只用 `cp`。**不要再往那条命令里加任何带反斜杠的转义。**

**改 TZ 引发锁永不自愈。** 把 app 容器从 UTC 改成 `Asia/Shanghai` 后，MySQL 的 `DATETIME` 不带时区，改动前写入的行被按新时区重新解释后落到「未来」，`now - createdAt` 成负数恒小于 TTL。表现：MySQL 算 27 分钟，Node 认为没到 15 分钟。已改用绝对值判断。**凡是比较 MySQL DATETIME 与当前时间的地方都要留意这个。**

### 2. 排查前先验证，别急着下结论

我曾断言「`ORDER_MSG_WEBHOOK_URL` 从没传进容器，留言推送一直是哑的」，依据是 `printenv` 里没有。**错了** —— `docker compose exec` 起的是另一个进程，不走 Next 的启动流程。真实链路是 Next standalone 把 `.env.production` 打进镜像，`server.js` 启动时用 `loadEnvConfig` 读进 `process.env`。用户的留言通知一直是正常的。

**由此引出一条 compose 写法铁律**：新增环境变量一律用**裸变量名**（`- FOO`），不要写 `- FOO=${FOO}`。后者在 FOO 未定义时会给容器一个**空字符串**，而 dotenv 遵循「已存在的 env 优先」，反而把镜像内 `.env` 的真实值**遮蔽掉** —— 那会让本来正常的功能失效。

### 3. 我又造成过一次全站宕机：`docker system df` 把 dockerd 撑爆了

2026-09-07 14:13，为了评估构建空间跑了 `docker system df` / `docker builder du` /
`du -sh /var/lib/docker/overlay2`。这几条要遍历所有镜像层算尺寸，
而这台机器有 **36 个悬空镜像**、overlay2 目录硬链接展开约 130G。
`dockerd` 的 RSS 冲到 1.4G（全机 1.87G），被内核 OOM 杀掉，**连杀 5 次**
（14:13:50 / 14:17:45 / 14:19:06 / 14:25:01 / 14:30:17）。
dockerd 被 SIGKILL 时它名下的容器随之消失，**beiguo 与 jishi 两个站点同时下线约 20 分钟**。
`restart: unless-stopped` 救不了这种情况 —— 容器不是「退出」，是随父进程一起没了。

**这台机器上永远不要跑**：`docker system df`、`docker builder du`、`du /var/lib/docker`。
看空间用 `df -h`（文件系统层面）+ `docker images`（只读元数据、不算尺寸）。
真要清理直接 `docker image prune -f`，不要先去「统计一下有多少」。

顺带：`du -sh /var/lib/docker/overlay2` 报出来的 130G 是**假的**（overlay2 用硬链接，
du 会重复计数），磁盘实际只有 40G。想知道真实占用只能看 `df -h`。

### 4. 其他

- **alpine 镜像不装 tzdata，`TZ` 会被静默忽略**，进程仍跑 UTC，不报错
- **`.next` 属主是 root 而运行时是 nextjs 用户** — 不 chown 会每次请求报 EACCES 并退化成完全不缓存
- **`route.ts` 只能导出 HTTP handler 和少数配置项**，多导出一个 schema 会让 `next build` 报「不是合法的 Route export」，公用校验放 `lib/`
- **动态路由 params 签名混用** — 26 个里只有 6 个是 Next15 的 `Promise<{id}>`，新文件跟同目录已有写法保持一致，混用会 build 失败
- **`docker compose exec` 的 stderr 会被 compose 的 WARN 淹没**，查东西时用 `2>/dev/null` 而不是 `2>&1`
- **mysql 客户端不带 `--default-character-set=utf8mb4` 中文全变 `?`**
- **中文限宽用 px 不用 ch** — `ch` 按西文 `0` 宽度算，对中文会算出接近实际字数一半的宽度

## 十、本轮（2026-09-07 第二轮）做了什么

### A1 · 去掉 7 天窗口，改增量累积 + 按月归档

原来有四处「7 天」，**只该去掉两处**：

| 位置 | 处置 | 理由 |
|---|---|---|
| `compose()` 的 `since` | **去掉** | 就是它让超期事件永远轮不到，表现为「只有最近一批」 |
| `rank()` 的 `RANK_WINDOW_DAYS` | **去掉**，改分层 | 同上 |
| `cluster()` 的 pending 窗口 | 放宽到 14 天，**并加终态** | 原来超期条目会永远停在 `eventId=null`：既不成事件也不被清理（purge 只删孤儿，而它们的 `triageState` 是 OK）。现在超龄判 `SKIP` |
| `collect()` 的 `MAX_ITEM_AGE_DAYS` | **保持 7 天不动** | 这是**收集窗口**不是处理窗口，它咬合着 30 天保留期与 `TRIAGE_STALE_DAYS`。放宽只会「花钱分诊 → 被保留期删掉 → 下轮又插回来」 |

**compose 改双车道**：新鲜（3 天内，3 条/轮）+ 积压（更老，2 条/轮）。
名额**固定切分**，不是「优先新鲜、有剩再给积压」—— 后者在信源稳定产出时永远剩不下名额。
积压排序按 `sourceCount / tier1Count` 而不是 `score`：score 带 36h 半衰期，
跨越几十天的候选之间衰减差几个数量级，按 score 排等价于纯按时间排。

**compose 加墙钟 7 分钟**。crontab 的 `--max-time 540` 是硬上限，到点 curl 断开、
服务端还在跑并占着锁。**锁 TTL 永远不能大于 540s**，只能让 compose 自己提前收工。

**rank 改分层**：热层（72h）每轮、温层（72h–14d）每小时一次、冷层只补 `baseScore` 为空的。
新增 `base_score` 列（不含衰减的原始分）：`score` 是 `Decimal(8,3)`，约三周后老事件全 round 成
`0.000`，归档页就排不出先后。历史行为 NULL，由冷层每轮补 200 条自愈，**不写一次性回填脚本**。

**归档页 `/news/archive/2026-09`**（不是 `/news/2026-09`）。后者要在 `[slug]` 这个动态段里
靠正则分流「2026-09」和「2026-09-06-a1b2c3d4e5」—— 正则少写一个锚点，
**全部新闻详情页会当场变成归档页**。为省 8 个字符引入一个全站级故障点不划算。
`/news` 底部有「按月回看」入口，sitemap 收录最近 24 个月的归档页。

**「最近补录」折叠行**：积压车道写出来的老事件按 `happenedAt` 排会沉到时间流中间，
首屏看不见。这一行是它们唯一的露出位置，**复用 `HIGHLIGHT_WHERE`**（含 `needsReview:false`）——
「happenedAt 很旧 + publishedAt 很新」几乎就是降级发布条目的特征，不过滤会精准地把最不该推的推上去。

### A2 · 全文层 detail（600–1200 字，2–4 段带小标题）

新增三列：`detail`(Text)、`detail_state`(RAW/DONE/SKIP)、`detail_tries`(Int)。

- **新事件**：跟摘要一次生成（compose 仍是「唯一的写作题」），`maxTokens` 900 → 2200
- **老事件**：独立的回填通道，**默认关闭**（`NEWS_DETAIL_BACKFILL=1` 开启）。
  三道闸：每轮最多 2 条、当日花费超预算 40% 就停、单条最多重试 3 次
- **detail 是可丢弃区块**：段数/字数/连续 18 字重合/数字回查/禁词/选题黑名单，
  任何一项不过就只丢这一块，事件照常发布。**不进 `needsReview` 队列** ——
  页面退回「只有摘要」本身就是合规状态，没有需要人看的残留
- **瞬时失败绝不写终态**：超时/限流/5xx 只 `detail_tries+1` 下轮重来。
  第四节踩坑 3（40 条丢 35 条）就是把瞬时失败当内容性结论写死导致的
- 后台可按段人工编辑，**刻意不提供「重新生成」按钮**——那会是无次数上限的付费入口

**顺带修了 `lib/llm.ts` 的记账**（这是 A2 的前置，不修就没有可信的成本数据）：
① 三级降级的 token 改累加（原来后一次覆盖前一次）
② 失败调用按真实 token 计费（原来写死 0，导致失败率一升高账面花费反而不动）
③ 日界改固定 +8 算术（原来用进程本地时区，alpine 无 tzdata 时会偏 8 小时）

## 十一、部署这一版（顺序不能改）

**不要用 `scripts/deploy.sh`**。它第 2/3 步 build+up、第 5 步才 `db push`，
顺序与「新增列」的要求正好相反：新镜像会在新列存在之前上线，
`/news/[slug]` 的 select 里带着还不存在的列 → 整页 500。
（详情页的 `getEvent` 已加 try/catch 兜到 404，但那是安全网不是方案。）

正确顺序是 **先 DDL、后 build**。六项变更全部是可空 `ADD COLUMN` 或 `CREATE INDEX`，
旧代码不读不写，所以「旧镜像还在跑的时候先建列」完全安全。


### 部署实录（这一轮踩了三个坑，都记下来）

**坑一：`exit 0` + 空输出 ≠ 成功。** 这台机器的 workbench exec 会话在长命令中途断开，

**坑二：构建日志说成功，其实产出的是旧镜像。** 一次 `docker compose build app`

`latest` 根本没动。表现是强制重建容器后新路由仍然 404。
**结论：构建前后各打印一次 `docker images --no-trunc --format '{{.ID}}' beiguo-shop-app:latest`，
两个 ID 相同就是没构建成功**，不要看日志。

**坑三：回滚标签打反了。** `docker tag ...:latest ...:rollback-xxx` 必须在 **build 之前**打。
build 之后 `latest` 已经是新镜像，这时打的标签指向新镜像，回滚时会滚到自己身上。

### 正确的部署顺序（在第十一节基础上修正）

```bash
docker inspect -f '{{.Image}}' beiguo-app
# 6) 冒烟要包含**新增路由**，且带一个负例（如 /coupon/不存在的码 应 404，
```

## 十六、2026-09-09：AI圈大事记静默宕机两天（Next 数据缓存把一个 HTML 拦截页冻住了）

站长报「collect 之后没有新增条目、管线不自动执行、也没有 AIHOT 内容」。
查下来是三件独立的事，其中第一件是真正的宕机，而且**藏了整整 39 小时没人看得出来**。

### 1. 根因：`fetch` 被 Next 的数据缓存冻住

现象非常具有迷惑性 —— 每一项指标都是绿的：

- `crond` 在跑，crontab 9 条任务完整，`rank` / `detail` 每轮都按时执行
- `news_sources.last_ok_at` 是当天的，16 个源**全部** `ok`、`failed: 0`
- collect 返回 `{"sources":16,"ok":16,"failed":0,"inserted":0}`

唯一异常的只有 `inserted: 0`，而 `inserted: 0` 本来就有一个完全正常的含义 ——「抓到了，但都已经在库里」。

实际发生的是：

```
.next/cache/fetch-cache/444bc794...  ← 190 个条目之一
{"kind":"FETCH","data":{"headers":{
   "content-type":"text/html; charset=UTF-8",     ← 不是 RSS，是拦截页
   "date":"Mon, 07 Sep 2026 17:35:29 GMT"}}}      ← 冻在 9-07
```

App Router 会把裸 `fetch()` 的响应写进磁盘上的数据缓存并**无限期**复用。
9-07 容器重启后的第一轮抓取，量子位回了一个 `text/html` 的页面（不是 feed），
这个响应被写进缓存 —— 此后每一次「抓取」都在读同一份 9-07 的 HTML：
解析出 0 条 → 入库 0 条 → 而 collect 依然报告 16/16 成功。

**路由段上的 `export const dynamic = 'force-dynamic'` 挡不住它。**
那行确实写在 `api/cron/news/route.ts` 顶部，但缓存条目实实在在地写出来了，
时间戳还在持续更新。别指望路由段配置能管到被 import 进来的库函数里发的请求。

证据链（三方交叉验证，不是推断）：
- 同一份 `fetchText + parseFeed` 在本机跑，量子位解析出 10 条，最新一条是**当天**的
- 容器内 `wget` 直连量子位，拿到的是**真 RSS**，pubDate 也是当天 → 网络与信源都没问题
- 只有走 Node `fetch` 的那条路读到的是 9-07 的 HTML → 缓存是唯一的差异点

**为什么 `force-dynamic` 没挡住**（在 `node_modules/next@14.2.3` 的编译产物里逐行确认过，不是猜的）：

- `app-route/module.js`：`switch (this.dynamic)` 里那句 `case "force-dynamic"` 被
  `if (isStaticGeneration)` 包着。真实 HTTP 请求进来时 `isStaticGeneration` 是 false，
  **这个导出在运行时什么都没设**。
- 同文件下一句 `staticGenerationStore.revalidate ??= this.userland.revalidate ?? false`
  —— 路由没导出 `revalidate`，于是 store 里是 `false`，而 `false` 在 Next 里的含义是**永久缓存**。
  这条路由不但没关掉缓存，反而把自己设成了更可缓存。
- 本可以救命的豁免没触发：`revalidate = 0` 只在 `hasNonStaticMethods` 时设，
  而它检查的是 `POST/DELETE/PATCH/OPTIONS`。`api/cron/news` 只导出 `GET`。
  **这个 cron 入口当初要是写成 POST，这个 bug 根本不会发生。**

**修复**：`src/lib/news/feed.ts` 的 `fetchText` 加 `cache: 'no-store'`。
抓的是每小时都在变的外部内容，缓存在这里没有任何意义，只会把某一秒的意外冻成永久状态。

> **千万不要再叠一个 `next: { revalidate: 0 }`。** 两个一起传不是「重复但无害」，
> 而是直接把修复作废：`patch-fetch.js` 同时收到 `cache` 与 `revalidate` 时只打一条 warn，
> 然后执行 `_cache = undefined` —— 你的 `no-store` 被丢掉，缓存又开回来了。
> 那条 warn 没人会看，于是**看起来修了、其实没修**。

### 1.1 同一个雷的另外三处（一并修了）

`autoNoCache` 的条件是 `(有 authorization 头 || 非 GET) && store.revalidate === 0`，
两个条件是**与**。我们的路由 `store.revalidate` 是 `false` 不是 `0`，
所以**「POST 不会被缓存」这个直觉在这个项目里是错的** —— 缓存键由 `fetchCacheKey(url, init)` 算出、含 body，
所以每个不同的 body 各存一份，缓存一年（`.next/cache/fetch-cache` 那 190 个条目就是这么来的）。

| 位置 | 后果 | 处理 |
|---|---|---|
| `api/admin/news/runs/route.ts` 手动触发按钮 | **最坏的一个**：GET + 固定地址 + 无 body = 每次点都是同一个缓存键。命中缓存时会重放上一次的 JSON，`res.ok` 为真 → 走成功分支 → 写一条 `ok:true` 的运行记录 → 界面显示「已执行」，而 cron 路由根本没进去、锁没抢过、管线一步没跑。**管线一出问题，你点这个按钮永远看到绿色** | 加 `cache: 'no-store'` |
| `lib/llm.ts` | 同一个 prompt 重试会拿回上一次那份回复。上次要是返回了解析不了的 JSON，重试多少次都还是它 | 加 `cache: 'no-store'` |
| `lib/aliyun.ts` | 发短信/邮件的响应缓存一年，纯白占磁盘 | 加 `cache: 'no-store'` |
| `lib/herosms.ts` | 已经写了 `cache: 'no-store'`，无需改动（幸好——接码状态轮询要是被冻住，每一单都会卡死） | ✅ 本来就对 |

> 部署即清缓存：`.next/cache` 在容器文件系统里，没有挂卷（compose 只挂了
> `forum_uploads` 与 `mysql_data`），重建容器就是空的。不需要手工去删。

### 2. 为什么两天没人发现 —— 观测口径的问题，已一并修掉

`inserted: 0` 把两种情况压成了同一个数字：

| 实际情况 | 旧报告 | 是否正常 |
|---|---|---|
| 抓到 30 条，都已在库 | `inserted: 0` | ✅ 正常 |
| 抓回来的根本不是 feed，0 条 | `inserted: 0` | ❌ 已经宕机两天 |

`CollectResult` 现在多两个字段，两种情况再也混不到一起：

- `details[].parsed` / `details[].bytes` —— 每个源解析出多少条、抓回多少字节
- 顶层 `unparsable: string[]` —— **抓到了字节却一条都解析不出**的源，非空就该有人去看

`[news/collect]` 那行日志也一并带上 `parsed` 与 `unparsable`。

顺带暴露出一个**早就存在**的问题：`jiqizhixin`（机器之心）与 `36kr` 返回的一直是 HTML 而不是 RSS，
lifetime `item_count` 都是 0 —— 它们从来没有产出过一条内容，只是以前看不出来。
`aibase` / `qwen` / `infoq-cn` / `anthropic` 的 `item_count` 也是 0，同样需要复查。

### 3. AIHOT 没有内容：库里根本没有这一行

`SEED_SOURCES` 里定义了 `aihot`（`enabled: false`，等 A1 积压消化后再开），
但 `news_sources` 表里 25 行**没有一行是它** —— 定义加进代码后从未执行过 seed。

`seedSources()` 对既有行的 `enabled` 是安全的：`common` 里**不含 `enabled`**，
所以跑 seed 不会把站长在后台手工停用的 `oschina` / `hn` / 7 个 X 源重新打开。
只有新建的行才会用种子里的 `enabled`。

**但 `?stage=seed` 依然不能随手跑。** `SEED_SOURCES` 现在有 33 条，库里只有 25 行 ——
差的 8 行里，`thedecoder` 与 `ithome` **没有写 `enabled: false`**，
走的是 `enabled: s.enabled ?? true`，一 seed 就会**立刻上线**，下一个 :05 直接开抓。
此外 seed 会把 25 行既有记录的 `feedUrl / weight / tier / role / kind / viaRelay`
全部覆写回种子值，后台里手工调过的会被静默改掉。

所以这次**没有跑 seed**，只单独插了 `aihot` 一行。
其余 7 行要不要加、`thedecoder` / `ithome` 要不要开，留给站长决定。

授权号 `AIHOTAPI20260907001` 是写死在 `lib/news/aihot.ts` 里的常量，不需要配环境变量。
已从服务器实测：`GET https://aihot.virxact.com/api/v1/items?limit=5` 带 `X-License` 返回 200 / 5870 字节。

### 4. 这次的教训

**「所有指标都绿」不等于「在工作」。**
这次每一个健康检查都是通过的：进程在、任务在跑、HTTP 200、失败数 0。
唯一能暴露问题的指标（`inserted`）恰好与一个正常状态共用同一个值。

订两条：

1. **抓外部内容的 `fetch` 一律显式写 `cache: 'no-store'`**，不要依赖路由段配置。
2. **不要让"什么都没发生"和"正常但无事可做"共用同一个数字。**
   新增一个只在异常时才非空的字段（这里是 `unparsable`），比在旧字段上加注释有用得多。

## 十七、2026-09-10：批量开票导出（后台一键导出待开发票）

后台发票页新增「导出待开发票」按钮，导出税局官方批量导入模板，拿去开票系统直接导入。

### 1. 为什么是「往官方模板里塞行」而不是自己生成 xlsx

模板（V260401，657KB）里藏着东西：

- 隐藏工作表 `excelVersion`，A4 写着 `pt:20260401` —— 导入端**会校验版本**
- 39 列里有 **17 处下拉数据验证**（发票类型、是否含税、是否展示购买方信息…），值必须是选项原文
- 另有 4.5MB 的行政区划、245 行国家地区等隐藏数据源表

自己拼一个「看起来一样」的工作簿，等于赌对方只读值、不校验版本。赌输了就是一整批发票开不出来。
所以实现只做一件事：**把 `<row>` 追加到两张表的 `</sheetData>` 之前，其余字节原样不动**。
自测里有一条断言直接比对未改动的 4.5MB 表在导出前后字节完全一致。

### 2. 模板结构（改版时对照这里）

| 表 | zip 内路径 | 表头行 | 数据起始行 | 列 |
|---|---|---|---|---|
| 1-发票基本信息 | `xl/worksheets/sheet1.xml` | 第 3 行 | **第 4 行** | A..AM（39） |
| 2-发票明细信息 | `xl/worksheets/sheet6.xml` | 第 3 行 | **第 4 行** | A..N（14） |

> 工作表文件名与顺序**不对应**（明细表是 sheet6.xml 不是 sheet2.xml），别按序号猜，
> 要从 `xl/workbook.xml` 的 `<sheets>` 里按 name 找 rId 再查 rels。

填写规则见 `src/lib/invoice-export.ts`，固定值全部提成常量，且**与模板下拉选项原文逐字比对**（自测里有断言）。

### 3. 「待开」的口径

`status='SUBMITTED' 且 pay_status='PAID'`，排序 `paidAt asc`（先付先开）。

**与财务台 `api/finance/invoices/[token]` 完全一致，两处必须一样。**
注意后台列表接口 `api/admin/invoices` 的 status 筛选**不带 payStatus 条件**，
所以后台列表里筛 SUBMITTED 看到的条数可能比导出的多 —— 导出的是真正该开的那些。

### 4. 规格型号：商品名 → 发票上印的字

只在买家勾了「展示 ChatGPT/Claude 字眼」时才填，没勾则规格型号/单位/数量三列一起留空。

商品名是运营随手起的，线上真实形态五花八门，规则是：切掉竖线右边的发货方式 →
去掉括号补充说明 → 抹掉「自助充值/代充/成品号/充值」这类话术 → 补「会员订阅」。

```
Claude pro 自助充值 | iOS订阅                            → Claude pro会员订阅
ChatGPT Pro 20x 自助充值 | 信用卡充值（无法覆盖plus和5x）  → ChatGPT Pro 20x会员订阅
Claude Max 20x成品号 | 自动发货                           → Claude Max 20x会员订阅
Claude MAX 5x自助充值（测试中）                           → Claude MAX 5x会员订阅
```

**认不出来的商品一律留空，不瞎编。** 线上有「Codex验证码-美区实体手机卡-单次接码」这种
根本不是订阅的商品，拼成「…单次接码会员订阅」会印在真发票上。
规格型号在模板里是**非必填**，留空完全合法；编一个假的则不然。

### 5. 三个容易踩的坑

**① 一律写成 `inlineStr`，不写数字。** 税号、银行账号是十几二十位纯数字，
一旦被当成数值，Excel 会显示成 `1.91202E+18`，账号就废了。模板填表说明第 6 条也写着
「所有内容输入均为文本格式输入」。

**② `.gitattributes` 必须有 `*.xlsx binary`。** 仓库根上有 `* text=auto`，
漏掉这条，git 会把 xlsx（本质是 zip）当文本做行尾转换，压缩流里的 `0x0A` 被改成 `0x0D0A`，
包直接损坏 —— 而且要等到有人下载、Excel 报「文件已损坏」才会发现。

**③ Dockerfile 必须显式 `COPY templates`。** Next 的 standalone 文件追踪只看
import/require 依赖图，`fs.readFile` 读的文件它一无所知。不写这行，镜像里就没有模板，
导出接口要到运行时才报 ENOENT。

### 6. 自测

```bash
npx tsx scripts/check-invoice-export.ts   # 120 条
```

除了纯逻辑，它还会**真的打开 templates/ 下的官方模板**校验：工作表名与 rId、
模板版本号、数据起始行、下拉选项原文、以及 22 个列头文字与代码里的列序一一对齐。
**模板换版时这个脚本会先响**，不会等到发票开错。

最后一组是端到端：真生成一个 xlsx、再解回来，验证行写进去了、隐藏表还在、
zip 条目数不变、未改动的大表字节一致。

### 7. 新增依赖：fflate

xlsx 是 zip，Node 没有内置 zip 读写（`zlib` 只有 deflate）。用了 `fflate`：
零依赖、纯 JS。本项目一贯抠依赖（上一轮还专门删掉了 `qrcode` 自己手写二维码），
这次加它的理由是：手写 ZIP 读+写约 120 行二进制代码，
而这是**开真实增值税发票**的路径，不值得为省一个 30KB 的库去赌自己写的中央目录没写错。

> 装的时候用了 `--registry=https://registry.npmmirror.com`（直连 npm 超时）。
> 顺带把 lockfile 里遗留的 `qrcode` 及其 24 个传递依赖清掉了 ——
> 那是上一轮删依赖时没同步的陈旧条目，源码里早就没有任何地方 import 它。

## 十八、2026-09-11：定价口径推倒重来（内推与券互斥）

站长报：同一单三个价 —— 商品页 1800、结算页 1700、收银台 1800。

### 1. 根因：`Math.min(定价, 专属价)`

我上一轮把 `quoteOrder` 的基准价写成了

```ts
const baseline = Math.min(baseAmount, referralAmount)   // ← 错
```

前提是「专属价一定比定价便宜」。**这个前提是错的。** 线上实际有 19 条
`referral_prices` 的专属价**高于**定价 —— 推广人自己加价，差额就是他的返现：

| 推广人 | 商品 | 定价 | 专属价 |
|---|---|---|---|
| 596 | Claude Max20x自助充值 | 1700 | **1800** |
| 271 | ChatGPT Pro 20x | 1430 | 1480 |
| 271 | ChatGPT Plus | 138 | 160 |
| 13 | 若干 | — | 99999（用来标记「不通过内推卖」）|

于是站长那一单：商品页 `/api/products?ref=` 显示 1800（专属价）→
结算弹窗调 `quoteOrder` 拿到 `min(1700,1800)=1700` → 服务端建单按专属价 1800。
**三处三个数**，买家完全不知道该信哪个。订单 `20260911E59909C5` 就是这么产生的
（实付 1800，已付款；金额本身是对的，错的只是中间那一屏显示 1700）。

### 2. 新规则：两条，没有第三条

```
① 走内推链接下单 → 一律按专属价，优惠券不可用
② 没走内推      → 按定价，券可选，默认不勾选
```

`quoteOrder` 里**没有 min、没有任何比较**。内推单在函数第一行就短路返回专属价。
`calcCoupon` 连 `referralAmount` 这个入参都删掉了 —— 它现在只回答
「这张券用在这个金额上能减多少」，根本不知道内推的存在。

**少一个分支，就少一处能对不上的地方。** 上一版「取更优」要求结算页和建单
两边都正确理解两套优惠的交互，结果就是两边算出不同的数。

### 3. 三处消费端

| 位置 | 改动 |
|---|---|
| `api/coupons/mine` | 返回 `referral: true/false`；内推单**直接返回空券列表**（结算页场景），`baseline` 即专属价 |
| `purchase-modal` | 内推单整块隐藏优惠券区，代之以一句说明「已按专属价计算，你的券不受影响」；普通单**默认不勾选**任何券 |
| `api/orders` | 无需改动 —— 内推单 `quote.applied==='referral'`，自然走「券没用上」分支：按专属价成交、**券不锁定**、原样留在账户里 |

买家手工构造请求把券塞进内推单也没用：服务端按专属价成交，券完好无损。

### 4. 为什么默认不勾选券

上一版是自动选中最省钱的那张。看着贴心，实际是：买家在商品页看到一个价，
点开弹窗又变成另一个，**第一反应是「这价怎么自己变了」**。
少一次困惑比多省几十块重要。券要用，买家自己点，点了上方金额立刻跟着变。

### 5. 自测

`npx tsx scripts/check-coupon.ts` —— **88 条**。
其中有一组专门的回归用例，就用站长报的那组数（定价 1700 / 专属价 1800）：

```
✓ 专属价高于定价：按专属价 1800，不是 min 取的 1700
✓ 专属价高于定价：baseline 同样是 1800
✓ 专属价高于定价 + 带券：还是 1800
✓ 专属价高于定价：不会被误判成 coupon
```

以及三条跨所有分支的恒等式：`baseline − discount === amount`、
内推单 `discount` 恒为 0、任何分支实付恒 > 0。

### 6. 留给站长的一个业务问题

**专属价可以高于定价**，意味着买家点推广链接进来，看到的价比公开站价还贵
（1800 vs 1700）。现在三处显示一致了，不再混乱，但「渠道价比官网价贵」
这件事本身要不要允许，是定价策略问题，不是 bug。
要限制的话，在后台设专属价那里加一条「不得高于商品定价」的校验即可。

## 十九、2026-09-14：商品页 SEO（Google 方向）

### 1. 查出来的问题：所有商品页在搜索引擎眼里是同一个页面

实测 `/products/3` 与 `/products/5`：

```
<title>贝果科技 - Claude & ChatGPT AI 订阅服务</title>   ← 两页完全一样
<meta name="description" ...>                            ← 两页完全一样
application/ld+json 块数: 0
```

原因：`products/[id]/page.tsx` 第一行是 `'use client'`，
**客户端组件用不了 `generateMetadata`**，只能继承 layout.tsx 的全站默认值。

讽刺的是不直接赚钱的新闻模块做得很规范（Server Component + `generateMetadata` +
`ArticleJsonLd`），而最该吃搜索流量的商品页一个都没有。

### 2. 改法：Server 外壳 + 客户端组件

`products/[id]/` 与 `products/` 各拆成两个文件：

| 文件 | 职责 |
|---|---|
| `page.tsx` | Server Component，只做 `<head>`：标题、描述、canonical、JSON-LD |
| `product-client.tsx` / `products-client.tsx` | 原来那 414 / 383 行，**一行没改** |

客户端组件仍靠 `useParams()` 自己取数，外壳不接管取数 ——
让外壳传数据下去就得改那 414 行的取数逻辑，风险不划算。
外壳单独查库只取 SEO 用的几个字段，用 React cache 去重。

### 3. canonical 是重点，不是附带

推广人分享出去的是 `/products/3?ref=CODE`，这些链接会被真实抓取。
带 ref 时接口返回的是**专属价**，而专属价可能高于网站定价
（线上 19 个商品如此；商品 3 定价 1750，推广人 596 的专属价 1800）。

不声明 canonical 的后果：Google 很可能收录带 ref 的副本，
**搜索结果里显示的价格比你官网还贵**，同时一批重复页面互相稀释权重。

已实测：`/products/3?ref=3b63639619` 的 canonical 指向 `https://bigolab.com/products/3`，
JSON-LD 里的价格是**定价 1750**（不是专属价 1800）—— 结构化数据只认公开价。

> 注意**不要**把 `?ref=` 加进 robots.ts 的 disallow。
> 禁止抓取会让 Google 读不到 canonical，反而更糟。canonical 才是这里的正解。

### 4. 结构化数据刻意不输出评分

站上没有真实评价体系。为了富摘要编一个 `aggregateRating` 是最典型的
结构化数据造假，会吃人工处罚，而且**影响整个域名**而不止这一页。
`sales` 是真实数字，但它是销量不是评分，不能拿来充数。
自测里有两条断言钉死这一点。

### 5. IndexNow

**先把预期摆正：这个协议 Google 不支持。** 支持方是必应、Yandex、Seznam、Naver。
Google 的收录只认 sitemap 的 lastmod 与 Search Console。
所以它解决的是「必应几分钟收录」，不是谷歌。

- 密钥走协议支持的 `keyLocation`，固定放 `/indexnow-key.txt`，
  不为了「文件名必须等于密钥」去开根级通配路由
- `compose()` 新增 `publishedSlugs`，**只记首发**（重写不产生新 URL）
- cron 路由跑完所有段后以 `await` 推送 —— 响应返回后没跑完的 Promise
  可能随请求上下文被丢掉，不能 fire-and-forget 到响应之后
- 推送自带 8s 超时、异常就地吞掉，最坏情况是这一轮不推
- fetch 带 `cache: 'no-store'` —— 同 `feed.ts` 那个坑，
  推送接口被数据缓存冻住意味着**第二次之后全是假成功**

已实测：提交返回 **HTTP 202**，说明对方成功抓取并校验了密钥文件
（也顺带证明 Cloudflare Tunnel 对外可达）。

### 6. 环境变量必须列进 docker-compose

`--env-file` 只负责 compose 文件里的**变量替换**，不会自动把变量注入容器。
`GOOGLE_SITE_VERIFICATION` / `BING_SITE_VERIFICATION` / `INDEXNOW_KEY`
三个都必须在 app 服务的 `environment:` 里列出来。

漏了这一步的表现是**静默失效**：`.env.production` 里明明配了，
验证 meta 就是不输出、IndexNow 永远推 0 条，而且没有任何报错。

### 7. sitemap 本来就有商品页（我一度判断错）

排查时我用 `grep | head -25` 看 sitemap.ts，输出在商品块之前被截断，
于是得出「商品页没进 sitemap」的错误结论并向站长报告过。
实际 HEAD 里第 117 行起一直有 productPages 块。实测 sitemap 共 433 条 URL，
其中商品页 15 条、新闻页 410 条。

> 顺带一个值得注意的比例：**sitemap 里 95% 是新闻页**，
> 而其中约三分之二是只有 147 字摘要的薄页（见下）。

### 8. 待决策：405 个已发布事件里 273 个是薄页

| | |
|---|---|
| 已发布事件 | 405 |
| 有全文层（detail）的 | 132 |
| **只有一段摘要的薄页** | **273（67%）** |
| 摘要平均字数 | 147 |

管线修好后三天从 141 涨到 405，约每天 +90，其中三分之二是薄页。

Google 2024 年起把 **scaled content abuse**（规模化生成内容）写进垃圾内容政策，
判定标准不是「是不是 AI 写的」，而是「是不是为排名批量生产」。
147 字 + AI 自动生成 + 每小时发布，正好命中这个特征组合。
**关键在于这类判定是站点级的** —— 真被判定，商品页会跟着一起被拖下去。

三个可选项（尚未实施，等站长决定）：
1. 提高全文层补齐率，让每页都有实质内容
2. **给没有全文层的事件加 `noindex`**，只留站内浏览，不进索引（最快止血，一行元数据）
3. 提高发布门槛，宁可一天 20 条有深度的

## 二十、2026-09-15：站内卡密兑换系统（多充值平台可插拔）

从不同商家拿货，同一商品的不同批次可能来自不同上游。设计目标只有一个：
**接第二家平台时前端一行都不用改。**

### 1. 分层

```
lib/redeem/types.ts        与厂商无关的领域类型（状态 / 字段 / 结果 / 指引）
lib/redeem/providers/
    sysa.ts                唯一知道 redeemgpt 长什么样的文件
lib/redeem/registry.ts     key -> 适配器
lib/redeem/service.ts      鉴权边界、限流、日志
app/(shop)/redeem/[provider]/    兑换页（动态段，所有平台共用）
app/api/redeem/[provider]/check|activate/
```

**接一家新平台 = 加一个适配器文件 + 在 registry 注册一行。**
路由 `/redeem/sysb`、接口 `/api/redeem/sysb/*`、后台下拉全部自动出现。

铁律：**上游的字段名、状态码、文案，一个都不许漏出适配器。**
前端只要直接读了上游 JSON，接第二家就得重写整个兑换页。

### 2. 三层命名，买家只看到最外那层

| | 值 | 谁能看到 | 能不能改 |
|---|---|---|---|
| `key` | `sysa` | URL + 数据库 | **不能**（改了历史卡密找不到适配器）|
| `adminLabel` | `A 系统（redeemgpt）` | 只有后台下拉 | 随时 |
| 对外名称 | 贝果科技 · AI会员自助充值系统 | 买家 | 随时 |

`check-redeem.ts` 里有断言专门检查**买家可见文案里不出现上游品牌**。

### 3. 放行规则（2026-09-15 简化过一次）

```
在 card_keys 里 + 状态 USED + 未停用  →  放行
能不能充                             →  上游的查询结果说了算
```

**曾经还要求 `redeem_provider` 必须等于当前路由的平台，已删。**
那层是错的：判断「这张卡能不能在这个系统里充」的权威是上游自己，
库里那个字段只是导入时的人工标注 —— 漏标、标错、旧卡没标，
都会让一张完全正常的卡在自家页面上被拒掉，而买家什么也做不了。

**防滥用的闸没有松**：真正拦住「拿我们当撞库跳板」的是前两条。
上游的 `check`/`activate` **不需要任何认证**，我们要是对任意字符串都往上转发，
别人就能用我们的域名枚举上游卡密，而上游看到的是**我们服务器的 IP** ——
轻则被封，重则失去货源。平台绑定从来不是安全边界。

> 反查用 `cardContentHash`（sha256(盐|明文)，确定性），
> 为此给 `content_hash` 单独加了索引：原有唯一索引前导列是 `product_id`，
> 单独按哈希查用不上它，否则每次兑换全表扫 1704 行。

### 4. 买家凭据：只过路，不留痕

`session_key` 是 Claude 的 sessionKey、`session_json` 里含 ChatGPT 的 `accessToken`
—— **等价于账号密码**。保证：

- **不落库**：`RedeemLog` 的字段是 `card_key_id / provider / action / state / message / request_id / ip`，
  **根本没有能装凭据的位置**（`logRedeem` 的签名里也没有这个参数，防止有人「顺手」传进来）
- **不进日志**：activate 路由的 catch 里绝不能打印 request body
- **不回显**、提交完前端立刻清空 state

### 5. 几个容易判断错的地方

- **`verify_failed` 归 COMPLETED 而不是 ERROR** —— 卡已消耗、钱已花，
  归到错误会让买家以为能再充一次，那是二次损失
- **严格区分「这张卡废了」和「稍后再试」** —— 让买家对着废卡反复重试是最典型的客服工单来源
- **两条通道都填时只发优先的那个**，不把两个一起发（买家会以为自己填的 uid 生效了）
- **上游 fetch 必须 `cache: 'no-store'`** —— 被 Next 数据缓存冻住的话，
  「激活成功」会被回放给后面每一个人，而卡密根本没提交出去

### 6. 指引由适配器按产品给出

两个产品的取值路径完全不同，所以**不能写死在页面里**：

| | 步数 | 路径 |
|---|---|---|
| Claude | 6 步 | 登录 → F12 → Application → Cookies → 找 `sessionKey` → 粘贴 |
| ChatGPT | 4 步 | 登录 → 打开 `/api/auth/session` → 复制整段 JSON → 粘贴 |

另有 GPT 专用的 `force` 开关（官方页面叫「放弃剩余会员时间 强制充值」）。
不给这个开关，账号已有订阅的买家会卡死在 `plan_not_allowed` 且看不懂原因。
三个细节：只对 Session 通道有效；文案必须把「剩余时间作废不可恢复」说在前面；
either/or 校验要排除它，否则只勾这个就会被当成「已填账号」带空凭据提交。

### 7. 卡密怎么关联到充值系统

- **导入时**：后台【卡密管理】导入卡片里的「本批充值系统」下拉
- **事后批量**：勾选卡密 → 「批量设充值系统…」下拉（任意状态都能改，
  它只是路由标注，不动金额也不动库存，所以这一支不触发 `syncAutoStock`）
- 列表里有「充值系统」列，能一眼看出哪些走站内、哪些还是跳外链

订单页兑换入口的优先级（**服务端决定，前端不要再判一遍**）：

```
redeemProvider 非空 → /redeem/<provider>?cdk=...（站内，相对路径）
否则 redeemUrl      → 本批专属外链
否则 product.cardRedeemUrl → 商品默认外链
```

> 前端那个 `isHttp()` 正则会把相对路径整个滤掉，所以加了 `isUsable()`。
> 漏了这一步的表现是「有卡密但没有兑换按钮」。

### 8. 上游实测记录（2026-09-15，只读，未消耗卡密）

用两张真卡打 `/api/check` 验证过协议翻译：

| 卡 | 上游返回 | 我们的翻译 |
|---|---|---|
| Claude 卡 | `app=claude`、`activation.ready` | `READY` + sessionKey/UID 两条通道 ✓ |
| ChatGPT 卡 | `app=gpt`、`activation.ready` | `READY` + Session/UID ✓ |
| 编造的卡 | `cdk.not_found`、**HTTP 200** | `NOT_FOUND` ✓ |
| 空卡密 | `input.invalid` | 有对应文案 ✓ |

两个印证了防御性写法必要性的细节：
**业务失败也返回 HTTP 200**（只看状态码会把「卡密不存在」当成成功）；
**失败时 `data` 是空字符串而不是对象**（`asObj()` 守卫挡住了 `data.app` 直接抛）。

上游还返回了文档里没有的 `rwd_type` 字段，我们没读 ——
多读一个未文档化的字段等于给自己埋一颗对方随时可以改的雷。

### 9.5 sysb 为什么会调上游的 V1 接口（`providers/sysb-lookup.ts`）

代理拿到的 V2 只有 4 个接口，**没有验卡能力**，文档还写着「无需提前调用验卡」。
后果是两个真实的坏体验：已经充完的卡照样摆出充值表单；买家得自己猜通道。
靠本站记下的上游订单号只能覆盖「从我们站里充的」卡 —— 在别处充掉的完全看不见。

站长授权后，改用上游自家「卡密查询」工具所调的三个**只读**接口：

| 通道 | 接口 | 请求体 | 判成功 |
|---|---|---|---|
| 信用卡 | `POST /api/v1/sub/queryOrder` | `{cdks:[cdk]}` | `code===200`，读 `results[].cdk_status` |
| iOS | `POST /gateway/gpt?action=query` | `{cdks:"cdk"}` | `status==='success'`，读 `data[].status` |
| Claude | `POST /gateway/claude?service=claude&action=cardQuery` | `{codes:[cdk]}` | `code` 为 0/200，读 `data[].status`（0未用 / 1,2已用） |

三条轮流问，**命中即停**；一张卡只有一条通道认得，通道由此确定 ——
这比按商品名猜可靠，商品名只用来决定先查哪条。

**这里有四条别人接手时很容易踩坏的约束：**

1. **用「查询」，不要用「验卡」。** `verifyCdk` / `action=verify` 会**锁定卡密约 3 分钟**
   （上游页面自己写着）。拿买家花钱买的卡挨个通道去验，是在用真卡做探测。
2. **绝不带 V2 Token。** 这是另一套面向浏览器的接口，发过去没用，只扩大暴露面。
   `sysb-lookup.ts` 刻意不 import `token()`。
3. **查不动就当「不知道」，放行。** 这些接口不在代理授权范围内，随时可能改版。
   任何失败一律返回 `null` 退回原流程 —— 一个非正式接口不该有权力让买家充不了值。
4. **账号邮箱必须打码再回前端。** 卡有可能已经转手，完整邮箱不该给到当前查询的人。

判定结果落到页面上的规则（`sysb.ts` 的 `fromLookup`）：除 `UNUSED` 外**一律
`fields:[]` 且 `state!=='READY'`。前端的 `showForm` 同时要求这两个条件，
少写一个就会在已核销的卡上漏出充值表单。`activate` 提交前会再查一次，
挡住绕过页面直接打接口的情况。

> 上游确认了通道时只返回**那一条** variant，前端 `variants.length > 1` 才渲染选择器 ——
> 只有一个选项的单选框等于把一件已经确定的事又推回给买家。
> 上游三条都查不到时才退回「三条都列出来 + 默认选中按商品名猜的那条」。

### 10. 【配色】商城页面不要用 components/ui 里的 Card / Input / Button

这三个是**后台浅色主题**的组件：`Card` 自带 `bg-white`、`Input` 是白底、
`Button` 的 outline 是深灰字。商城侧是深色渐变背景，套上去就是**白底白字、整页看不见**
—— 兑换页第一版就是这么翻车的，站长一眼就发现了。

尤其注意：`.glass` 定义在 `@layer components` 里，**优先级低于 utility class**，
所以 `<Card className="glass">` 里赢的是 `Card` 自带的 `bg-white`，不是 `glass`。
以为加个 glass 就能改深色，是错的。

商城侧一律用原生元素 + 这套 token：

```
面板   rounded-2xl border border-white/10 bg-white/[0.04] backdrop-blur-xl
输入框 rounded-xl border border-white/10 bg-white/[0.04] text-white/90
       placeholder:text-white/25 focus:border-purple-400/50
主按钮 bg-gradient-to-r from-violet-600 to-purple-600 text-white
次按钮 border border-white/12 bg-white/[0.06] text-white/80
```

**改完要真的打开看。** 本地 `npm run dev` + 浏览器里跑一段脚本，
遍历所有叶子节点比对前景色与实际背景色的亮度，检出「都亮」或「都暗」的元素 ——
比肉眼看截图可靠得多（截图还会拍到重绘假象）。兑换页改完实测：
49 个叶子节点、0 处低对比，且指引/文本域/开关/按钮都确认渲染出来了。

## 二十一、2026-09-15：友情链接与招商位（顺带下架导航里的「游戏」「关于」）

### 1. 做了什么

| | |
|---|---|
| 前台导航 | 去掉「游戏」「关于」，新增「友链」→ `/links`。**页面本身没删**：`/games`、`/about` 仍可直达，`/about` 的入口还在首页与 footer，sitemap 也照收 |
| 前台 `/links` | 招商区（大卡 + 次级卡 + 「此位招商中」空位）、友链墙、互链须知、本站信息一键复制（HTML / Markdown 片段）、在线申请弹窗 |
| 后台 `/admin/links` | 审核队列（待审/展示中/已下线/已拒绝 四个 tab 带角标）、增删改、logo 上传、排序、生效与到期时间、回链巡检、页面文案与招商参数配置 |
| 通知 | 新增 `link.applied` 事件，前台有人提交申请就推企业微信，带一键前往后台的链接 |

### 2. 数据模型：一张表 `friend_links`

友链和招商位共用 `FriendLink`，靠两个字段分流：

- `slot`：`FRIEND` 友链墙 / `SPONSOR` 招商位
- `status`：`PENDING` 待审核 → `APPROVED` 展示中 → `OFFLINE` 已下线；`PENDING` → `REJECTED` 已拒绝

**为什么不拆两张表**：两者字段重合八成以上，真正的差别只有「收不收钱、有没有到期时间」。
拆开就要把列表、审核、排序、巡检各写两遍，而后台其实是同一个审核队列。

**REJECTED 与 OFFLINE 为什么要分开**：拒绝是「没通过」，下线是「通过过但现在不挂了」
（对方撤链 / 赞助到期）。合成一个状态就查不出「这家是不是曾经互挂过」，续约和追责都没依据。
前台申请时也靠这个区分：OFFLINE 的可以重新申请并复用同一行，REJECTED 的直接挡回去。

页面文案（导语、收录标准、招商权益、招商位总数、本站信息…）存在 `settings` 表的
一行 JSON 里，key = `friend_links_page`。读的时候一律与代码里的默认值合并，
数据库里那行坏了也不会让前台白屏。

### 3. 四个不能改错的地方

**① 招商位的 rel 是硬约束，不做后台开关。**
Google 明确要求付费/赞助换来的链接必须标 `rel="sponsored"`，未标注本身就构成 link scheme，
处罚的是**整个域名**而不是那一条链接。所以 `outboundRel()` 里 `SPONSOR` 恒定输出
`sponsored nofollow`，界面上那个 dofollow 下拉在选中招商位时是禁用的。
同时写 `nofollow` 是因为**百度不认 sponsored**，会把它当普通链接。
卡面上还有肉眼可见的「广告」二字 —— 那是给人看的，`rel` 是给爬虫看的，两个都要有。

**② 友链页不能加 noindex。**
常见误解是「友链页 noindex 就安全了」。实际上长期 noindex 的页面，Google 最终会停止
跟随其上的链接（noindex 事实上退化成 nofollow），结果是对方一点权重都拿不到，
发现后就会把我们撤掉，互挂直接崩掉。权重控制靠**逐条的 rel**，不靠整页 noindex。

**③ 回链巡检只记结论，绝不自动改状态。**
`POST /api/admin/links/[id]/check` 会去对方页面上找本站域名，把结果写进
`backlink_ok / backlink_note / checked_at`，**不动 `status`**。
自动下线看着省事，但对方站在 Cloudflare 后面返回一次 403、或者临时抖一下，
就会把一个正常的合作方悄悄摘掉 —— 这在友链圈是最伤关系的事。标红，人看一眼再决定。

后台那个「一键巡检」是在**浏览器里串行**调单条接口的，不是服务端批量：
nginx 的 `proxy_read_timeout` 只有 90s，一次抓几十个外站必然超时
（前端拿到 504，服务端还在空跑）。

**④ `/links` 必须服务端直出，不能改成客户端 fetch。**
这一页存在的意义就是让出站链接真的出现在 HTML 里。对方站长验证我们有没有挂他，
用的基本都是「纯 HTTP 拉 HTML + 匹配域名」的工具（本项目自己的 `checkBacklink` 就是这么干的），
百度爬虫也基本不执行 JS。更要命的是 `robots.ts` 里 disallow 了 `/api/`，
连 Googlebot 的渲染器都不会去抓那条接口 —— 客户端取数等于**所有**爬虫和检测工具
都看到一个空壳，招商位买家买到的是一张没人看得见的卡片。
所以 `page.tsx` 是 `force-dynamic` 的 Server Component，数据取好再传给客户端组件。
第一版就是踩了这个坑（照搬了 `/products` 的「server 壳只管 metadata」范式），
改完之后的验收命令见第 6 节最后那条 grep。

### 4. 安全上的几处刻意设计

- **出站地址只认 http/https**，`normalizeUrl()` 还会拒掉带账号密码的地址和不含点的主机名。
  `logo` 另外允许 `/uploads/` 开头的本站相对路径，但禁 `..`。
  友链表单是全站最典型的存储型 XSS 入口，`<a href>` 与 `<img src>` 都吃外部输入。
- **`checkBacklink` 挡了私网地址**（10/8、127/8、172.16/12、192.168/16、169.254 云元数据、
  100.64/10、::1、fc00::/7）。**这不是完整的安全边界**：域名解析后仍可能指向内网
  （DNS rebinding）。该接口只有管理员能调、且不回显响应体，风险可接受；
  要彻底解决得自己实现带 lookup 校验的 undici agent，代价远大于收益。
- **公开接口 `/api/links` 是白名单式显式 select**，`contact / remark / apply_ip` 一个都不往外发。
  项目在买家订单接口上踩过一次 `{...row}` 整行外泄的坑，这里从第一版就不给机会。
- **申请接口**：蜜罐字段（命中就装作成功，不给脚本任何反馈）+ 同 IP 每小时 3 次限流
  + 同域名只留一条记录。用的是现成的 `src/lib/news/rate-limit.ts`，没再造一个。

### 5. `/api/upload` 改了两处（论坛照常用，无需改动）

- 新增 `scope` 表单字段，白名单 `forum | links`，不传就是 `forum`。
  **绝不能直接用前端传来的目录名**，那就是任意路径写入。
- 用量上限从「只数 `uploads/forum`」改成「数 `uploads` 根目录下所有子目录」。

友链 logo 落在 `public/uploads/links/`，和论坛配图共用 docker named volume `forum_uploads`，

### 7. 这一版刻意没做的（想做再捡）

按性价比排序，都是调研里确认有价值但这轮范围外的：

1. **定时巡检 cron + 先告警后下线**。现在是人工点。要做的话放已有的 cron 容器里，
   连续 3 次失败才降级，且必须把 Cloudflare 挑战页（403/503/「Just a moment...」）
   单独归为 BLOCKED 不计入失败 —— 直接判死会误杀一大批正常站。
2. **邮件通知**（审核结果 / 掉链告警给 7 天宽限 / 招商位到期提醒）。邮件基建现成的。
3. **申请进度自查页**（发个 token，对方自己看状态、改简介、撤回），仿收据 token 的做法。
4. **巡检日志表**（存标题、正文 hash、命中片段）。防的是「申请时是技术博客，
   三个月后改成赌博站」—— 标题剧变或正文指纹漂移就告警。
5. **favicon / 首屏截图本地化**：审核通过时抓一次存成本站资源，别热链第三方。
6. **招商位自助下单**：项目有现成的 Product/Order/Payment/Invoice，
   把广告位做成一个特殊商品，付款后自动建 SPONSOR 记录（付款不等于自动上线，仍要过内容审核）。

### 8. 已知取舍（不是遗漏，是权衡后接受的）

- **回链巡检的 SSRF 只挡到字面地址。** `isBlockedHost` 拦了私网/回环/云元数据段与
  IPv4-mapped IPv6，跳转终点也复查一次，但域名解析后仍可能指向内网（DNS rebinding）。
  彻底解决要自己实现带 lookup 校验并 pin 住 IP 的 undici agent，代价远大于收益。
  当前的缓冲是：只有管理员能触发、响应体不回显、总时长 10s、只读前 512KB。
- **域名查重是应用层「先查后插」，没有数据库唯一约束。** 并发提交两条同域申请理论上都能落库。
  代价只是审核队列里多一条重复项，人工删掉即可；换成加一列 `host` + 唯一索引才是根治，
  但那是一列派生数据，三条写路径（申请 / 后台新建 / 后台改址）都得记得同步，
  以表的规模（几十上百条）不值得。
- **「游戏」页下架导航后成了站内孤岛。** `/games` 及三个子页现在没有任何来自外部的内链，
  只在 sitemap 里留着。sitemap 不传权重，零内链的页面在 Google 那里的典型归宿是
  「已抓取 — 尚未编入索引」。**这需要你拍板**：认可它还有价值就在 footer 补个入口，
  认可它没价值就把 `/games` 从 `sitemap.ts` 删掉 —— 别停在中间态，
  向爬虫提交一个自己都不肯链的 URL 没有意义。

顺手核过一处：论坛正文的外链渲染（`src/lib/markdown.ts:50`）已经是
`rel="noopener noreferrer nofollow"`，UGC 外链这条没有漏。若要更规范可以再补一个 `ugc`，
但那只是锦上添花，不是隐患。

## 二十二、2026-09-15：卡密导出 Excel

### 1. 做了什么

后台「卡密管理」加了两个导出入口，导出的是真正的 `.xlsx`：

| 入口 | 位置 | 范围 |
|---|---|---|
| 「导出所有卡密」 | 商品选择器那一行 | **全站所有商品**，不看任何筛选 |
| 「导出这 N 张」 | 卡密列表卡片头部 | 当前筛选（商品 / 状态 / 批次 / 关键词 / 是否关联订单），跨全部页码 |
| 「脱敏版」小字链接 | 挨着第一个按钮 | 同样的表，卡密列做掩码，适合只要台账不要卡密本体的场景 |

导出的列：ID、商品、卡密、状态、订单号、外部发卡归属、批次、备注、成本、售价、利润、
兑换平台、兑换链接、发出时间、导入时间。表头加粗、冻结首行、开自动筛选。

### 2. 为什么自己写 xlsx（`src/lib/xlsx.ts`）

**不能用 csv。** 卡密长这样：`1234567890123456`、`0012-3456-7890`、`2024-1-1-ABCD`。
csv 交给 Excel 打开时，这三种会分别变成 `1.23457E+15`、丢掉前导零、**被识别成日期**。
卡密一旦被改写就是废卡，而且在表里肉眼看不出来 —— 运营照着发货，买家拿到的是废的。
xlsx 每个单元格自带类型，写成 `inlineStr` 就永远是那串字符。

**不装 exceljs / xlsx 包。** 这台机器 1.8G 内存，而我们要的只是一张平表。
`fflate` 已经是项目依赖（发票导出在用），xlsx 本质就是一个 zip 装几个 XML，
手写那几个 XML 比拖一个 20MB 的包进来划算。

`src/lib/xlsx.ts` 是通用的，以后别处要导表直接用，不要再造第二个。

### 3. 自测：`npx tsx scripts/check-xlsx.ts`（50 条）

覆盖两类**静默失败**，tsc 和 next build 一个都拦不住：

- **结构写错** → Excel 弹「文件已损坏，是否修复」。断言六个部件齐全、交叉引用正确、
  styles 的各个 `count` 与实际子元素数一致、worksheet 子元素顺序符合 schema
  （`dimension → sheetViews → sheetFormatPr → cols → sheetData → autoFilter`，顺序错了
  Excel 不给任何有用提示）、列名 26 进位（Z→AA、AZ→BA、第 703 列 AAA）、零行时 dimension 合法。
- **值被悄悄改写** → 断言长数字串 / 前导零 / 类日期串 / 两端空格 / XML 特殊字符全部原样，
  控制字符被剔除，超长截到 32767，NaN 与 Infinity 不写进数值格，
  `null` 是空格子而不是 `0`（「未知」和「零」在成本利润表上是两件事）。

另外用 Python 的 openpyxl 真实加载过一遍（零告警 + 11 项断言），确认不是「只有我自己能读」。

### 4. 安全：这是全站最敏感的一个导出

导出来的文件里是明文卡密 —— 那就是商品本体，谁拿到谁能直接用。做了三件事：

1. **鉴权靠 middleware**（`/api/admin/*` 统一校验 ADMIN），路由内不另起一套。
2. **`Cache-Control: no-store, no-cache, must-revalidate`**，不让任何中间层留副本。
3. **每次导出都往企业微信推一条**（范围、数量、含不含明文、筛选条件、来源 IP、时间）。
   后台没有操作日志表，这条推送就是唯一的痕迹 —— 真出事时，「什么时候被导走过」
   比任何事后分析都关键；它同时也是一层威慑：干这件事会留下声响。
   事件名 `cardkey.exported`，想关掉就在 `NOTIFY_EVENTS` 白名单里排除它（但**不建议关**）。

前端在明文导出前还有一道 `confirm`，写明「文件里是明文卡密、不要转发、会推送记录」。
注意 `confirm` 是纯文本对话框，那段文案里不要写 markdown 强调，`**` 会原样显示成星号。

### 5. 两条数量上的红线

- `ROW_LIMIT = 50000`：xlsx 是整份在内存里拼出来再压缩的，没有流式写入。
  现网 1727 张离这个数很远，设它是为了挡住「将来几十万张一次导出把机器 OOM 掉」。
  真到那天应该按商品或批次分次导。
- 单元格 32767 字符：超了整份文件打不开，`src/lib/xlsx.ts` 里会截断并补省略号。

### 6. 上线

**没有数据库变更**，照第十一节的常规流程走即可（备份 → build → `up -d app`），
跳过 db push 那两步。冒烟：登录后台 → 卡密管理 → 点「导出所有卡密」→
文件能打开、卡密列没被改写、企业微信收到一条 `🔐 卡密被导出`。

## 二十三、2026-09-15：⚠️ CVE-2025-29927（Next middleware 绕过）—— 线上在暴露，待处置

做卡密导出时顺带查出的**严重线上漏洞**，与导出功能本身无关、是既有问题。

### 是什么

本项目 Next 锁死在 14.2.3，该版本存在 CVE-2025-29927：请求带一个
`x-middleware-subrequest: src/middleware:src/middleware:src/middleware:src/middleware:src/middleware`
头，就能让 `src/middleware.ts` **整个不执行**。而全站 `/admin` 与 `/api/admin/*`
的 ADMIN 校验只有 middleware 这一层 —— 于是**未登录即可访问任意后台接口**。

线上实测（只探状态码、未取数据）：
```
无凭据            → 401 请先登录
带绕过头          → 400 请选择商品   ← 打到了路由处理器本身，middleware 被跳过
```
危害面：`/api/admin/cardkeys?reveal=1` 明文卡密、`/api/admin/users` 客户信息、
订单、发票 PII…… 全都在裸奔。nginx 的 `ports: "80:80"` 还让公网 IP 能绕开
Cloudflare 直连源站，边缘 WAF 也救不了。

### 已做的部分缓解（随代码走，未部署）

1. **卡密导出接口 `/api/admin/cardkeys/export` 补了路由内独立 `requireAdmin`**：
   即使 middleware 被绕过，这个「一键导出全站明文卡密」的口也会自己返回 403。
   已随本次提交上线包一起。**但这只护住了这一个接口，其它后台接口仍在裸奔。**
2. **nginx 加了 `proxy_set_header x-middleware-subrequest "";`**（本节代码已改，未部署）：
   在反代层把客户端传入的这个头清空，一刀切堵掉**全站**的绕过。所有外部流量
   （域名回源 + IP 直连）都过这个 location，两条入口都覆盖。

### 待你拍板的两步

**第一步（急、低风险、几秒钟）——上 nginx 缓解，全站立即止血：【2026-09-15 已部署完成并验证】**
```bash
cd /opt/beiguo/beiguo-shop && git pull origin main
docker compose --env-file .env.production exec -T nginx nginx -t   # 先测配置
# ⚠️ 不能只 `nginx -s reload`：nginx.conf 是单文件 bind-mount，git pull 是
#    「写新文件再 rename 覆盖」，换了 inode，容器还绑在旧 inode 上，reload 读到的
#    仍是旧配置（本次实测：reload 后绕过头还是 400）。必须重建 nginx 容器重新绑定：
docker compose --env-file .env.production up -d --force-recreate nginx
docker compose --env-file .env.production exec -T nginx nginx -T 2>/dev/null | grep middleware-subrequest  # 复核已加载
# 验证：带绕过头应变回 401（而不是 400）
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: bigolab.com" \
  -H "x-middleware-subrequest: src/middleware:src/middleware:src/middleware:src/middleware:src/middleware" \
  http://127.0.0.1/api/admin/cardkeys
```
不重建镜像、不动 app/db，只重启 nginx 容器（停机就那一两秒）。公网 + 内网实测绕过均已变回 401。

**第二步（根治）——升级 Next 到 14.2.x 最新补丁版（≥14.2.25，建议 14.2.33）：**
14.2.x 内的补丁升级，无 breaking change。改 `package.json` 的 next 版本 →
`npm install` 重新生成 lock → 重建镜像（约 6-7 分钟）→ `up -d app`。
这一步要重建镜像、且动了核心依赖，建议单独一次、上线后完整冒烟（下单/支付/开票/
新闻管线/后台各页都点一遍）。可以和下一个功能上线合并，但 nginx 那步**别等它**。

> 两步的关系：nginx 那道是「边界清洗」，升级是「根上修好」。只做 nginx 也能挡住
> 已知的公网利用；但 Next 不升，将来任何「构造内部头」类的新变种都还得靠这一道兜着，
> 所以两步都要做，只是有先后缓急。
