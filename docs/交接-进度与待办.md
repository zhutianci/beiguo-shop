
### 三个必须知道的坑

**① PowerShell 会把命令拆坏。** 带空格、引号、或前导 `--` 的参数会被 PowerShell 重新分词，远程命令直接变形（实际踩过：`git log --format="%H %s"` 被拆成三段）。**所有远程命令一律 base64 传输**：

```powershell
$script = @'
<多行 bash>
'@
$norm = $script -replace "`r`n","`n"
$b64=[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($norm))
& $wb exec -i i-2ze8s6my1msl5q6thpum -r cn-beijing --timeout 600 -c "echo $b64 | base64 -d | bash"
```

**② exec 会话对长输出会中途截断。** 耗时命令（build / db push / 管线）必须后台跑再轮询：

```bash
nohup <命令> > /tmp/x.log 2>&1 &
# 之后另起一次 exec：
for i in $(seq 1 280); do pgrep -f "<关键词>" >/dev/null || break; sleep 3; done
cat /tmp/x.log
```

**③ 本地 sleep 被工具链拦截**，等待逻辑要写在服务器端的 bash 里。

```bash

# 查 MySQL（必须带 --default-character-set=utf8mb4，否则中文全是 ?）
```

## 四、AI圈大事记（最复杂的模块）

**先读 `.claude/skills/ai-news-pipeline/SKILL.md`**，那是契约，改动前必看。

### 定位（这条决定其他所有设计）

**是「行业动态聚合工具」，不是新闻站。** 《互联网新闻信息服务管理规定》要求的许可拿不到，策略是让内容不落入其定义：只做自写摘要 + 外链原文，绝不转载；不碰政策/监管/地缘/裁员等「社会公共事务」选题；作者硬编码「贝果科技 AI 资讯助手」，不署真人名；AI 生成标识必须出现在 6 处（法定义务）。

**为内容质量拆掉这条基础，不划算。** 上一轮用户两次要求「搬运 aihot.virxact.com 的内容」，都按此原则挡下并给了替代方案 —— 见待办。

### 管线（六段，各自独立抢锁，任一段失败不影响其他段）

```
collect  每小时05分  抓 feed（零 LLM、零依赖、单源熔断）
triage   每小时05分  分诊：是否 AI 相关、是否命中黑名单、归类
cluster  每小时15分  同事件聚合（urlHash 免费快路 + 实体指纹 + 小模型判定，不用向量）
compose  每小时25分  抓原文正文 → 写摘要/推荐理由/AI评分（唯一的写作题）
rank     每15分钟    重算热度（明细落 scoreDebug，可解释）
digest   21:00/周一09:00  日报周报
```

### LLM

当前用**智谱 GLM**（`glm-4-flash` 分诊 / `glm-4-plus` 写作）。境内直连实测：GLM 401/55ms、DeepSeek 401/87ms、百炼 401/34ms 全部可达；**`api.openai.com` 超时、`api.anthropic.com` 403，均不可用**。换供应商只改 `LLM_PROVIDER` + `LLM_API_KEY` + model 名。

日预算硬闸 `NEWS_DAILY_BUDGET_CENTS=300`（3 元/天），超支当天降级为「只去重不写摘要」。

### 信源可达性（2026-09-04 从该 ECS 实测，新增源前必须实测）

✅ 机器之心、量子位、36氪、InfoQ、少数派、掘金、AIbase、通义博客、IT之家、**hnrss.org**、TechCrunch:AI、The Verge:AI、Ars Technica:AI、MIT TechReview、The Decoder、微软研究院、OpenAI RSS、Anthropic News、GitHub API、arXiv API、Simon Willison

❌ **X/Twitter、Reddit、HuggingFace（含 hf-mirror）、DeepMind、Meta AI、Mistral、Google News、V2EX、RSSHub 公共实例、CSDN、知乎热榜**

⛔ **开源中国已停用** — 它的 news feed 是码云项目发布流水（「灵界 OS v4.0.0」），题材不符且单次 40 条会刷屏

**媒体源用「AI 专版」RSS 而不是全站版** — 全站版里手机汽车游戏占大头，每条都要花一次分诊调用才能剔除，等于为噪音付费。

### 踩过的坑（都是线上真实发生的）

1. **glm-4-flash 吐裸对象** — 提示词里的 JSON 示例被 `join('\n')` 拆成两行，模型认成内层对象形状，把最外层 `results` 数组整个丢掉。**给模型的 JSON 示例必须完整在同一行**
2. **批量越大越浪费** — 给 8 条只答第一条。`NEWS_TRIAGE_BATCH=3` 后每批答全，延迟反而更低
3. **漏答条目被永久判死** — 原逻辑标 `FAILED` 永不重试，40 条丢了 35 条。已改为留 RAW 重试，7 天陈旧清理兜底
4. **素材被锁死在一句话** — 只用 feed 的 description，摘要写不出细节，换强模型也没用。已加 `lib/news/extract.ts` 抓原文正文（零依赖启发式提取），效果显著：

   > 改前：阿里已发表两篇关于循环Transformer的顶会论文，该技术因GPT-6而受到关注。
   > 改后：…提出 MeSH 和 SpiralFormer 解决方案…MeSH 使模型减少 33% 非嵌入参数的同时，准确率提升 1.06 个百分点，额外计算开销仅 0.014%。

## 六、血泪教训（同一个坑不要踩第二次）

### 1. 我自己造成过两次线上故障

**crontab 被删光字母 r。** 容器命令里写了 `tr -d '\r'` 想防 CRLF，反斜杠被 YAML 折叠 + shell 双引号两层处理吃掉，变成 `tr -d 'r'` —— `curl`→`cul`、`cron`→`con`，**全部定时任务静默失效且 crond 不报错**，连原有的收款单清理和接码轮询一起挂。现已改用 `.gitattributes` 强制 LF，容器命令里只用 `cp`。**不要再往那条命令里加任何带反斜杠的转义。**

**改 TZ 引发锁永不自愈。** 把 app 容器从 UTC 改成 `Asia/Shanghai` 后，MySQL 的 `DATETIME` 不带时区，改动前写入的行被按新时区重新解释后落到「未来」，`now - createdAt` 成负数恒小于 TTL。表现：MySQL 算 27 分钟，Node 认为没到 15 分钟。已改用绝对值判断。**凡是比较 MySQL DATETIME 与当前时间的地方都要留意这个。**

### 2. 排查前先验证，别急着下结论

我曾断言「`ORDER_MSG_WEBHOOK_URL` 从没传进容器，留言推送一直是哑的」，依据是 `printenv` 里没有。**错了** —— `docker compose exec` 起的是另一个进程，不走 Next 的启动流程。真实链路是 Next standalone 把 `.env.production` 打进镜像，`server.js` 启动时用 `loadEnvConfig` 读进 `process.env`。用户的留言通知一直是正常的。

**由此引出一条 compose 写法铁律**：新增环境变量一律用**裸变量名**（`- FOO`），不要写 `- FOO=${FOO}`。后者在 FOO 未定义时会给容器一个**空字符串**，而 dotenv 遵循「已存在的 env 优先」，反而把镜像内 `.env` 的真实值**遮蔽掉** —— 那会让本来正常的功能失效。

### 3. 我又造成过一次全站宕机：`docker system df` 把 dockerd 撑爆了

2026-09-07 14:13，为了评估构建空间跑了 `docker system df` / `docker builder du` /
`du -sh /var/lib/docker/overlay2`。这几条要遍历所有镜像层算尺寸，
而这台机器有 **36 个悬空镜像**、overlay2 目录硬链接展开约 130G。
`dockerd` 的 RSS 冲到 1.4G（全机 1.87G），被内核 OOM 杀掉，**连杀 5 次**
（14:13:50 / 14:17:45 / 14:19:06 / 14:25:01 / 14:30:17）。
dockerd 被 SIGKILL 时它名下的容器随之消失，**beiguo 与 jishi 两个站点同时下线约 20 分钟**。
`restart: unless-stopped` 救不了这种情况 —— 容器不是「退出」，是随父进程一起没了。

**这台机器上永远不要跑**：`docker system df`、`docker builder du`、`du /var/lib/docker`。
看空间用 `df -h`（文件系统层面）+ `docker images`（只读元数据、不算尺寸）。
真要清理直接 `docker image prune -f`，不要先去「统计一下有多少」。

顺带：`du -sh /var/lib/docker/overlay2` 报出来的 130G 是**假的**（overlay2 用硬链接，
du 会重复计数），磁盘实际只有 40G。想知道真实占用只能看 `df -h`。

### 4. 其他

- **alpine 镜像不装 tzdata，`TZ` 会被静默忽略**，进程仍跑 UTC，不报错
- **`.next` 属主是 root 而运行时是 nextjs 用户** — 不 chown 会每次请求报 EACCES 并退化成完全不缓存
- **`route.ts` 只能导出 HTTP handler 和少数配置项**，多导出一个 schema 会让 `next build` 报「不是合法的 Route export」，公用校验放 `lib/`
- **动态路由 params 签名混用** — 26 个里只有 6 个是 Next15 的 `Promise<{id}>`，新文件跟同目录已有写法保持一致，混用会 build 失败
- **`docker compose exec` 的 stderr 会被 compose 的 WARN 淹没**，查东西时用 `2>/dev/null` 而不是 `2>&1`
- **mysql 客户端不带 `--default-character-set=utf8mb4` 中文全变 `?`**
- **中文限宽用 px 不用 ch** — `ch` 按西文 `0` 宽度算，对中文会算出接近实际字数一半的宽度

## 十、本轮（2026-09-07 第二轮）做了什么

### A1 · 去掉 7 天窗口，改增量累积 + 按月归档

原来有四处「7 天」，**只该去掉两处**：

| 位置 | 处置 | 理由 |
|---|---|---|
| `compose()` 的 `since` | **去掉** | 就是它让超期事件永远轮不到，表现为「只有最近一批」 |
| `rank()` 的 `RANK_WINDOW_DAYS` | **去掉**，改分层 | 同上 |
| `cluster()` 的 pending 窗口 | 放宽到 14 天，**并加终态** | 原来超期条目会永远停在 `eventId=null`：既不成事件也不被清理（purge 只删孤儿，而它们的 `triageState` 是 OK）。现在超龄判 `SKIP` |
| `collect()` 的 `MAX_ITEM_AGE_DAYS` | **保持 7 天不动** | 这是**收集窗口**不是处理窗口，它咬合着 30 天保留期与 `TRIAGE_STALE_DAYS`。放宽只会「花钱分诊 → 被保留期删掉 → 下轮又插回来」 |

**compose 改双车道**：新鲜（3 天内，3 条/轮）+ 积压（更老，2 条/轮）。
名额**固定切分**，不是「优先新鲜、有剩再给积压」—— 后者在信源稳定产出时永远剩不下名额。
积压排序按 `sourceCount / tier1Count` 而不是 `score`：score 带 36h 半衰期，
跨越几十天的候选之间衰减差几个数量级，按 score 排等价于纯按时间排。

**compose 加墙钟 7 分钟**。crontab 的 `--max-time 540` 是硬上限，到点 curl 断开、
服务端还在跑并占着锁。**锁 TTL 永远不能大于 540s**，只能让 compose 自己提前收工。

**rank 改分层**：热层（72h）每轮、温层（72h–14d）每小时一次、冷层只补 `baseScore` 为空的。
新增 `base_score` 列（不含衰减的原始分）：`score` 是 `Decimal(8,3)`，约三周后老事件全 round 成
`0.000`，归档页就排不出先后。历史行为 NULL，由冷层每轮补 200 条自愈，**不写一次性回填脚本**。

**归档页 `/news/archive/2026-09`**（不是 `/news/2026-09`）。后者要在 `[slug]` 这个动态段里
靠正则分流「2026-09」和「2026-09-06-a1b2c3d4e5」—— 正则少写一个锚点，
**全部新闻详情页会当场变成归档页**。为省 8 个字符引入一个全站级故障点不划算。
`/news` 底部有「按月回看」入口，sitemap 收录最近 24 个月的归档页。

**「最近补录」折叠行**：积压车道写出来的老事件按 `happenedAt` 排会沉到时间流中间，
首屏看不见。这一行是它们唯一的露出位置，**复用 `HIGHLIGHT_WHERE`**（含 `needsReview:false`）——
「happenedAt 很旧 + publishedAt 很新」几乎就是降级发布条目的特征，不过滤会精准地把最不该推的推上去。

### A2 · 全文层 detail（600–1200 字，2–4 段带小标题）

新增三列：`detail`(Text)、`detail_state`(RAW/DONE/SKIP)、`detail_tries`(Int)。

- **新事件**：跟摘要一次生成（compose 仍是「唯一的写作题」），`maxTokens` 900 → 2200
- **老事件**：独立的回填通道，**默认关闭**（`NEWS_DETAIL_BACKFILL=1` 开启）。
  三道闸：每轮最多 2 条、当日花费超预算 40% 就停、单条最多重试 3 次
- **detail 是可丢弃区块**：段数/字数/连续 18 字重合/数字回查/禁词/选题黑名单，
  任何一项不过就只丢这一块，事件照常发布。**不进 `needsReview` 队列** ——
  页面退回「只有摘要」本身就是合规状态，没有需要人看的残留
- **瞬时失败绝不写终态**：超时/限流/5xx 只 `detail_tries+1` 下轮重来。
  第四节踩坑 3（40 条丢 35 条）就是把瞬时失败当内容性结论写死导致的
- 后台可按段人工编辑，**刻意不提供「重新生成」按钮**——那会是无次数上限的付费入口

**顺带修了 `lib/llm.ts` 的记账**（这是 A2 的前置，不修就没有可信的成本数据）：
① 三级降级的 token 改累加（原来后一次覆盖前一次）
② 失败调用按真实 token 计费（原来写死 0，导致失败率一升高账面花费反而不动）
③ 日界改固定 +8 算术（原来用进程本地时区，alpine 无 tzdata 时会偏 8 小时）

## 十一、部署这一版（顺序不能改）

**不要用 `scripts/deploy.sh`**。它第 2/3 步 build+up、第 5 步才 `db push`，
顺序与「新增列」的要求正好相反：新镜像会在新列存在之前上线，
`/news/[slug]` 的 select 里带着还不存在的列 → 整页 500。
（详情页的 `getEvent` 已加 try/catch 兜到 404，但那是安全网不是方案。）

正确顺序是 **先 DDL、后 build**。六项变更全部是可空 `ADD COLUMN` 或 `CREATE INDEX`，
旧代码不读不写，所以「旧镜像还在跑的时候先建列」完全安全。


### 部署实录（这一轮踩了三个坑，都记下来）

**坑一：`exit 0` + 空输出 ≠ 成功。** 这台机器的 workbench exec 会话在长命令中途断开，

**坑二：构建日志说成功，其实产出的是旧镜像。** 一次 `docker compose build app`

`latest` 根本没动。表现是强制重建容器后新路由仍然 404。
**结论：构建前后各打印一次 `docker images --no-trunc --format '{{.ID}}' beiguo-shop-app:latest`，
两个 ID 相同就是没构建成功**，不要看日志。

**坑三：回滚标签打反了。** `docker tag ...:latest ...:rollback-xxx` 必须在 **build 之前**打。
build 之后 `latest` 已经是新镜像，这时打的标签指向新镜像，回滚时会滚到自己身上。

### 正确的部署顺序（在第十一节基础上修正）

```bash
docker inspect -f '{{.Image}}' beiguo-app
# 6) 冒烟要包含**新增路由**，且带一个负例（如 /coupon/不存在的码 应 404，
```

## 十六、2026-09-09：AI圈大事记静默宕机两天（Next 数据缓存把一个 HTML 拦截页冻住了）

站长报「collect 之后没有新增条目、管线不自动执行、也没有 AIHOT 内容」。
查下来是三件独立的事，其中第一件是真正的宕机，而且**藏了整整 39 小时没人看得出来**。

### 1. 根因：`fetch` 被 Next 的数据缓存冻住

现象非常具有迷惑性 —— 每一项指标都是绿的：

- `crond` 在跑，crontab 9 条任务完整，`rank` / `detail` 每轮都按时执行
- `news_sources.last_ok_at` 是当天的，16 个源**全部** `ok`、`failed: 0`
- collect 返回 `{"sources":16,"ok":16,"failed":0,"inserted":0}`

唯一异常的只有 `inserted: 0`，而 `inserted: 0` 本来就有一个完全正常的含义 ——「抓到了，但都已经在库里」。

实际发生的是：

```
.next/cache/fetch-cache/444bc794...  ← 190 个条目之一
{"kind":"FETCH","data":{"headers":{
   "content-type":"text/html; charset=UTF-8",     ← 不是 RSS，是拦截页
   "date":"Mon, 07 Sep 2026 17:35:29 GMT"}}}      ← 冻在 9-07
```

App Router 会把裸 `fetch()` 的响应写进磁盘上的数据缓存并**无限期**复用。
9-07 容器重启后的第一轮抓取，量子位回了一个 `text/html` 的页面（不是 feed），
这个响应被写进缓存 —— 此后每一次「抓取」都在读同一份 9-07 的 HTML：
解析出 0 条 → 入库 0 条 → 而 collect 依然报告 16/16 成功。

**路由段上的 `export const dynamic = 'force-dynamic'` 挡不住它。**
那行确实写在 `api/cron/news/route.ts` 顶部，但缓存条目实实在在地写出来了，
时间戳还在持续更新。别指望路由段配置能管到被 import 进来的库函数里发的请求。

证据链（三方交叉验证，不是推断）：
- 同一份 `fetchText + parseFeed` 在本机跑，量子位解析出 10 条，最新一条是**当天**的
- 容器内 `wget` 直连量子位，拿到的是**真 RSS**，pubDate 也是当天 → 网络与信源都没问题
- 只有走 Node `fetch` 的那条路读到的是 9-07 的 HTML → 缓存是唯一的差异点

**为什么 `force-dynamic` 没挡住**（在 `node_modules/next@14.2.3` 的编译产物里逐行确认过，不是猜的）：

- `app-route/module.js`：`switch (this.dynamic)` 里那句 `case "force-dynamic"` 被
  `if (isStaticGeneration)` 包着。真实 HTTP 请求进来时 `isStaticGeneration` 是 false，
  **这个导出在运行时什么都没设**。
- 同文件下一句 `staticGenerationStore.revalidate ??= this.userland.revalidate ?? false`
  —— 路由没导出 `revalidate`，于是 store 里是 `false`，而 `false` 在 Next 里的含义是**永久缓存**。
  这条路由不但没关掉缓存，反而把自己设成了更可缓存。
- 本可以救命的豁免没触发：`revalidate = 0` 只在 `hasNonStaticMethods` 时设，
  而它检查的是 `POST/DELETE/PATCH/OPTIONS`。`api/cron/news` 只导出 `GET`。
  **这个 cron 入口当初要是写成 POST，这个 bug 根本不会发生。**

**修复**：`src/lib/news/feed.ts` 的 `fetchText` 加 `cache: 'no-store'`。
抓的是每小时都在变的外部内容，缓存在这里没有任何意义，只会把某一秒的意外冻成永久状态。

> **千万不要再叠一个 `next: { revalidate: 0 }`。** 两个一起传不是「重复但无害」，
> 而是直接把修复作废：`patch-fetch.js` 同时收到 `cache` 与 `revalidate` 时只打一条 warn，
> 然后执行 `_cache = undefined` —— 你的 `no-store` 被丢掉，缓存又开回来了。
> 那条 warn 没人会看，于是**看起来修了、其实没修**。

### 1.1 同一个雷的另外三处（一并修了）

`autoNoCache` 的条件是 `(有 authorization 头 || 非 GET) && store.revalidate === 0`，
两个条件是**与**。我们的路由 `store.revalidate` 是 `false` 不是 `0`，
所以**「POST 不会被缓存」这个直觉在这个项目里是错的** —— 缓存键由 `fetchCacheKey(url, init)` 算出、含 body，
所以每个不同的 body 各存一份，缓存一年（`.next/cache/fetch-cache` 那 190 个条目就是这么来的）。

| 位置 | 后果 | 处理 |
|---|---|---|
| `api/admin/news/runs/route.ts` 手动触发按钮 | **最坏的一个**：GET + 固定地址 + 无 body = 每次点都是同一个缓存键。命中缓存时会重放上一次的 JSON，`res.ok` 为真 → 走成功分支 → 写一条 `ok:true` 的运行记录 → 界面显示「已执行」，而 cron 路由根本没进去、锁没抢过、管线一步没跑。**管线一出问题，你点这个按钮永远看到绿色** | 加 `cache: 'no-store'` |
| `lib/llm.ts` | 同一个 prompt 重试会拿回上一次那份回复。上次要是返回了解析不了的 JSON，重试多少次都还是它 | 加 `cache: 'no-store'` |
| `lib/aliyun.ts` | 发短信/邮件的响应缓存一年，纯白占磁盘 | 加 `cache: 'no-store'` |
| `lib/herosms.ts` | 已经写了 `cache: 'no-store'`，无需改动（幸好——接码状态轮询要是被冻住，每一单都会卡死） | ✅ 本来就对 |

> 部署即清缓存：`.next/cache` 在容器文件系统里，没有挂卷（compose 只挂了
> `forum_uploads` 与 `mysql_data`），重建容器就是空的。不需要手工去删。

### 2. 为什么两天没人发现 —— 观测口径的问题，已一并修掉

`inserted: 0` 把两种情况压成了同一个数字：

| 实际情况 | 旧报告 | 是否正常 |
|---|---|---|
| 抓到 30 条，都已在库 | `inserted: 0` | ✅ 正常 |
| 抓回来的根本不是 feed，0 条 | `inserted: 0` | ❌ 已经宕机两天 |

`CollectResult` 现在多两个字段，两种情况再也混不到一起：

- `details[].parsed` / `details[].bytes` —— 每个源解析出多少条、抓回多少字节
- 顶层 `unparsable: string[]` —— **抓到了字节却一条都解析不出**的源，非空就该有人去看

`[news/collect]` 那行日志也一并带上 `parsed` 与 `unparsable`。

顺带暴露出一个**早就存在**的问题：`jiqizhixin`（机器之心）与 `36kr` 返回的一直是 HTML 而不是 RSS，
lifetime `item_count` 都是 0 —— 它们从来没有产出过一条内容，只是以前看不出来。
`aibase` / `qwen` / `infoq-cn` / `anthropic` 的 `item_count` 也是 0，同样需要复查。

### 3. AIHOT 没有内容：库里根本没有这一行

`SEED_SOURCES` 里定义了 `aihot`（`enabled: false`，等 A1 积压消化后再开），
但 `news_sources` 表里 25 行**没有一行是它** —— 定义加进代码后从未执行过 seed。

`seedSources()` 对既有行的 `enabled` 是安全的：`common` 里**不含 `enabled`**，
所以跑 seed 不会把站长在后台手工停用的 `oschina` / `hn` / 7 个 X 源重新打开。
只有新建的行才会用种子里的 `enabled`。

**但 `?stage=seed` 依然不能随手跑。** `SEED_SOURCES` 现在有 33 条，库里只有 25 行 ——
差的 8 行里，`thedecoder` 与 `ithome` **没有写 `enabled: false`**，
走的是 `enabled: s.enabled ?? true`，一 seed 就会**立刻上线**，下一个 :05 直接开抓。
此外 seed 会把 25 行既有记录的 `feedUrl / weight / tier / role / kind / viaRelay`
全部覆写回种子值，后台里手工调过的会被静默改掉。

所以这次**没有跑 seed**，只单独插了 `aihot` 一行。
其余 7 行要不要加、`thedecoder` / `ithome` 要不要开，留给站长决定。

授权号 `AIHOTAPI20260907001` 是写死在 `lib/news/aihot.ts` 里的常量，不需要配环境变量。
已从服务器实测：`GET https://aihot.virxact.com/api/v1/items?limit=5` 带 `X-License` 返回 200 / 5870 字节。

### 4. 这次的教训

**「所有指标都绿」不等于「在工作」。**
这次每一个健康检查都是通过的：进程在、任务在跑、HTTP 200、失败数 0。
唯一能暴露问题的指标（`inserted`）恰好与一个正常状态共用同一个值。

订两条：

1. **抓外部内容的 `fetch` 一律显式写 `cache: 'no-store'`**，不要依赖路由段配置。
2. **不要让"什么都没发生"和"正常但无事可做"共用同一个数字。**
   新增一个只在异常时才非空的字段（这里是 `unparsable`），比在旧字段上加注释有用得多。

## 十七、2026-09-10：批量开票导出（后台一键导出待开发票）

后台发票页新增「导出待开发票」按钮，导出税局官方批量导入模板，拿去开票系统直接导入。

### 1. 为什么是「往官方模板里塞行」而不是自己生成 xlsx

模板（V260401，657KB）里藏着东西：

- 隐藏工作表 `excelVersion`，A4 写着 `pt:20260401` —— 导入端**会校验版本**
- 39 列里有 **17 处下拉数据验证**（发票类型、是否含税、是否展示购买方信息…），值必须是选项原文
- 另有 4.5MB 的行政区划、245 行国家地区等隐藏数据源表

自己拼一个「看起来一样」的工作簿，等于赌对方只读值、不校验版本。赌输了就是一整批发票开不出来。
所以实现只做一件事：**把 `<row>` 追加到两张表的 `</sheetData>` 之前，其余字节原样不动**。
自测里有一条断言直接比对未改动的 4.5MB 表在导出前后字节完全一致。

### 2. 模板结构（改版时对照这里）

| 表 | zip 内路径 | 表头行 | 数据起始行 | 列 |
|---|---|---|---|---|
| 1-发票基本信息 | `xl/worksheets/sheet1.xml` | 第 3 行 | **第 4 行** | A..AM（39） |
| 2-发票明细信息 | `xl/worksheets/sheet6.xml` | 第 3 行 | **第 4 行** | A..N（14） |

> 工作表文件名与顺序**不对应**（明细表是 sheet6.xml 不是 sheet2.xml），别按序号猜，
> 要从 `xl/workbook.xml` 的 `<sheets>` 里按 name 找 rId 再查 rels。

填写规则见 `src/lib/invoice-export.ts`，固定值全部提成常量，且**与模板下拉选项原文逐字比对**（自测里有断言）。

### 3. 「待开」的口径

`status='SUBMITTED' 且 pay_status='PAID'`，排序 `paidAt asc`（先付先开）。

**与财务台 `api/finance/invoices/[token]` 完全一致，两处必须一样。**
注意后台列表接口 `api/admin/invoices` 的 status 筛选**不带 payStatus 条件**，
所以后台列表里筛 SUBMITTED 看到的条数可能比导出的多 —— 导出的是真正该开的那些。

### 4. 规格型号：商品名 → 发票上印的字

只在买家勾了「展示 ChatGPT/Claude 字眼」时才填，没勾则规格型号/单位/数量三列一起留空。

商品名是运营随手起的，线上真实形态五花八门，规则是：切掉竖线右边的发货方式 →
去掉括号补充说明 → 抹掉「自助充值/代充/成品号/充值」这类话术 → 补「会员订阅」。

```
Claude pro 自助充值 | iOS订阅                            → Claude pro会员订阅
ChatGPT Pro 20x 自助充值 | 信用卡充值（无法覆盖plus和5x）  → ChatGPT Pro 20x会员订阅
Claude Max 20x成品号 | 自动发货                           → Claude Max 20x会员订阅
Claude MAX 5x自助充值（测试中）                           → Claude MAX 5x会员订阅
```

**认不出来的商品一律留空，不瞎编。** 线上有「Codex验证码-美区实体手机卡-单次接码」这种
根本不是订阅的商品，拼成「…单次接码会员订阅」会印在真发票上。
规格型号在模板里是**非必填**，留空完全合法；编一个假的则不然。

### 5. 三个容易踩的坑

**① 一律写成 `inlineStr`，不写数字。** 税号、银行账号是十几二十位纯数字，
一旦被当成数值，Excel 会显示成 `1.91202E+18`，账号就废了。模板填表说明第 6 条也写着
「所有内容输入均为文本格式输入」。

**② `.gitattributes` 必须有 `*.xlsx binary`。** 仓库根上有 `* text=auto`，
漏掉这条，git 会把 xlsx（本质是 zip）当文本做行尾转换，压缩流里的 `0x0A` 被改成 `0x0D0A`，
包直接损坏 —— 而且要等到有人下载、Excel 报「文件已损坏」才会发现。

**③ Dockerfile 必须显式 `COPY templates`。** Next 的 standalone 文件追踪只看
import/require 依赖图，`fs.readFile` 读的文件它一无所知。不写这行，镜像里就没有模板，
导出接口要到运行时才报 ENOENT。

### 6. 自测

```bash
npx tsx scripts/check-invoice-export.ts   # 120 条
```

除了纯逻辑，它还会**真的打开 templates/ 下的官方模板**校验：工作表名与 rId、
模板版本号、数据起始行、下拉选项原文、以及 22 个列头文字与代码里的列序一一对齐。
**模板换版时这个脚本会先响**，不会等到发票开错。

最后一组是端到端：真生成一个 xlsx、再解回来，验证行写进去了、隐藏表还在、
zip 条目数不变、未改动的大表字节一致。

### 7. 新增依赖：fflate

xlsx 是 zip，Node 没有内置 zip 读写（`zlib` 只有 deflate）。用了 `fflate`：
零依赖、纯 JS。本项目一贯抠依赖（上一轮还专门删掉了 `qrcode` 自己手写二维码），
这次加它的理由是：手写 ZIP 读+写约 120 行二进制代码，
而这是**开真实增值税发票**的路径，不值得为省一个 30KB 的库去赌自己写的中央目录没写错。

> 装的时候用了 `--registry=https://registry.npmmirror.com`（直连 npm 超时）。
> 顺带把 lockfile 里遗留的 `qrcode` 及其 24 个传递依赖清掉了 ——
> 那是上一轮删依赖时没同步的陈旧条目，源码里早就没有任何地方 import 它。

## 十八、2026-09-11：定价口径推倒重来（内推与券互斥）

站长报：同一单三个价 —— 商品页 1800、结算页 1700、收银台 1800。

### 1. 根因：`Math.min(定价, 专属价)`

我上一轮把 `quoteOrder` 的基准价写成了

```ts
const baseline = Math.min(baseAmount, referralAmount)   // ← 错
```

前提是「专属价一定比定价便宜」。**这个前提是错的。** 线上实际有 19 条
`referral_prices` 的专属价**高于**定价 —— 推广人自己加价，差额就是他的返现：

| 推广人 | 商品 | 定价 | 专属价 |
|---|---|---|---|
| 596 | Claude Max20x自助充值 | 1700 | **1800** |
| 271 | ChatGPT Pro 20x | 1430 | 1480 |
| 271 | ChatGPT Plus | 138 | 160 |
| 13 | 若干 | — | 99999（用来标记「不通过内推卖」）|

于是站长那一单：商品页 `/api/products?ref=` 显示 1800（专属价）→
结算弹窗调 `quoteOrder` 拿到 `min(1700,1800)=1700` → 服务端建单按专属价 1800。
**三处三个数**，买家完全不知道该信哪个。订单 `20260911E59909C5` 就是这么产生的
（实付 1800，已付款；金额本身是对的，错的只是中间那一屏显示 1700）。

### 2. 新规则：两条，没有第三条

```
① 走内推链接下单 → 一律按专属价，优惠券不可用
② 没走内推      → 按定价，券可选，默认不勾选
```

`quoteOrder` 里**没有 min、没有任何比较**。内推单在函数第一行就短路返回专属价。
`calcCoupon` 连 `referralAmount` 这个入参都删掉了 —— 它现在只回答
「这张券用在这个金额上能减多少」，根本不知道内推的存在。

**少一个分支，就少一处能对不上的地方。** 上一版「取更优」要求结算页和建单
两边都正确理解两套优惠的交互，结果就是两边算出不同的数。

### 3. 三处消费端

| 位置 | 改动 |
|---|---|
| `api/coupons/mine` | 返回 `referral: true/false`；内推单**直接返回空券列表**（结算页场景），`baseline` 即专属价 |
| `purchase-modal` | 内推单整块隐藏优惠券区，代之以一句说明「已按专属价计算，你的券不受影响」；普通单**默认不勾选**任何券 |
| `api/orders` | 无需改动 —— 内推单 `quote.applied==='referral'`，自然走「券没用上」分支：按专属价成交、**券不锁定**、原样留在账户里 |

买家手工构造请求把券塞进内推单也没用：服务端按专属价成交，券完好无损。

### 4. 为什么默认不勾选券

上一版是自动选中最省钱的那张。看着贴心，实际是：买家在商品页看到一个价，
点开弹窗又变成另一个，**第一反应是「这价怎么自己变了」**。
少一次困惑比多省几十块重要。券要用，买家自己点，点了上方金额立刻跟着变。

### 5. 自测

`npx tsx scripts/check-coupon.ts` —— **88 条**。
其中有一组专门的回归用例，就用站长报的那组数（定价 1700 / 专属价 1800）：

```
✓ 专属价高于定价：按专属价 1800，不是 min 取的 1700
✓ 专属价高于定价：baseline 同样是 1800
✓ 专属价高于定价 + 带券：还是 1800
✓ 专属价高于定价：不会被误判成 coupon
```

以及三条跨所有分支的恒等式：`baseline − discount === amount`、
内推单 `discount` 恒为 0、任何分支实付恒 > 0。

### 6. 留给站长的一个业务问题

**专属价可以高于定价**，意味着买家点推广链接进来，看到的价比公开站价还贵
（1800 vs 1700）。现在三处显示一致了，不再混乱，但「渠道价比官网价贵」
这件事本身要不要允许，是定价策略问题，不是 bug。
要限制的话，在后台设专属价那里加一条「不得高于商品定价」的校验即可。
