## 0. 结论速览：对设计影响最大的 16 条

1. **上游是 hero-sms，它继承了已关停的 SMS-Activate。** 它同时提供两套协议：兼容 SMS-Activate 的 `handler_api.php`，和新的 `/api/v1` REST。本站现有的单品接码用的是兼容协议。SMS-Activate 在 2025-12 关停时，用户余额被困（提现门槛 $30），这是「余额制」风险的现成案例。【文档】【竞品】
2. **时序硬约束**：普通激活有效期 20 分钟，少数「服务×国家」组合是 40/45/60 分钟，以取号返回的 `activationEndTime` 为准。取号后 **120 秒内**不能取消（`EARLY_CANCEL_DENIED`，`info.minActivationTime=120`）。**收到码之后**不能取消（`OTP_RECEIVED`），所以也就不能换号。20 分钟内没收到码，上游自动退回余额（状态 10）。【文档】【规则】
3. **上游只在没收到码时退款**：主动取消是状态 8，超时自动退款是状态 10。我方给买家退款，应以上游进入 8 或 10 为准，不能只看自己的计时器。【文档】【官网】
4. **我方真实成本是 `retail`**，也就是 getPrices 的 `cost`，等于 `default × 1.2`，不是 `default`。近 14 天的账单扣费全部等于 retail。【实测】
5. **价格是阶梯库存。** offers 接口返回 `map = {价格: 数量}`、`counts.defaultPrice`（起价档库存）和 `counts.total`（任意价库存）。有的组合起价档很薄，比如 dr/16 的 total 是 163,186，defaultPrice 只有 63。**map 和 counts 的精确语义有冲突**（见 3.4），属于未确认。【实测】【未确认】
6. **运营商只筛库存，不改价格。** 公开 API 拿不到按运营商的价格和库存（getOperators 只给代码列表），只有官网的非公开接口有。【实测】【推断】
7. **取号可能失败**，返回 `NO_NUMBERS`（HTTP 200 纯文本）、`WRONG_MAX_PRICE`（带 `info.min`）、`NO_BALANCE`、`BANNED`（带 scope 和解封时间）、`CHANNELS_LIMIT`、`SERVICE_NOT_AVAILABLE`。**上游取号接口不支持幂等键**，所以超时了就不知道到底买没买到。【文档】
8. **再收短信免费**：同一次激活在有效期内可以收多条短信，额外的短信会自动送达。取全部短信用 `getAllSms` 或 v1 的 `/otp`，但**激活取消或退款后就取不到了**。【文档】【官网】
9. **Webhook 只有 `sms-incoming` 一种事件**，没有签名（只能靠两个来源 IP 做白名单）。开 webhook 要先开 2FA，并且只推到 HTTPS 地址。取消、超时、退款都不推送，只能轮询。【文档】
10. **每个账户限流 50 RPS**，超限封 10 秒。【规则】
11. **封禁规则**：同一「国家+服务」取号 ≥100 个且成功率 <6%，封 30 分钟；有 5 个以上组合被封，全账户封 30 分钟；取号量 500/750/1000 以上且成功率 <3% 时，同时等码的号码数分别限为 10/5/1。**所有买家共用我们一个账户**，所以任何一个买家的失败都算在我们头上。转售商身份（`resellerUserId`）可以把封禁隔离到单个买家，但这个参数只在 v1 `POST /activations` 的文档里出现。【规则】【文档】
12. **转售商红线**：不得复制 HeroSMS 的名称、logo、配色；不得把买家引到 HeroSMS 客服；售后由我们自己负责；加价不受限制。【规则】
13. **上游余额只有 $12.44**（09-29）。近 14 天共 73 次激活，只成功 23 次（31%），同一订单连换 5 个号才成功一次的情况常见。**换号是刚需**，而且余额必须有告警和停售保护。【实测】（**站长 09-29 决定**：不设停售线、不设每日扣费上限，余额低于 $2 时企业微信告警；下单锁价前核对余额够付本单取号上限，见设计 E26、E65。）
14. **本站收款不是支付宝商户接口**：买家扫站长的个人收款码、手输「唯一金额」，安卓手机上的 SmsForwarder 把到账通知转发给网站，网站按金额匹配订单（`src/lib/vmq.ts:537`）。**所以不存在自动原路退款**，拿不到付款人账号，也没有退款 API。5-竞品草稿 §5.5 里「`alipay.trade.refund` 全自动原路退」**在本站不可行**，本文已纠正。【仓库】
15. **站内已有余额**（`User.balance`、`BalanceLog`），但目前只进不出：只有推荐返现和管理员调整会写入，买家找客服提现。**没有余额支付**，不过枚举 `PayMethod.BALANCE` 已经存在（`prisma/schema.prisma:389-393`），店面开关也预留了 `balancePay` 和 `wallet`（`src/lib/storefront/public.ts:23-24`）。【仓库】
16. **现有单品接码是「一个商品对应固定的服务+国家」**，一单一行 `SmsActivation`（`orderId @unique`），换号时覆盖同一行。新板块需要「一单多号」的明细表，以及按单保存的报价快照。【仓库】

### 1.3 v1 REST（请求头鉴权）

以下都来自【文档】，另有标注的除外。

- **`POST /activations`（购买）**：`service`\*、`country`\*、`amount`\*（1–10）、`operator`（默认 any，正则 `^([a-zA-Z0-9!_]{2,},)*[_a-zA-Z0-9!]{2,}$`，`!` 推测表示排除，**未确认**）、`maxPrice`（≥0.0067）、`fixedPrice`、`duration`（传了就是租用）、`verificationType`、**`resellerUserId`**（`^[a-zA-Z0-9_.@-]{1,36}$`）。返回 `{"data":[Activation]}`，Activation 的字段是 `id, status, phone, service, country, countryPhoneCode, operator, price, createdAt, expiredAt, verificationType, subtype, otpList[]`。错误有 403 `BANNED_GLOBAL/BANNED_SPECIFIC`、404、422、500。**文档没列 402，余额不足时返回什么，未确认；没号时返回什么，也未确认。**
- **`DELETE /activations/{id}`**：取消并退款，返回 204。只有没收到过 OTP 的激活才能取消。
- **`POST /activations/{id}/finish`**：完成，不退款，返回 204。
- **`POST /activations/{id}/replace`（换号）**：返回新的 `{"data":[Activation]}`，示例里 status=4。**前置条件、是否计费、旧激活怎么处理，文档都没写**。官网提示「2 分钟后可更换号码」，失败文案是「变更激活号码失败」。【官网】【未确认】
- `GET /activations`：进行中的激活，每条带完整 `otpList`，`size` 1–25。**v1 没有按 id 查单个激活的接口。**
- `GET /activations/history`：`from`\*/`to`\*（ISO8601），可按 `services[]`、`countries[]`、`statuses[]`（6/8/10）筛选，也可 `search`。返回 `data[{id, createDate, service, country, phone, moreCodes, cost, status, phoneCode, currency}]`、`totals{sum, successCount}`、`meta`。
- `GET /activations/{id}/otp/last`、`GET /activations/{id}/otp`：最后一条 OTP、全部 OTP。
- `GET /activations/stats?date=`：`{国家:{服务:{count, success, percent}}}`。
- **`GET /activations/offers/{sms|call}?services=&countries=`（取代 getPrices）**：`data[服务][国家] = {prices:{default, retail, min}, counts:{total, physical, defaultPrice}, map:{价格:数量}}`；`meta.order.rate`（按评分排序的服务和国家）、`meta.order.deliverability.countries[服务]`（按到达率排序的国家）。错误：404 `OFFER_NOT_FOUND`、429 `RATE_LIMIT`。
- `GET /classifiers/activations/custom-durations`（免鉴权）：`{data:{服务:{国家:分钟}}}`。实测只有 10 个服务有例外时长：`cy, md, ig, ft, wx, ya, ff, tg, bte, dh`，取值 40/45/60 分钟；其中 tg 只在国家 6 和 151 上是 45 分钟。
- reactivate、prolong、Emails 系列：本期不用。

### 1.4 Webhook【文档】

- 只有一种事件 `sms-incoming`，POST JSON，只推到 HTTPS 地址。字段：`activationId, phoneFrom, service, text, code(可为 null), country, receivedAt`。规格的 required 里有 `id`，但 properties 里没定义，自相矛盾。
- 最多配 3 个 URL，**要先开 2FA**【官网】。超时 3 秒，非 200 算失败，至少重试 7 次，间隔 20–30 秒，总共至少 3 分钟。
- **没有签名**，来源 IP 是 `84.32.223.53`、`185.138.88.87`。应该用「activationId + OTP id」或「activationId + receivedAt + text」做幂等去重。【推断】

### 1.5 状态码【文档 + 官网前端】

`ActivationStatusTypes` 的取值是 `[1,2,3,4,6,7,8,10]`，文档没给含义。官网前端代码里的映射：2 已收到短信（语音验证时是已收到来电）、3 等待重发、4 等待短信、6 成功、8 已取消、10 已退款；1 和 7 前端没映射【未确认】；**前端对任何未知值一律显示「已取消」**。History 状态：6 已完成、8 已取消、10 已退款。【推断】8 是主动取消，10 是超时自动退款或客服退款。

### 1.6 解析要点（文档自相矛盾、以及和实测不一致的地方）

1. 先看 HTTP 状态码，再看响应体是 `{` / `[` 开头还是纯文本，去掉可能包裹的引号。
2. `NO_NUMBERS` 有三种形态：getNumber 是 200 文本，getRentNumber 是 404 JSON，v1 文档没写。
3. getStatusV2 在已取消时返回文本 `STATUS_CANCEL`。
4. 数字字段在示例里经常是字符串（`activationId`、`activationStatus`、`countryCode`、`canGetAnotherSms:"1"`）。
5. setStatus 的示例值 1 不在枚举里。
6. v1 key 无效时实测是 403 `BAD_API_KEY`，文档写的是 401。
7. getCountries 实际返回对象，不是数组，还多一个 `rent` 字段。
8. getNumberV2 示例里的 2 小时有效期只是示例。
9. **getActiveActivations 的 `activationTime` 没有时区**（示例是 `2022-06-01 16:59:16`；getStatusV2 示例是 `+03:00`），**不能用来算截止时间**。
10. 兼容协议的 URL 带 `api_key`，**记日志时绝不能把 URL 原样打出来**。

## 2. 规则与时序

| 问题 | 结论 | 标注 |
|---|---|---|
| 激活有效期 | 默认 20 分钟；custom-durations 里的组合是 40/45/60 分钟；**以取号返回的 `activationEndTime` 为准** | 规则 + 实测 |
| 最早可取消 | 取号满 120 秒 | 文档 + 规则 |
| 取消是否退款 | 没收到码就退回上游余额；收到码后不能取消，也不退款 | 规则 |
| 超时 | 有效期内没收到码，自动退回余额（状态 10） | 规则 |
| 扣费时点 | 原文：收到 OTP 并显示后才算购买完成，没收到码就退回。取号时余额必须够，否则返回 402。**实际是取号先扣、失败再退（SMS-Activate 惯例），这是推断** | 规则；机制为推断 |
| 再收一条 | 额外的短信自动送达，官网说不收超额费用；兼容协议可以调 `setStatus=3`；能不能再收，看 `canGetAnotherSms` 和国家的 `retry` 字段 | 官网 + 文档 |
| 多条短信 | getStatus 只给一条；取全部用 getAllSms 或 v1 `/otp`、`otpList`；webhook 每条推一次 | 文档 |
| 完成 | setStatus 6 或 finishActivation；前端要求必须已经有码；不手动完成的话，到期自动结束（推断） | 文档 + 官网；到期自动结束为推断 |
| 号码被目标平台拒收 | API 没有「号码不可用」之类的状态。可以满 2 分钟后取消或换号；号码已被注册、要求 2FA 等供应商问题，可以找客服退款，要截图和从买号开始的录屏 | 规则 |
| 长时效或租用号码 | 取号满 2 分钟后、20 分钟内可以取消并退款；超过 20 分钟不退（`FREE_CANCELLATION_EXPIRED`） | 规则；本期不涉及 |
| 封禁与流程限制 | 见 §0 第 11 条；前端还有「取消太多号码已被封禁」的提示 | 规则 + 官网 |
| 转售商 | 要向客服申请；取得身份后每次激活传买家 ID，封禁只针对该买家；红线见 §0 第 12 条 | 规则 |
| API 实现错误造成的问题 | 不退款 | 规则 |

**一次激活的时间线（标准 20 分钟号）**

```
T0 取号成功（ACTIVE, status 4）
│  T0 ~ T0+120s：cancel / replace → 409 EARLY_CANCEL_DENIED
├─ T0+120s 起：可以取消（8，退回余额）或换号
│   任意时刻收到码 → status 2，从此 cancel → 409 OTP_RECEIVED；之后的短信自动追加、不再收费
├─ T0+20min（activationEndTime）：
│   · 没收到码 → 上游自动退款（status 10），getAllSms → 409 NOT_ACTIVE
│   · 收到过码 → 激活结束（推断会自动 finish）
```

### 3.4 实测与文档的冲突（未确认，设计必须两头都安全）

1. **`counts.defaultPrice` 和 `map` 对不上。** dr/16 的 defaultPrice 是 63，可 `map["0.0450"]`（正好等于 retail）是 79,335；ot/48 分别是 107,360 和 178,907。**规格示例里 map 的数值还大于 total**（tg/6 的 total 是 22,598，map 第一档却是 286,896）。所以 map 是不是累计库存、defaultPrice 到底按哪个价统计，都**未确认**。4b 草稿的结论「展示库存用 defaultPrice」是偏保守的读法。
2. **defaultPrice=0 时，map 的第一档可能高于 retail**（规格示例 tg/48）。这时按 retail 报价，取号必然返回 WRONG_MAX_PRICE 或 NO_NUMBERS。
3. **带 maxPrice 取号时，实际扣的是档位价还是 maxPrice，未确认。** 本站单品配了 smsMaxPrice，账单扣费却等于 retail，推断是按实际档位价扣。
4. **v1 `/replace` 的计费和前置条件未确认。**
5. **getStatusV2 在等码时返回什么、getStatus 在上游自动退款（10）之后返回什么，都未确认。** getStatus 的状态枚举（`STATUS_WAIT_CODE / WAIT_RETRY / WAIT_RESEND / CANCEL / OK`）是有文档的，所以设计的单查用 getStatus；「上游已结束」一律以 v1 history 为准（设计 D17、§3.1）。
6. **history 的 `cost` 字段在已取消的行上也有值，不代表扣了费。**【实测，2026-09-29 `probe2.out`】状态 8 的行 cost 分别是 0.6、0.18、0.66……（就是号码标价）；而 `totals.sum = 7.5494` 对应 `successCount = 23`（共 73 行），只是成功单的实扣。结论：上游实扣只认状态 6（或 `moreCodes` 非空）的行，对账不能用「cost > 0」判断扣费（设计 §9.4）。
7. **40 / 45 / 60 分钟的例外时长号码，20 分钟后还能不能免费取消，说法冲突。**规则页「取消较长期限的购买」一节写「仅可在购买后 20 分钟内取消并获得退款；超过 20 分钟后，即使未收到验证码，号码费用也不予退还」；官网前端的取消确认文案也写「免费取消只在前 20 分钟内」；只有 API 文档把这条限制限定在 ≥24 小时的号上。实测 custom-durations：ig 在 126 个国家、wx 在 190 个国家是 60 分钟，tg 在 6、151 是 45 分钟——都是热门组合。【规则】【官网】【文档】【未确认】（U13；设计 D42 先按「取号后 19 分钟没码就取消」处理，S2 用真钱验证）

## 4. hero-sms 网站 UX 观察（2026-09-29，未登录浏览 + 前端文案和代码还原）

方法：用内置浏览器看 `/cn` 和英文版，桌面 1440×900、手机 375×812。登录后才能看到的部分，从 `msg_cn.json`、规则页、退款 PDF、前端 chunk 只读还原。引用原文每条不超过 15 字。

### 4.1 购买漏斗
- 入口是**全站通用的左侧抽屉**（约 350px 宽），顶栏「接收短信」按钮拉出；手机上是全屏面板。步骤是 1. 选服务 → 2. 选国家 → 3. 购买或自定义。选中后收成带 × 的 chip，下一步随之展开。【实测】
- **登录墙来得很早**：未登录可以看服务、国家、起价和库存，但一点国家就弹登录框；第 3 步（运营商、时长、购买按钮）未登录时完全看不到。【实测】
- 手机端的 App 下载横幅会压住购买面板顶部；选完服务后，国家列表要 3–5 秒才出来，期间只有转圈，没有骨架屏。【实测】

### 4.2 服务选择
- 默认按人气排序（Full rent 排第 1）；每行显示图标、名称、库存「N 个」、「起 $x」（4 位小数）。库存状态分三种：有实体号、「仅虚拟号」（橙色）、「无可用号码」（红色）。先显示 5 行，每点一次「显示更多」加 5 行。**没有分类，也没有服务级收藏**（收藏的单位是「服务+国家」）。【实测 + 代码】
- 搜索：用 `Intl.Collator`、`sensitivity:"base"`（忽略大小写和重音），排序是完全相等 > 前缀 > 包含；**别名能命中**（gpt、chat、tg 都能搜到 OpenAI）；代码里专门处理了**输入法组字**（组字没结束时不过滤）。**中文别名一律搜不到**（「电报」「微信」都不行），**也没有拼写纠错**（telgram 搜不到）。【实测 + 代码】
- **搜不到时**：列表只剩一行「Any other」，下面一行灰字，大意是没找到这个服务、建议用 Any other 激活。**但没说明 Any other 的适用范围**（没告诉用户已单列的服务不要选它）。【实测】

### 4.3 国家选择
- 标题旁有「10 个热门国家」徽章。中英文都能搜。排序有 5 种：按质量（默认，按到达率）、按受欢迎度、便宜、贵、按数量。**换服务后排序会重置。**【实测 + 代码】

### 4.7 「没收到验证码？」弹窗

### 5.2 大厂模式与对应到本站的做法

| 模式 | 要点 | 本站怎么用（设计里的对应做法） |
|---|---|---|
| Stripe PaymentIntent 状态机 | 状态单向推进；以服务端事件为准，不信前端跳转 | 订单（付款）和号码尝试（履约）拆成两台状态机，所有迁移都用 CAS |
| Stripe 幂等键 | 同一个键返回首次的结果 | 下单带 clientToken；换号、取消带 version（乐观锁）；余额流水用 bizKey 唯一 |
| 预授权 → 扣款 → 撤销 | 先冻结，成功再扣，失败解冻 | 个人收款码做不了预授权，改成「直接收款 + 失败自动退回余额」 |
| 支付宝异步通知与主动查询 | 至少投递一次，要主动查询兜底 | 本站已有：金额匹配 CAS（`vmq.ts:682-729`）加对账补履约（`vmq.ts:854`） |
| Transactional Outbox | 状态和待办写在同一个事务 | 付款 CAS 的同一事务里，把接码单推进到「待取号」，由定时任务兜底 |
| SAGA 补偿 | 补偿本身也会失败，需要重试 | 放号失败 → RELEASING 队列重试；退款失败 → 重试并告警 |
| 对账 | 每天三方对账 | 我方号码尝试 ↔ 上游 history ↔ 余额流水 |

### 5.3 合规提示（只是提示，不是法律意见）

### 6.9 坑清单（设计必须避开）
1. 载体商品上架会外泄，下架会被拦截 → 保持下架，只给新路径开例外。
2. 动态定价会被 `pay/vmq/create:99` 的比价拦下。
3. acquireForOrder「已有记录就返回」、换号覆盖同一行 → 新板块要新表。
4. **给现有 `herosms.ts` 加超时会制造「不知道买没买到」的情况**：旧的 acquireForOrder 遇到超时会抛错，GET /sms 的自愈会再取一次号，可能重复购买。**新板块用独立客户端，不改旧客户端的行为。**
5. 币种和精度：美元最多 4 位小数，现有列只有 2 位，渠道利润还把它当人民币用。
6. 退号结果不检查 → 利润被高估，或者码到了买家却看不到。
7. 退款全靠人工，【待退款】只写在备注里，没有推送，也没有筛选入口。
8. 收款方式对小额单不友好：唯一金额最多加 0.49 元；金额池 50 格全站共用；每次都要手输金额。
9. 各种营销钩子默认都会触发。
10. schema 铁律：只新增表、新增可空或带默认值的列、新增索引；上线顺序是「备份 → 预览 DDL（零删除）→ 过 `scripts/ops/ddl-gate.sh` 闸门 → db push → 再换镜像」。

12. 服务条款第四节没有接码的退款规则（`src/app/(shop)/terms/page.tsx:98-108`）。
13. nginx 真实 IP 问题（交接文档第三十节）：按 IP 的限流和日志 IP 不可信；webhook 靠 IP 白名单同样不可信。

| # | 未确认的事 | 设计怎么防（详见设计文档） |
|---|---|---|
| U1 | map 和 defaultPrice 的精确语义 | 报价成本取「有货的最低档」；库存展示取保守值；能不能卖由 cap 以内是否有档位决定；取号失败自动退款（设计 §4.2、§3） |

| U8 | resellerUserId 在兼容协议里是否生效 | 本期不传；取得转售商身份后，用开关切到 v1 购买（D23）。**站长 09-29 决定：本期不申请转售商身份**，`resellerMode` 保持关闭 |
| U9 | v1 购买在余额不足、没号时的返回 | 本期取号用兼容协议的 getNumberV2（错误码有文档） |
| U10 | 运营商是否影响价格 | 价格按组合定；指定运营商取不到号时，按买家勾选的选项改用任意运营商，或者退款 |
| U11 | 到期后上游是否自动 finish 已收码的激活 | 到期后主动调 finish，忽略 NOT_ACTIVE |

| U13 | 40 / 45 / 60 分钟的例外时长号码，取号 20 分钟后没码时还能不能免费取消（§3.4 第 7 条） | 验证前一律按「取号后 19 分钟没码就主动取消」处理，页面只显示 20 分钟；遇到 `FREE_CANCELLATION_EXPIRED` 记亏损、整单照样退回余额；S2 仅管理员期间用真钱验证（设计 D42、E55） |
| U14 | 线程上限（CHANNELS_LIMIT）的 `max_allowed` 是否只在「成功率 <3%」时才出现，平时有没有默认上限；已收码的号算不算占线程 | 按返回的 `max_allowed` 与剩余线程收单、受限期间暂停换号；新板块在途号码数另设上限给旧单品留线程（设计 D43、E5） |
