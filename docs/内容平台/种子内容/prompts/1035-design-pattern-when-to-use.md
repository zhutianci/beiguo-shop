**怎么填变量**：[预计未来的变化] 是判断要不要引入模式的关键依据。如果分支很多年才加一个，现在的 if-else 可能就是最好的写法；如果下个季度要加三个，就值得把变化点抽出来。

**常见坑**：
- 为了「用上设计模式」而重构，一个简单功能拆成五个类、三层接口，后来的人更难看懂。模板要求先给最简单的方案。
- 在 Python、JavaScript 这类函数是一等公民的语言里，很多经典模式（策略、命令）用一个函数字典就能实现，不需要照搬面向对象语言的写法。
- 改造时顺手改了行为。先确保有测试覆盖，再小步改结构。

**追问技巧**：追问「如果一年后需求变成按地区选择不同的支付方式组合，这个结构还能撑住吗」，检验方案对未来变化的适应性。想学习时可以追问「用这段代码讲解策略模式和工厂模式的区别」。

### 示例输出

> 示例，仅供参考（Python，按支付方式分支）

**问题本质**：变化点是「支付方式」，但每种方式的逻辑分散在 `pay()`、`refund()`、`query()` 三个函数的分支里，新增一种要改三处。

**推荐**：每种支付方式实现同一组方法，用字典注册。这是策略模式的轻量写法，不需要工厂类。

```python
from typing import Protocol

class PaymentChannel(Protocol):
    def pay(self, order) -> str: ...
    def refund(self, order, amount) -> None: ...

CHANNELS: dict[str, PaymentChannel] = {
    "alipay": AlipayChannel(),
    "card": CardChannel(),
}

def pay(order):
    channel = CHANNELS.get(order.channel)
    if channel is None:
        raise ValueError(f"不支持的支付方式：{order.channel}")
    return channel.pay(order)
```

新增一种支付方式：新写一个类，在 `CHANNELS` 中加一行。

**不建议**：抽象工厂、模板方法——目前各支付方式的流程差异很大，没有可复用的公共骨架。
