**怎么填变量**：[对可靠性的要求] 和 [是否需要顺序] 决定了方案复杂度。通知类消息偶尔丢一条影响不大，扣款、发货类消息绝对不能丢；只有同一个业务对象的消息需要顺序，全局顺序几乎没有必要，代价也很大。

**常见坑**：
- 在数据库事务里直接发消息：事务回滚了，消息却已经发出去；或者事务提交了，发消息时网络断了。用事务发件箱模式把「写业务数据」和「记录待发消息」放在同一个事务里。
- 消费端先确认再处理，处理过程中进程崩溃，消息就丢了。
- 以为开启了某种「精确一次」配置就不用做幂等。跨系统的业务操作仍然需要消费端去重。

**追问技巧**：追问「假设消费者处理到一半时宕机、消息中间件某个节点故障、网络分区，分别会发生什么」，逐一确认方案的薄弱环节。

### 示例输出

> 示例，仅供参考（事务发件箱，节选）

```sql
-- 与订单更新在同一个数据库事务里写入
INSERT INTO outbox (id, aggregate_id, event_type, payload, created_at, sent)
VALUES (?, ?, 'OrderPaid', ?, NOW(), FALSE);
```

后台任务定期扫描 `sent = FALSE` 的记录发送到消息队列，收到发送确认后再标记为已发送。由于可能重复发送，消费端必须幂等：

```sql
INSERT INTO consumed_events (event_id) VALUES (?);  -- event_id 为主键，冲突即说明已处理
```

| 环节 | 措施 |
|---|---|
| 生产 | 事务发件箱 + 发送确认 |
| 存储 | 多副本，写入需多数副本确认 |
| 消费 | 处理成功后手动确认；失败重试 5 次后进入死信队列并告警 |
