**怎么填变量**：[分析需求] 决定先建什么，不要为了「完整」一次性建几十张表。[团队现状] 很重要：两三个人的团队维护完整的五层架构负担很重，可以先合并部分层次。

**常见坑**：
- 事实表的粒度没有定清楚，一张表里既有订单级数据又有商品明细级数据，汇总时金额被重复计算。
- 用户等级、商品类目这类会变化的属性直接覆盖，回看历史时只能看到现在的等级，历史分析全部失真。
- 每个报表需求都从明细层单独算一遍，同一个指标出现多种口径。常用的指标沉淀到汇总层统一计算。

**追问技巧**：追问「把现有的这 20 张报表用到的表梳理一遍，找出可以合并或重复计算的地方」，或「给这个模型补充数据质量校验规则」（可配合 1129 号提示词）。

### 示例输出

> 示例，仅供参考（事实表设计节选）

| 业务过程 | 事实表 | 粒度 | 主要度量 | 类型 |
|---|---|---|---|---|
| 下单 | dwd_trade_order_item | 每个订单中的每个商品一行 | 购买数量、商品原价、优惠分摊金额 | 事务事实表 |
| 支付 | dwd_trade_payment | 每笔支付流水一行 | 支付金额 | 事务事实表 |
| 订单全流程 | dwd_trade_order_lifecycle | 每个订单一行，记录下单、支付、发货、签收时间 | 各环节耗时 | 累积快照 |

```sql
-- 需要保留历史的用户维度表：每个版本一行，记录生效与失效日期
CREATE TABLE dim_user_history (
  user_id      BIGINT,
  user_level   STRING,
  city         STRING,
  start_date   STRING COMMENT '版本生效日期',
  end_date     STRING COMMENT '版本失效日期，当前版本为 9999-12-31'
)
PARTITIONED BY (dt STRING);
```
