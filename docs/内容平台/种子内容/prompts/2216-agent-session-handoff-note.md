prompt: |
  你即将结束这次会话，接下来会由一个看不到本次对话的新智能体（或新会话里的你）继续这项工作。请写一份交接说明。它只会读到这份说明和工作目录里的文件，所以凡是只存在于本次对话里的信息，都必须写进去。

  补充信息：
  - 交接原因：[交接原因]
  - 接手方（新会话、另一种智能体、人）：[接手方]
  - 交接说明保存的位置：[保存位置]
  - 我特别想强调的事：[特别提醒]

  请按以下结构写，每节都要有，没有内容的写「无」：

  1. 目标与完成标准：用户最初要什么（尽量引用用户原话），做到什么程度算完成，哪些是明确说了不做的。
  2. 当前状态一句话：例如「5 个子任务完成 3 个，第 4 个改了一半，测试未跑」。
  3. 已完成并验证的部分：逐条写做了什么、涉及哪些文件或对象、用什么方式验证过（命令与结果）。只做了没验证的，放到第 4 节，不要写在这里。
  4. 进行中与未验证的部分：停在哪一步、已经改动但未完成的文件、当前处于不一致状态的地方（例如迁移跑了一半）。
  5. 关键决定与理由：做过的取舍，以及用户明确表达过的偏好和禁令。接手方最容易推翻的决定要写清为什么不能改。
  6. 试过但行不通的路：尝试了什么、失败现象、为什么放弃，避免接手方重走一遍。
  7. 环境与操作须知：怎么启动、怎么测试、用到的命令、需要的权限或凭据放在哪里（只写位置，不写凭据内容）、耗时长或有副作用的操作。
  8. 下一步：按顺序列出接下来 3–5 个具体动作，第一个动作要具体到可以直接执行。
  9. 待用户确认的问题：列出需要人来决定的事项及各选项的影响。
  10. 不要做的事：可能造成损害或违背用户意愿的操作清单。

  写作要求：
  - 区分三种说法：「已验证」「我认为但未验证」「不知道」，不要把推测写成事实。
  - 写路径、命令、标识符时用原文，不要用「那个配置文件」这类指代。
  - 篇幅控制在一屏半以内；细节多的内容指向文件位置而不是全文复述。
  - 写完后自查：一个完全没看过本次对话的人，只凭这份说明能否开始第 8 节的第一个动作？不能就补全。

**怎么用**：在长会话快结束时把整段提示词发给当前的智能体。[交接原因] 写「上下文快满」「今天先到这里」「换另一个工具继续」之类；[保存位置] 建议写成工作目录里的一个文件（如 docs/handoff.md），新会话第一句话就是「先读 docs/handoff.md 再继续」。[特别提醒] 写你最怕被忘掉的那件事，比如「生产数据库只读，任何写操作先问我」。

**常见失败与调整**：
- 把「写了代码」写成「已完成」。提示词里专门区分了已验证和未验证，交接后发现不符，就让它补上验证命令和输出。
- 交接说明只是对话流水账。要求按十节结构重写，重点是状态和下一步，而不是过程。
- 遗漏用户说过的禁令。在第 5、10 节不够时追问「回顾本次对话，用户说过哪些不要做」。

**追问**：「把这份交接说明压缩成新会话可用的开场提示词」「对照交接说明，列出你现在最不确定的三件事」。

**与上下文管理方案的区别**：站内的上下文工程提示词是设计应用层面的方案；本条是此刻就要写出来的那份交接文档。
