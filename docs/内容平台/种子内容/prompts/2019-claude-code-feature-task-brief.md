  [功能或改动描述]

  [背景与使用者]

  - 需要改动的位置（我已知的）：[相关文件或目录]
  - 可以参考的现有写法：请先阅读 [参考实现的文件]，新代码沿用它的结构、命名和错误处理方式。

  ## 验收检查（完成的标准）
  - 行为：[验收用例]（请写成输入与期望结果，例如「未登录访问返回 401」）
  - 可运行的检查：[测试与检查命令]
  - 全部检查通过才算完成。检查失败时修复根本原因，不要通过跳过测试、放宽断言或吞掉错误来让它通过。

  ## 工作步骤
  1. 探索（只读，不修改任何文件）：阅读上面提到的文件和与之相关的调用方，弄清现有的数据流和约定。把你的发现和不确定的地方简要告诉我。
  2. 计划：列出要新增和修改的文件、每个文件改什么、实现顺序、需要补哪些测试、有哪些风险。然后停下来等我确认。有两种可行方案时并列给出并说明取舍。
  3. 实现：按确认后的计划做。先写或更新测试，再写实现；每完成一个可独立验证的部分就运行相关检查。
  4. 验证与汇报：运行全部验收检查，把实际运行的命令和输出结果贴出来作为证据；说明改了哪些文件、有没有偏离计划、还有哪些已知的遗留问题。
  5. 我确认后再提交，提交信息说明做了什么以及原因。

  如果在实现中发现计划有问题，停下来告诉我，不要自行扩大改动范围。

**这份任务说明对应的官方建议**（据 Claude Code 官方文档「Best practices」，资料核对于 2026-10-10）：
- **给 Claude 一个能自己运行的检查**：测试、构建、lint，或与设计稿比对的截图。没有检查时它只能凭「看起来做完了」来判断，验证就落在你身上；并建议让它展示证据（测试输出、运行的命令及结果），而不是只说「已完成」。
- **先探索、再计划、再编码**：把调研和计划与实现分开，避免解决错问题。官方同时提醒，改动很小、一句话就能说清 diff 的任务可以跳过计划直接做。
- **在提示词里给具体上下文**：限定范围、指向能回答问题的来源、指出仓库里可参考的现有模式、描述症状和「修好」的标准。
- **针对根本原因而不是症状**。

**怎么填变量**：[参考实现的文件] 是省返工最有效的一项，例如「src/widgets/HotList.tsx 是一个写得比较规范的组件」。[验收用例] 写 2–5 条具体的输入与期望结果；[测试与检查命令] 写仓库里实际使用的命令，如 `pnpm test`、`pnpm typecheck`。也可以在 Claude Code 里用 `@` 引用文件，让它直接读取。

**配合 Plan 模式**：官方推荐在探索和计划阶段使用 plan mode（只读、不改文件），确认计划后再切回正常模式实现。切换方式和快捷键见本站「Claude Code Plan 模式怎么用」教程。

**常见问题与调整**：
- 同一个问题纠正了两次还不对 → 官方建议此时清空上下文重新开始，把刚学到的教训写进新的任务说明，通常比在长对话里继续纠正效果好。
- 探索阶段读了太多文件 → 把范围收窄，或说明「调查部分请用子代理完成，只把结论带回来」。
- 需求本身还没想清楚 → 先让它采访你：「我想做……，请就实现方式、边界情况和取舍向我提问，问完后写成 SPEC.md。」再新开会话按规格实现。
