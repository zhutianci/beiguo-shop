**怎么填变量**：[部署方式] 一定要写，很多人用语言自带的锁（比如 Java 的 synchronized、Python 的 threading.Lock）解决了单机测试，上线多实例后照样出错。事务边界要贴清楚，代码里哪一段在事务内、哪一段在事务外直接影响结论。

**常见坑**：
- 「我已经加了事务」是最常见的误解。默认隔离级别下，两个事务完全可以读到同一个库存值，然后各自减 1。
- 能用一条带条件的 UPDATE 解决的，就不要上分布式锁。条件更新简单、可靠、没有锁过期的问题。
- 并发测试要真正并发：用线程池或异步同时发起请求，而不是循环里一个接一个地调用。

**追问技巧**：修复后追问「在这个方案下，如果数据库主从延迟、或者请求在提交前超时重试，还会出错吗」，把边界情况也问到。

### 示例输出

> 示例，仅供参考（库存超卖）

| 时刻 | 请求 A | 请求 B | 库存 |
|---|---|---|---|
| t1 | 读到库存 1 | | 1 |
| t2 | | 读到库存 1 | 1 |
| t3 | 判断大于 0，写入 0 | | 0 |
| t4 | | 判断大于 0，写入 0（应拒绝） | 0，卖出 2 件 |

推荐修复：把判断放进 UPDATE，并检查受影响行数。

```python
from django.db.models import F

updated = Product.objects.filter(id=pid, stock__gte=qty).update(stock=F("stock") - qty)
if updated == 0:
    raise OutOfStock()
```
