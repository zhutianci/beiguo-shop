**怎么填变量**：[业务描述] 可以很粗糙，甚至只是几句话。事件风暴的价值就在于通过提问把隐藏的规则挖出来。最好在环节一就把业务方拉进对话，或者把他们的回答原样贴给 AI。

**常见坑**：
- 一上来就讨论表结构和类设计，绕过了业务梳理。这条提示词刻意从「发生了什么事」开始，因为事件是业务人员最容易说清楚的东西。
- 同一个词在不同场景含义不同却混用（比如「客户」既指下单人又指付款公司），这是后期最多 Bug 的根源。词汇表一定要做。
- 聚合划得太大，一个聚合包含了整个业务，导致并发冲突和性能问题。聚合应该只包含必须同时保持一致的部分。

**追问技巧**：模型出来后追问「用三个真实的业务案例（包括一个例外情况）走一遍这个模型，看是否每一步都有对应的命令和事件」。

### 示例输出

> 示例，仅供参考（环节一节选：企业报销审批）

| 顺序 | 领域事件 | 追问 |
|---|---|---|
| 1 | 报销单已创建 | 草稿是否需要保存？ |
| 2 | 报销单已提交 | 提交后还能修改金额吗？ |
| 3 | 审批已通过 / 审批已驳回 | 驳回后是重新提交还是新建一张单？ |
| 4 | 审批已超时 | 超过几天算超时？超时后自动通过还是转交？ |
| 5 | 款项已支付 | 支付失败时会产生什么事件？ |

**发现的矛盾**：你提到「提交后不能修改」，又提到「财务可以调整金额」——这里是否是两个不同的操作（员工修改、财务核减）？
