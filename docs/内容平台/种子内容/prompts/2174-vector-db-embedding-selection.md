**为什么不让它直接推荐产品**：向量数据库和 Embedding 模型更新极快，模型凭训练时的记忆给出的「某某最快、某某最便宜」很可能已经过时，甚至把不同版本的特性混在一起。这条提示词把模型的作用限定在它擅长的部分：帮你把需求理清、搭出对比框架、列出该核实的问题、设计用自己数据做的对比测试。具体的性能、价格和功能，一律以各产品的最新官方文档和你自己的测试为准。

**怎么填变量**：[查询特点] 里「是否需要过滤」最影响选型——需要「只在某个用户自己的文档里搜」「只搜最近三个月」的，要重点核实带过滤检索的实现方式和性能。[团队与环境] 请如实写运维人力，「没有专职运维」本身就是一个很强的选型依据。数据量用「多少条、每条大概多长」来描述比只说「很多」有用。

**常见问题与调整**：
- 得到的对比表太泛 → 追问：「把对比表每一格改写成对我的场景的具体影响，并标出哪三个维度对我最关键。」
- 想知道要不要一步到位 → 追问：「如果先用现有数据库的向量扩展，出现哪些信号时应该迁移到专用向量库？迁移要做哪些事？」
- Embedding 候选太多 → 追问：「根据我的语言、是否可外发数据、最大文本长度三个条件，先排除哪些类别？」
- 需要具体型号的最新信息 → 打开模型的联网搜索，并要求它给出官方文档链接与日期，再自行核对。

### 示例输出

> 示例，仅供参考（场景：内部知识库搜索，约 20 万个文本块，已有 PostgreSQL，无专职运维）

**判断**：属于「数据量不大、已有关系型数据库」的情况。20 万条的规模下，使用现有数据库的向量扩展通常可以满足需求，并且权限过滤可以直接用已有的表关联来做，不必新增一套需要运维的系统。

**必须核实的问题（节选）**
1. 所用数据库版本对应的向量扩展支持哪些索引类型，带过滤条件检索时的行为如何；
2. 向量维度对索引大小和内存的影响，现有实例的规格是否足够；
3. 备份恢复是否随数据库现有机制一并覆盖。

**倾向性建议**：先用现有数据库的向量扩展，配合一个支持中文的 Embedding 模型做小规模测试。这个建议在以下条件下会改变：数据量增长到现有实例难以承载、查询延迟不能满足要求，或需要现有方案不提供的检索能力。
