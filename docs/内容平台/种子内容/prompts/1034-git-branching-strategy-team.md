**怎么填变量**：[发布频率] 和 [产品形态] 是选择分支模型的决定因素。每天多次部署的 Web 服务适合简单的模型（主干或 GitHub Flow）；需要应用商店审核、或要同时给不同客户维护多个版本的产品，才需要发布分支这类更重的结构。

**常见坑**：
- 照搬 Git Flow，结果小团队维护 develop、release、master 多条长期分支，流程繁琐，合并总出错。模型的复杂度要和发布方式匹配。
- 功能分支存活太久（几周甚至几个月），合并时冲突巨大。分支越短命越好，大功能可以拆小或者用功能开关先合入主干。
- 热修复只合进了生产分支，没有合回开发分支，下个版本上线后问题又出现了。

**追问技巧**：追问「把这份规范里需要在代码托管平台上配置的项列成清单，并说明在哪里设置」，或者「写一个合并请求模板」。

> 示例，仅供参考（推荐方案节选：10 人团队，Web 服务每周发布）

**推荐**：GitHub Flow 加发布标签。只有 main 一条长期分支，所有功能通过短期分支合入；每周从 main 打标签发布。

| 分支 | 命名示例 | 存活时间 | 规则 |
|---|---|---|---|
| main | main | 长期 | 禁止直接推送；合并需 1 人评审且 CI 通过 |
| 功能 | feature/PROJ-123-coupon-limit | 不超过 3 天 | 压缩合并到 main |
| 修复 | fix/PROJ-130-price-rounding | 不超过 1 天 | 同上 |

**不推荐 Git Flow 的原因**：每周发布、只有一个线上版本，不需要单独的 develop 和 release 分支，多一层分支只会增加合并成本。
