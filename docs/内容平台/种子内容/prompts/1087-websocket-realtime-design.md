**怎么填变量**：[通信方向] 是选型的关键：只需要服务端推送（通知、状态更新、AI 流式输出）时，SSE 实现更简单，基于普通 HTTP，更容易通过各种代理；需要客户端频繁发送消息（聊天、协同编辑）时才需要 WebSocket。[规模] 用来评估单机连接数和是否需要专门的推送服务。

**常见坑**：
- 部署多实例后，用户 A 连在实例 1、消息却在实例 2 产生，消息就送不到。需要发布订阅或路由机制把消息分发到正确的实例。
- 代理或负载均衡默认的空闲超时较短，没有心跳的连接会被悄悄断开，客户端却以为还连着。
- 服务重启后所有客户端在同一秒重连，形成连接风暴。重连要加随机延迟。

**追问技巧**：追问「设计一个压测方案，验证单实例能否承载 5000 个长连接」，或「用户同时打开多个标签页时，如何避免重复连接和重复提醒」。

### 示例输出

> 示例，仅供参考（订单状态推送，节选）

**推荐**：SSE。只需服务端推送，基于普通 HTTP，浏览器原生支持自动重连，并且可以通过最后事件编号实现断线补发。

**多实例分发**：订单服务状态变化 → 发布到 Redis 频道 → 每个推送实例订阅该频道 → 只推送给本实例上该用户的连接。

```js
// 客户端：浏览器断线后会自动重连，并在请求头中带上最后收到的事件编号
const es = new EventSource('/api/stream/orders', { withCredentials: true })
es.addEventListener('order-status', (e) => {
  const data = JSON.parse(e.data)
  updateOrderRow(data.orderId, data.status)
})
es.onerror = () => showBanner('连接中断，正在重连…')
```

```js
// 服务端（Node.js）：定期发送注释行作为心跳，防止代理断开空闲连接
res.writeHead(200, { 'Content-Type': 'text/event-stream', 'Cache-Control': 'no-cache', Connection: 'keep-alive' })
const timer = setInterval(() => res.write(': ping\n\n'), 25000)
req.on('close', () => clearInterval(timer))
```
