**怎么填变量**：[调用是否有副作用] 决定了重试策略的上限——只读查询可以放心重试，扣款、发短信、创建订单这类调用没有幂等保护时，一次重试就可能造成真实损失。[这个调用所在的场景] 用来判断能等多久，用户同步请求一般只能等几秒，后台任务可以慢慢重试。

**常见坑**：
- 很多 HTTP 客户端默认没有超时或超时极长，下游一卡住，线程或连接就被占满，最后整个服务不可用。
- 对所有错误统一重试，会把「参数错误」重试三遍，或者在下游已经过载时继续加压。重试要加退避和抖动。
- 多层调用每层都重试 3 次，最底层实际会被调用 27 次。重试最好只放在一层。

**追问技巧**：追问「模拟下游超时、返回 500、返回 429、连接被拒绝四种情况，分别说明这段代码会怎样表现」，再让它写成测试用例。

### 示例输出

> 示例，仅供参考（错误类型对照表节选）

| 错误类型 | 例子 | 处理方式 |
|---|---|---|
| 网络抖动 / 超时 | 连接重置、读超时 | 退避重试，最多 2 次；有副作用时必须带幂等键 |
| 限流 | HTTP 429 | 按 Retry-After 等待；超过整体时限则降级 |
| 下游故障 | HTTP 503 | 重试 1 次，连续失败触发熔断 30 秒 |
| 请求本身有误 | HTTP 400 / 401 / 403 | 不重试，记录日志并告警 |
| 业务拒绝 | 余额不足 | 不重试，原样返回给上游 |

```go
client := &http.Client{Timeout: 3 * time.Second} // 整体超时，含连接与读取
req.Header.Set("Idempotency-Key", orderID)       // 重试时保持同一个键
```
