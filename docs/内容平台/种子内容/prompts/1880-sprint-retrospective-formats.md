prompt: |
  你是一名敏捷教练，帮我设计并主持下一次 Sprint 回顾会。目标只有一个：会后留下不超过 3 条真的会被执行的改进项。

  团队情况（人数、合作多久、现场还是远程）：[团队情况]
  这个 Sprint 发生的主要事情：[本期发生的事]
  上次回顾定下的改进项及完成情况：[上次改进项进展]
  回顾会时长：[回顾会时长]
  团队当前的气氛：[团队气氛]

  第一步，选形式。从下面三种里推荐一种，并说明为什么适合现在的团队：
  - Start-Stop-Continue（开始做、停止做、继续做）：直接、省时，适合新团队或时间短的时候；
  - 4L（喜欢的、学到的、缺少的、渴望的）：适合想多谈感受和收获、气氛偏沉闷的时候；
  - 帆船法（风是推动力、锚是拖累、礁石是前方风险、岛是目标）：适合需要对齐方向、或连续几次回顾内容雷同的时候。
  上次用过的形式，这次优先换一种。

  第二步，排议程。按五个环节分配时间：开场、收集信息、找出原因、决定行动、收尾。开场必须先过上次的改进项：完成了哪些、没完成的原因；连续两次都没完成的，要么删掉、要么缩小。

  第三步，预填。根据我给的本期情况，在所选形式的每个栏目里预填 2–3 条可能的发言，用来在冷场时启发大家，并注明「仅供引导，不代替团队发言」。

  第四步，把问题变成改进项。给出引导话术：先归类，再投票（每人 3 票），对得票最高的 1–2 类追问原因。每条改进项按这个句式写：「从下个 Sprint 起，由某人负责，我们做某件具体的事，到某天用某个现象检查是否有效」。

  约束：
  - 改进项最多 3 条，必须是团队自己能决定的事；需要管理层解决的另列为「上报事项」。
  - 「加强沟通」「提高质量意识」这类无法检查的话，一律改写成具体动作。
  - 不点名批评个人；涉及个人的问题改为描述流程。

  输出：推荐形式及理由 → 议程表 → 预填内容 → 引导话术 → 改进项记录模板。

**怎么填变量**：[本期发生的事] 好事坏事都写，比如「提前两天完成目标」「周三线上故障，三个人处理了一整天」。[上次改进项进展] 如实写，没做就写没做。[团队气氛] 可以写「大家不太愿意开口」「最近加班多，有怨气」，模型会据此选形式和开场方式。

**常见失败与调整**：
- 每次列出十几条问题，一条也没落地。宁可只定一条并做完，也不要定五条。
- 改进项写成「加强沟通」。追问模型：具体是谁、在什么时候、做什么动作。
- 上次的改进项没人提起。开场不先过旧账，团队很快就明白回顾会说了也白说。
- 领导在场，大家只讲客套话。可以改为匿名写便签，或请领导只参加最后的行动环节。

### 示例输出

> 示例，仅供参考（虚构：7 人团队，远程办公，本期出过一次线上故障）

**推荐形式**：帆船法。上两次都用了 Start-Stop-Continue，内容开始重复；本期的故障适合放在「礁石」里讨论以后怎么避开，而不是追究是谁造成的。

**议程（60 分钟）**

| 环节 | 用时 | 做法 |
|---|---|---|
| 开场 | 8 分钟 | 过上次 2 条改进项：「评审 24 小时内完成」已做到；「补接口文档」未做，讨论缩小为只补 3 个核心接口 |
| 收集信息 | 15 分钟 | 各自在在线白板的风、锚、礁石、岛四个区域写便签 |
| 找出原因 | 15 分钟 | 归类、每人 3 票，对最高票追问原因 |
| 决定行动 | 17 分钟 | 定不超过 3 条改进项 |
| 收尾 | 5 分钟 | 每人用一个词评价本次回顾 |

**改进项（示例）**：从下个 Sprint 起，由俞工负责，发布前在预发布环境跑一遍支付主流程并在群里贴结果；两个 Sprint 后检查是否还出现同类线上故障。
