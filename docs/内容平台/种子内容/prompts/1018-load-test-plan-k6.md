**怎么填变量**：[预期业务量] 和 [用户行为比例] 是整个方案的基础，可以从历史监控里取峰值数据。没有数据就写「估计」，AI 会在方案里标出这些假设，压测前要和业务确认。

**常见坑**：
- 只压单个接口，得出「每秒能扛 5000 次」的结论，真实场景里多个接口共享数据库和缓存，实际容量会低得多。按业务比例混合压测更接近真实情况。
- 压测机自身成为瓶颈（CPU 打满、带宽不够），测出来的是压测机的极限。脚本要监控压测机资源。
- 压测时没有隔离短信、支付等外部接口，可能真的给用户发了几万条短信。压测环境里这些调用必须指向模拟服务。

**追问技巧**：压测完成后，把 k6 的汇总输出和同时间段的服务器监控数据贴回去，问「瓶颈最可能在哪一层，下一步该看什么」。

### 示例输出

> 示例，仅供参考（k6 脚本节选）

```js
import http from 'k6/http'
import { check, sleep } from 'k6'

export const options = {
  scenarios: {
    browse: {
      executor: 'ramping-arrival-rate',
      startRate: 50, timeUnit: '1s', preAllocatedVUs: 200,
      stages: [
        { target: 560, duration: '5m' },   // 加压到峰值的 70%（浏览）
        { target: 560, duration: '20m' },  // 保持
        { target: 0, duration: '2m' },
      ],
      exec: 'browse',
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.001'],
    http_req_duration: ['p(95)<300'],
  },
}

export function browse() {
  const res = http.get(`${__ENV.BASE_URL}/api/products/1001`)
  check(res, { '返回商品数据': (r) => r.status === 200 && r.json('id') === 1001 })
  sleep(Math.random() * 2 + 1)
}
```
