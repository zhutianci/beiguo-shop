**怎么填变量**：[业务规则] 是最有价值的部分，通用规则（非空、唯一）谁都能想到，真正能拦住问题的往往是业务规则，例如「退款金额不能大于实付金额」「已发货订单必须有物流单号」。[更新方式] 决定及时性规则怎么写。

**常见坑**：
- 所有规则失败都只发告警，数据有问题的报表照样产出，业务看到错误的数字。会导致报表错误的问题要阻断下游任务。
- 规则太多太严，每天都有一堆告警，最后大家都不看了。按影响程度分级，宁缺毋滥。
- 只检查本表，不检查与上游的行数对比，数据同步丢了一半也发现不了。

**追问技巧**：追问「把这些规则的执行结果做成一个数据质量看板，展示每张表每天的通过率」，或「上游源系统经常改字段，怎么尽早发现」。

### 示例输出

> 示例，仅供参考（dbt 配置节选）

```yaml
models:
  - name: dwd_orders
    columns:
      - name: order_id
        data_tests:
          - not_null
          - unique
      - name: status
        data_tests:
          - accepted_values:
              values: ['PENDING', 'PAID', 'CANCELLED', 'REFUNDED']
      - name: user_id
        data_tests:
          - relationships:
              to: ref('dim_users')
              field: user_id
```

```sql
-- 自定义规则：已支付订单必须有支付时间，且实付不大于应付（返回违规行，结果不为空即失败）
SELECT order_id, status, paid_at, paid_amount, payable_amount
FROM {{ ref('dwd_orders') }}
WHERE (status = 'PAID' AND paid_at IS NULL)
   OR paid_amount > payable_amount
```

| 规则 | 级别 | 理由 |
|---|---|---|
| order_id 唯一 | 阻断 | 重复会导致所有销售额被放大 |
| 昨日数据行数比过去 4 周同日均值低 50% 以上 | 告警 | 可能是同步失败，也可能是真实下降，需要人工确认 |

说明：较新版本的 dbt 中测试的配置键为 `data_tests`，旧版本为 `tests`，以你所用版本的文档为准。
