**怎么填变量**：[重复交代的内容] 是设计的出发点，把你每次开新会话都要再说一遍的话列出来，例如「提交信息用中文」「这个项目的测试要先起数据库」「上次试过某方案不行」。[可用记忆载体] 写你实际能用的，比如「编程智能体会自动读取仓库根目录的说明文件，另外可以让它读写一个 memory 目录」。[禁止写入的信息] 至少包括口令、密钥和他人的个人信息。

**常见失败与调整**：
- 什么都往里记，索引变成流水账。回到第 4 步收紧写入规则，尤其是「能从代码里读到的不记」。
- 记忆只增不改，同一件事有三条互相矛盾的记录。要求写入前先查重并更新旧条目，记录日期。
- 把大段规则全放进始终加载的文件。那会长期占用上下文，按第 1 步只留少量必须的，其余放到按需读取的文件。

**追问**：「按这个方案，把下面这段对话里值得记住的内容写成记忆条目」「给我一份每月整理记忆的检查清单」。只想写项目说明文件的，可用站内的 CLAUDE.md / AGENTS.md 提示词。

### 示例输出

> 示例，仅供参考（虚构：个人开发者用编程智能体维护一个网店项目）

**索引文件（节选）**

```
- [提交规范](commit-style.md) — 中文提交信息，不加署名行
- [数据库变更流程](db-change.md) — 先同步表结构再发布，顺序不能反
- [构建内存问题](build-oom.md) — 本机构建会内存不足，需先停掉其他容器
```

**一条记忆的模板**

```
# 数据库变更流程
结论：表结构改动必须先同步到数据库，再替换应用版本。
为什么：顺序反了会导致新版本启动时报字段不存在（2026-09 发生过一次）。
怎么用：凡是改动了表结构定义文件的任务，在发布步骤前提醒使用者执行同步。
来源：使用者明确要求　记录日期：2026-09-25
```

**写入判断示例**：使用者说「这次导出先用 CSV」——一次性要求，不记；使用者说「以后导出都用 CSV」——偏好，写入。
