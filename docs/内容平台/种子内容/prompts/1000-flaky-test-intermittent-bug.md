**怎么填变量**：[出现频率] 和 [只在哪些条件下出现] 是最关键的线索——「只在 CI 失败」多半是环境或并行问题，「单独跑能过、整套跑不过」几乎一定是测试之间共享了状态。测试代码和被测代码都要贴，只贴测试很难判断。

**常见坑**：
- 最常见的「修法」是把等待时间从 1 秒改成 5 秒，问题会变少但不会消失，还让整套测试变慢。正确做法是等待一个明确条件（元素出现、消息到达、任务完成）。
- 时间类问题经常藏在「月底、跨年、凌晨 0 点、夏令时切换」这些边界上，可以让 AI 写一个把系统时间固定到这些时刻的测试。
- 偶现问题修完要多跑几十次再下结论，跑一次通过说明不了什么。

**追问技巧**：加完诊断日志、拿到一次失败的完整日志后贴回去，说「根据这份日志，排除掉哪些假设、剩下哪个最可能」。

### 示例输出

> 示例，仅供参考（现象：订单列表测试在 CI 上约 15% 失败，本地单独跑全过）

| 类别 | 可能性 | 依据 |
|---|---|---|
| 顺序相关 | 高 | 测试用 `created_at` 倒序取第一条，而另一个测试也往同一张表插数据，未清理 |
| 时间相关 | 中 | 两条数据在同一毫秒插入时排序不稳定 |
| 并发相关 | 低 | 未见异步调用 |

提高复现率：

```bash
# pytest：随机顺序 + 重复 50 次（需安装 pytest-randomly、pytest-repeat）
pytest tests/test_orders.py -p randomly --count=50 -x
```

修复方案：每个测试在独立事务里运行并回滚；排序改为 `ORDER BY created_at DESC, id DESC`，保证同一时间戳下顺序稳定。
