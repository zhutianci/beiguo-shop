**项目指令是什么**：Claude 的项目（Projects）有自己的知识库和项目指令，写好的指令会用于该项目里的每一个对话；同一项目里的不同对话默认不共享上下文，所以想让所有对话都知道的东西，要放进知识库或项目指令。按帮助中心的说明，项目的名称和描述只是给你自己看的，Claude 读不到。项目功能的套餐范围和文件限制见本站「Claude Projects 怎么用」教程，以官方说明为准。

**为什么让它先采访**：自己闷头写指令，最容易写成一堆形容词（专业、简洁、有洞察）。让 Claude 提问、你贴样例，它才能把「我想要的样子」落成可执行的规则。第一步里它问到「以前不满意的情况」时请认真回答，这部分直接决定 `<do_not>` 写什么。

**怎么填变量**：[知识库资料清单] 逐份列出并注明性质，如「品牌手册 2026 版（权威）」「去年的推文合集（风格参考）」「竞品资料（可能过时）」。[指令长度上限] 建议 600–1000 字，太长的指令里重要规则反而容易被淹没。

**常见问题与调整**：
- 用了一阵发现它老犯同一个错 → 回到项目里说：「把这次的问题用一句话加进项目指令的合适位置，并检查有没有可以删掉的旧条目。」然后把新版本粘贴回去。
- 指令和知识库资料冲突 → 在 `<knowledge>` 里写明谁优先，例如「口径以《价格表》为准，推文合集里的旧价格不要引用」。

### 示例输出

> 示例，仅供参考（项目：一家烘焙店的公众号与朋友圈内容；节选）

```
<purpose>
这个项目用来写门店的公众号推文和朋友圈文案。读者是周边三公里的老顾客，多数在手机上快速浏览，所以每篇只讲一件事。
</purpose>
<knowledge>
《产品手册》里的品名、配料和价格是准确的，写到产品信息时以它为准。《往期推文》只用来参考语气，其中的价格和活动已经过期，不要引用。手册里没有的产品信息，先问我，不要自己描述口味和配料，因为涉及过敏原。
</knowledge>
<when_unsure>
涉及折扣力度、活动截止日期、到货时间时先向我确认。
</when_unsure>
```

**测试问题示例**：「帮我写一条海盐卷的朋友圈」——指令生效时，品名与价格应与《产品手册》一致，并且不超过四行。
