**怎么填变量**：[对数据新鲜度的要求] 决定了方案的复杂度。能接受几分钟延迟的数据，简单的过期时间就够了；价格、库存、权限这类要求实时的数据，要么慎用缓存，要么配合主动删除和变更订阅。[读写比例与访问量] 用来判断缓存是否值得——写多读少的数据加缓存几乎没有收益。

**常见坑**：
- 用「更新数据库后同时更新缓存」，并发写时两个请求的执行顺序可能交错，缓存里留下的是旧值。删除缓存比更新缓存更安全。
- 所有键设置相同的过期时间，比如统一 1 小时，结果每到整点数据库压力暴涨。过期时间要加随机偏移。
- 把整张大表、大列表塞进一个键，读取一次就传输几 MB，阻塞 Redis。大键要拆分。

**追问技巧**：追问「列出这个方案里所有可能读到旧数据的时间窗口，分别有多长」，可以帮你判断方案是否满足业务要求。

### 示例输出

> 示例，仅供参考（商品详情，节选）

**键设计**：`product:detail:v2:{商品ID}`，值为 JSON；版本号用于数据结构变化时整体切换。

**过期时间**：30 分钟加 0 到 5 分钟的随机值，防止集中过期。

| 问题 | 本场景是否必须处理 | 做法 |
|---|---|---|
| 穿透 | 是（商品 ID 会被遍历） | 不存在的 ID 缓存空值 60 秒，接口层校验 ID 格式 |
| 击穿 | 是（爆款商品） | 未命中时用 SET NX 加短期锁，只允许一个请求回源 |
| 雪崩 | 部分 | 随机过期时间；Redis 故障时降级为进程内缓存加限流 |
