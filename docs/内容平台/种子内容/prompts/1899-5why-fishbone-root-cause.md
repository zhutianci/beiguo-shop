prompt: |
  【角色】你是带班组做现场改善的精益辅导员，擅长用鱼骨图和 5Why 把「大家都觉得是这个原因」变成「验证过确实是这个原因」。
  【输入】
  - 问题现象：[问题现象]
  - 发生的工序、岗位或业务环节：[发生环节]
  - 已经掌握的事实和数据：[已知事实与数据]
  - 问题出现的频率与规律：[发生频率与规律]
  - 参与分析的人：[参与分析的人]
  【任务】
  1. 把问题写成一句可衡量的话：什么对象、什么偏差、从何时起、偏差多大。不带原因，也不带对策。
  2. 鱼骨图（文字版）：按人、机、料、法、环、测六类，每类列 2–4 个可能原因。每个原因标注状态：已有事实支持、已有事实排除、待验证，并注明依据是我提供的哪条信息。某一类确实无关的，写「未发现相关因素」，不为凑数而编。
  3. 缩小范围：变化点在哪里？有问题和没问题的情形之间差别是什么？据此选出 2–3 个最可疑的原因。
  4. 对每个可疑原因做 5Why：
     - 每一层的回答必须是事实或可验证的判断，不是猜测，也不是对人的评价；
     - 每写完一层，用「因为……所以……」从下往上倒着读一遍，读不通就说明中间跳了步；
     - 不必正好问五次，问到「改了它问题就不再发生，而且是我们自己能改的」为止；
     - 追到「某人疏忽」时不能停，继续问：为什么疏忽能够发生？为什么发生之后没有被发现？
     - 一个「为什么」有多个答案时分叉，分别往下追。
  5. 验证计划：为每条根因写验证方法（现场观察、数据对比、小范围试验）、需要的数据、判定标准、负责人。未经验证的只能称为「疑似根因」。
  6. 对策方向：每条根因给一个临时对策和一个长期对策，长期对策优先考虑防错和标准化，其次才是培训和提醒。
  【约束】
  - 只使用我提供的事实；需要补充调查的列进「待收集信息」，不替我假设现场情况。
  - 办公或服务类问题，可以把六类改为人、流程、系统、信息、环境、考核，并说明做了替换。
  【输出格式】问题陈述 → 鱼骨图文字版 → 可疑原因筛选 → 5Why 追问链 → 验证计划表 → 对策方向。

**怎么填变量**：[问题现象] 写看到的事实和数字：「10 月起 3 号线封口不良率从 0.5% 升到 2.1%」。[发生频率与规律] 很有用：只在夜班出现？只在某台设备？换料后才开始？规律能直接排除一大半原因。[已知事实与数据] 没有数据就写「暂无」，不要写猜测。

**常见失败与调整**：
- 问到「操作员没注意」就停下，对策是「加强培训」。下个月换一个人照样出错，要继续问为什么这个环节允许出错。
- 每个为什么都靠猜。五层猜测叠在一起，结论基本不可信，每一层都要回到现场或数据去核实；原因不止一个时要分叉追。

### 示例输出

> 示例，仅供参考（虚构：某食品厂包装线封口不良）

**问题陈述**：3 号包装线的袋装产品封口不良率，自 10 月第 2 周起由 0.5% 上升到 2.1%，集中在夜班。

**鱼骨图（节选）**
- 机：封口刀温度波动（已有事实支持：夜班记录显示温度在 165–185 度之间波动，白班稳定在 180 度上下）；
- 料：10 月更换包装膜供应商（已有事实排除：白班使用同一批膜，不良率正常）；

**5Why 追问链**
1. 为什么封口不良？——封口刀温度有时低于工艺下限 175 度。
2. 为什么温度会偏低？——夜班开机后预热不到 10 分钟就开始生产。
3. 为什么预热时间不够？——夜班接班后要补白班欠下的产量，班长要求尽快开机。
4. 为什么没有被拦住？——设备未设温度下限联锁，温度不够也能运行；作业指导书只写「预热后开机」，没有写温度和时间。

倒读：因为没有联锁、指导书也没写明标准，所以预热不足也能开机；因为预热不足，所以温度偏低、封口不良。读得通。

**验证计划**：连续 3 个夜班预热到 180 度后再开机，不良率回落到 0.5% 左右即证实。负责人：夜班班长。长期对策方向：增加温度下限联锁，修订作业指导书。
