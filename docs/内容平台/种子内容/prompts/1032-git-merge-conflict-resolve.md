**怎么填变量**：冲突内容要包含完整的冲突标记和上下文，最好把整个冲突文件贴上。双方的提交信息非常重要，AI 靠它理解「为什么改」，否则只能根据代码猜。

**常见坑**：
- rebase 时，冲突标记里的「当前」一侧其实是你要合入的上游分支，你自己的改动在另一侧，和 merge 正好相反。很多人在 rebase 时选错了一边，把自己的改动丢掉了。
- 只解决有冲突标记的地方，忽略了隐性冲突。合并完能编译不代表逻辑正确，一定要跑测试。
- 遇到看不懂的冲突就直接选「全部用我的」，悄悄覆盖了同事的修复。拿不准时问对方。

**追问技巧**：解决完后，把 `git diff` 的结果贴回去，问「检查合并结果是否同时保留了双方的改动，有没有遗漏」。

### 示例输出

> 示例，仅供参考（merge，当前分支 feature/coupon，合入 main）

**冲突块 1**：`calcPrice()`

- 当前一侧（feature/coupon，你的改动）：在折扣计算中加入优惠券抵扣；
- 合入一侧（main，同事的改动）：把会员折扣从固定 9 折改为按会员等级取折扣率；
- 判断：改了同一逻辑的不同方面，需要融合。

```js
function calcPrice(order, user, coupon) {
  const rate = memberRate(user.level)                    // 来自 main：按等级取折扣
  const discounted = order.total * rate
  return Math.max(0, discounted - (coupon?.amount ?? 0)) // 来自你的分支：优惠券抵扣
}
```

**需要你决定**：优惠券应该在会员折扣之前还是之后抵扣？两种顺序的最终金额不同。

**隐性冲突**：main 把 `getMemberDiscount()` 改名为 `memberRate()`，你的分支在 `cart.js` 中仍调用旧函数名，合并后会报错。

```bash
git add src/price.js src/cart.js
npm test                        # 提交前先确认测试通过
git commit                      # 完成合并
```

如果在提交之前想放弃这次合并、回到合并前的状态：`git merge --abort`。
