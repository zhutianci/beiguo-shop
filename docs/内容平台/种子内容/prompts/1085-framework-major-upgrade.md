**怎么填变量**：[依赖清单] 要完整贴上，框架升级的大部分工作量往往来自第三方依赖的兼容性。[已知用到的特殊功能] 很重要，自定义的安全配置、过滤器、序列化配置等通常是迁移中最费时间的部分。

**常见坑**：
- 开一个升级分支埋头改两个月，主干同时在开发新功能，最后合并时冲突巨大。尽量把升级拆成可以独立上线的小步。
- 没有足够的测试就开始升级，改完不知道哪里坏了。先给核心流程补测试，作为升级的安全网。
- 忽略「默认行为变化」，代码能编译、能启动，但某些接口的序列化格式、安全规则悄悄变了。逐条核对迁移指南中的默认值变化。

**追问技巧**：执行过程中把编译错误或启动报错贴回来，问「这属于迁移指南中的哪一项变更，怎么改」；也可以追问「把这份计划拆成可以分配给 3 个人并行处理的任务」。

> 示例，仅供参考（Spring Boot 2.7 升级 3.x，节选）

**路径**：先升级到 2.7 的最新小版本并消除所有弃用警告 → 运行时升级到 Java 17 → 升级到 3.x。

| 变更 | 影响位置 | 处理方法 | 工作量 |
|---|---|---|---|
| Java 最低版本要求提高 | 构建与部署镜像 | 升级运行时与基础镜像 | 1 天 |
| javax 包名迁移为 jakarta | 校验注解、Servlet 过滤器、持久化注解 | 使用自动化迁移工具批量替换后人工检查 | 3 天 |
| 安全配置写法变化 | 自定义安全配置类（需确认） | 按新的组件化配置方式重写 | 2 天 |

**需要核对发布说明的依赖**：旧版本的接口文档生成库、某些只支持 javax 的第三方组件。
