## 一、这一包改了什么（买家看得见的）

| 以前 | 现在 |
|---|---|
| 不登录也能发帖、评论，即发即公开 | **发帖、评论、传图都要登录**；以前的匿名帖照常显示 |
| 发出去就公开 | **新人（L0）和成员（L1）发帖先审后发**；创作者（L2，3 篇精选以上）和管理员直接发布 |
| 评论即发即显 | 仍然即发即显；**只有命中外链（新人）、联系方式、敏感词的进待审** |
| 改帖不重审 | L0 / L1 改了已过审帖子的标题或正文，**回到待审**（防「先发干净的过审再改成广告」） |
| 发帖没有声明 | 发帖要选**原创声明**（原创首发 / 已在别处发布 / 转载）和**是否用 AI 撰写**；非首发和转载必须填原文地址 |
| 详情页整页客户端渲染，正文不在 HTML 里，标题继承列表页 | **服务端直出**：标题、正文、第 1 页评论都在 HTML 里，每帖有自己的 title / description / canonical / DiscussionForumPosting |
| 作者可以把帖子挪进「官方公告」板块 | 换板块与发帖同一套规矩 |
| `//evil.com` 被当成站内链接放行 | 拦下；正文外链 `rel` 加 `ugc` |
| 帖子 images 什么字符串都收 | 只收本站论坛上传目录的地址 |
| 上传的照片原样保存（含 GPS 坐标） | **去掉 EXIF / XMP / 注释**，保留 JPEG 的方向标签（竖拍照片不会躺倒）；每张图入库留痕（`media_assets`） |
| 删除帖子是硬删 | **软删除**，后台「已删除」里可以恢复 |

**收录**：`lib/content/policy.ts` 的 `INDEXING_OPEN = false`，所有帖子详情页一律 `noindex, follow`。
这与 `seo/restructure` 的决定一致（老论坛整体 noindex）。放开收录是 P1 的事，**不要顺手改这个开关**。

## 二、后台（`/admin/forum`）

- 帖子管理：新增「审核状态」筛选（待审按先到先审排序）、通过 / 驳回（**驳回必须填原因**，作者在帖子页看得到）、「已删除」筛选与恢复。
- 新增「待审评论」面板：通过 / 驳回 / 删除。
- 所有运营与审核操作改走 `/api/admin/forum/posts/[id]`、`/api/admin/forum/comments/[id]`（经 `adminGuard`：查库复核角色 + 同源校验）。
  前台 `PATCH /api/forum/posts/[id]` **不再接收** pinned / featured / locked / status。
- 有内容进待审时推送 `forum.review`（企业微信 / 钉钉 webhook + 微信机器人「运营」类别），链接直达待审列表。
  **如果线上 `.env.production` 设了 `NOTIFY_EVENTS` 白名单，要把 `forum.review` 加进去**，否则收不到。

## 三、数据库变更（只加，不删不改）

```
forum_posts     + review_status VARCHAR(16) NOT NULL DEFAULT 'APPROVED'
                + review_note VARCHAR(500) NULL
                + reviewed_at DATETIME(3) NULL
                + originality VARCHAR(24) NOT NULL DEFAULT 'ORIGINAL_FIRST'
                + source_url VARCHAR(500) NULL
                + ai_assist VARCHAR(8) NOT NULL DEFAULT 'NONE'
                + content_updated_at DATETIME(3) NULL
                + deleted_at DATETIME(3) NULL
                + INDEX (review_status, created_at)
forum_comments  + review_status VARCHAR(16) NOT NULL DEFAULT 'APPROVED'
                + INDEX (review_status)
media_assets    新表
```

- **`review_status` 的库默认值是 APPROVED，是故意的**：加列那一刻，存量帖子和评论要保持公开；
  如果默认 PENDING，db push 完、新镜像还没换上之前，老帖会集体从前台消失。新帖由接口按信任等级**显式写入**，不靠默认值。
- 全部是新增列（带默认值或可空）和新表，`db push` **不需要** `--accept-data-loss`。
  上线前照 09-04 的做法先预览一遍 DDL，确认零 DROP：
  ```
  npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script
  ```
- 顺序（交接文档的铁律）：**先 db push，再换镜像**。反过来，新代码会查不存在的列。
  db push 的命令与内存注意事项见记忆 / 交接文档（生产镜像没有 prisma CLI，用临时容器跑；1.8G 内存先确认 swap）。

```bash
# 3. 后台 /admin/forum 能看到「待审评论」面板与审核状态筛选
```

## 六、已知的、留给后面的

- **删除返回 404 而不是 410**：App Router 的页面里没有简单的办法回 410，Google 的说法是两者长期效果一样。P1 做内容页时再看。
- **违规降级**：等级「只升不降」，违规扣分要等 P2 有了违规记录与积分流水。
- **评论审核只看风险检测**：图片里的二维码、谐音联系方式检测不到，靠举报（P2）和人工巡查。
- **图片压缩成 WebP**：P0 只剥元数据、不重编码。是否引入 sharp 要先评估服务器构建内存（设计 §10.4）。
- **`ForumLike` 唯一约束**：没加。加之前要先查重复数据。
