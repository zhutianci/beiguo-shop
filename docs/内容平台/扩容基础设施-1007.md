# 内容扩容基础设施（2026-10-07，分支 exp/infra）

> 背景：这一轮要一次加入约 1,600 条提示词、280 篇教程、150 个 AI 应用（合计约 1,900 个新页面，学习平台总量到约 2,400 / 300 / 150）。
> 这份文档讲清：定时放量、AI 应用种子格式、规模化改动、镜像与部署步骤。代码改动见本分支 4 个提交（`git log release/opt-1007..exp/infra`）。

## 一、为什么要定时放量

一夜之间新增近两千个同模板页面，正是 Google「规模化内容滥用」（scaled content abuse）的典型样子，而它的判定与处罚是**站点级**的——
商品页、充值落地页会一起掉（同 `src/lib/news/thin.ts` 里新闻薄页的判断）。所以新内容一律先进队列、每天放一小批，每批内类型 / 大类 / 主题混合。

## 二、定时放量（SCHEDULED）

| 项 | 说明 |
|---|---|
| 状态 | `forum_posts.review_status = 'SCHEDULED'`。全站「公开」口径都是 `reviewStatus === 'APPROVED'`（`policy.isPublic`、`queries.PUBLIC_WHERE`），所以它天然不公开：不进任何列表 / 计数 / hub / 搜索 / sitemap / IndexNow / robots index。作者与管理员能打开详情（顶部提示「定时发布队列中」），路人 404。 |
| 导入 | `import-seed-content.ts --schedule`：与 `--publish` 同一个「够不够格」的判定（图像类要有图、教程 / 应用要有 checkedOn 且无截图占位），够格的建成 SCHEDULED，不够格的照旧待审。`--publish` 与 `--schedule` 互斥。 |
| 顺序 | 导入结束时把队列里**全部** SCHEDULED 条目重排 `release_rank`（1 起）。算法 `prisma/release-order.ts`：分桶「类型 \| 模型大类 \| 第一个主题（教程取第一个产品）」，逐层按比例均匀散布、各子组相位错开。自测（模拟 2,030 条）：每天 40 条里三种类型与占比偏差 < 1 条、同一主题桶至多 2 条、至少覆盖 35 个不同的桶。确定性：输入相同顺序就相同，重复导入不搅乱。 |
| 放出 | `GET /api/cron/content-release`（`x-cron-secret` 头，与其他 cron 一样；nginx 对外 404 掉 /api/cron/*）。每天 10:00 跑一次，放 `CONTENT_RELEASE_PER_DAY` 条（不设 = 40，0 = 暂停，上限 500）。按**上海自然日**封顶：数 `released_at` 落在今天的条数，只补差额——同一天调多少次都不会超量。`vmq_locks`（`content:release`）防并发。只放 `status=1`、未删除的。 |
| 放出时写什么 | `review_status=APPROVED`、`reviewed_at = released_at = 现在`、**`created_at` 改为放出时刻**（同一批按队列顺序每条错开 1 秒）、`content_updated_at` 清空、`last_reply_at = 现在`。于是「最新」排序、页面发布日期、sitemap lastmod 都是放出时间。 |
| IndexNow | 放出后把其中「可收录」（`contentIndexable`，与页面 robots / sitemap 同一判定）的地址一次推送；`CONTENT_INDEXING_OPEN` 关着或没配 `INDEXNOW_KEY` 时不推。 |
| 不做的事 | 不触发 `onPublished`（积分、关注者通知）：这些是站方编辑账号的种子内容，每天 40 条通知会淹没关注者——与导入 `--publish` 一致。 |
| 后台 | `/admin/forum` 帖子管理上方的「定时发布队列」卡片：队列条数（按类型）、今天已放 / 每天上限、预计几天放完；「立即放出 N 条」（1–200，不看每天上限，但计入今天的条数，当天 cron 会相应少放）。帖子列表的审核状态筛选加了「定时发布队列（按放出顺序）」，标签显示队列序号。手动「审核通过」一条队列中的条目 = 提前放出（同样改发布时间、记 `released_at`）。接口 `GET/POST /api/admin/content/release`（adminGuard）。 |
| 编辑 | 作者 / 编辑修改队列中的条目：管理员与创作者改完仍在队列（不会提前公开），命中联系方式 / 敏感词或新人修改转待审（`policy.postReviewOnEdit`）。 |

## 三、AI 应用种子格式（`docs/内容平台/种子内容/apps/{NN}-{slug}.md`）

```yaml
---
title: "Perplexity 是什么、怎么用：AI 搜索引擎上手指南"   # ≤200，搜索问法
slug: perplexity-ai-search        # 小写 ASCII，APP 内唯一
name: Perplexity                  # ≤60
url: https://www.perplexity.ai/   # 官网，必须 https，≤500
pricing: 免费+付费                 # ≤60，自由文本
platforms: 网页 / iOS / 安卓 / Windows / macOS   # ≤100
trialNote: 免费账号可直接使用基础搜索   # 选填 ≤200
products: []        # 0–2 个 PRODUCT 标签 slug
models: []          # 0–2 个 MODEL 标签 slug
topics: [office]    # 0–3 个 TOPIC 标签 slug
excerpt: ...        # ≤160
checkedOn: 2026-10-07   # YYYY-MM-DD，不能是未来日期
sources: [https://...]  # 至少 1 个链接
verify: []          # 选填：站长要核对的点（不导入）
---
（正文：可读字数 ≥200。是什么 → 能做什么 → 怎么上手 → 免费与付费 → 适合谁 / 不适合 → 注意事项；
  插图写 ![说明](seed:a{NN}-xxx.png)，文件放 prisma/seed-assets/，下一行写来源，与教程同一机制）
```

编译（`npx tsx scripts/build-seed-bundle.ts`）严格校验，任何一条不过就不写文件：**字段白名单**（写错键名如 `topic:` 直接报错）、必填、长度上限（与 `app_specs` 列宽一致）、slug、https、日期、sources 是链接、标签种类与个数、插图文件名 / 存在 / ≤1.5MB、正文可读字数 ≥ `MIN_APP_CHARS`（200）、联系方式 / 敏感词。两个文件官网相同只提醒（同一官网的不同产品页是允许的）。有【截图】占位的提醒、导入后待审。

导入：`type=APP` + `app_specs`（`selfPromo=false`、`relation=null`）、原创首发、AI 部分辅助、`checked_on` 存进 forum_posts（详情页显示「资料核对于 …」）。随 `--publish` 直接公开 / `--schedule` 进队列；`--refresh-apps` 按新版重写已导入的（只动 `--author` 自己发的；已公开的不会被撤回队列）。
APP 收录门槛（`policy.qualityGateReason`）：原创首发、非 AI 主笔、非自荐、正文可读字数 ≥200——种子格式全部满足。`/apps` 列表与详情无需改动即可展示；详情标题里已有应用名时不再前缀「X 怎么样：」。

## 四、规模化（约 2,850 条之后）

- **列表卡片不再取正文**：`CARD_INCLUDE`（会把整篇 Markdown 取出来只为截 90 字）→ `CARD_SELECT`；没有摘要也没有 useCase 的少数几条单独补查。影响 /prompts 各页、/guides、/apps、/learn、专题、相关内容、收藏 / 合集、搜索结果卡片。
- **可收录计数**：`countIndexable(where, atLeast)` 按 id 倒序分批、数到门槛就停（hub 3–8 条、学习首页 5 条、作者页 1 条）；以前每个 hub 每 5 分钟把最多 1000 条正文整段取出来。
- **热门**：候选按发布时间倒序取、上限 1500 → 3000（以前没有 orderBy，超限时丢哪些不确定；只取 7 个整数列）。
- **学习首页专题封面**：原来每个标签一个嵌套 `take 3`（Prisma 嵌套分页会把所有关联行取回再截）→ 一次取最近 600 条带图提示词在内存里分配。
- **内容 sitemap**：一次查询取齐闸门列与标签（不再按几千个 id 二次查 post_tags），hub 计数用 Map；硬上限 45,000 个地址 / 45MB（协议 50,000 / 50MB），超了告警。约 3k 地址时远在上限之内，暂不分段。dev 环境 220 个地址冷 3s / 热 1s（dev 模式，生产更快，且 Cache-Control 1 小时）。
- **筛选条**：一行超过 14 个胶囊时，行内只留条数最多的 10 个（当前选中的一定在内），其余进行尾「全部 N 个」展开面板（原生 `<details>`，无 JS；总览页主题按图像 / 视频 / 文本分组；换筛选后自动收起）。`/apps` 不再查用不到的标签计数。
- **分页**：补首页 / 末页入口（`1 … 4 5 6 … 100`）。所有 hub 都分页（提示词 24 / 页，教程、应用 20 / 页）。
- **复合索引**：`forum_posts (type, status, review_status, created_at)`、`(type, status, review_status, featured, featured_at)`（列表的两种排序）、`(review_status, release_rank)`、`(released_at)`。
- **搜索**：AI 应用按应用名也能搜到。搜索仍是 LIKE 全表扫（约 3k 行 × 正文），已有限频，量级内可接受；再大要换全文索引。

## 五、种子图与镜像

- 现状：`prisma/seed-assets/` 40MB；本轮各代理可能再加 150–300MB。Dockerfile 的 builder `COPY . .` 与 runner `COPY --from=builder /app/prisma ./prisma` 会把它们整个带进**每一个**运行镜像（每次构建多传几百 MB 构建上下文，每个保留的回滚镜像各占一份；这台机器磁盘只剩十几 G）。
- 运行时代码从不读它（只有导入脚本读），而导入一直是在**临时容器里挂宿主机的 `$PWD/prisma`** 跑的。所以 `.dockerignore` 加 `prisma/seed-assets`，运行镜像不再带它——**镜像减小约 40MB，以后不随种子图增长**。
- 防误用：导入脚本启动时检查种子包引用的图是否都在 `prisma/seed-assets/`，缺图直接停手并提示「挂宿主机 $PWD/prisma」（以前缺图会静默把图像提示词变成待审、把教程插图行删掉）。确实要跳过时加 `--allow-missing-images`。
- 仍要注意：种子图进 git 后，服务器 `git pull` 要多拉这些字节（一次性）；`forum_uploads` 卷会多出同等体积（导入时复制）。导入前 `df -h /` 留足余量。

## 六、部署步骤（在原上线手册基础上新增 / 变化的）

1. **备份**（同原手册）。
2. **DDL 预览**（同原手册的 `migrate diff`）：应只有
   `ALTER TABLE forum_posts ADD COLUMN release_rank INT NULL, ADD COLUMN released_at DATETIME(3) NULL` 与 4 条 `CREATE INDEX`，零 DROP。
   然后 `db push`（旧镜像不读新列，零影响；forum_posts 几百行，建索引瞬间完成）。
3. 构建、`up -d --no-deps app`（同原手册）。
4. **重建 cron 容器**（crontab 新增了放量任务，不重建不生效）：
   `docker compose --env-file .env.production up -d --no-deps --force-recreate cron`
   自检：`docker compose exec cron cat /etc/crontabs/root | grep content-release`。
5. （可选）每天条数：`.env.production` 加 `CONTENT_RELEASE_PER_DAY=40`（不加就是 40；要先暂停就写 0），改完只重启 app。compose 已传这个变量。
6. **本地**编译种子包并提交：`npx tsx scripts/build-seed-bundle.ts`（apps/ 一起编译，校验不过不写文件）。
7. **导入用 `--schedule`**（不要用 `--publish`）：临时容器挂宿主机 `$PWD/prisma` 与 `forum_uploads` 卷，命令同上次（见 `合并上线手册-SEO批1+内容平台.md` 第 7 步 / 上线实录），只把 `--publish` 换成 `--schedule`：
   `npx tsx prisma/import-seed-content.ts --author <站长邮箱> --schedule --uploads-dir <forum_uploads 挂载点>`
   期望末行：`……其中进入定时放量队列 N 条……；队列现有 N 条，已按类型 / 大类 / 主题交错重排`。缺图会直接报错（说明没挂对目录）。
8. 验证：后台 `/admin/forum` 的「定时发布队列」卡片条数对得上；随便打开一条队列中的详情（未登录应 404）；`/sitemap-content.xml` 地址数没有变。
   想当天就放第一批：`docker compose exec cron sh -c 'curl -fsS --max-time 120 -H "x-cron-secret: $(cat /run/cron_secret)" http://app:3000/api/cron/content-release'`（同一天再到 10:00 不会重复放）。
9. 观察：Search Console「已抓取 - 尚未编入索引」比例；异常时 `CONTENT_RELEASE_PER_DAY=0` 重启 app 即暂停放量（已放出的不受影响）。

回滚：镜像回滚即可；库不用回退（新列旧代码不读）。注意旧代码不认识 SCHEDULED——队列中的条目在旧版里同样不公开（旧版公开口径也是 APPROVED），只是后台看不到筛选项。

## 七、改动清单

- **schema（只加）**：`forum_posts.release_rank INT NULL`、`forum_posts.released_at DATETIME(3) NULL`；索引 `(type,status,review_status,created_at)`、`(type,status,review_status,featured,featured_at)`、`(review_status,release_rank)`、`(released_at)`。`review_status` 列不变（VarChar(16)，新值 `SCHEDULED`）。
- **环境变量**：`CONTENT_RELEASE_PER_DAY`（不设 = 40，0 = 暂停），已加进 `docker-compose.yml` app `environment:`（裸变量名）与 `.env.production.example`。
- **cron**：`cron/crontab` 新增 `0 10 * * *` 调 `/api/cron/content-release`（GET + x-cron-secret）。**部署须重建 cron 容器。**
- **Dockerfile / .dockerignore**：排除 `prisma/seed-assets`；Dockerfile 只加了注释。
- **新接口**：`GET /api/cron/content-release`、`GET/POST /api/admin/content/release`。
