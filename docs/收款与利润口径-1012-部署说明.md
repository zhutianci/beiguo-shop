# 收款通知重发识别 / 收款码切换 / 利润口径 —— 部署说明（2026-10-12）

三项改动，分两次构建上线。**都没有数据库与环境变量改动**，只换 app 镜像。

## 一、改了什么

### 1. 手机重发同一条到账通知的识别（`75a8ede`）

起因：站长收到「¥135 到账、与 order#2711 同金额、10 分钟内刚到过一笔」的告警，但那个时间没有真实收款。
查线上原文：那条通知末尾的手机端时间是 09:36:56，正是 09:36:58 已匹配给 #2711 的那一条——手机在 2 分 32 秒后把它又发了一遍。
近两天约 25 条不同通知里有 18 条被手机发了 2~3 次（间隔 3 秒 ~ 5 分半），旧逻辑只认 60 秒内的相同原文。

- 原文带「年-月-日 时:分:秒」的，按原文摘要占一行 `vmq_seen:<32hex>`（settings 表，保留 7 天）。
- 首次已处理完 → 之后再来的一律是重发：不匹配、不进待处理、不推送；后台「收款监控」显示「最近一次忽略的手机重发」。
- 首次没处理完（抛错回了 500、等手机重试）→ 照常匹配，但只认首次收到之前就建好的收款单。
- 顺带堵住的洞：重发若晚于金额冷却期（15 分钟），原来会把同金额的新待支付单标成已支付。
- 细节见 `VMQ_SETUP.md` 第七节、`src/lib/vmq.ts` 的 `registerNotice`。

### 2. 后台收款码上传 / 切换（`271c391`）

后台「收款监控 → 收款码（支付宝）」可上传最多 10 张、点「设为当前」切换，收银台约 3 秒内换码，不用重新构建。
每次上传 / 切换 / 删除都要再输登录密码，写审计并推送 `vmq.qr_changed`。细节见 `VMQ_SETUP.md` 第三节。

### 3. 利润口径（`17a0316`）

站长定的口径（`src/lib/referral-report.ts`），后台订单列表（每行 + 合计）、卡密数据分析、微信机器人日报与「利润」指令四处同步：

- **利润 = 卡差价，不再扣内推返现**。已结算的返现只在旁边标「待返现 ¥X」。
- **已取消 / 已退款的单不计卡密利润，即使卡已经发出去了**（`profitCounted`）。订单列表里这类单利润显示「不计」，
  合计注明不计的单数；卡密分析里这些卡不计流水与利润，张数与成本照常计。

**经验：**

- 这台 1.8G 机器白天构建第一次用了 68 分钟、第二次 40 分钟（10-10 是 32 分钟、10-11 凌晨 36 分钟）。编译进程实际要约 1.4G，内存只剩 500M 左右，全靠换页。根治仍是 ECS 升 4G。
- 需要停 jishi 的构建，用下面这种 wrapper 起（构建结束自动恢复 jishi，输出末行 `WRAPPER DONE build_exit=…`）：

```sh
cat > /tmp/build-wrapper.sh <<'WRAP'
#!/bin/sh
cd /opt/beiguo/beiguo-shop || exit 9
docker stop jishi-app jishi-nginx jishi-cloudflared
sh scripts/ops/build-with-swap.sh
code=$?
docker start jishi-app jishi-nginx jishi-cloudflared
echo "WRAPPER DONE build_exit=$code $(date '+%H:%M:%S')"
WRAP
setsid nohup sh /tmp/build-wrapper.sh > /tmp/build-with-swap.out 2>&1 < /dev/null &
```

（「收款监控 → 最近一次识别到的到账金额」下面会出现「最近一次忽略的手机重发」，settings 表会出现 `vmq_seen:*` 行）。
