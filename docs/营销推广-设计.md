## 0. 一句话

后台「客户 → 营销推广」：用区块编辑器在线排版推广邮件（实时所见即所得预览、内置精美模板、商品卡片、优惠券直发），
选「全部活跃用户 / 按条件筛选 / 手工指定」受众，经阿里云邮件推送的专用批量发信地址 `marketing@mail.bigolab.com`
**每秒至多 1 封**匀速发出；自带一键退订、订阅偏好、投诉/退信抑制、频控、静默时段、预热爬坡、每日试探放量、
熔断自动暂停、点击 → 下单归因报表。

## 1. 已拍板的决定

| # | 决定 | 依据 |
|---|---|---|
| D1 | **老用户与新用户默认可接收，随时一键退订**（opt-out）。后台保留开关 `defaultEligible`，可随时切回「仅明确订阅者」 | 站长 2026-09-25 选择。**已知风险**：广告法 §43、互联网电子邮件服务管理办法 §13(二)、消保法 §29 要求事先同意；QQ 邮箱群发指南点名「不加选择地给所有注册用户发送商业性邮件」。D2–D6 与第 5 节的熔断/预热/试探是为了把风险压到最低，**都不能省** |
| D2 | **主题前强制「(AD)」**（可改为「【广告】」，不能去掉） | 管理办法 §13(三)；QQ 邮箱「主题前加注(AD)」。与是否同意无关，是独立义务 |
| D3 | 页脚强制：经营主体全称、品牌、**能收信的联系邮箱**、「你为什么收到这封邮件」、**「退订营销邮件」**链接、订阅偏好链接、「交易邮件不受影响」；编辑器删不掉 | 广告法 §43「明示真实身份和联系方式…提供拒绝继续接收的方式」；管理办法 §14 联系方式含电子邮件地址、30 日内有效 |
| D4 | **退订立即生效**（队列里的也立刻拦住）；发 RFC 8058 `List-Unsubscribe` + `List-Unsubscribe-Post` 头 | 消保法实施条例 §24「立即停止」；Gmail/Yahoo 批量发信要求 |
| D5 | 隐私政策逐句改写（第 10.5 节列全了），注册页加告知语并留痕 | PIPL §14/§17；现行 `/privacy` 第 77 行「不会…用于商业推广」等 11 处与新行为矛盾 |
| D6 | 营销只走 `marketing@`（批量类型），**绝不在交易邮件里夹带推广** | 互联网广告管理办法 §17；阿里云「不可乱用通道」 |
| D7 | 发送用 **SingleSendMail 逐封调用**，不用 BatchSendMail | 官方：单一发信接口「可发送触发邮件和批量邮件」；Batch 模板每次改都要人工审核 1–3 个工作日，且一次 100 封是我们控制不了的突发 |
| D8 | 打开/点击追踪**自建**（`ClickTrace=0`），不用阿里云邮件标签 | 阿里云数据只留 1 个月；自建可按用户归因到订单；回执查询按专用发信地址即可（接口规定 AccountName/TagName/ToAddress 三选一） |
| D9 | 编辑器**自研区块模型 + 自研渲染器**，富文本内核 TipTap v3（MIT，锁定 3.31.3） | SaaS 编辑器运行时加载境外脚本且自定义区块收费；GrapesJS/Easy Email/MJML 过重，MJML 多列依赖 `<style>` 媒体查询而 QQ/163 对 `<style>` 支持存疑 |
| D10 | 邮件优惠券两种：**直发到账户**（防转发、不受「同一网络限领」误伤）与**领取链接**（复用 `/coupon/<code>`） | 公开领取有 IP/设备限领，NAT 下误伤；直发复用抽奖的「系统批次」机制 |
| D11 | 从营销邮件点进来的访问**清除本机旧的推广码**（链接带 `via=mail`） | 推广价与券互斥（交接文档第十八节）：旧推广码会让邮件承诺的券不可用、价格还可能比邮件高。邮件带来的订单是站方自己的营销，不算推广人的 |

## 2. 范围

### 2.1 这一版做

- 活动全生命周期：草稿 → 测试发送 → 发送前检查（含预计完成时间）→ 立即/定时发送 → 发送中（进度、「为什么还没发」、暂停/继续/取消/撤回定时）→ 报表
- 区块编辑器（全屏）+ 5 套内置模板（新品上架 / 限时优惠券 / 老客召回 / 简洁通知 / 空白）+ 另存为模板 + 复制历史活动；桌面/手机/暗色/无图预览、以某用户身份预览
- 受众：全部活跃用户（默认排除长期不活跃）/ 条件筛选（含一键预设）/ 手工指定（用户管理页多选、粘贴 ID 或邮箱）；预估人数、排除原因、预计频控跳过数
- 订阅体系：三态（默认/明确订阅/已退订）+ 三个主题（优惠活动 / 新品上架 / 资讯教程）+ 暂停 30 天；退订页（免登录）、个人中心开关、注册告知留痕、全部变更留痕
- 抑制名单：硬退信、连续软退信、投诉、无效地址、手工
- 发送治理：全局 1 封/秒、每日上限、阿里云日额度占比上限、发送时段（默认 9–21 点）、预热爬坡（按前一天表现决定是否升级）、每日试探放量、频控、收件域名交错、熔断、全局急停
- 阿里云同步：投递回执、投诉与退订屏蔽名单、无效地址库、账户额度与信誉等级
- 报表：送达、点击（过滤机器）、打开（标注仅供参考）、退订、投诉、链接点击排行、跳过原因、**5 天末次点击归因的订单与货款**、「点了没买」名单与 CSV 导出；用户详情页的营销记录卡
- 流量分析新增「邮件」来源
- 企业微信通知：开始、完成、自动暂停/急停
- 审计日志

### 2.2 刻意不做

| 不做 | 理由 |
|---|---|
| A/B 测试 | 每组 ≥5000 人才有统计意义 |
| 自动化旅程 | 先把单次活动做扎实 |
| 发给非注册用户邮箱 | 这些邮箱是为特定用途收集的（闲鱼导入、开票、充值目标） |
| 千人千面推荐 | PIPL §24 另有要求 |
| EventBridge 推送 | 需站长在控制台配规则；轮询 API 够用 |
| 两栏图文区块、倒计时、对比表、用户评价 | 幽灵表复杂度高而受众以手机为主；对比表/评价有广告法风险；倒计时要服务端出 GIF |
| 「重发给未打开的人」 | 打开数不可靠；小名单上重发是垃圾信号 |
| 独立营销子域名 | 需改 DNS（第 13 节强烈建议），代码只读环境变量，换地址零改动 |

## 3. 总体架构

```
 后台 /admin/marketing（adminGuard）
   活动列表 · 全屏编辑器(区块列表+属性 | 实时预览 iframe) · 受众 · 检查并发送 · 报表
   模板 · 订阅与退订 · 发送设置（含阿里云账户状态、急停）
        │ /api/admin/marketing/*                  │ 预览 = 同一个渲染器（浏览器端执行）
        ▼                                         ▼
 lib/marketing/*（服务端）                 lib/marketing/render.ts / lint.ts（同构、零依赖）
 config · policy · audience · consent · snapshot · personalize · worker · transport · sync · stats · coupon
        │
 MySQL：marketing_campaigns / _messages（发件箱）/ _links / _events / _consents / _consent_logs /
        _suppressions / _templates / _audits · settings: marketing_config · mkt_halt · mkt_account · mkt_sync
        │
 cron 每分钟 POST /api/cron/marketing      → worker（锁 mkt:send，单趟 ≤ 35s 开始新发送）
 cron 每 5 分钟 POST /api/cron/marketing-sync → sync（锁 mkt:sync，单趟 ≤ 45s）
        │
 阿里云 DirectMail：SingleSendMail · SenderStatisticsDetailByParam · ListBlockSending · QueryInvalidAddress · DescAccountSummary

 公开（免登录）：/unsubscribe/[token] 页面 · /api/mkt/unsubscribe/[token]（RFC 8058 一键）· /api/mkt/prefs/[token]
               /api/mkt/o/[token] 打开像素 · /api/mkt/c/[token]/[idx] 点击跳转
 前台：个人中心「邮件订阅」卡 · 注册告知语 · 隐私政策改写 · 邮件落地清推广码（via=mail）
```

**为什么「cron 每分钟一趟」而不是常驻循环**：项目没有常驻任务机制，app 容器 `oom_score_adj=+500` 是整机 OOM 的首选牺牲者，
部署也会杀进程。状态全在库里、每分钟一趟可重入，进程被杀最多产生一封「不知道发没发」的 UNKNOWN（第 5.5 节），下一分钟自动接上。

**时间不变量**（写死，测试钉住）：`SENDING 回收阈值 5 分钟 > 锁 TTL 3 分钟 > 单趟最长 60 秒`；
单趟 35 秒后不再开始新发送，单封 HTTP 10 秒超时，crontab `--max-time 58`。

## 4. 数据模型（全部新增表，不改任何已有表）

> 只有 `CREATE TABLE`，没有 `ALTER`/`DROP`。旧镜像跑新库零影响。
> 用于比较的时间字段一律由应用写 `new Date()`；`@default(now())` 只用于展示（交接文档「改 TZ 引发锁永不自愈」）。
> 所有来自外部的文字（阿里云回执、UA、错误信息）写库前一律 `clip(s, 列宽)`（MySQL 严格模式超长直接报错）。

// ============ 营销推广（邮件） ============

/// 用户对营销邮件的偏好。没有行 ≡ status=DEFAULT、无主题限制、未暂停。
model MarketingConsent {
  id          Int       @id @default(autoincrement())
  userId      Int       @unique @map("user_id")
  // DEFAULT：未明确表态（能否发由 marketing_config.defaultEligible 决定）
  // SUBSCRIBED：用户亲手点过「确认订阅」；UNSUBSCRIBED：已退订
  // 只调主题/暂停不改变 status —— 否则 opt-out 下的一次微调会被误记成明确同意
  status      String    @default("DEFAULT") @db.VarChar(16)
  topicsOff   String?   @map("topics_off") @db.VarChar(64) // 逗号分隔：PROMO,PRODUCT,NEWS
  pausedUntil DateTime? @map("paused_until")
  source      String    @db.VarChar(24) // 最后一次变更来源
  createdAt   DateTime  @default(now()) @map("created_at")
  updatedAt   DateTime  @updatedAt @map("updated_at")

  @@map("marketing_consents")
}

/// 告知/同意/退订留痕。只增不删、不设保留期（ISC：保留同意记录；注销后因法定证据义务保留，隐私政策已写明）。
model MarketingConsentLog {
  id            Int      @id @default(autoincrement())

  // NOTICE(注册时展示了告知语) | SUBSCRIBE | UNSUBSCRIBE | TOPICS | PAUSE | RESUME
  action        String   @db.VarChar(20)
  detail        String?  @db.VarChar(255)
  // register | profile | token_page | one_click | admin | complaint | aliyun_sync
  source        String   @db.VarChar(24)
  campaignId    Int?     @map("campaign_id")
  messageId     Int?     @map("message_id")

  createdAt     DateTime @default(now()) @map("created_at")

  @@index([userId])
  @@index([email])
  @@index([messageId])
  @@index([createdAt])
  @@map("marketing_consent_logs")
}

**Setting 表的四个键**（每个键只有一类写者 —— 避免整块 JSON 覆盖把别人的急停冲掉）：

| 键 | 写者 | 内容 |
|---|---|---|
| `marketing_config` | 后台设置页 | 第 6 节策略 |

## 5. 发送管线

### 5.1 活动状态机（所有状态写入都是条件更新 CAS）

```
DRAFT ──launch──▶ SCHEDULED ──worker 到点物化，CAS(SCHEDULED→SENDING)──▶ SENDING ──CAS(SENDING→COMPLETED)──▶ COMPLETED
  ▲                  │  │                                                  │   ▲                                │
  │    unschedule ◀──┘  │ pause（SCHEDULED|SENDING→PAUSED）                ▼   │ resume                        │ requeue
  └──(未物化时)          └──────────────────────────────────────────▶ PAUSED ◀── 熔断/内容错误/券失效/商品变更   │（COMPLETED→SENDING）
 cancel：SCHEDULED|SENDING|PAUSED → CANCELLED
```

写入规则（`updateMany({ where:{ id, status:{ in: 允许的来源态 } } })`，检查 count）：

| 动作 | 来源态 → 目标态 | 附带 |
|---|---|---|
| launch | DRAFT → SCHEDULED | 冻结快照、建券批次；`testedHash===contentHash`、`expectedCount`、`expectedContentHash` 都要对上 |
| 物化完成 | SCHEDULED → SENDING | count=0 时重读：CANCELLED → 本活动 QUEUED/CLAIMED 全改 CANCELLED；PAUSED → 只写 materializedAt |
| 完成 | SENDING → COMPLETED | 仅当已物化且无 QUEUED/CLAIMED/SENDING 行；只有 CAS 成功的那一次发「完成」通知 |
| pause / 自动暂停 | SCHEDULED/SENDING → PAUSED | statusNote 写原因；自动暂停对已 COMPLETED 的活动无效（改走全局急停） |
| resume | PAUSED → SENDING（已物化）/ SCHEDULED（未物化） | `breakerResetAt=now`、`canaryDay=null`、`failStreak=0` |
| cancel | SCHEDULED/SENDING/PAUSED → CANCELLED | 同事务把 QUEUED/CLAIMED → CANCELLED；worker 每趟再扫一次；未物化且券批次 0 张 → 批次置 ENDED |
| unschedule | SCHEDULED（且未物化）→ DRAFT | 清快照与 links；删除 0 张的券批次；保留 testedHash |
| requeue | 行：FAILED(可重试类) / UNKNOWN(`UNKNOWN_NOT_FOUND`) → QUEUED；活动 COMPLETED → SENDING | 二次确认；其他 UNKNOWN 不许重排（阿里云可能已受理） |

### 5.2 消息状态机

```
QUEUED ──CAS──▶ CLAIMED ──发前复核/发券通过──▶ SENDING ──HTTP──▶ SENT ──sync──▶ delivery=DELIVERED/INVALID/SPAM/FAILED
  ▲                │                               │
  │                ├─复核不通过 → SKIPPED(reason)   ├─连接阶段失败（请求没出去）→ QUEUED 退避
  │                ├─频控未到间隔 → QUEUED(nextAttemptAt)  ├─阿里云明确拒绝 → 见 5.5
  │                └─活动已取消 → CANCELLED；已暂停 → QUEUED  └─超时/响应阶段异常 → UNKNOWN（绝不自动重发）
  └── 管理员 requeue（仅 FAILED 可重试类 + UNKNOWN_NOT_FOUND）
回收：CLAIMED 超过 2 分钟 → QUEUED（请求没发出）；SENDING 超过 5 分钟 → UNKNOWN(INTERRUPTED)，sentAt=claimedAt
```

**不变量（测试钉死）**
1. `(campaignId, email)` 唯一 → 物化可重入、永不重复
2. 只有 `QUEUED→CLAIMED` 的 CAS 成功（count===1）才会继续 → 两个 worker 同时跑也不双发
3. `SENDING` 超时一律 `UNKNOWN`，不自动重发（阿里云没有幂等键）
4. 发出去之前一定重读活动状态与收件人资格（退订立即生效）
5. 相邻两次**真实调用阿里云**的间隔 ≥ `1000/ratePerSec` 毫秒（跳过的行不占间隔、不占额度）

### 5.3 worker 一趟（`POST /api/cron/marketing`）

```
t0=now；deadline=t0+35s
1. assertCronAuth → 抢锁 mkt:send（抢不到：{skipped:'locked'}）
2. 严格读 config、halt（失败则中止）
3. 回收（5.2）；扫已取消活动残留的 QUEUED/CLAIMED → CANCELLED
4. 物化：取最早一个到点 SCHEDULED 且未物化的活动（每趟至多一个）→ 5.6；异常 → 该活动 PAUSED(statusNote)，不影响其他活动
5. 若 !config.enabled、halt.until>now、不在发送时段 → 收尾结束
6. 同步健康检查（非 dry-run）：有 SENDING 活动，且 mkt_sync.lastOkAt 超过 60 分钟（或从未成功且最早开始发送已超 60 分钟）→ 急停「回执同步中断」
7. 账户级熔断（今日回执，5.8）→ 可能急停
8. 商品复核：每个 SENDING 活动按 refs 重读商品（下架/改价）与券批次（非 ACTIVE）→ 不符则暂停该活动
9. 预算 = 5.7 的今日额度 − 今日已用（今日已用 = 营销 SENT+SENDING+UNKNOWN + 今日测试发送数）
10. 循环直到 deadline / 预算用完 / 无可发：
    a. 每 5 秒重读 enabled 与 halt
    b. 选活动：SENDING，按 id 先来先发；该活动今日试探未放行且今日已发 ≥ canarySize → 按 5.8 判断放行/等待/暂停
    c. 选行：该活动 status=QUEUED、nextAttemptAt 为空或已到、收件域名不在退避中，ORDER BY sortKey, id
    d. CAS QUEUED→CLAIMED(claimedAt=now)；count≠1 → 下一条
    e. 重读活动状态：CANCELLED → 行 CANCELLED；非 SENDING → 行 QUEUED，跳过该活动
    f. 复核资格（5.4，含频控）→ SKIPPED / 延后
    g. 直发券：重读批次（非 ACTIVE → 活动暂停，行放回 QUEUED）；发券（第 9 节，幂等）
    h. 个性化（5.9）→ 行 CLAIMED→SENDING（写 subjectSent）→ transport.send（10 秒超时）
    i. 按 5.5 分类落库；更新活动 failStreak；预算−1；补足间隔
11. 完成检测（5.1）→ 通知
12. 释放锁；返回小 JSON（cron.log 不轮转）
```

### 5.4 资格判定（物化时算 1–10，发送前再算 1–8 + 11）

`eligibility(ctx) → null | SkipReason`，顺序：

| # | 条件 | SkipReason |
|---|---|---|
| 1 | 用户不存在或 `status≠1` | `DISABLED` |
| 2 | 没有邮箱/格式不对（**物化时只计数、不写行**） | `NO_EMAIL` |
| 3 | 测试域名（`.local` `.test` `.invalid` `.example` `example.com/.org/.net`） | `TEST_ADDRESS` |
| 4 | 邮箱在抑制名单 | `SUPPRESSED` |
| 5 | consent.status=UNSUBSCRIBED | `UNSUBSCRIBED` |
| 6 | consent.pausedUntil > now | `PAUSED` |
| 7 | 活动主题在 topicsOff 里 | `TOPIC_OFF` |
| 8 | status=DEFAULT 且 `defaultEligible=false` | `NO_CONSENT` |
| 9 | （仅 DEFAULT 用户，`sunset.enabled` 默认开）已收 ≥3 封营销、近 90 天无点击且无付款 | `SUNSET` |
| 10 | 受众 `excludeInactive`（ALL 默认开）：注册 >180 天、近 365 天无付款、近 180 天无营销点击 | `INACTIVE` |
| 11 | 频控：7 天 ≥ max7d 或 30 天 ≥ max30d → `FREQ_CAP`（跳过）；距上一封 < minHours → **延后**（nextAttemptAt=上一封+minHours，不跳过） | `FREQ_CAP` |

频控计数口径：同邮箱 status ∈ {SENT, SENDING, UNKNOWN}，时间取 `COALESCE(sentAt, claimedAt)`，排除本行。

### 5.5 发送结果分类（`classifySend`，纯函数，测试钉死）

传输层 `rpcCall` 先把结果归成四类：`ok` / `api_error`(有阿里云 Code) / `connect_error`(请求没出去：ENOTFOUND、EAI_AGAIN、ECONNREFUSED、UND_ERR_CONNECT_TIMEOUT) / `unknown_error`(超时、响应阶段异常、5xx 且无 Code)。

| 情形 | 判定 | 行 | 活动 / 全局 |
|---|---|---|---|
| 成功 | ok | SENT(envId, sentAt) | failStreak=0 |
| 不确定 | unknown_error | UNKNOWN(sentAt=claimedAt) | 连续 2 次 → 急停 15 分钟 + 通知 |
| 没发出去 | connect_error | QUEUED，attempts+1，退避 1m/5m/30m/2h；≥5 次 → FAILED(`CONNECT`) | 本趟结束 |
| 限流 | Code 以 `Throttling` 开头 | QUEUED，**不占** attempts，+2 分钟 | 本趟结束 |
| 服务端临时错误 | `ServiceUnavailable` `InternalError` `InternalServiceError`（带 Code） | 同「没发出去」 | — |
| 收件人无效 | `InvalidToAddress` `InvalidToAddress.Spam` `InvalidReceiverName.Malformed` `EmailFormatError` | FAILED + 抑制(INVALID) | — |
| 额度用尽 | `InvalidQuota` | QUEUED（原样） | 急停到**次日发送时段开始** + 通知 |
| 反垃圾拒发 | `InvalidSendMail.Spam` | FAILED(`SPAM_REJECT`)（不再排队） | 暂停该活动；10 分钟内不同行连续 2 次 → 急停 24 小时 |
| 配置/账号 | `InvalidMailAddress*` `InvalidUserStatus*` `InvalidUser.NotFound` `Forbidden*` `InvalidIP.NotFound` `SignatureDoesNotMatch` `InvalidAccessKeyId*` `MissingParameter*` `User.*` | QUEUED（原样） | 急停 24 小时 + 通知（后台可手动解除） |
| 内容问题 | `InvalidSubject*` `InvalidBody*` `InvalidHtmlBody*` `InvalidTextBody*` `InvalidFromAlias*` `InvalidReplyAddress*` | QUEUED（原样） | 暂停该活动（statusNote 说明；TextBody 问题可在设置里关掉纯文本版后继续） |
| 其他 | 其余 Code | FAILED(Code) | failStreak+1；≥5 → 暂停该活动 |

测试发送走同一分类，但**只记录结果，不触发暂停/急停**。

### 5.6 物化（worker 锁内、每趟至多一个活动、全部集合查询）

1. `resolveAudience(spec)` → 用户 id 集合（第 8 节）；每批 `IN` 查询，**禁止逐人调用 vip-server 的单用户函数**
2. 一次性批量取：用户（id,email,nickname,status,createdAt）、consents、suppressions、付款统计 groupBy（sum/max paidAt）、近 90/180 天点击、已收营销封数、`email_codes` 里 REGISTER 且 used 的邮箱（验证过的）
3. 逐人算 5.4 的 1–10；邮箱小写去重；有邮箱的全部写行（排除的写 SKIPPED+reason，报表能解释「为什么没收到」）
4. `sortKey` = 层级 × 100000 + 层内按收件域名轮转的序号：
   - 0：90 天内付过款；1：曾经付过款；2：90 天内注册或 90 天内点过营销邮件；3：验证过邮箱；4：其余（从没验证过、从没付过款 —— 最可能退信，放最后）
   - 同层内 qq.com / 163.com / gmail.com … 交错（阿里云：不要频繁同时向同一个收信方服务商发送同样主旨的邮件）
5. `createMany({ skipDuplicates:true })` 每批 500；token=`randomBytes(16).hex`
6. CAS SCHEDULED→SENDING（5.1），写 recipientCount、materializedAt、startedAt；通知「开始发送」

### 5.7 今日额度（北京时间，固定 +8 运算，不依赖进程 TZ）

```
quota      = mkt_account.dailyQuota（24h 内取到的） 否则 500
quotaCap   = floor(quota × maxQuotaShare)                 // 给验证码/订单/到期提醒留余量（额度按账户共享）
warmupCap  = warmupLevel(过去发送日表现) → schedule[level] 或 ∞（5.8）
dailyLimit = min(dailyCap, quotaCap, warmupCap)
budget     = max(0, dailyLimit − 今日已用)
```
所有「今天」「次日 9 点」「第几个发送日」都用 `lib/marketing/time.ts` 的 `bjDayStart / bjHour / nextWindowStart / bjDateKey`。
SQL 里按北京日期分组一律 `DATE(col + INTERVAL 8 HOUR)`（Prisma 存 UTC）。

### 5.8 风控：预热、试探、熔断

**预热等级**（`warmupLevel`，纯函数）：取最近 60 天、不含今天的发送日（北京日期）及每天回执统计，按时间顺序：
达标日（有回执 ≥20 且 无效 <3%、垃圾 <1%、投诉 0、无反垃圾拒发；回执不足 20 视为达标）level+1，不达标保持；
若距上一个发送日 >45 天，level 归零。`warmupCap = level < schedule.length ? schedule[level] : ∞`。

**每日试探**（`canarySize` 默认 50）：每个活动每个发送日先发 50 封，然后暂停选取该活动，直到
「今日已发中 ≥80% 有回执」或「最后一封已过 30 分钟」→ 用这批回执算活动熔断：通过 → `canaryDay=今天` 放行；不通过 → 暂停。
今日预算不足 50 的不设试探。

**熔断**（`evaluateBreaker`，纯函数）：统计口径只算**有回执的行**，且 `deliveryAt > breakerResetAt`（继续发送后当天的试探从 `max(当天零点, breakerResetAt)` 重新计数，代码审查 C0）；另外「发信方问题」（`SENDER_SIDE_CLASSES`：我方 SPF/DKIM/DMARC 失败、发信人/域名被拉黑）占有回执行 >10% 也触发（代码审查 C19）；账户级熔断的起点由急停记录里的 `acctSince` 决定，只有管理员解除「账户级熔断」本身才移动它（代码审查 C1）；
样本 ≥30 时：无效率 >5%、或垃圾率 >2.5%、或投诉 ≥2（样本 ≥700 时改为 >0.3%）→ 触发。
- 活动级：worker 每趟 + 试探点评估 → 暂停活动 + 通知
- 账户级：今日全部营销回执 → 急停到次日窗口 + 通知
阈值依据：阿里云升级线（无效 <5%、垃圾 <2.5%）；降级线 9%/10%，封禁线 11%/15%。

2. **投递回执**：待查 = SENT/UNKNOWN 且 72 小时内、且 delivery 为空或 =FAILED。
   `SenderStatisticsDetailByParam(AccountName=marketing@, StartTime/EndTime=北京时间 yyyy-MM-dd HH:mm，前后各放宽 2 小时, Length=100, NextStart 翻页)`，每趟 ≤30 页；
   时间以 `UtcLastUpdateTime`（秒，可能是数字或字符串）为准（`LastUpdateTime` 带 Z 但其实是北京时间）；
   匹配：ToAddress 小写 = email **且** Subject = subjectSent **且** utc ≥ claimedAt−60 秒，取最早一条；
   Status 0/2/3 → DELIVERED/INVALID/SPAM（终态）；4 → FAILED（72 小时内继续复查）；detail=`clip(ErrorClassification+' '+Message)`
3. **ErrorClassification 映射**：`SmtpNxBox` `SysOutRcptOnAccountLevelBounceList` `SysOutInvRcpt` `SysIncomingInvRcpt` `SmtpZPermErr` `SysOutDnsResolveFail` → 抑制 HARD_BOUNCE；
   `SysOutRecipientReportedSpam` → 抑制 COMPLAINT + 退订；`SysOutRecipientUnsubscribed` → 退订 —— 这两类是阿里云**因旧投诉/旧退订拦下了本封**，本封没送达，**不在本封上记 complainedAt/unsubscribedAt、不计入本活动的熔断**（代码审查 C16）；
   `SENDER_SIDE_CLASSES`（SmtpAuthFail/SmtpSpfFail/SmtpDmaFail/SmtpMfBad/SmtpDbl）→ 不抑制收件人、不计软退信，计入熔断（代码审查 C19）；
   `SmtpMfFreq` `SmtpMfdFreq` `SmtpIPFreq` `SmtpRcptFreq` `SmtpMfLimit` → 该收件域名退避 1 小时（`mkt_sync.domainBackoff`）；
   同一邮箱连续 3 次 status 4（非频率类）→ 抑制 SOFT_BOUNCE
4. **UNKNOWN 对账**：同样的匹配规则查到 → SENT（sentAt=claimedAt）；claimedAt 超过 2 小时仍查不到 → errorCode=`UNKNOWN_NOT_FOUND`（此后才允许 requeue）
5. **投诉与退订屏蔽名单**：`ListBlockSending(BlockType=REPORT|UNSUB, 不限 SenderEmail（整个账户，覆盖换过的旧发信地址与同域交易地址，代码审查 C15）, BeginTime=blockCursor, EndTime=now, MaxResults=500, NextToken 翻页)`（Unix 秒）；
   REPORT → 抑制 COMPLAINT + 退订(source complaint) + 就近消息 complainedAt；UNSUB → 退订(source aliyun_sync)；
   首次运行从 30 天前开始（上线前把阿里云已有的屏蔽名单导进来）；游标 = EndTime − 1 小时（重叠、操作幂等）。**投诉数据阿里云按天更新**，账户级熔断因此有约一天滞后——这正是预热第一天只发 200 封、先发最活跃用户的原因
6. **无效地址库**：每天一次 `QueryInvalidAddress(StartTime/EndTime=yyyy-MM-dd, NextStart)` → 抑制 INVALID（首次拉 30 天）
7. 全部成功 → `mkt_sync.lastOkAt=now`；任何一步失败写 `lastError`，不抛；单行处理 try/catch

## 12. 不能改错的地方

1. **消息 CAS + 唯一约束**是不重复发的全部保证；**活动状态写入全部 CAS**，否则「取消了还在发」
2. **SENDING 超时一律 UNKNOWN，不自动重发**；UNKNOWN 只有同步确认查不到后才允许人工重排
3. **发送前复核资格**（退订立即生效是法律要求）
4. 退订页 **GET 不改状态**；RFC 8058 端点**不看 Content-Type、不对有效 token 限流**
5. 点击跳转**只认库里存的 URL**
6. 营销只从 `ALIYUN_DM_MARKETING` 发，没配就停
7. 主题前缀、尊称、页脚退订/身份/联系邮箱是**法律或平台义务**，不做成可关
8. 金额口径 `Order.amount`（不含税）
9. 事件 90 天、发送记录 2 年与隐私政策绑定；改保留期先改 `/privacy`
10. 渲染器与 lint 是同构纯函数，不许 import prisma/fs/window
11. worker/sync 读配置与急停**失败即中止**，绝不回落默认值
12. 预览 iframe **不给 allow-scripts**；不许用 `dangerouslySetInnerHTML` 展示邮件 HTML
13. 管理员不能把退订用户改回订阅、不能解除投诉抑制
14. 券名、UTM 里不出现活动名（活动名只给后台看）
