# 渠道自定义域名（2026-09-30 站长提出）

> 上位文档：`docs/多渠道分销-设计.md`（v3）、`docs/多渠道分销-二期改动.md`。与之冲突处以本文为准，实现完成后把设计 4.2 / 4.4 对应段落改掉。
> 场景：某渠道的客户想用自己的域名 `tibo.pw`（注册在西部数码）作为店铺地址，地址栏显示 `tibo.pw`。
> 线路方案（已与站长确认）：客户在西部数码把 `tibo.pw` 的 DNS 服务器改成**站长 Cloudflare 账号**分配的 NS，域名注册仍在西部数码；站长在 Cloudflare 隧道里给 `tibo.pw`、`www.tibo.pw` 加路由（HTTP → `nginx:80`，Host Header 留空）。
> Cloudflare 规定隧道只给同一账号下的域名转发流量（`cfargotunnel.com only proxies traffic for DNS records in the same Cloudflare account`），所以客户保留自家 DNS、直接 CNAME 到隧道的做法走不通。

## 0. 目标与不变量

- 目标：
  - 一个渠道可以登记若干域名：原来的 `xxx.bigolab.com` 一级子域名，外加任意数量的**自定义域名**（如 `tibo.pw`、`www.tibo.pw`）；
  - 其中一个是**主域名**，`Tenant.origin` = `https://<主域名>`，系统邮件、邀请链接、metadataBase 都用它；
  - 渠道的非主域名在浏览器里打开前台或渠道后台页面时，跳转到主域名。
  - 自定义域名只有在**持续通过连通校验**时才当主域名用（第 9 节）：设主前当场校验，之后 cron 每 10 分钟复验；失联时自动改用子域名。
- 不变量（**不能破坏现有分销逻辑**）：
  1. 主站（`PLATFORM_HOSTS`）的行为逐字不变；休眠态（`CHANNELS_ENABLED` 未设）逐字不变。
  2. lulu、shop 等只有子域名的渠道，行为逐字不变：主域名就是子域名，不会发生跳转。
  3. 店面只从数据库认：未登记的域名绝不当渠道；已登记但停用的域名返回 404，**绝不回落主站**；查库报错返回 500，同样不回落。
  4. 权限、JWT aud（渠道代码）、Cookie（host-only）、同源校验（Origin 必须等于 Host）、账本、定价、通知，全部与域名无关，一律不改。
  5. **不改 schema**：`tenant_domains(host 唯一, tenant_id, is_primary, status)` 已经足够。

## 1. 域名分类与校验（`src/lib/storefront/hosts.ts` 纯函数 + `admin-tenants.ts`）

`classifyTenantHost(raw) → { host, kind: 'SUB' | 'CUSTOM' } | 错误`，由超管后台的添加 / 设主操作调用：
- **SUB**：`xxx.bigolab.com` 一级子域，规则同现在（`isChannelCandidateHost`、保留名、不能是主站）。
- **CUSTOM**：不在 `.bigolab.com` 之下、也不等于 `bigolab.com` 的主机名，要满足：
  - `normalizeHost` 通过（ASCII、小写、无端口、无尾点）；
  - 至少两段；每段 1–63 个 LDH 字符，首尾不能是 `-`；
  - 顶级域是 2–63 位字母，或 `xn--` 开头（IDN 的 punycode）；
  - 总长 ≤ 120（列宽）；
  - 不是 IPv4 字面量；
  - 不在 `PLATFORM_HOSTS` 里；
  - 不是 `localhost`，不以 `.local`、`.internal`、`.localhost` 结尾。
  - `.test` 只在非生产环境（`NODE_ENV !== 'production'`）允许，给本地测试用。
- `bigolab.com` 的多级子域（`a.b.bigolab.com`）仍拒绝：Universal SSL 只覆盖一级子域名。

## 2. 店面解析（`src/lib/storefront/resolve.ts`）

- 新增「自定义域名集合」：`tenant_domains` 里所有**不以 `CHANNEL_HOST_SUFFIX` 结尾**的 host（不论启用或停用），常驻内存。
  - 60 秒 TTL；`invalidateStorefrontCache()` 同时清掉它；
  - 同一时刻只有一次加载在进行，并发请求共用这一次。
  - 假库注入（`setStorefrontDbForTest`）要能提供这份列表：`StorefrontDb` 增加 `listCustomHosts()`。
- 判定顺序（在设计 4.4 表格上插一行）：
  - 休眠 → 主站；
  - 主站白名单 → 主站；
  - `*.bigolab.com` 一级子域 → 查 `tenant_domains`（现状不变）；
  - **在自定义域名集合里 → 查 `tenant_domains`，后续和子域名同一套**：登记且启用 → 渠道；登记但停用 → null（404）；
  - **形如域名但未登记（含未登记的 `*.bigolab.com` 一级子域）→ null（404，2026-10-01 加固）**：观察期也不再按主站渲染。nginx 已把这类 Host 按 channel 放行，应用若回落主站，就是设计 4.4 第 4 条禁止的「渠道流量落到主站」（例如先给隧道加了 `tibo.pw` 的路由、还没登记，`tibo.pw` 上会显示整份主站、按主站价下单、订单记到主站）。上线前已核对应用日志近 1.5 天：这类 Host 只有 `ifconfig.me`、`icanhazip.com`、`checkip.amazonaws.com` 等扫描器，没有正常流量；
  - 其余（IP、不含点的 Host、非法 Host、`a.b.bigolab.com` 多级子域）→ 现状（观察期：主站 + 日志；严格期：null）。
- 集合加载失败（查库报错）：只要是非主站、非子域的 Host 一律**抛错**（500）。不能因为「没加载到」就把自定义域名当主站渲染——设计 4.4 第 4 条禁止回落主站。
  - 上一次成功加载的集合在 TTL 过期后，允许最多再沿用 5 分钟（记日志），降低数据库短暂抖动时的影响；
  - 从未加载成功过，就抛错。
- 随机 Host 不会逐个查库：只查一次集合。原来「只有后缀 Host 才查库，防随机 Host 刷库」这条要求仍然成立。
- 每个店面额外带上 `canonicalHost`（主域名）。`toPublicStorefront` 下发 `origin` 已经够用，客户端用 `new URL(origin).host` 比对，不新增公开字段。

## 3. 超管后台

- `upsertDomain`（`admin-tenants.ts`）与 `POST /api/admin/tenants/[id]/domains`：
  - 改用 `classifyTenantHost`，接受 SUB 与 CUSTOM 两类；
  - 新增动作 `action: 'primary'`：把某个**已启用**的域名设为主域名。在同一个事务里（先锁渠道行）完成：
    - 取消其他域名的主标记、设这一个为主；
    - `Tenant.origin = https://<host>`；
    - 写审计 `tenant.domain_primary`（diff 与 publicDiff 都是 `{ from: 旧主域名, to: 新主域名 }`）；
    - 给渠道发站内通知（类型 `TENANT_STATUS`，标题「店铺主域名已改为 https://<host>」）。
  - 不能停用主域名（400「先把其他域名设为主域名再停用」）；
  - 不能把停用的域名设为主域名；
  - 同一个 host 被别的渠道占用 → 409（现状）；
  - 所有写操作之后 `invalidateStorefrontCache()`（现状）。
- `normalizeChannelOrigin`（建站时填站点地址）：建站时仍只接受 `https://<子域>.bigolab.com`。自定义域名一律在建站之后经「添加域名 → 设为主域名」接入，这样流程只有一条。
- 渠道详情页的「域名」卡片（`tenant-detail.tsx`）：
  - 列表显示每个域名的类型（子域名 / 自定义域名）、启用状态、是否主域名，并提供「设为主域名」按钮；
  - 添加框同时接受两类域名，提示文案：「自定义域名需先在 Cloudflare 接入并给隧道加路由（见《自定义域名接入教程》），否则买家打不开」；
  - 文案里写明「设为主域名后，系统邮件与邀请链接改用新域名；旧域名的页面会自动跳转过去；买家在新域名上需要重新登录一次」。

## 4. 非主域名跳转（`src/components/storefront/primary-host-redirect.tsx`）

- 客户端组件 `PrimaryHostRedirect({ origin })`：`location.host` 不等于主域名的 host 时，执行 `location.replace(origin + location.pathname + location.search + location.hash)`。
- 挂载点：
  - `(shop)/layout.tsx`：只在渠道店面挂载，并且放在 DRAFT 暂停页判断**之后**、正常外壳里；DRAFT 暂停页本身不跳；
  - 渠道后台布局 `src/app/partner/layout.tsx`：渠道店面。
- 为什么放在客户端：Next 14 的服务端布局拿不到当前路径；middleware 的 matcher 是写死的静态四项，不覆盖前台页面。跳转只是展示层的便利，安全边界不靠它。
- 不跳的地方：
  - 所有 `/api/*`，保证打开着的旧页面还能下单、付款；
  - `(shop)` 之外的页面：收银台 `/pay/*`、收据、开票链接、退订、财务台、快捷回复——带令牌的链接照常在原域名打开。
  - 主站永远不挂这个组件。
- 防循环：`origin` 解析失败，或 host 已经相同，就什么都不做。

## 5. nginx（`nginx/nginx.conf`）

- `map $host $site_known` 在 `*.bigolab.com` 正则后面再加一条：非 IP、非 `bigolab.com` 体系的「看起来像域名」的 Host 一律按 `channel` 处理。
  ```
  ~^(?!(?:\d{1,3}\.){3}\d{1,3}$)(?:[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.)+(?:xn--[a-z0-9-]{1,59}|[a-z]{2,63})$  channel;
  ```
  - 精确匹配优先：`bigolab.com`、`www.bigolab.com`、`localhost`、`127.0.0.1` 仍是 main；`app`（不含点）和 IP 走 default（观察期当 main，严格期 444），不变。
  - 自定义域名因此自动拿到渠道那一套防护：`/admin` 404、`/api` 白名单、noindex 响应头。**以后接入新的自定义域名不用改 nginx**，要紧急下线某个域名就加一行精确的 `closed`。
  - 副作用：扫描器带的陌生域名 Host 改按 channel 处理（`/admin` 404、API 白名单、noindex），应用里没登记的一律 **404（2026-10-01 加固，第 2 节）**；`unknown_host.log` 以后只记录 IP 与不含点的 Host。这些 Host 本来就没有正常流量（N1：钱路径全走 bigolab.com；2026-10-01 核对应用日志只有扫描器）。
- 公网 IP 直连入口（容器 8080）对 `/api/domain-check` 一律 404（`location ^~ /api/domain-check { return 404; }`，第 9.2 节）：合法校验只走 Cloudflare → 隧道 → 容器 80。

## 9. 连通校验：自定义域名必须持续证明「还接在本站」（2026-09-30 终审补充）

### 9.1 为什么

- 子域名（`lulu.bigolab.com`）的 DNS 在站长手里；自定义域名（`tibo.pw`）的**注册商账号在客户手里**（接入教程写明：域名仍在客户的西部数码账号里，续费、实名、转移由客户自己管）。客户让域名过期、把 DNS 服务器改回去、或者指到自己的服务器，平台原本没有任何感知。
- 自定义域名一旦是主域名，平台生成的所有链接都指向它：交易邮件、收据 / 邀请 / 开票这些**带令牌**的链接、收银台回跳；旧子域名页面上的跳转组件也会把买家送过去。买家账号两站通用（`partner-page.ts` / `buyer-notify.ts`：两站同一账号），假登录页收走的密码在 `bigolab.com` 上同样能用。
- 改造前所有渠道 Host 都是站长 DNS 下的 `*.bigolab.com`，渠道方不可能在店铺的正式地址上放自己的页面。自定义域名打破了这一点，所以「这个域名仍接在本站」必须是一个**持续被验证**的事实，而不是设主那一刻站长的一句确认。

### 9.2 怎么证明（`src/lib/tenant/domain-verify.ts`、`src/app/api/domain-check/route.ts`）

- 平台生成随机 nonce，**走公网**请求 `https://<host>/api/domain-check?n=<nonce>`（与买家同一条路：公网 DNS → Cloudflare → 隧道 → nginx 容器 80 → 应用；不跟随 3xx，8 秒总超时，失败隔 3 秒重试一次）。
- 探测本身按「对方是恶意服务器」来写（2026-10-01 加固，`probeViaNetwork`）：
  - 先 `dns.lookup(all)`，任一地址是私网 / 回环 / 链路本地 / CGNAT / 保留段（IPv4 与 IPv6，含 IPv4 映射、NAT64、6to4 内嵌地址）→ 判失败、**不发请求**；连接只用这次检查过的地址（自带 lookup，不二次解析，防 DNS rebinding）；
  - 用 `node:https`，不用 `fetch`（`fetch` 会按 Content-Encoding 自动解压，几 KB 的 br 炸弹就能撑爆 1 GB 内存上限的主站进程）；请求头 `accept-encoding: identity`，响应 content-encoding 非空且不是 identity → 失败；content-type 必须是 `application/json`；content-length > 4096 → 失败；body 流式读取，累计超过 4096 字节立即断开判失败；8 秒总超时覆盖解析、连接、TLS 与读 body（慢速滴灌同样失败）。
- 失败原因分两层：**归类原因**（解析不到 / 指向了非公网地址 / 连接失败 / 证书错误 / 返回内容不符；另有「本站校验出错」只在本站自己算不出期望值时出现，例如 `JWT_SECRET` 缺失——期望值在发请求**之前**算，算不出就不发请求、不重试，免得应答端同样因缺密钥回的 503 被记成客户域名「返回内容不符」）进渠道站内通知与站长群告警；**技术细节**（HTTP 状态码、错误码）只在超管后台（设主失败提示、渠道详情校验状态）出现。
- 应答端只在渠道店面上应答（主站、未知 Host、停用的域名 404；渠道任何营业状态都应答），返回 `{ proof }`：`HMAC-SHA256(domain-verify 密钥, "v1|host|渠道代号|nonce")`。密钥从 `JWT_SECRET` 派生（`tenant/crypto` 新增用途 `domain-verify`），不新增环境变量。
  - 客户自己的服务器算不出 proof；把请求转给本站却换成别的 Host，proof 绑定的 host 对不上。
  - 原样反代到本站（Host 不变）能通过——那时流量仍由本站处理，属于接受的残余风险（9.5）。
- nginx 渠道 `/api` 白名单加 `domain-check` 一项（余额、充值、短信接码仍不在白名单里）。
- nginx 公网 IP 直连入口（容器 8080）对 `/api/domain-check` 一律 404：否则客户把域名 A 记录直接指到服务器公网 IP、绕开站长的 Cloudflare，校验照样通过——那已经不是「域名在站长的 Cloudflare 里」了。

### 9.3 什么时候校验

- **设为主域名前**（`setPrimaryDomain`，只对 CUSTOM）：事务外先做前置检查（未登记 404、停用 400），再校验；不通过 → 400（`reason: DOMAIN_NOT_VERIFIED`），什么都不改。通过后在设主的同一事务里写一条新鲜的校验记录。
  - 本渠道必须还有**启用中的子域名**（失联时要退到它），否则 400。相应地，主域名是自定义域名时，最后一个启用中的子域名不能停用（`upsertDomain` 400）。只有子域名的渠道（lulu、shop）不受这两条影响。
  - 对**已经是主域名**的自定义域名再调一次 = 立即重新校验并刷新记录（后台「重新校验」按钮），`changed=false`、不写审计；原本处于降级状态的立即解除（不必等两趟），并推「已恢复」（站长群 6 小时节流与 cron 共用；渠道通知按 `told` 对齐，不节流，见 9.4）。
- **cron 每 10 分钟复验**（`POST /api/cron/tenant-domains`，x-cron-secret；crontab 第 3、13、23… 分）：主域名是自定义域名、且没有停业（TERMINATED）的每个渠道各校验一次。子域名渠道不发任何请求；已停业的渠道不再复验、也不告警。
- **并发**：一趟探测最长十几秒，期间站长可能点了「重新校验」或换了主域名。cron 的写入是条件写入：锁渠道行（与设主同一把锁），确认主域名仍是这个 host、渠道没停业、校验记录与开跑前读到的逐字相同，才写入；否则放弃本次写入（下一趟再来），不拿旧 host / 旧计数覆盖新结果。站长手动校验通过的写入不做条件判断（刚当场验证过，且持同一把锁串行）。

### 9.4 记录与降级（`src/lib/storefront/domain-health.ts`，不改 schema）

- 记录存 `settings` 表，一个渠道一行：key = `tenant_domain_health:<tenantId>`，value = JSON `{ host, okAt, checkedAt, fails, oks, down, reason, detail, downAlertAt, upAlertAt, told }`（`reason` 是归类原因，`detail` 只给超管；`told` = 渠道最近一条通知说的状态 `down` / `up` / `null`，没有这个字段的旧记录按两个告警时间戳推断）。
- **健康** = 记录的 host 等于当前主域名、不在降级状态（`down`）、最近一次成功在 40 分钟内、连续失败趟数 < 2。没有记录、记录损坏、host 对不上、过期，一律不健康（fail closed）。
- **状态抖动**（2026-10-01）：降级仍是连续两趟失败；恢复改为**连续两趟成功**（`down` 是个闩，成功一趟不解除），防晚高峰时通时断的域名每 10 分钟在自定义域名与子域名之间来回跳。站长手动「重新校验」通过立即解除。
- 店面解析（`resolve.ts` 的 `toChannelStorefront`）：只在 `Tenant.origin` 是自定义域名时读这份记录（每渠道缓存 30 秒，`invalidateStorefrontCache()` 一并清掉）。不健康时，店面的 `origin` / `canonicalHost` 改用该渠道**启用中的第一个子域名**：
  - `tenantOrigin` / `tenantMailOpts` / 邀请链接 / 渠道通知里的「前往渠道后台」/ metadataBase 改走子域名；
  - 旧子域名不再跳走；自定义域名上的页面（如果还有人到得了）跳回子域名；
  - **库里的 `Tenant.origin` 不动**，恢复健康后自动切回。
  - 子域名渠道不经过这一步，不多查一次库——不变量第 2 条不受影响。
- 告警：cron 发现「刚降级」→ 平台企业微信告警 + 渠道站内通知「自定义域名 xxx 暂时无法访问」；恢复时各推一次「已恢复」。
  - **站长群**：同一域名的降级 / 恢复告警各自 6 小时内最多一次；仍在降级中、距上次降级告警满 6 小时、**且本趟仍失败**，再提醒一次（降级中第一趟通过时 `down` 还没解除，但不能在刚通过的时刻推「仍未恢复」）。
  - **渠道站内通知不节流、只跟状态走**（2026-10-01 复核）：记录里的 `told` 记住渠道最近一条通知是「暂时无法访问」还是「已恢复」，实际状态与它不一致才发一条。否则「降级→恢复→6 小时内再降级」时第二次降级被节流，渠道最新一条通知是「已恢复」、实际却已改走子域名。刷屏上限由「两趟」滞回兜住（一来一回至少 40 分钟）。
  - 通知与告警只写归类原因，不写 HTTP 状态码、错误码。
- 降级但本渠道已没有启用中的子域名（理论上设主与停用子域名都拦了，脏数据才会出现）：只停止跳转（`canonicalHost` 置空），链接仍用自定义域名，告警里写明「请尽快处理」。
- cron 停摆超过 40 分钟，记录过期 → 同样降级（没人复验，就不能再假定域名还在我们手里）；`resolve.ts` 发现这种情况时给站长群告警一次（每渠道 6 小时最多一次，不阻塞请求，失败只记日志），提示检查 cron 容器与 `/api/cron/tenant-domains`。这种降级不置 `down`：cron 恢复后一趟成功即切回。

### 9.5 接受的残余风险与约定

- **这套校验防的是「意外失联」**：域名过期、客户改了 NS、解析被指到别处——签名对不上或连不上，就退回子域名。
  **它防不住有意作恶的 DNS 控制者**：域名的 DNS 在客户手里，客户可以在自己的 Cloudflare 边缘（或任何反代）按路径、来源选择性转发——`/api/domain-check` 原样转给本站，其余页面给自己的服务器——HTTP 层面无法区分。后者只能靠合作约定（下面那条）与**站长随时可以把主域名设回子域名、停用该域名**兜底。

- 客户**原样反代**到本站（Host 不变）能通过校验：流量仍由本站处理，但经过了客户的服务器。无法用 HTTP 校验排除，靠协议约束。
- 两次复验之间（最长约 20 分钟 + 30 秒缓存）如果域名被指走，这段时间内发出的邮件、跳转仍指向它。
- 约定写进接入教程（给客户）：**域名是主域名期间，不得在未通知站长的情况下修改 DNS 服务器、解析，或让域名过期**；不用了先通知站长切回子域名，再改 DNS。
- 站长侧：Cloudflare 上该站点不要让 `/api/domain-check` 吃到质询，否则服务端校验失败、设不了主域名。**免费版的 Bot Fight Mode 不能用 WAF 自定义规则跳过，只能整个关掉**（Security → Bots）；WAF 托管质询、自定义规则可以给这个路径加跳过。隧道离线时 Cloudflare 回 **HTTP 530（error 1033）**。
- 站长在自己电脑上 curl 通过，不代表服务端（阿里云出口 IP）也能通过：Cloudflare 的质询与限速看来源。**以后台「重新校验」（服务端发起）的结果为准。**
