# 下单有奖（抽奖）

> 2026-09-24 上线。**改抽奖相关代码前先读这份。** 它发的是真金白银的优惠券，
> 一个校验漏掉就是「无限抽奖」或「替别人把奖抽掉」。

---

## 一、它是什么

后台「订单与营销 → 抽奖管理」开启活动后，**活动期间下的每一张订单**（货款达到参与门槛）
都附带一次抽奖机会，付款后在「我的订单」里「与客服在线沟通」后面出现一个红包按钮
「下单有奖」。抽过之后按钮变成拆开的红包，文字显示「已中奖 / 未中奖」。

奖项两类：

| 类型 | 中奖后 | 兑现 |
|---|---|---|
| `COUPON` 优惠券（满减 / 商品券，面额、门槛、有效天数可配） | 自动发到买家「我的优惠券」 | 买家下次下单自己用 |
| `CUSTOM` 自定义奖品（文字描述 + 兑奖方式） | 出现在「我的优惠券 → 我的奖品」，企业微信推送 | 线下兑现，后台「标记已兑现」 |

**不设中奖数量，只按概率。** 所有启用奖项的概率之和 ≤ 100%，余下就是「未中奖」。

## 二、四条不可动摇的规则

### 1. 资格在建单那一刻确定，而且和订单同一个事务

`/api/orders` POST 在 `prisma.$transaction` 里先建订单、再调
`createEntryIfEligible(tx, cfg, order)`：活动开启且 `amount ≥ minOrderAmount`
（按分比较，`amount` 是不含税货款）就建一行 `lottery_entries(state=PENDING)`。

- **活动关闭期间下的单永远没有这一行**，事后开启活动也不补。这就是
  「后台抽奖功能未开放期间下单的，则没有抽奖按钮及功能」。
- **关闭活动不收回已发出的资格。** 活动期间下了单、还没来得及抽的，关闭后照样能抽 ——
  买家是看到活动才下的单。要止损请把奖项停用或调低概率，而不是指望关开关。
- 同一个事务：「订单建好了、资格行没建上」这种状态不存在。分两步写的话，进程在中间崩一次，
  这张单就永远没有按钮，而买家是冲着活动来的。

### 2. 一单一抽靠数据库，不靠「先查后写」

- `lottery_entries.order_id` 是 **UNIQUE**：一张订单最多一行资格。
- 抽奖时在事务里 `updateMany({ where: { id, state: 'PENDING' } → DRAWN })`，
  **只有把 PENDING 翻成 DRAWN 的那一次**才发奖。两个标签页同时点、连点十次，
  其余请求拿到的都是同一份结果（`alreadyDrawn: true`），不会报错，也不会多发。
- 发券、奖项计数与翻状态在**同一个事务**里：发券失败整个回滚成 PENDING，买家可以重试。
  不会出现「显示已抽、奖却没发」或「奖发了、还能再抽」。

`scripts/itest-lottery.ts` 实测：同一订单并发 12 次 → 恰好 1 次真正抽奖、只发 1 张券；
把 coupons 表临时改名制造发券失败 → 资格回滚为 PENDING，恢复后重试正常发奖。

### 3. 以订单号为校验标准，但订单号不是凭证

订单号**不是秘密**：它出现在交易邮件、企业微信推送、客服聊天里。所以
`POST /api/lottery/draw { orderNo }` 的校验是：

| 检查 | 挡的是什么 |
|---|---|
| 必须登录，且订单 `userId` = 当前用户 | 拿别人的订单号替他把奖抽掉 |
| 「订单不存在」与「不是你的订单」**同一句话、同一个 404** | 拿接口试探别人的订单号是否存在 |
| 订单号格式 `^[0-9A-Z]{8,32}$` | 注入与超长输入（查询本身也是参数化的） |
| 必须有 `lottery_entries` 行 | 活动关闭期间下的单 |
| `payStatus = PAID` 且 `deliveryStatus ≠ CANCELLED` | 建一堆不付款的订单无限抽 |
| 资格 `state ≠ VOID` | 已退款的订单 |
| 账户 `status = 1` | 被禁用的账户（`getCurrentUser` 现在也会把禁用账户当作未登录） |
| 事务内再查一次订单状态 | 与后台「取消 / 退款」并发 |
| 每用户每分钟 20 次 | 刷接口 |

**选奖在服务端**，用 `crypto.randomInt(0, 10000)`，客户端除了订单号什么都传不进来。

### 4. 概率用整数万分比，不用浮点

`LotteryPrize.rateBp`：1 = 0.01%，10000 = 100%。后台录入的百分比文本按**字符串**解析
（`parseRateToBp('12.5') → 1250`），不是 `parseFloat × 100`（`1.005` 会被浮点算错）。

选奖：奖项按 `sortOrder, id` 在 `[0, 10000)` 的数轴上首尾相接各占 `rateBp` 格，
随机数落在哪一格就是哪个奖，落在所有奖项之外就是未中奖。
`scripts/check-lottery.ts` **穷举全部 10000 个随机数**，断言每个奖项被选中的次数恰好等于
它的 `rateBp` —— 不是抽样统计的「大概对」。

合计 ≤ 100% 在保存奖项时校验（事务内读全部奖项再算）。两个管理员同时改奖项理论上仍可能
合计超过 100%，这时 `pickPrize` 按顺序截断，排在后面的奖项实际概率变小，不会越界。

## 三、奖品怎么落库

### 券奖项：一次中奖一个「单张批次」

`CouponGrant` 有 `@@unique([couponId, userId])`（每账户每批次一张）。如果一个奖项对应一个
共用批次，**同一个人两单都抽中同一奖项时第二张会撞唯一约束**。放宽那条约束要 DROP 索引，
而 `scripts/deploy.sh` 写死了 `--accept-data-loss`，本项目明令避开这类 DDL。

所以每次中奖建一个 `Coupon`：`source='LOTTERY'`、`total=1`、`claimed=1`、
`code='lt-<16位随机十六进制>'`，再给中奖人建一张 `CouponGrant`。之后它就是一张普通的券，
走完全相同的锁定 / 核销 / 释放 / 过期流程（`lib/coupon.ts` 一行没为它改）。

`source` 非空的批次：

- **领取接口与 `/coupon/<code>` 页一律当作不存在**（否则知道 code 的人就能领走别人的奖）
- 后台券列表默认不显示（否则被每次中奖刷屏），筛选「抽奖发放」可以看到

中奖券同样受「走内推链接的订单不能用券」约束 —— 那是全站定价口径，不为抽奖开例外。

### 自定义奖品

只在 `lottery_entries` 里记快照（`prizeName` / `prizeDetail`），`fulfillState=PENDING`，
企业微信推送「有人中奖」。线下兑现后在后台「抽奖记录」里点「标记已兑现」（CAS，只能从 PENDING 翻）。

### 快照

`prizeName / prizeType / prizeDetail(JSON)` 在中奖时拷下来。之后奖项改名、改面额、被停用，
都不影响已中奖记录和买家看到的内容。有中奖记录的奖项**只能停用、不能删除**。

## 四、退款与取消

订单 `payStatus → REFUNDED`（目前只有 API 能写），或**已付款的订单被后台改成「已取消」**
（后台没有退款按钮，线下退款后通常就是这么操作的），都会调用 `voidLotteryForOrder`：

- 还没抽 → 资格作废（VOID），之后再也抽不了。注意：之后把订单改回未取消，作废的资格不会恢复
- 抽中了券 → **这张券所在的单张批次置为 ENDED**，券还没用（AVAILABLE）的直接作废。
  券正挂在另一张待付款订单上（LOCKED）时券本身不动：那张订单付了款照常核销（付款核销不看批次状态，
  「原价 − 优惠 = 实付」对得上）；那张订单被放回的话，建单时会因「该券所属活动已结束」被拒。
  只作废 AVAILABLE、不结束批次的话，LOCKED 的券被放回后就「复活」了 —— 复查时抓到过这个漏洞
- 已经用掉（USED）的券不动 —— 那是另一笔订单的账
- 自定义奖品未兑现 → 标记作废

**与抽奖并发：** 退款写库与买家拆红包可能同时发生。`voidLotteryForOrder` 的「PENDING → VOID」没抢到时
会重读一次，按已抽的路径把刚发出的奖收回（`scripts/itest-lottery.ts` 覆盖了 LOCKED 的情形）。

## 四·补 · 奖池为空

所有奖项都停用（或概率都为 0）时，`drawForOrder` 直接返回 409「奖池暂未开放」，**资格原样保留**，
不会记一次「未中奖」替买家把机会用掉。买家弹窗里「開」按钮同样不可点。
所以「把奖项全部停用」只能暂停抽奖，不能作废已发出的资格；要控成本请停用高价值奖项或调低概率。

## 五、代码在哪

| 文件 | 职责 |
|---|---|
| `src/lib/lottery.ts` | 纯函数：概率解析、选奖、资格判定、奖项校验、买家视图。**不碰数据库** |
| `src/lib/lottery-server.ts` | 活动配置（Setting `lottery_config`）、`createEntryIfEligible`、`drawForOrder`、`voidLotteryForOrder` |
| `src/app/api/lottery/draw` · `info` · `mine` | 买家接口 |
| `src/app/api/admin/lottery/*` | 后台：配置、奖项、抽奖记录（路由内独立 `requireAdmin`） |
| `src/app/admin/lottery/page.tsx` | 后台页面 |
| `src/components/lottery/*` | 红包按钮与抽奖弹窗 |
| `scripts/check-lottery.ts` | 纯函数断言（含 10000 个随机数穷举） |
| `scripts/itest-lottery.ts` | 数据库集成测试（并发、回滚、越权、退款）。**只能对库名含 dev/test 的一次性库跑** |

## 六、合规提醒（站长留意）

《反不正当竞争法》对有奖销售的要求：奖的种类、兑奖条件、奖金金额或者奖品、兑奖时间和方式等
信息要明确；**最高奖金额不得超过五万元**。抽奖弹窗会原样展示后台「活动规则」和奖池清单，
请在活动规则里写清兑奖方式与期限。
