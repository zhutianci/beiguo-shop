# 短信接码与站内余额 · 部署说明（按包分节）

> 设计契约见 `docs/短信接码-设计.md`（先读第 0 章、附录 B；各包范围见 §11 分包表、§6.6 编号清单）。
> 每个包一节，只写本包的差异；通用步骤（回滚标签 → 备份校验 → 预览 DDL → 闸门 → 执行审过的 SQL → 阳性对照 → 构建 → 只重启 app → cron）
> 照 §11「上线步骤」与交接文档第五、十一、十四节。**服务器三条铁律**：远程命令 base64 传、耗时任务后台跑、**绝不跑 `docker system df`**。

## B0 余额底座（兼容改造，不给买家加新功能）

### 一、这一包做了什么

- **余额分两格**：`users.balance` 原样作「返现余额」（可提现，含义不变）；新增 `users.topup_cents` 作「充值余额」（不可提现，默认 0 = 历史余额全部算返现，零回填）。
- **唯一记账函数** `src/lib/wallet/ledger.ts` 的 `postInTx`：一条带两个条件的更新同时改两格 → 事务里读回 → 一事件一行流水一个 `biz_key`。
  推荐返现结算（`lib/referral.ts`）与后台调余额 / 提现（内推管理「提现/调整」，`api/admin/referrals/balance`）改走它，**入参、金额、note 格式、页面操作与改造前相同**，流水多写 `topup_after_cents`、`biz_key`（`adj:<请求号>`）。
- **预扣模块** `lib/wallet/hold.ts`（H1–H4，给 S2 用；B0 没有任何调用方会产生预扣）。
- **钱包页 `/wallet` 按两格重做**（可用余额 = 两格合计；充值 / 返现两行；四个累计数按流水类型算；分类筛选）。
  B0 时 `canUseForJiema=false`（`sms_config` 还不存在）：页面保留旧口径「余额暂不能直接用于支付订单」，没有 [充值]、[去接码]、开票提示。
  个人中心卡片显示两格总额（B0 时 = 改造前余额）；推荐面板写「返现余额 ¥x（可提现）」。
- **后台「客户 → 余额与充值」`/admin/wallet`**：负债看板、用户余额、流水（CSV）、充值单 / 预扣（B1 / S2 前为空）、对账、设置（`wallet_config`）、调整弹窗
  （返现 + / 提现 / 充值格补偿 / 充值退还（必填支付宝流水号）/ 返现扣回；**不能记 LATEPAY**）。
- 后台用户列表「余额」列显示两格总额（悬停看拆分）；用户详情与流水详情按两格显示，**HOLD 等流水不再被当成返现流水去核对**。
- **每日对账** `/api/cron/wallet-reconcile`（W1–W9，只读，不一致推 `wallet.alert`，报告写 `settings.wallet_reconcile_last`）。
- **构建前检查**（`scripts/check-tenant-boundary.mjs`，`npm run build` 的 prebuild）新增规则 16（写余额只经 ledger、预扣只经 hold）、规则 17（依赖方向）。
- 企业微信新增事件 `wallet.alert`（默认推）、`wallet.topup`（可选，NOTIFY_EVENTS 不显式列出就不推；B1 才会触发）。

### 二、数据库变更（ADD COLUMN ×4、CREATE UNIQUE INDEX ×1、CREATE TABLE ×1；零 DROP / MODIFY）

```sql
ALTER TABLE `balance_logs` ADD COLUMN `biz_key` VARCHAR(64) NULL,
    ADD COLUMN `topup_after_cents` INTEGER NULL,
    ADD COLUMN `topup_delta_cents` INTEGER NOT NULL DEFAULT 0;
ALTER TABLE `users` ADD COLUMN `topup_cents` INTEGER NOT NULL DEFAULT 0;
CREATE TABLE `balance_holds` ( … `order_id` 唯一、(state, held_at)、(user_id, created_at) 两个索引 … );
CREATE UNIQUE INDEX `balance_logs_biz_key_key` ON `balance_logs`(`biz_key`);
```

（上面是本地 `prisma migrate diff` 的实际输出顺序，与设计 §5.6 列的语句逐条等价。）表尾追加列，MySQL 8 走 INSTANT，不锁表、不拷表。
**旧镜像跑在新库上不受影响**：旧代码写流水时新列取默认值。

`settings` 会多出：`wallet_config`（种子写入）、`wallet_reconcile_last`（对账写入）、可选的 `wallet_reconcile_exempt`（豁免名单）。

### 三、部署顺序（在 §11 通用步骤上的差异）

```bash
# 0) 回滚标签（build 之前）+ 1) 备份并校验 Dump completed —— 照通用步骤

# 2) 预览 DDL（交接文档第五节的临时容器命令，--script）→ 存成 /tmp/b0-preview.sql，检查字节数 > 0

#    期望输出最后一行：✅ 闸门通过，且与本期预期清单逐条一致（钱包 B0：…）
#    预期清单（6 项）：
#      COLUMN balance_logs.biz_key / COLUMN balance_logs.topup_after_cents / COLUMN balance_logs.topup_delta_cents /
#      COLUMN users.topup_cents / INDEX UNIQUE balance_logs.balance_logs_biz_key_key / TABLE balance_holds
#    多一项、少一项、默认值不是 0、缺索引 → 退出码 1，停手

# 4) 执行闸门审过的 SQL（或 db push --skip-generate，不带 --accept-data-loss）
# 5) 阳性对照（三条都要看到）
#    SHOW CREATE TABLE users;         → `topup_cents` int NOT NULL DEFAULT '0'
#    SHOW CREATE TABLE balance_logs;  → topup_delta_cents DEFAULT '0'、topup_after_cents、biz_key，以及 UNIQUE KEY `balance_logs_biz_key_key`
#    SHOW CREATE TABLE balance_holds; → UNIQUE KEY `balance_holds_order_id_key`、两个 KEY

# 6) 种子：wallet_config 出厂值（可重复执行；已存在就不动）
mysql … --default-character-set=utf8mb4 beiguo_shop < scripts/ops/wallet-b0-seed.sql     # 最后一条 SELECT 恰好 1 行

# 7) 旧账核对（只读）并存档；把 ① 的名单与差额逐个列给站长过目
mysql … --default-character-set=utf8mb4 --table beiguo_shop < scripts/ops/wallet-b0-legacy-check.sql \
  > /opt/beiguo/backups/wallet-b0-legacy-check-$(date +%Y%m%d%H%M).txt
#    ② 两条计数都应为 0；③ 是改造前的余额合计（上线后「余额与充值」看板的负债应与它一致，B0 没有预扣）
#    ⑤ 负余额的用户（旧代码并发提现可能扣成负数；① 查不出「余额 = 流水 = 负数」的人）应当没有输出。有的话同样逐个列给站长，二选一：
#       a) 站长同意补平 → 上线后到「余额与充值 → 调整余额 → 返现余额 +」补到 0（写 ADJUST 流水，恒等式不破）；
#       b) 不处理 → 和第 8 步剔除的用户一起写进 wallet_reconcile_exempt（W1 / W2 / W8 跳过、报告列出），否则 W2 从上线第一天起天天告警

# 8) 「历史对齐」流水（站长 Q10 已同意补）：只在 ① 有输出、且站长逐个同意之后做
#    编辑 scripts/ops/wallet-b0-align.sql 顶部的 SET @ids = '12,34'（站长同意补的用户 id），再执行；留空 = 什么都不写
#    只写流水（type=ADJUST、biz_key=migrate:u<id>、note「历史余额对齐（B0 上线）」），不改 users.balance；可重复执行
#    站长剔除（不补）的用户：取消注释脚本末尾第 ④ 段，写进 wallet_reconcile_exempt 豁免名单（W1 / W2 / W8 跳过、报告列出）

# 9) 构建（先征得站长同意临时放开 swap，后台跑、轮询到真正结束）→ 只重启 app → 核对镜像 id
#    推送前本地已跑 npx tsc --noEmit 零错误；prebuild 的 check-tenant-boundary 含新规则 16 / 17

# 10) crontab 加一行（已在 cron/crontab 里），然后 up -d --no-deps --force-recreate cron，再 cat /etc/crontabs/root 核对
#     10 3 * * * curl -fsS --max-time 240 -H "x-cron-secret: $(cat /run/cron_secret)" "http://app:3000/api/cron/wallet-reconcile" >> /var/log/cron.log 2>&1
```

- **新环境变量**：无。若生产 `NOTIFY_EVENTS` 配了白名单，要把 `wallet.alert` 加进去（对账不一致、配置读坏都走它）；`wallet.topup` 可选，B0 用不到。
- **开关初值**（`wallet_config` 种子）：`balancePayEnabled=true`、`topupEnabled=false`、`topupAudience=ADMIN_ONLY`、档位 ¥5/10/15/20/50、单笔 ¥1–1,000、`pendingTopupPerUser=2`、`latepayAuto=true`。
  B0 时这份配置只影响后台「设置」的显示与 `canUseForJiema`（`sms_config` 不存在 → 恒为 false）。**不要建 `sms_config` 行**（S1 的事）。
- **充值开关在 B0 打不开**：代码常量 `TOPUP_AVAILABLE=false`（`src/lib/wallet/config.ts`），「设置」里充值开关与受众置灰、保存 `topupEnabled=true` 会 400，
  钱包页不出 [充值]；看板显示「充值：○ 未上线」。**B1 交付时把常量改成 true**（B1 的部署说明里再写开放步骤）。
- **读不到 `wallet_config`**（行不存在 / JSON 坏 / 校验不过）时：充值、新单选余额、迟到付款自动退入按关闭处理（fail-closed，不回落出厂值），推一次 `wallet.alert`
  （行不存在也推；进程内 1 小时节流）；释放、确认、退款、提现、返现入账不读它。后台看板会红字提示，到「设置」点「填入出厂值」再保存一次即可——
  「设置」按库里那一行自己的版本号（`storedVersion`，校验不过的行也给）做乐观并发，坏掉的配置总能从页面修好，不用登服务器改库。
- **每日对账**在一个只读事务里跑（一致性快照，与白天的记账并发也不误报）；日常逐行只核近 48 小时有变动的记录，**每周日（北京时间）全量**；
  预扣等式与全站两格合计每天都全量（SQL 聚合）。

### 四、冒烟（上线后立刻做）

1. **钱包页总额不变**：找一个有返现余额的真实用户（或站长自己的号），`/wallet` 的「可用余额」= 改造前的余额；充值余额 ¥0.00；累计返现、已提现与流水一致；个人中心卡片同一个数。
2. 未登录 `GET /api/account/wallet` → 401；渠道域名（lulu）`GET /api/account/wallet`、`/wallet` → 404。
3. `GET /api/cron/wallet-reconcile` 不带密钥 → 拒绝；带 `x-cron-secret` → 200，`failed` 为空。
4. **推荐返现真实入账一次**（等一笔推荐订单完成，或看最近一条）：`balance_logs` 那条 `type=REFERRAL`、note「订单#<id> 内推返现」、`topup_after_cents` 不为空（=0）、`biz_key` 为空。
5. **后台提现一次**（内推管理「提现/调整」填负数，或「余额与充值 → 调整余额 → 返现余额 −」）：流水 `type=WITHDRAW`、`biz_key=adj:<请求号>`、`topup_after_cents` 有值；
   断网重试（同一请求号再点一次）提示「这笔此前已记账成功，本次未重复记账」，只扣一次。
6. 后台用户详情点开一条**返现流水**与一条**调整流水**：详情都不报错；返现流水仍有「关联订单 / 返现记录」核对，调整流水没有「没有找到对应的返现记录」之类的警告。
7. 「余额与充值 → 对账 → 全量跑一次」：W1–W9 全部 ✓（W1 若报历史用户，说明第 8 步漏补或该补豁免）。
8. 「余额与充值」看板负债 = 第 7 步 ③ 的余额合计；「用户余额」按总余额排序正常；流水导出 CSV 用 Excel 打开中文不乱码。
9. 「余额与充值 → 调整余额」选「充值余额 −（充值退还）」不填流水号 → 提示必填；接口直接传 `kind: "LATEPAY"` → 400。
10. 「余额与充值 → 设置」：标题显示「版本 1」；充值开关与受众是灰的；看板一行写「充值：○ 未上线」。
11. 流水导出 CSV：提现那条的「返现格变动」在 Excel 里是数字（右对齐、能求和，不是 `'-50.00` 文本）；「时间（北京）」列是北京时间。
12. 内推管理「提现/调整」填一段 200 字以上（≤255）的备注照常记账（与改造前一致）。

### 五、回滚

- **B0 单独回滚（换回旧镜像）是安全的**：新列、新表留在库里，旧代码不认识也不碰；旧代码写流水时新列取默认值，恒等式照样成立。
- 回滚后若再上 B0：不用重跑 DDL；`wallet-b0-seed.sql`、`wallet-b0-align.sql` 都可重复执行。
- B1（充值）开放之后原则上不再回滚到 B0 之前（见设计 §5.6）。

## B1 充值与载体订单框架（默认关，仅管理员可见）

### 一、这一包做了什么

- **余额充值**（`/wallet/topup` 页面、`GET|POST /api/wallet/topup`、`GET /api/wallet/topup/[orderNo]`）：档位 ¥5/10/15/20/50 + 自定义整数元（出厂 ¥1–1,000，按 `wallet_config` 的 `minCents` / `maxCents` 下发与校验，文案按配置拼）；**不设充值余额总额上限**；
  同一买家待支付充值单 ≤2 张；下单事务锁住用户行（幂等 clientToken、同金额复用、待支付张数都在锁内）；同一请求里发起收款单并照 `pay/vmq/create` 事后复核，失败就当场关单。
  充值单 = 挂 **TOPUP 载体商品**的普通订单（下架、价格 0），商品名「余额充值 ¥50.00」，内部 `remark` 形如 `topup|ct:<token>|terms:<版本>|return:<回跳>`（`buyerRemark` 为空）。
- **到账入账**：`fulfillOrder(orderId, { via: 'VMQ', vmqId })` 在翻 PAID 的**同一事务**里给充值格加上**那张收款单的实付**（含识别尾差）、写 TOPUP 流水（`topup:<orderId>`），订单直接 DELIVERED；
  Payment 一行 ALIPAY（金额 = 充值额、`tradeNo` = 收款单号）；**不加载体商品销量**；事务之后什么都不做（不推「订单已支付」、不发邮件、不开票、不结算返现）。
  载体单的付款 CAS 额外要求「未取消」——**关了的充值单永远不再翻成已付款**（D41）。
- **迟到付款退入余额**（`lib/wallet/latepay.ts`）：关单之后才到、关单瞬间才到、重复付的钱，一律按「待核实条目」的**实收**退进买家充值格（LATEPAY 流水）。
  能确定归属的**自动退**（`closed_while_matching`、`duplicate_payment`、以及按收款单表验证唯一的「付完马上取消」`no_pending_match`，`wallet_config.latepayAuto` 控制，出厂开）；
  其余在 **`/admin/vmq` 待核实列表的「退入买家余额」**里：看候选订单 → **必填支付宝交易号**（16–32 位数字）→ 退入（同一交易号只能退一次，写审计 `wallet.latepay`）。
  涉及接码 / 充值订单的条目「标记已处理」必须二选一：「线下已原路退回支付宝」/「核实不是新到账」（条件更新，不会覆盖退入事务写下的标记）。
  这两类订单的**「补单」按钮会被拒绝**。充值单退入后不写订单留言，买家在钱包页顶部横幅与流水「付款退回余额」里看到。
- **收银台**：状态接口对充值单多给 `next=/wallet?topup=<单号>`，付款成功跳钱包页（「充值成功，¥x 已到账」+「暂不支持开票，可联系客服开票处理」，30 秒没到账改提示「到账确认较慢…」）；
  充值单的**过期页**不再「返回重新发起」，改为「如果你已经付了款，请不要再付…」+ [去我的余额] [联系客服]。
- **口径排除充值单**（D40：充值是预收款、不计营收）：我的订单（及页头未读红点）、首页实时成交（两种载体都排除）、仪表盘总收入 / 总订单（改为「已付款订单数」）/ 按站拆分、
  会员累计消费、个人中心累计消费、营销「已购」与归因、后台用户详情、后台订单列表「流水合计」。仪表盘多一格「今日充值入账（不计营收）」。
- **载体单保护**：通用订单后台对充值单（与将来的接码单）整单只读（保存 → 409）；`/api/orders/[id]/invoice`、`/receipt` 与邮箱查订阅等票据入口对载体单一律 409「暂不支持开票，可联系客服开票处理」；
  商品后台不能上架 / 改价 / 改发货方式 / 删除载体商品（列表标「系统载体」）。

改了什么（行为变化，冒烟时留意）：
