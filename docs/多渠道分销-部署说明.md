# 渠道分站（P0）部署说明

> 配套：`docs/多渠道分销-设计.md`（下称「设计」，章节号以它为准）第 15 章、`docs/多渠道分销-实施分包.md` 第 11、12 节。
> 本文只写**怎么上线、怎么验、怎么退**；为什么这样设计看设计文档。命令默认在服务器 `/opt/beiguo/beiguo-shop` 下、root 执行。
>
> **通用铁律**（与以往各次部署相同）：
> - 远程命令用 Bash + base64 传递；耗时任务一律后台跑、轮询日志，不在前台等。
> - **绝不跑 `docker system df` / `docker builder du` / `du -sh /var/lib/docker/*`**——会把 dockerd 撑爆、整机两个站一起掉（交接文档第六节第 3 条）。
> - 每一步都用阳性对照验证（「查到了期望的东西」，而不只是「没报错」）。
> - **任何时候不得用旧 commit 的 schema 跑 `db push`，也不要跑 `scripts/deploy.sh`**（它写死了 `--accept-data-loss`，会删掉整本渠道账）。

## 〇、上线分三段，各自独立、顺序不能反

| 段 | 做什么 | 对外效果 | 何时做 |
|---|---|---|---|
| **A 应用发布** | DDL → 种子 → 构建新镜像 → 只换 app | 主站照常（代码**休眠**：`CHANNELS_ENABLED` 不开，任何 Host 都按主站处理、不查 `tenants` 表）；后台多了「来源站」列、「渠道」菜单等（见第一节） | 先做；可以分批做多次，每次都走 A 段 |
| **N nginx 发布** | 按 Host 分流；lulu 指向**静态停业页** | 主站不变；公网 lulu 只看到停业页 | A 段稳定后单独一次 |
| **G 开业** | 打开应用开关 → nginx 把 lulu 改 `channel` → DRAFT 验收 → ACTIVE | lulu 开门营业 | N 段观察期内即可，站长定日子 |

为什么 N 必须在 G 之前、且 lulu 先 `closed`：应用休眠期如果 lulu 的请求进了应用，会渲染整份主站、按主站价下单、订单记到主站（设计 4.4 第 4 条禁止的「回落主站」）。停业页是纯静态文件，不进应用。

## 一、发布说明（主站在休眠期也能感知到的变化，逐条告诉站长）

设计 4.10 列出的可感知变化，外加各包实施时新增的几条：

1. 后台订单 / 用户 / 卡密 / 发票 / 收据 / 财务台 / 快捷回复 / 到账 / 统计多了「来源站」列与筛选（休眠期全部是「主站」）。
2. 根布局改为动态渲染：about、terms、login 等页面不再构建期预渲染，每次请求都渲染（观察内存，见第七节 M12）。
3. 新登录签发的 JWT 带 `aud=main`；**老 token 照常有效**（`JWT_LEGACY_TOKENS` 默认 accept，上线 30 天后改 `reject`）。
4. 仪表盘「总收入」口径不变（改造前就已排除「已付但已取消」的订单；上线前复核更正了本条原先「数字可能变小」的说法），只是多了按来源站拆分（休眠期只有「主站」一组，与总收入相等）。
5. 后台订单保存（改价、改状态）改成 CAS：**打开订单弹窗之后**这张单被改过（另一位管理员保存，或买家到账、自动发卡、接码往备注里追加记录等系统写入），再保存会收到 409「订单已变化，请刷新」——关掉弹窗重新打开即可（弹窗打开时会取最新状态作为基线；终审修正后不再以「列表加载时」为基线）。
6. 标已付弹窗多一个「实收金额」（主站单选填；填了才会补建收款记录）。
7. 外部订单「清空」只清主站的行（休眠期全部行都是主站，实际无变化）。
8. 卡密批量「改售价」拒绝修改渠道单的卡（休眠期没有渠道单，实际无变化）。
9. 后台把用户提权为 ADMIN 时校验他不是渠道成员（休眠期没有成员，实际无变化）。
10. **商品删除保护**（主会话 D12）：有渠道上架、订单或已发出卡密的商品只能下架、不能删除。
11. 后台菜单多了「渠道」组（渠道管理、运营概览、售后申请、对账自检；结算单在「渠道管理 → 某渠道 → 结算单」里）和「系统 → 审计日志」；休眠期这些页面是空态，属正常。「售后申请」有待处理时菜单右侧显示红色数字（后台每 60 秒与切页面时各查一次，休眠期恒为 0、不显示）。
12. 买家侧（WP2）：留言接口的返回少了几个内部字段（买家端只用 `id / sender / content / createdAt`，不受影响）；兑换页里「已停用」「未售出」的卡与「未找到该卡密」提示相同；兑换接口多了「同一 IP + 卡密前 8 位」每分钟 16 次的限频（查询与激活各算一次，约 8 张 / 分钟；上线前复核由 8 放宽到 16，避免同批卡连续兑换被误拦）。
13. 新订单显式写 `tenant_id=1`，买家备注同时写进 `buyer_remark`（主站读取端不受影响）。
14. 渠道对账 cron 每天 03:00 顺带检查一遍主站订单的快照列（L3，只读）。
15. 登录 / 注册 / 发验证码 / 找回密码 / 登出五个接口加了写接口同源校验（设计 4.6 C4，集成阶段补）：兄弟子域（如 view.bigolab.com）或外站页面发来的请求一律 403「请求来源异常，请刷新页面后重试」。主站自己的页面、App 内置浏览器、不带 Origin 的脚本调用都不受影响。
16. 超管侧同源校验不再把请求自带的 `X-Forwarded-Host` 当作本站（nginx 也已把它置空）；经 Cloudflare 隧道改写 Host 的情况仍由 `NEXT_PUBLIC_APP_URL` / `APP_URL` 兜底，站长后台操作不受影响。
17. 后台订单留言区逐条标出「渠道回复」（休眠期没有渠道单，实际无变化）。
18. 后台「用户详情 → 按站」的发票 / 收据张数改为与订单页同一套关联规则计数（订单 id、外部订单行、sourceKey 快照），存量主站票据照常计入（新列 `shop_order_id` 零回填，只按它数会显示 0）。
19. 后台「订单导入 / 外部订单」多了「来源站」列与筛选（休眠期全部是「主站」）。

## 二、本地门槛（每次发布前在开发机跑，全部通过才往下走）

```bash
npx tsc --noEmit                                   # 必须零错误
node scripts/check-tenant-boundary.mjs             # 边界检查（也挂在 prebuild 上）：必须「零违规」
node scripts/check-tenant-boundary.mjs --strict    # 集成收尾时：「待他包处理的已知例外」也按违规算，必须为 0
node scripts/check-tenant-boundary.mjs --doc-paths # W8-9：设计里要改造的路径都在分包第 13 节有所有者
node scripts/itest-tenant/merge-routes.mjs --check # 路由总表与实际目录一致
# 渠道测试总入口（串行；库名必须含 dev / test，否则拒绝运行）
DATABASE_URL="mysql://root:123456@localhost:3306/beiguo_dev" npm run itest:tenant
```

- `run-all` 依次跑：边界检查（含自测、`--doc-paths`）→ 路由总表核对（含自测）→ `check-tenant-math` → `check-tenant-ledger` → `itest-tenant/wp0..wp7` → 二期 `mods-f / mods-p1 / mods-p2 / mods-p3` → `cross-tenant`（含 nginx 层，本机要有 docker）。最后一段打印每步汇总，任何一步失败即整体失败。
- **必须串行**：每个 itest 开头都会 `cleanupAll()` 清测试数据，并行跑会互相清掉夹具，表现为与改动无关的偶发失败（主会话 D10）。
- `cross-tenant.ts --strict`：把「待集成」项也算失败。发布前应当为 0（见第九节）。
- 边界检查基线（2026-09-26，在 HEAD `24f5b0f` 上跑）：扫描 504 个文件，R7=1（`api/orders/route.ts` 原地建单）、R9=3（`jwt-secret.ts` 拒绝名单、`same-origin.ts` 与 `track/view` 读 `x-forwarded-host`）、R10=1（路由总表不存在），其余 0。集成收尾后（2026-09-26）：扫描 708 个文件，`--strict` 零违规，已知例外只剩 1 条永久例外（`jwt-secret.ts` 的拒绝名单本身）。
- **堆上限实测**：Dockerfile 的 `next build` 带 `--max-old-space-size`（服务器 1.8G 内存，靠它把 V8 堆压住）。代码量变化大的版本，发布前在开发机用同一上限跑一次 `NODE_OPTIONS=--max-old-space-size=<Dockerfile 里的值> npm run build`（含 prebuild），能过再上服务器；过不了就调高 Dockerfile 里的值并在这里记一笔。

## 三、环境变量（`.env.production`）

compose 里一律是**裸变量名**（`- FOO`，不写 `- FOO=${FOO}`：后者在变量未定义时会给容器一个空串，反而遮蔽镜像里 `.env.production` 的真实值）。**不写 = 代码默认值 = 休眠**。

| 变量 | 上线时的值 | 说明 |
|---|---|---|
| `CHANNELS_ENABLED` | `0` | 总开关，只有 `1` 才是开。**开 1 之前 nginx 里 lulu 必须已是 `closed`**（G1） |
| `HOST_STRICT` | `0` | `1` = 严格期（未登记 Host 404）。与 nginx 严格期**同一天**切（N6） |
| `PLATFORM_HOSTS` | `bigolab.com,www.bigolab.com,app,localhost,127.0.0.1` | 主站 Host 白名单。**站长若用服务器公网 IP 进后台，开 `CHANNELS_ENABLED` 之前要把 IP 加进来**，否则 `/admin` 404（M14） |
| `CHANNEL_HOST_SUFFIX` | 不写 | 默认 `.bigolab.com`；只认一级子域 |
| `JWT_LEGACY_TOKENS` | `accept` | 上线 30 天后改 `reject`（force-recreate app 即可） |
| `TENANT_DATA_KEY` | **现生成** | 见下 |
| `PRIVATE_FILES_DIR` | 不写 | 默认 `/app/private`（compose 已挂持久卷 `private_files`） |

**`TENANT_DATA_KEY`（主会话 D8）**：渠道收款账号 / 企业微信 webhook 的加密密钥，与 `JWT_SECRET` 解耦（站长要轮换 `JWT_SECRET`，轮换后已录的收款账号不能解不开）。

```bash
cd /opt/beiguo/beiguo-shop
# 判据是「这一行存在且值非空」，不看长度：hex（64 字符）与 base64（`openssl rand -base64 32` 是 44 字符）都合法（crypto.ts parseDataKey）。
# 只在缺失时生成；已有值一律不动——哪怕看起来不对也不自动覆盖（覆盖 = 已录的收款账号全部解不开），交给人看。
if grep -q '^TENANT_DATA_KEY=.' .env.production; then
  echo "已有，别动（值是否合规见下一步应用日志 / 录入收款账号时的提示）"
elif grep -q '^TENANT_DATA_KEY=' .env.production; then
  echo "有一行 TENANT_DATA_KEY= 但值为空：停手，人工确认这台机器之前没有用过别的密钥，再手工填入一个用 openssl rand -hex 32 生成的值"
else
  cp .env.production .env.production.bak-$(date +%Y%m%d%H%M%S)
  echo "TENANT_DATA_KEY=$(openssl rand -hex 32)" >> .env.production
fi
grep -c '^TENANT_DATA_KEY=' .env.production        # 期望 1
```

- **生成一次、永远别丢别改**：改了之后已录入的收款账号全部解不开，只能逐个重新录入。把它和 `JWT_SECRET` 一起记进站长的密码保管处。
- 缺失或短于 32 字节时，录入 / 查看收款账号一律拒绝（提示「未配置数据密钥」），其余功能不受影响（fail closed）。
- `.env.production` 会被 Next standalone 打进镜像（交接文档第六节第 2 条），所以**改完 env 要重新构建**才能让镜像里那份也更新；只改 compose 传入的值 force-recreate 即可生效（运行时 env 优先）。

## 四、A 段：应用发布（每次都走）

### A0 准备

```bash
cd /opt/beiguo/beiguo-shop && set -a && . ./.env.production && set +a
git rev-parse --short HEAD                  # 记下来：旧版本号，回滚标签用
df -h /                                      # 可用 < 2GB 先 docker image prune -f && docker builder prune -f（不要 system df）
```
后台「发送设置」关闭营销「启用发送」（构建与重启期间不发营销邮件）。

### A1 回滚标签 + 备份

```bash
OLD=$(git rev-parse --short HEAD)
docker tag beiguo-shop-app:latest beiguo-shop-app:rollback-$OLD
docker images beiguo-shop-app --format '{{.Tag}}' | grep rollback-$OLD      # 阳性对照：标签在

F=/opt/beiguo/backups/beiguo_shop_$(date +%Y%m%d_%H%M%S).sql
docker compose --env-file .env.production exec -T db mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \

tail -3 "$F" | grep -q "Dump completed" && echo "备份完整：$F" || echo "备份不完整，停手"
```

### A2 拉代码

```bash
git pull origin main
git log -1 --format='%h %s'
docker run --rm -v $PWD:/w:ro -w /w node:20-alpine node scripts/check-tenant-boundary.mjs   # 宿主机没有 node（2026-09-26 核实），用临时容器跑。阳性对照：「✅ 零违规」——同时证明 scripts/itest-tenant.routes.json 已随提交拉下来（缺它 R10 报「路由总表缺失」，A6 构建会失败）
ls -la nginx/closed.html scripts/ops/ddl-gate.sh scripts/ops/build-with-swap.sh scripts/sql/tenant-seed.sql   # 四个文件都在（缺一个就是提交漏了，停手）
grep -c 'tenant-' cron/crontab                      # 期望 2（tenant-release、tenant-reconcile）；0 = crontab 的修改没提交，停手（A7 才发现就晚了：镜像已换）
```

> **注意 nginx 已在磁盘上换新**：`git pull` 之后 `nginx/nginx.conf` 就是 N 段的新版本（单文件 bind-mount）。N 段之前 nginx 容器**只要因任何原因重启**（宿主机重启、dockerd 重启、A6 构建时 OOM 连带杀容器——2026-09-25 发生过），就会加载新配置：Host 分流与 `X-Forwarded-Host` 置空会提前生效，而 `closed.html` 的卷还没挂（lulu 请求 404、不进应用；主站与新配置兼容）。所以：
> - A2 之后先跑一次 N3 的 `nginx -t` 临时容器检查（只读，不影响线上），确认新配置本身能加载；
> - A6 / A7 之后若发现 nginx 容器重启过（`docker inspect -f '{{.State.StartedAt}}' beiguo-nginx` 晚于 A2 的时间），立即按 N4 的检查清单逐条核对，必要时按 N7 回滚这一个文件。

### A3 DDL 预览 + 闸门（禁止在 app 容器里执行：容器里是旧 schema）

```bash
NET=$(docker inspect -f '{{range $k, $v := .NetworkSettings.Networks}}{{$k}}{{end}}' beiguo-db)
docker run --rm --network "$NET" -v "$PWD/prisma":/work/prisma:ro -w /work \
  -e DATABASE_URL="mysql://root:$MYSQL_ROOT_PASSWORD@db:3306/beiguo_shop" \
  -e npm_config_registry=https://registry.npmmirror.com \
  -e PRISMA_ENGINES_MIRROR=https://registry.npmmirror.com/-/binary/prisma \
  node:20-alpine sh -c 'apk add --no-cache openssl >/dev/null && npx -y prisma@5.22.0 migrate diff \
    --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script' > /tmp/preview.sql 2>/tmp/preview.err
echo "exit=$?"; wc -c /tmp/preview.sql

# 闸门：① 0 字节 = 命令失败（不是没有变更）② 语句开头的 DROP / MODIFY / CHANGE / RENAME 必须为 0
#       ③ 首次发布渠道分站加 --expect-p0：与本期预期清单逐条比对（多一条、少一条都失败）
sh scripts/ops/ddl-gate.sh /tmp/preview.sql --expect-p0
```

### A4 先 DDL（旧镜像仍在跑，零影响）

> **元数据锁（MDL）**：ALTER 开始与结束都要短暂拿表的排他 MDL。若有未提交的长事务占着 `orders`，ALTER 会排队，排在它后面的所有读写（下单、到账回调）一起挂住；MySQL 默认 `lock_wait_timeout` 是一年，prisma 又没法设会话级超时。所以：
> 1. 先查长事务：`SELECT trx_id, TIMESTAMPDIFF(SECOND,trx_started,NOW()) FROM information_schema.innodb_trx;`（应为空或都是几秒内）；
> 2. `SET GLOBAL lock_wait_timeout = 30;`（先记下原值）→ db push → 立刻 `SET GLOBAL lock_wait_timeout = <原值>`。拿不到锁时 ALTER 30 秒后失败退出，而不是无限期卡住全站；db push 按差异执行，重跑即可补齐。
> 3. db push 本身也用 `setsid nohup` 后台跑：容器里下载 prisma 要几分钟（2026-09-26 实测 6 分钟，真正执行 DDL 只用了 1.94 秒）。

### A6 构建（服务器上，临时放开 swap；站长已同意，每次执行前在群里说一声）

```bash
# 必须 setsid + </dev/null 完全脱离会话：只用 `nohup … &` 时，workbench exec 会话一结束进程就被连带取消
# （2026-09-26 安全修复部署实录：首次立刻 EXIT=1、无输出）

```

- **日志为空、进程已经不在**：多半是被会话连带杀掉（没用 setsid）或被 `kill -9`——trap 没跑到。先 `ls /tmp/build-with-swap.state`：在就先 `sh scripts/ops/build-with-swap.sh --restore` 还原 swappiness，再重新发起构建。
- **Node 堆上限**：Dockerfile 里 `next build` 的 `--max-old-space-size` 见文件内注释（终审阶段按新代码在开发机实测后定值）；构建日志出现 `JavaScript heap out of memory` 就是它不够——这不是内存组 OOM，swap 与看门狗帮不上，改 Dockerfile 里的值重新构建。

脚本做的事（`scripts/ops/build-with-swap.sh` 文件头有全文说明）：
1. 探测 cgroup 版本：`stat -fc %T /sys/fs/cgroup` 不是 `tmpfs`（v1）就**直接停手**（退出码 3，没改任何设置）。
2. 记录原值后把 `vm.swappiness` 与 buildkit 内存组 `memory.swappiness` 设为 60（buildkit 组在构建开始后才出现，脚本等它出现再写）；原值另存 `/tmp/build-with-swap.state`。
3. 看门狗每 2 秒把 `next build` 进程树 `oom_score_adj` 设为 1000（真 OOM 时先杀构建、不杀站点）。
4. 后台 `docker compose --env-file .env.production build app`，日志写 `/tmp/beiguo-build-*.log`。
5. **无论成败都还原**两项设置（`trap`）。脚本被 `kill -9` 时 trap 跑不到：`sh scripts/ops/build-with-swap.sh --restore` 按状态文件还原（下次运行发现状态文件会拒绝构建，逼你先还原）。
6. 检查 `beiguo-app`、`jishi-app`、`beiguo-db`、`beiguo-nginx`、`beiguo-cloudflared` 与 jishi 的 cloudflared 存活；比对构建前后镜像 ID，**相同即失败**（next build 被 OOM 杀掉会静默 0 退出）。

退出码：0 成功；1 构建失败或镜像没变；2 前置条件不满足（非 root、磁盘不足、残留状态文件）；3 不是 cgroup v1；4 构建后有站点容器不在运行（**立刻人工查看** `dmesg | grep -i oom`）。

构建日志里要看的两行：
- `[tenant-boundary] ✅ 零违规…`（prebuild 边界检查；有违规构建直接失败）。
- `[prerender] routes=N`：根布局动态化之后应为 0（设计 4.8）。集成阶段本地生产构建已核对为 0，Dockerfile 默认 `ARG PRERENDER_STRICT=1`（硬闸）：有页面被预渲染就构建失败，日志列出路由。急着出版本时可临时 `docker compose build --build-arg PRERENDER_STRICT=0`（只打印），事后必须修掉。

## 九、回滚与下线

**回滚 app**（只切镜像，**数据库不回滚**）：
```bash
docker tag beiguo-shop-app:rollback-<旧版本号> beiguo-shop-app:latest
docker compose --env-file .env.production up -d --no-deps --force-recreate app
docker inspect -f '{{.Image}}' beiguo-app     # 核对是旧镜像
```
- 旧镜像在新 schema 上照常运行（旧代码不读新列）；新表、新列留在库里。
- **回滚期间与之后任何人不得用旧 commit 的 schema 跑 `db push` 或 `scripts/deploy.sh`**：旧 schema 没有 `tenant_*` 表与新列，`--accept-data-loss` 会删掉整本渠道账。
- **lulu 已开业时，先下线渠道站再动 app**：nginx 里 lulu 改回 `closed` 并 force-recreate nginx，再回滚 app。否则旧代码不认 Host，lulu 会渲染整份主站，这期间的订单记到主站、事后无法区分。
- 不要在部署目录 `git checkout` 旧 commit（会把磁盘上的 schema 换回旧版）；看旧代码用 `git worktree`。
- 回滚到旧镜像后 cron 的两个 `tenant-*` 地址返回 404，只在 cron 日志记一行，不影响业务。
- 前滚：修好后按 A 段重新发布；DDL 已在库里，预览为空是正确的，但要确认 A4 的 `SHOW COLUMNS` 阳性对照在。

**一键下线**（设计 15.6）：

| 层 | 做法 | 生效 | 用于 |
|---|---|---|---|
| 1 应用总开关 | `CHANNELS_ENABLED=0` + force-recreate app | 约 30 秒 | **只能与第 3 层一起用**：先 nginx 改 closed，再关应用开关 |
| 2 租户状态 | 后台把渠道置 `SUSPENDED`（暂停营业横幅、拒绝新单、后台只读）或 `TERMINATED`（停业页；终止仍走结清流程；允许从 SUSPENDED 直接终止，主会话 D7） | 下一次请求 | 对账失败、风控、违约调查 |
| 3 nginx | map 里 lulu 改为 `closed` + force-recreate nginx | 秒级 | 回滚、应用故障、备案整改 |
| 4 Cloudflare | 删除 lulu Public Hostname | 分钟级 | 长期停用 |

渠道功能整体废弃时：下线路由即可；`Tenant` 系列模型与新增列必须保留在 schema 里（加注释「已废弃，勿删」）。

## 十六、运维记录：新建渠道 shop 的邀请链接 404（2026-09-27）

**现象**：站长在后台新建 `shop`（shop.bigolab.com，10:28），也在 Cloudflare 加了路由。随后打开渠道主邀请链接，得到 404。

**原因**：nginx 的 `map $host $site_known` 只精确登记了 lulu。shop 落到 default，被当成主站处理，而主站 Host 的 `/partner`、`/api/partner` 一律 404。应用这边的店面解析本来是对的：`tenant_domains` 已登记，首页由应用按渠道渲染。

**修复**（`768e069`，10:36:47 force-recreate nginx）：`map` 里加一条正则 `~^[a-z0-9-]+\.bigolab\.com$ channel;`。
- 精确匹配优先：bigolab.com、www 仍是 main；某个渠道要紧急下线，就加一行精确的 `host closed;`。
- 验证：主站与 www 行为不变；lulu 不变；shop 带 noindex，`/admin` 与非白名单接口 404，`/partner/*` 进入应用。

**附带处理**：站长 10:31 把 shop 改成了「已停业」。后台状态机里停业是终态；`tenant_domains.host` 与 `tenants.code` 都唯一，这个域名也无法再登记给新渠道。
- 核实 shop 没有成员、上架、订单、账目，停业也只改了状态、没有别的连带操作，邀请仍有效。
- 站长确认后，10:38 用一个事务把它改回 `DRAFT`（条件 `status='TERMINATED'`，影响 1 行），并写审计 `tenant.status`（`reason_code=OPS_RESTORE`，actor 为 SYSTEM，diff 带 `via=ops-sql`）。
- 公网验证：shop 首页显示「本站暂停访问」，`/partner/login` 与邀请页 200，`/admin` 404。

### 以后新建渠道（全程后台 + Cloudflare，不用动服务器）
1. 超管后台「渠道 → 渠道管理 → 新建」：代码、域名（`xxx.bigolab.com`，只认一级子域）、费率。新建后是「筹备中」，前台显示「本站暂停访问」。
2. Cloudflare → 隧道 → 添加路由（Published application / Public Hostname）：
   - Subdomain `xxx`，Domain `bigolab.com`；
   - Service `HTTP`，URL `nginx:80`；
   - **HTTP Host Header 留空**；
   - DNS 里已有同名记录就先删。
3. 后台授权商品、设进货价、录收款账号，邀请渠道主。对方先在主站注册，再打开邀请链接、登录并接受。
4. 渠道主定价上架；可用预览账号走一单；然后改为「营业」。
5. **「已停业」不可逆**，而且域名会永久占用。只是想暂时关站，用「暂停营业」。
6. 客户想用自己的域名（地址栏显示如 `tibo.pw`）：建站后按第十七节接入，不用改服务器与 nginx。

## 十七、渠道自定义域名接入（2026-09-30 站长提出；契约 `docs/多渠道分销-自定义域名.md`）

场景：某渠道的客户想用自己的域名（例：`tibo.pw`，注册在西部数码）作为店铺地址，地址栏显示 `tibo.pw`。
线路（已与站长确认）：客户把 `tibo.pw` 的 **DNS 服务器**改成站长 Cloudflare 账号分配的 NS（域名注册仍在客户的西部数码账号里）；站长在 Cloudflare 接入这个域名，并在现有隧道里给 `tibo.pw`、`www.tibo.pw` 加路由。客户保留自家 DNS、直接 CNAME 到隧道行不通：Cloudflare 隧道只给**同一个账号**下的域名转发流量。

### 17.1 发布说明（站长能感知到的变化）

- 超管后台「渠道详情 → 域名」：除了 `xxx.bigolab.com` 子域名，还能添加客户自己的域名；每行显示类型（子域名 / 自定义域名）、启用状态、是否主域名，并有「设为主域名」按钮。
- **主域名**就是站点地址（`Tenant.origin`）：系统邮件、邀请链接、页面 canonical 都用它。设为主域名后：
  - 系统邮件与邀请链接从下一封起改用新域名；
  - 旧域名（例如 `lulu.bigolab.com`）上打开前台或渠道后台页面，会自动跳到新域名的同一路径；
  - 买家与渠道成员在新域名上要**重新登录一次**（登录态按域名隔离，这是安全设计，不是故障）；
  - 渠道会收到一条站内通知「店铺主域名已改为 https://…」，操作日志里有「平台修改主域名」。
- 主域名不能停用（先把别的域名设为主域名再停用）；停用的域名不能设为主域名；一个域名只能属于一个渠道。
- 建站时「站点地址」仍只收 `https://<子域名>.bigolab.com`；自定义域名一律建站后在详情页添加。
- nginx：形如域名的陌生 Host 现在按渠道口径处理（`/admin` 404、`/api` 白名单、noindex 响应头）；应用里没登记的这类 Host（含没登记的 `*.bigolab.com` 子域）一律 **404（2026-10-01 加固）**，观察期也不再按主站渲染；`unknown_host.log` 以后只记 IP、不带点的 Host 与 bigolab.com 多级子域。**以后接入新的自定义域名不用改 nginx。**
- nginx 公网 IP 直连入口（宿主机 80 → 容器 8080）对 `/api/domain-check` 一律 404：连通校验只认「Cloudflare → 隧道 → 容器 80」这条路。
- lulu、shop 这类只有子域名的渠道：行为不变（主域名就是子域名，不会跳转）。主站、休眠态不变。
- **自定义域名的连通校验**（契约第 9 节）：客户的域名注册在客户自己手里，随时可能过期或被指走，所以：
  - 点「设为主域名」时，系统先经公网请求 `https://<域名>/api/domain-check` 核对签名，没接到本站就报「还没有接到本站（原因）」，什么都不改；
  - 之后 cron 每 10 分钟复验一次；**连续两趟失败**（或 40 分钟没有成功记录），店面自动改用该渠道的子域名生成邮件与链接、旧子域名不再跳走，站长群收到告警、渠道收到站内通知；**连续两趟成功**后自动切回，再推一次「已恢复」（防晚高峰抖动来回跳）。站长群的降级 / 恢复告警各自 6 小时最多一次，仍未恢复（且那一趟仍失败）满 6 小时再提醒一次；渠道站内通知不节流，只在状态与渠道上次收到的不一致时发（「暂时无法访问」「已恢复」严格交替，渠道最新一条永远是真实状态）。库里的站点地址不动；已停业（TERMINATED）的渠道不再复验、不告警；
  - 通知与告警只写归类原因（解析不到 / 指向了非公网地址 / 连接失败 / 证书错误 / 返回内容不符；「本站校验出错」= 本站自己缺 `JWT_SECRET` 之类，查我们自己的配置），HTTP 状态码等细节只在超管后台显示；
  - 40 分钟没有成功记录（多半是 cron 停了）时，站长群会收到一条「校验记录过期」告警（每渠道 6 小时最多一次），提示检查 cron 容器；
  - **能力边界**：这套校验防的是意外失联（过期、改 NS、指到别处），防不住有意作恶的 DNS 控制者（例如在自己的 Cloudflare 边缘把 `/api/domain-check` 原样转给本站、其余页面给自己的服务器）；后者靠合作约定与站长随时可以停用兜底（契约 9.5）；
  - 渠道详情「域名」卡片顶部显示校验状态；主域名行有「重新校验」按钮（修好 DNS 后点一下立即恢复并推「已恢复」，不必等 cron 连续两趟）；
  - 主域名是自定义域名时，至少要保留一个启用中的子域名（失联时退到它）。

### 17.2 上线步骤（没有 DDL，没有新环境变量）

0. **上线前核对**（只读）：
   - 查应用日志里形如域名的未知 Host，确认没有正常流量（本次起这类 Host 观察期也 404）：`docker logs --since 72h beiguo-app 2>&1 | grep '未知 Host' | sort | uniq -c | sort -rn | head -50`。**2026-10-01 主会话已核对近 1.5 天：只有 `ifconfig.me`、`icanhazip.com`、`checkip.amazonaws.com` 等扫描器**；上线当天再看一眼，出现陌生的正常业务域名就停手。
1. **A 段只换 app**（第四节）：A0–A2 照常；**A3 预览应为空**（本次不改 schema），不为空就停手；A4、A5 跳过；A6 构建；A7 只换 app；A8 冒烟加下面几条：
   - 超管后台 lulu 详情「域名」卡片能打开，lulu.bigolab.com 显示「子域名 / 主域名 / 启用」；
   - `docker exec beiguo-app sh -c 'wget -qO- --header "Host: lulu.bigolab.com" http://127.0.0.1:3000/ | grep -c data-primary-host-redirect'` → `0`（lulu 不挂跳转）；
   - 同一条把 Host 换成 `bigolab.com` → `0`（主站永远不挂）。
2. **N 段 force-recreate nginx**（第五节 N3 的临时容器 `nginx -t` → N4 的 force-recreate），再验证：
   ```bash
   docker exec beiguo-nginx nginx -T 2>/dev/null | grep -c 'xn--'                                          # ≥ 1：加载的是新文件
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: tibo.test' http://127.0.0.1/admin                  # 404（按渠道口径）
   # 余额、接码接口：先看主站 Host 进得去（401 / 200 或 503），再看同一路径换成 tibo.test 被 nginx 白名单挡成 404。
   # 必须拿真实存在的路径做对照：不存在的路径不管判成 channel 还是 main 都是 404，证明不了白名单生效
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: bigolab.com' http://127.0.0.1/api/account/wallet     # 401（主站：路由存在，未登录）
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: tibo.test'   http://127.0.0.1/api/account/wallet     # 404（渠道 /api 白名单外）
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: bigolab.com' http://127.0.0.1/api/jiema/catalog      # 200 或 503（主站：接码目录，未开放时 503）
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: tibo.test'   http://127.0.0.1/api/jiema/catalog      # 404
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: tibo.test'   http://127.0.0.1/api/wallet/topup       # 404
   curl -sI -H 'Host: tibo.test' http://127.0.0.1/ | grep -i x-robots-tag                                 # noindex, follow
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: bigolab.com' http://127.0.0.1/                      # 200（主站不变）
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: lulu.bigolab.com' http://127.0.0.1/admin           # 404（不变）
   ```
   `tibo.test` 没在后台登记：应用对它的页面一律 404（2026-10-01 加固，不再按主站渲染），这里只验 nginx 这一层。
   连通校验应答端：隧道入口（容器 80）要能穿过渠道白名单；公网 IP 直连入口（宿主机 80 → 容器 8080）一律 404（契约第 9 节）。
   宿主机上 `curl http://127.0.0.1` 走的是 8080，所以隧道入口要进 nginx 容器里测（nginx:alpine 自带 busybox wget）：
   ```bash
   docker exec beiguo-nginx wget -qO- --header 'Host: lulu.bigolab.com' 'http://127.0.0.1:80/api/domain-check?n=abcdefghijklmnop1234'   # {"success":true,"data":{"proof":"…43 位…"}}
   docker exec beiguo-nginx wget -S -qO- --header 'Host: bigolab.com' 'http://127.0.0.1:80/api/domain-check?n=abcdefghijklmnop1234' 2>&1 | grep 'HTTP/'   # 404（主站不应答）
   curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: lulu.bigolab.com' 'http://127.0.0.1/api/domain-check?n=abcdefghijklmnop1234'   # 404（8080 入口一律拦）
   ```
3. **cron 容器 force-recreate**（crontab 新增 `tenant-domains` 一行）：`docker compose --env-file .env.production up -d --no-deps --force-recreate cron`，再 `docker compose exec cron grep -c tenant-domains /etc/crontabs/root` → `1`。没有自定义主域名时这条任务几毫秒返回、不发任何请求。
   - 这一步漏了的后果：自定义域名设为主域名 40 分钟后，因为没人复验，店面会自动改用子域名（安全方向的降级，不会出错，但地址栏不再是客户的域名）。
4. 三段都做完才算上线。上线前先给「Hero-SMS 短信接码」会话发消息确认服务器空闲，并 rebase 到最新的 origin/main（契约第 8 节）。
5. **回滚**：app 切回上一版镜像即可，数据库不用动；但**已经接入自定义域名之后**再回滚，要先把自定义域名的流量挡在应用外面，再换镜像。
   - 原因：上一版镜像不认自定义域名，不管库里这个域名是启用还是停用，都会在观察期把 `tibo.pw` 当成主站渲染（整份主站、按主站价下单、订单记到主站）。「在后台停用」只在新镜像上有效，**单靠它不够**。
   - 顺序：① Cloudflare 隧道里删掉 `tibo.pw`、`www.tibo.pw` 两条路由（请求不再到达服务器）；或者在**回滚后仍在用的那份** `nginx.conf` 的 map 里给它们各加一行 `closed`（如 `tibo.pw closed;`，只出停业页）并 force-recreate nginx——nginx 也要按 N7 回滚时，这两行要加在回滚后的文件里。② 后台把主域名设回子域名、停用自定义域名（`Tenant.origin` 回到子域名，邮件与邀请链接不再指向进不去的域名）。③ 再切 app 镜像。
   - 还没接入任何自定义域名时，直接切镜像即可；nginx 回滚见 N7。
   - 回到旧镜像后，crontab 里的 `tenant-domains` 一行每 10 分钟打一次旧镜像没有的 `/api/cron/tenant-domains`，得到 404、cron 日志记一行失败——**无害**，可以不管；想干净就同时把 `cron/crontab` 回滚到上一版并 `docker compose --env-file .env.production up -d --no-deps --force-recreate cron`。
   - **新镜像的后台已经打不开**（没法点「设为主域名」「停用」）时，用 SQL 完成第②步（先做第①步挡流量；`<渠道id>`、`<子域名>`、`<自定义域名>` 换成实际值，子域名形如 `lulu.bigolab.com`，都不带 `https://`）：
     ```sql
     START TRANSACTION;
     SELECT id, code, origin FROM tenants WHERE id = <渠道id> FOR UPDATE;            -- 记下旧 origin，核对是自定义域名
     UPDATE tenants SET origin = CONCAT('https://', '<子域名>') WHERE id = <渠道id>;
     UPDATE tenant_domains SET is_primary = 0 WHERE tenant_id = <渠道id>;
     UPDATE tenant_domains SET is_primary = 1, status = 1 WHERE tenant_id = <渠道id> AND host = '<子域名>';
     UPDATE tenant_domains SET is_primary = 0, status = 0 WHERE tenant_id = <渠道id> AND host IN ('<自定义域名>', 'www.<自定义域名>');
     INSERT INTO audit_events (at, actor_user_id, actor_kind, tenant_id, action, target_type, target_id, result, reason_code, reason, diff, public_diff)
       SELECT NOW(3), NULL, 'SYSTEM', id, 'tenant.domain_primary', 'tenant', code, 'OK', 'OPS_SQL',
              '运维回滚：新镜像后台不可用，SQL 把主域名改回子域名并停用自定义域名',
              JSON_OBJECT('from', '<自定义域名>', 'to', '<子域名>', 'disabled', JSON_ARRAY('<自定义域名>', 'www.<自定义域名>')),
              JSON_OBJECT('from', '<自定义域名>', 'to', '<子域名>')
       FROM tenants WHERE id = <渠道id>;
     SELECT host, is_primary, status FROM tenant_domains WHERE tenant_id = <渠道id>;  -- 核对：子域名 1/1，自定义域名 0/0
     COMMIT;
     ```
     审计记成 `actor_kind='SYSTEM'`、`reason_code='OPS_SQL'`：渠道后台看到「平台修改主域名」，超管能从 reason 看出是运维 SQL。
     SQL 改完之后 app 进程里还有最多 60 秒的域名缓存；马上要切镜像的话无所谓，不切的话 `docker compose --env-file .env.production restart app` 让它立即生效。

### 17.3 接入一个自定义域名：站长侧步骤（草稿）

**前置**：渠道已建好、子域名能正常打开；客户已确认要用的域名（以下以 `tibo.pw` 为例），并知道要改 DNS 服务器。

1. **Cloudflare 接入域名**（站长账号，与 bigolab.com 同一个账号）：
   - Dashboard → 添加站点（Add a domain / Onboard a domain）→ 输入 `tibo.pw` → 选 Free 计划；
   - 让 Cloudflare 快速扫描现有 DNS 记录。**如果客户的域名还有邮箱（MX、SPF 等）或其他用途，先向客户要一份西部数码里现有的解析记录截图，逐条核对 Cloudflare 里都有**（切换 NS 之后西部数码的解析不再生效，漏掉的记录会让客户的邮箱等服务中断）；
   - 扫描出来的 `tibo.pw`、`www` 的 A / CNAME 记录**先删掉**（后面隧道路由会自动建 CNAME，已有同名记录会冲突）；
   - Cloudflare 给出两个 NS（形如 `xxx.ns.cloudflare.com`、`yyy.ns.cloudflare.com`），**原样发给客户**，连同《自定义域名接入教程》。
2. **等客户改完 NS**：Cloudflare 里该站点状态从 Pending 变成 Active（通常几分钟到几小时，最长 48 小时，可在站点概览里点「重新检查」）。Active 之后 Universal SSL 证书自动签发（覆盖 `tibo.pw` 与 `*.tibo.pw`，一般十几分钟内）。
   - SSL/TLS 加密模式选 Full（隧道本身是加密的，模式不影响回源；统一选 Full 与 bigolab.com 一致）；打开「始终使用 HTTPS」。
   - 不要为这个站点加任何「忽略 Host 的自定义缓存键」规则（设计 4.2 第 3 条）。
3. **超管后台登记**（先登记、后加隧道路由）：渠道详情 → 域名 → 添加 `tibo.pw`、`www.tibo.pw`（都启用，**先不要设为主域名**）。
   - 为什么先登记：**登记之后才能设为主域名，也才能在第 4 步用 curl 看到跳转标记来验收**。没登记的域名应用一律 404（2026-10-01 加固：先加隧道路由也不会再被渲染成主站），所以顺序不再关乎串站，只关乎能不能设主、能不能验收。登记本身不带来流量（第 1 步已删掉这两个名字的 A / CNAME，隧道路由还没加，此时它们在公网解析不出来）。
   - 添加框的提示「自定义域名需先在 Cloudflare 接入并给隧道加路由……否则买家打不开」说的是**设为主域名之前**必须做完这些；登记这一步可以、也应该先做。
4. **隧道加路由**：Zero Trust → Networks → Tunnels → 本站隧道 → Public Hostname（新界面叫 Published application routes）→ 添加两条：
   - Subdomain 留空、Domain `tibo.pw`；Service `HTTP`、URL `nginx:80`；
   - Subdomain `www`、Domain `tibo.pw`；Service `HTTP`、URL `nginx:80`；
   - 两条都**HTTP Host Header 留空**（设了的话应用收到的 Host 不是 `tibo.pw`，认不出店面）；Service 必须是 `nginx:80`，不能填 `app:3000`（会绕过 nginx 的渠道 `/api` 白名单）；
   - 保存后 Cloudflare 自动建 `tibo.pw`、`www.tibo.pw` 指向隧道的 CNAME（橙色云）。
   - **验收（此时还不是主域名：用 curl 看，不要拿浏览器地址栏判断）**：这时 `tibo.pw` 是这个渠道的非主域名，页面先返回 200，再由浏览器里的跳转组件换到当前主域名（例如 `lulu.bigolab.com`）的同一路径——**浏览器里地址栏变成子域名是正常的**，能跳过去本身就说明 DNS、证书、隧道都通了。逐条核对：
     ```bash
     curl -sI https://tibo.pw/ | head -1                                                    # HTTP/2 200，没有 30x；证书有问题 curl 会直接报错
     curl -s  https://tibo.pw/ | grep -o 'data-primary-host-redirect="[^"]*"'               # ="https://lulu.bigolab.com"：认出是这个渠道，跳转目标是当前主域名
     curl -s  https://tibo.pw/partner/login | grep -o 'data-primary-host-redirect="[^"]*"'  # 同上：渠道后台登录页也认出来了
     curl -s -o /dev/null -w '%{http_code}\n' https://tibo.pw/admin                          # 404
     curl -s -o /dev/null -w '%{http_code}\n' https://www.tibo.pw/                           # 200
     curl -s 'https://tibo.pw/api/domain-check?n=abcdefghijklmnop1234'                       # {"success":true,"data":{"proof":"…"}}：连通校验应答端可达
     ```
     第一条是 404、第二条**什么都没输出**，说明应用没认出这个渠道（多半是第 3 步没登记、登记到了别的渠道，或者隧道改写了 Host Header）：回第 3 步核对，改好再验。
     最后一条如果返回 HTML（Cloudflare 质询页）或 403：该站点开了 Bot Fight Mode / WAF 质询。**免费版的 Bot Fight Mode 不能用 WAF 自定义规则放行，只能整个关掉**（该站点 Security → Bots → Bot Fight Mode 关）；WAF 托管质询、自定义规则可以给 `/api/domain-check` 加跳过。返回 **HTTP 530（页面写 error 1033）** = 隧道离线，或隧道里没有这个域名的路由。
     **这些 curl 在站长电脑上通过，不代表服务端也能过**：设主与复验是服务器（阿里云出口 IP）发起的，Cloudflare 的质询、限速按来源判断，家里宽带过得去、机房 IP 可能被质询。**以第 5 步 / 后台「重新校验」的结果为准。**
5. **设为主域名**：第 4 步的验收都通过后，点 `tibo.pw` 行的「设为主域名」。系统会先经公网请求 `https://tibo.pw/api/domain-check` 核对签名（契约第 9 节）：
   没通过会提示「https://tibo.pw 还没有接到本站（归类原因（细节））」、什么都不改——按原因回到第 2、4 步排查：`解析不到（ENOTFOUND）` = NS 还没生效或隧道路由没加；`指向了非公网地址` = 解析结果是内网 / 保留地址（记录配错了）；`证书错误` = Universal SSL 还没签发好；`返回内容不符（HTTP 403 / 503）` = Cloudflare 质询（见上一步的 Bot Fight Mode）；`返回内容不符（HTTP 530）` = 隧道离线或没加路由；`返回内容不符（校验值不符…）` = 请求到了别处，**不要**强行绕过。通过之后：
   - `https://lulu.bigolab.com/…`、`https://www.tibo.pw/…` 的页面自动跳到 `https://tibo.pw/…`；
   - 邀请链接、系统邮件改用 `https://tibo.pw`；
   - 告诉渠道站长：成员与买家要在新域名上重新登录一次；以前发出去的旧链接仍可打开（页面会跳转，收银台、收据、开票链接在原域名照常打开）。
6. **验收**（公网）：
   - `https://tibo.pw/` 200，地址栏保持 `tibo.pw`；浏览器锁标志正常（证书为 Cloudflare 签发、覆盖 tibo.pw）；`curl -s https://tibo.pw/ | grep -c data-primary-host-redirect` → `0`（主域名上不挂跳转）；
   - `https://lulu.bigolab.com/products` → 跳到 `https://tibo.pw/products`；
   - `https://tibo.pw/admin` 404；`https://tibo.pw/api/account/wallet`、`https://tibo.pw/api/jiema/catalog` 404——同一路径在 `https://bigolab.com` 上分别是 401、200 或 503，对照着看才说明是渠道白名单挡住的，而不是路径不存在；
   - 用测试买家在 `tibo.pw` 登录、下一单小额，收银台正常。

**紧急下线某个自定义域名**：后台先把主域名设回子域名，再停用该域名（立即 404；只在新版镜像上成立，要回滚镜像时见 17.2 第 5 步）；来不及进后台时，在 nginx map 里加一行精确的 `tibo.pw closed;` 并 force-recreate nginx（只出停业页）。
**客户要收回域名**：先按上面把主域名设回子域名并停用自定义域名，再请客户把 DNS 服务器改回西部数码默认，最后在 Cloudflare 删除该站点与两条隧道路由。

**收到「自定义主域名连续校验失败」告警时**（契约第 9 节）：店面此时已经自动改用子域名（邮件、链接、跳转），买家不受影响，不用抢时间。
1. 看告警里的归类原因，再到渠道详情「域名」卡片看细节（错误码、HTTP 状态码只在后台显示）：`解析不到` / `连接失败` 多半是域名过期或客户改了 DNS 服务器；`返回内容不符`（细节是「校验值不符」）表示这个域名已经指到别的服务器——**按域名已不在我们手里处理**。
2. 联系客户确认；域名找回来之前，按上面「紧急下线」把主域名设回子域名、停用该自定义域名（否则 cron 一旦又校验通过就会自动切回）。
3. 修好之后在渠道详情点主域名行的「重新校验」，通过即立即恢复（不点也行：复验连续两趟通过后自动切回）。

**收到「已超过 40 分钟没有成功的连通校验记录」告警时**：不是客户域名的问题，是定时复验没跑。店面已安全地改用子域名。检查 `docker ps` 里 `beiguo-cron` 是否在跑、`docker exec beiguo-cron grep -c tenant-domains /etc/crontabs/root` 是否为 1、`docker logs --tail 50 beiguo-cron` 里 `/api/cron/tenant-domains` 是否返回 200；修好后下一趟通过即切回。

**接受的残余风险**（契约 9.5，已与站长确认写入）：这套校验防的是**意外失联**（过期、改 NS、指到别处），**防不住有意作恶的 DNS 控制者**——例如客户在自己的 Cloudflare 边缘把 `/api/domain-check` 原样转给本站、其余页面给自己的服务器，HTTP 层面无法区分。域名注册在客户手里，平台只能「发现并退回子域名」，不能阻止客户改 DNS；两次复验之间最长约 20 分钟的窗口内发出的邮件与跳转仍指向该域名；客户原样反代到本站能通过校验。所以接入前要让客户同意接入教程里「是主域名期间不得擅自改 DNS 服务器、解析或让域名过期」这一条；作恶的情形靠这条约定与**站长随时可以把主域名设回子域名、停用该域名**兜底。

### 17.4 客户侧步骤（草稿，完整版见《自定义域名接入教程》，可直接转发给客户）

1. 西部数码登录 → 管理中心 → 域名管理 → 找到 `tibo.pw` → 管理；
2. 确认域名已实名认证、状态正常；如果开了 DNSSEC，先关闭；
3. 如果这个域名还用来收邮件或有别的网站，把「域名解析」里的现有记录截图发给站长；
4. 「修改 DNS 服务器」→ 选自定义 DNS → 填站长给的两个 Cloudflare NS → 保存；
5. 等待生效（几分钟到 48 小时），然后告诉站长；之后解析改由站长的 Cloudflare 管理，在西部数码改解析不再生效。
