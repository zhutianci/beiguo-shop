### 1.3 「6 笔待付订单，收款监控里只有 3 条」的原因

收款监控列的是**收款单**（`vmq_orders`），不是订单。订单要点了「去支付」才生成收款单。两道闸门数的东西不一样：

- **下单闸门**（`src/app/api/orders/route.ts:497`）数的是「这个人**名下有效的收款单**有几张」（`countOpenOrderPayments`），满 3 张才拒绝下单；
- **付款闸门**（`src/app/api/pay/vmq/create/route.ts:123`）数的同样是收款单，满 3 张拒绝发起付款。

对方的脚本先下 1 单并付款（1 张收款单）→ 4 秒内再连下 5 单（此时收款单还是 1 张，5 单全部放行）→ 逐个发起付款，
第 2、3 张成功、第 4–6 张被 429。于是 6 单 3 收款单。

代码注释写了为什么下单闸门不数订单：**没发起过付款的订单永远不会被自动取消**，数订单的话，放弃过订单的正常买家会被永久锁住。
所以真正的漏洞是两件事叠在一起：**下单闸门数错了对象 + 未付款订单没有过期机制**。修法见 3.1。

## 二、P0：今天就能做，不用构建

### 2.1 关掉源站公网 80，让所有流量只能经过 Cloudflare【抗 DDoS 的头号缺口】

现状（10-15 实测）：服务器 `182.92.209.103` 的 80 端口对公网开放，nginx 8080 是 `default_server`，**任何 Host 都会转进站点**。
这意味着：

- 全网扫描器（Censys / Shodan / FOFA）按页面标题就能把这个 IP 和 bigolab.com 对上——源站 IP 等于公开的；
- 一旦有人直接打源站 IP，**Cloudflare 的 WAF、限速、DDoS 吸收全部失效**，1.8G 内存的机器几百并发就会卡死，主站和 jishi 一起倒；
- Cloudflare 隧道是**出站**连接，站点对外服务根本不需要任何入站端口。

`docs/nginx-真实IP修复-部署说明.md` 第七节早已提议关掉，至今没做。做法：

1. `docker-compose.yml` 里 nginx 的 `ports` 改成 `"127.0.0.1:80:8080"`（只留给服务器本机 curl 冒烟），
   `up -d --no-deps --force-recreate nginx`（站点断几秒，选低峰）；
2. 阿里云安全组入方向删掉 80 / 443（第二层保险）。

同时要站长确认的其它对外端口（不属于本站，但在同一台机器上，被打一样会拖垮本站）：

| 端口 | 是什么 | 建议 |
|---|---|---|
| 22 | sshd，`PermitRootLogin yes`（仅密钥） | 服务器操作已全部走 Workbench，安全组里 22 可以只放行自己的 IP 或干脆关掉 |
| 81 | 另一个 docker 站点（jishi？） | 同理，若也走隧道就只绑 127.0.0.1 |
| 8443 | RDViewer `rdvserver` | 按 rdviewer 自己的设计确认是否必须公网直连 |

### 2.2 Cloudflare 后台（站长自己点，不碰服务器）

1. **封这两个 IP**：Security → WAF → Tools → IP Access Rules，`103.151.173.99`、`76.74.220.173` Block（对方会换，属于止血不是根治）。
2. **自定义规则：直接拦扫描路径**（命中的全是扫描器，真人永远不会访问）：
   URI 路径包含 `/.env`、`/.git`、`wp-login`、`wp-content`、`xmlrpc.php`、`/actuator`、`phpmyadmin`，或以 `.php` 结尾 → Block。
3. **速率限制规则**（免费版一般只给一条，以后台实际显示为准）：`/api/` 下的 POST，同一 IP 10 秒内超过 20 次 → Block。
   正常买家一次下单 + 付款只有个位数 POST。
4. **别开的东西**：
   - **Bot Fight Mode 不要开**：它会拦掉手机上 SmsForwarder 推到账通知（`/api/pay/sms-notify`）、第二站的发卡接口、微信机器人回调——
     免费版没法给这些路径开例外，**到账通知一断，所有订单都付了款却不发货**；
   - **Under Attack Mode 只在真被打的时候临时开**，同样会挡住上面这些机器回调；更好的应急做法见 4.4；
   - 不要按国家封海外：客户里有不少港澳台与海外 gmail 用户。

## 四、P2：纵深防御与可观测性

### 4.1 nginx 按真实 IP 限速（Cloudflare 之后的第二道闸）

nginx 现在完全没有 `limit_req`，任何洪水都直接打到 Node。nginx 已经通过 realip 拿到真实访客 IP，可以加：

| 区 | 匹配 | 速率 | 说明 |
|---|---|---|---|
| `auth` | `/api/auth/` | 1 次/秒，突发 10 | 登录、注册、发码 |
| `api_write` | `/api/` 下的写请求 | 5 次/秒，突发 20 | 下单、付款、上传 |
| `general` | 其余 | 30 次/秒，突发 100 | **要宽**：一次正常翻页会触发十几个 `_rsc` 预取请求（日志实测 2 秒内 15 个） |

超限返回 429。共享内存各 10MB（约 16 万个 IP），对 1.8G 内存可以忽略。SmsForwarder、发卡 API、Googlebot 的频率都远低于阈值。
改 nginx 要 `--force-recreate nginx`（断几秒）。

### 4.2 安全告警与日报（复用微信机器人）

- **实时**：蜜罐命中、自动封号、一次性邮箱注册被拦、单人 5 分钟多单、后台新 IP 登录、到账未匹配（已有）。
- **每日安全简报**（早上 9 点）：昨日 404 最多的 5 个 IP、429 / 403 次数、新注册按邮箱域名分布、新账号未付单数、自动封禁名单。

### 4.3 日志留存：现在只够查 38 小时

nginx 日志走 docker json-file，`20MB × 5` 个文件，本次实测最早只能查到 38 小时前。被攻击往往隔几天才发现。
建议另写一份**只含 `/api/` 与所有 4xx / 5xx** 的安全日志到宿主机目录，按天切割、gzip、保留 30 天（体积估计每天几 MB）。

### 4.4 被 DDoS 时的应急手册（写进交接文档）

1. Cloudflare 加一条临时自定义规则：**页面路径**（排除 `/api/pay/sms-notify`、`/api/inventory/`、`/api/bot/`、`/api/mkt/`）→ Managed Challenge。
   比 Under Attack Mode 好：机器回调不受影响，到账发货不断；
2. 若打的是源站 IP：说明 2.1 没做，立刻在安全组关 80；
3. 机器内存吃紧时先停 jishi 三容器给主站腾内存（同构建时的做法）；
4. 事后把攻击 IP 段加进 IP Access Rules。

### 4.5 备份：现在没有自动备份

服务器上只有部署前手工打的 dump，**和数据库在同一块盘上**。被黑、误删、磁盘故障都会连备份一起没。
机器上装着阿里云云备份客户端（`hbrclient`），请站长在控制台确认是否有备份策略在跑；没有的话建议：

- 每天凌晨 `mysqldump` + 校验 `Dump completed` + gzip，上传阿里云 OSS（异地），保留 14 天；
- 或开 ECS 云盘自动快照（按天，保留 7 天）。两者都有最省事。

### 4.6 其他小项

- 上传接口只校验文件头，「PNG 文件头 + 垃圾数据」也能传上去（本次那个 72 字节文件）。目前以 `image/png` + `nosniff` 发出所以无害，
  后续可加「能否解出宽高」的校验（不引 sharp，读 IHDR / SOF 即可）。
- HSTS 仍是 `max-age=300`（10-07 起待定）。
- Next 14.2.35 已含 middleware 绕过（CVE-2025-29927）与 RSC 相关修复，暂无需升级。

## 五、越权（IDOR）复查结果

10-15 对 `src/app/api/` 下除 `admin/`、`cron/` 外的全部路由做了只读扫描（`partner/*` 只核对守卫与查询范围）。
**没有发现能读到或改动别人订单、余额、券、发票、卡密的越权或批量赋值漏洞**——与对方这次实测的结果一致。

对方重点试过的几处，代码层面也确认是安全的：

- `PATCH /api/account/profile`：zod 只放行 `nickname`，写库条件 `{ id: user.id, status: 1 }`；
- `GET /api/orders`：完全不读 `userId` / `all` / `paid` / `status`，基础条件固定为本人 + 本店面；
