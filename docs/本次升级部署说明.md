# 本次升级 · 服务器部署说明

> 适用于本次「列表分页 + 卡密对象化 + 卡密数据分析 + 订单筛选与利润 + 收款监控去 VmqApk + 收据来源与手动开具 + 用户详情页 + 发票必选项 + 一批现存缺陷修复」的升级。
> 服务器路径 `/opt/beiguo/beiguo-shop`，`.env.production` 是 `.env` 的软链，docker network `beiguo-shop_app-network`。

---

## 一、数据库变更清单

全部是**新增可空列 / 新增带默认值的非空列 / 新增索引 / 放宽 NOT NULL**，MySQL 与 Prisma 都判为非破坏性变更。
**本次没有任何删列、改列名、缩短字段长度或新增唯一约束**，所以不会丢数据。

| 表 | 变更 | 说明 |
|---|---|---|
| `card_keys` | 新增 `cost` `sold_price` `profit`（Decimal 可空）、`redeem_url`（可空） | 成本 / 售价快照 / 利润；`profit=NULL` 表示「利润未知」，不是 0 |
| `card_keys` | 新增索引 `(status, used_at)`、`(product_id, batch)` | 按发出时间聚合、按批次批量改成本 |
| `orders` | 新增索引 `(created_at)`、`(pay_status, paid_at)` | 后台订单深翻页与按到账日聚合 |
| `receipts` | 新增 `source`（默认 `'BUYER'`）、`items`（Text/JSON）、`remark`、`issued_at`、`updated_at`（可空） | 来源标记 + 手动开具的 DIY 条目 |
| `receipts` | `claude_account`、`subscription_type` 由 NOT NULL 放宽为可空 | 手动开具的收据没有订阅账户/类型 |
| `receipts` | 新增索引 `(source)` | 后台按来源筛选 |
| `invoices` | 新增 `show_ai_wording`（Boolean 可空） | 买家申请发票时的必选项 |
| `announcements` | **新建表** | 站点公告（后台「系统设置」发布，买家进入前台弹窗）。新建表不影响任何现有数据 |

**关于历史数据**：
- `receipts.source` 是「NOT NULL + 默认值」，MySQL 执行 ALTER 时会把全部历史行自动填成 `BUYER`——**这就是回填手段本身**，不需要额外脚本。
- `invoices.show_ai_wording` 刻意做成**可空**而不是 `default(true)`：历史发票和管理员手工建的空壳记录应显示「—」，不能误标成「买家选择了展示」。
- `card_keys` 的三个金额列需要跑一次回填脚本（见第三步）。

> ⚠️ `scripts/deploy.sh` 第 51 行写死了 `--accept-data-loss`，任何破坏性变更都不会有提示。本次变更全部安全，但以后改 schema 前请自己 diff 一遍字段名，确认是「新增」而不是「重命名」——Prisma 把重命名视为 DROP + ADD。

## 二、部署顺序（不可颠倒）

```
① git pull  →  ② prisma db push（加列）  →  ③ 重新构建并启动  →  ④ 跑回填脚本
```

- **先 db push 再构建**：新代码会读 `cost/profit` 等列，列不存在会 500。
- **回填必须放在最后**：回填脚本用的是容器里的 Prisma Client，而 Client 是在 `docker compose build` 时用新 schema 生成的。
- ③ 和 ④ 之间有几分钟窗口期，卡密列表的利润列会显示「未知」，跑完 ④ 即恢复正常，不影响交易。

## 三、服务器命令

### 0）先备份数据库（建议）

```bash
cd /opt/beiguo/beiguo-shop
set -a; . ./.env.production; set +a
docker compose exec -T db mysqldump -uroot -p"${MYSQL_ROOT_PASSWORD}" beiguo_shop > ~/backup_$(date +%Y%m%d_%H%M).sql
ls -lh ~/backup_*.sql | tail -1
```

### 1）拉代码

```bash
cd /opt/beiguo/beiguo-shop
git pull
```

### 2）加列（prisma db push）

先确认 swap 还在（1.8G 内存无 swap 时 db push 会被 OOM Killed）：

```bash
free -h
```

若 Swap 为 0，先加 2G：

```bash
sudo dd if=/dev/zero of=/swapfile bs=1M count=2048
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

然后用临时容器跑 db push（生产镜像里没有 prisma CLI 本体，必须用国内镜像源拉引擎，否则会卡死）：

```bash
cd /opt/beiguo/beiguo-shop
set -a; . ./.env.production; set +a
docker run --rm --network beiguo-shop_app-network \
  -v "$PWD/prisma":/work/prisma -w /work \
  -e DATABASE_URL="mysql://root:${MYSQL_ROOT_PASSWORD}@db:3306/beiguo_shop" \
  -e npm_config_registry=https://registry.npmmirror.com \
  -e PRISMA_ENGINES_MIRROR=https://registry.npmmirror.com/-/binary/prisma \
  node:20-alpine sh -c '
sed -i "s/dl-cdn.alpinelinux.org/mirrors.aliyun.com/g" /etc/apk/repositories
apk add --no-cache openssl
npx -y prisma@5.22.0 db push
'
```

> 本次全是新增/放宽，**不需要** `--accept-data-loss`。如果它提示需要这个参数，说明有非预期的破坏性变更，**先停下来排查**，不要直接加参数。

### 3）重新构建并启动

```bash
cd /opt/beiguo/beiguo-shop
docker compose --env-file .env.production build app
docker compose --env-file .env.production up -d
docker compose ps
```

### 4）回填卡密成本 / 售价 / 利润

先干跑一遍看统计（不写库）：

```bash
docker compose exec -T app npx -y tsx prisma/backfill-cardkey-cost.ts --dry-run
```

确认数字合理后正式执行：

```bash
docker compose exec -T app npx -y tsx prisma/backfill-cardkey-cost.ts
```

脚本行为：
- 所有 `cost IS NULL` 的卡回填为 **0**（你的口径：现有卡密成本按 0 算，从今天起再算利润）
- 已发出且挂本站订单的卡：`soldPrice` = 订单金额按张数**按分整数分摊**（最后一张吃余数，保证各卡售价之和 = 订单金额），`profit = soldPrice - cost`
- 外部站发卡（只有 `external_ref`）：`soldPrice/profit` **保持 NULL**，即「利润未知」，不会写 0
- 未使用 / 已停用的卡：不定价
- 只处理 `soldPrice IS NULL` 的卡，**可以重复执行**，不会覆盖后台手工改过的数据；分批 500 条，不会把内存打爆

### 5）验证

```bash
docker compose logs --tail 100 app
```

浏览器逐项确认：

- 后台 → **仪表盘**：新增「网站自助下单（卡密）」分析块
- 后台 → **订单管理**：日期区间、商品分类筛选可用；成本/利润列有值

## 四、上线后最需要盯的一件事

**收款监控的金额识别规则收紧了。** 现在只接受「你已成功收款 X 元」这类强信号，
并且会主动拒绝「上一笔播报：支付宝到账 X 元」（那是上一笔的金额，拿来匹配会把别人的订单标成已支付）。

风险在于：**一笔到账被拒的后果不是「稍后重试」**——20 分钟后 `closeExpired` 会把该订单置为「已取消」，
买家钱付了、页面却显示已取消。

所以上线后第一天请这样盯：

1. 自己下一笔 0.01 元的单，真实付款，确认订单能自动转「已完成」。
2. 后台 →「收款监控」→ 诊断区。被规则拒掉的通知会用**琥珀色高亮**显示，并写明原因：
   - `broadcast_rejected`：播报类通知，按规则拒绝（正常）
   - `no_strong_signal`：没出现强信号词，**这条要重点看**——如果你的手机转发的是别的文案格式，需要调整规则
3. 万一真单被误拒：后台 →「收款监控」→ 找到对应收款单 → 点「补单」，会强制标记已支付并履约（幂等，不会重复发卡）。

本地随时可以重跑识别规则自测：

```bash
npx tsx scripts/check-amount-parse.ts
```

## 五、回滚

```bash
cd /opt/beiguo/beiguo-shop
git log --oneline -5          # 找到升级前那个 commit
git checkout <上一个commit>
docker compose --env-file .env.production build app
docker compose --env-file .env.production up -d
```

新增的数据库列是可空的，旧代码不读它们，**回滚代码不需要回滚数据库**。
只有 `receipts.claude_account` / `subscription_type` 放宽为可空这一项，
如果回滚后又有手动开具的收据（这两列为 NULL），旧代码渲染收据页会显示空白——概率极低，真遇到把那几条 MANUAL 收据删掉即可。
