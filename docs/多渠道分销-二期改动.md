## 0. 站长原话与拍板

原话：「副站的销量可以和主站保持一致（副站产生的订单销量也加到总销量中），副站产生的订单，在主站中的利润直接计算为副站进货价减去我的成本价，显示到订单管理中。另外副站的订单通知、和各种副站的消息通知，均不再发送到我的 webhook 推送，该站站长可以在设置中心设置推送的方式，可以选择企业机器人，也可以选择邮箱方式推送。另外每个副站可以设置其自己的客服邮箱、客服微信昵称、客服二维码等信息。」

拍板（AskUserQuestion，2026-09-26）：
- **提醒**：「需要站长处理的照推」。新订单、付款、发货、收据、买家留言、渠道站注册这类**纯通知**不再推站长 webhook，改推渠道站长。人工发货或补发、库存不足、待开发票、发票失败、到账或履约异常、渠道售后申请、各类【渠道告警】照推站长，并标明来自哪个渠道。
- **客服信息**：「渠道自己设，未设时显示主站客服」。渠道站长在设置中心填写，超管后台也能查看和修改；渠道没填的项回退主站。

## 1. M1 销量：两站显示同一个总销量

现状：`Product.sales` 在付款时对所有订单（含渠道单）按件累加（`vmq.ts` fulfillOrder、后台标已付），已经是全站合计；渠道单另外累加 `TenantListing.sales`（本店销量）。渠道前台显示的却是 `TenantListing.sales`。

改动：
1. `src/lib/pricing.ts` 的 `listStorefrontProducts`、`getStorefrontProduct`：渠道前台卡片与详情的 `sales` 改为 `Product.sales`，与主站一致。
2. 渠道首页的「累计销量」合计与主站首页同一口径：全站在售商品 `Product.sales` 之和（不是只加渠道上架的那几个）。
3. 渠道后台 `/partner` 商品页保留「本店销量」（`TenantListing.sales`），新增只读列「全站销量」（`Product.sales`）。`PartnerListingDTO` 加 `globalSales`，要在 selects 白名单里登记。
4. 超管「商品授权与进货价」表头「销量」改为「本渠道销量」。
5. **不回填**：渠道单从一开始就计入了 `Product.sales`。
6. 测试：渠道单付款后 `Product.sales` 与 `TenantListing.sales` 都 +qty；渠道前台 `/api/products` 的 sales 等于 `Product.sales`。

## 2. M2 利润：渠道单在后台订单管理显示「进货价 − 成本」

口径（逐单，单位分），抽成纯函数 `src/lib/admin/channel-profit.ts`，列表、汇总、详情三处共用：

```
A  = toCents(order.amount)                 // 渠道售价（不含税）
RG = refundedGoodsCents ?? 0 ; Rg = settleRefundedCents ?? 0
进货净额 P = settleState==='EXCLUDED' ? (A − RG)                      // 成员自买：不给渠道分钱，站长全收
           : mulDivRound(supplyCents, A − min(Rg, A), A)             // tenant/math.ts；未计提(NULL/MISSING)也按快照算
站长所得货款 G = P + (settleLossCents ?? 0) − (RG − Rg)                // 加渠道承担的损失，减站长承担退给买家的货款
成本 C = Σ 该单 USED 卡密 cost（AUTO）| Σ SmsActivation.cost（SMS）| null（MANUAL 或无成本数据）
利润 = G − C；C 为 null → 利润 null（显示「进货 ¥x · 成本未登记」，不能显示成 0 或等于进货价）
AUTO 单里有 cost 为 0/null 的卡：按 0 计，但标 costUnknown，悬停提示「部分卡密成本未录入」
```
- 无退款时 G = supplyCents，利润 = 进货价 − 成本，与站长原话一致；有退款时按上式扣减。悬停提示写明「进货净额（扣除退款）− 成本」。
- 手续费、发票分成利润**不计入**这一列（站长原话只说进货价 − 成本）。详情页的渠道结算区另列一行完整拆分：进货净额、成本、利润，以及手续费收入、发票利润，仅供参考。
- 列表接口：渠道单成本与利润要包含 `payStatus in (PAID, REFUNDED)`；SMS 单按 orderId 批量取 `smsActivation.cost`（与 detail 同口径）。汇总卡把渠道单拆出：渠道流水（渠道售价）、渠道进货净额、渠道利润。
- 页面：「金额」列对渠道单加一行小字「进货 ¥x」；「利润」列对渠道单用上式，提示改为「进货净额 − 成本」。
- 主站单口径与显示**逐字不变**。渠道侧永远看不到成本（不改）。

## 3. M3 通知路由：渠道的纯通知不再推站长，渠道站长自选企业微信或邮箱

### 3.1 停止推站长 webhook（改调用点，不在 notify() 里过滤）
| 调用点 | 改法 |
|---|---|
| `app/api/orders/route.ts` 渠道分支 `notifyOrderCreated` | 删掉 |
| `lib/vmq.ts` fulfillOrder 里的 `notifyOrderPaid`（渠道单） | 渠道单不推；**唯一例外**：`!delivered && deliveryType !== 'SMS'`（人工发货商品，或自动发货但库存不足待补发）→ 推一条精简的「[渠道代码] 渠道单待人工发货 / 待补发」（订单号、商品、件数、原因，不带金额以外的买家信息） |
| `lib/order-billing.ts` `notifyReceiptCreated` | `tenantId !== 1` 不推 |
| `app/api/orders/[id]/messages/route.ts` `notifyBuyerMessage` | `order.tenantId !== 1` 不推（渠道通知 BUYER_MESSAGE 照写） |
| `app/api/auth/register/route.ts` `notifyUserRegistered` | 只在主站店面推；渠道站注册改为渠道通知 `CUSTOMER_JOINED` |

照推站长（不改）：`notifyLowStock`、`notifyInvoiceReady`/`pushInvoiceReady`、`notifyInvoiceFailed`、`notifyFulfillFailed`（终审 2026-09-26：按第 0 节「标明来自哪个渠道」，渠道单加 `[lulu]` 前缀，主站单逐字不变）、`notifyVmqUnmatched`、`notifyWebhookRejected`，以及全部 `alertPlatform`（下单配置异常、快照、计提、对账、收款变更、渠道售后与封禁申请）。已带 site 标签的保持带标签。

### 3.2 渠道推送方式
- 数据（只新增）：`Tenant.noticeWecomOn Boolean @default(true)`、`Tenant.noticeEmailOn Boolean @default(false)`、`Tenant.noticeEmail String? VarChar(120)`、`TenantNotice.emailedAt DateTime?`。两种方式可以同时开。现有按类型的 `noticePrefs` 对两种方式都生效。
- 企业微信：沿用现有加密 webhook 与推送逻辑，`noticeWecomOn=false` 时不推。
- 邮箱：
  - 设置时验证归属：邮箱等于当前操作人的登录邮箱时直接保存（注册时已验证过）；否则发验证码（`verify-code.ts` 新增用途 `NOTICE`，沿用现有限频与 `consumeCode`），验证通过才保存。
  - 发信：`tenant/notice.ts` 在事务提交后按 `noticeEmailOn` 发 `sendTenantNoticeEmail`（新模板，写在 `mail.ts`）。模板要求：
    - 主题「【贝果科技】店铺后台通知：{类型}」；正文是类型、编号、摘要，加一个「前往渠道后台」按钮（`Tenant.origin` + 对应后台路径）。
    - **不含**买家邮箱、卡密、留言正文、免登录链接、财务台链接、微信号、二维码。
    - 发送前过 `findBannedWord`，命中就把摘要降级为「请登录渠道后台查看」。
  - 每个渠道限频：每小时 20 封、每天 100 封，按 `TenantNotice.emailedAt` 计数；超出不发（站内通知照写），并在当天第一次超出时在站内通知里留一条说明。成功后写 `emailedAt`。
- 新增通知类型（`TenantNoticeKind`，列宽 VarChar(24) 够用，不改表）：
  - `CUSTOMER_JOINED`：渠道站有新客户注册；
  - `ORDER_DELIVERED`：站长为渠道单人工发货、补发完成或标记已交付。
  前台文案、设置页偏好开关同步加上。
- 设置中心（`/partner/settings`，OWNER）：「推送方式」卡片，含企业微信机器人开关（沿用已有 webhook 配置）、邮箱开关、邮箱地址（带验证）、各自的「发送测试」按钮。邮件测试的文案不能出现「微信」。
- 超管渠道详情只读显示推送方式：企业微信已配置 / 已开，邮箱已开 + 掩码地址。

## 4. M4 渠道客服信息

### 4.1 数据与回退
- 数据（只新增，可空）：`Tenant.supportWechat VarChar(40)`、`supportQrUrl VarChar(160)`、`supportEmail VarChar(120)`、`supportHours VarChar(40)`。
- 主站客服信息收成常量 `src/lib/contact.ts`：`PLATFORM_CONTACT = { wechat: 'GenuineMarxist', qrUrl: '/wechat-qr.jpg', email: null, hours: '9:00-22:00' }`。主站零查库，**渲染结果逐字不变**。
- 渠道取值：
  - **微信号与二维码作为一组**：渠道设了其中任意一项，就用渠道的（没设二维码则隐藏二维码）；两项都没设则整组用主站的。这样不会出现「渠道微信号 + 主站二维码」的错配。
  - 邮箱、服务时间：渠道的，未设则用主站的（主站当前没有客服邮箱，即不显示）。
- `Storefront` 与 `PublicStorefront` 加 `contact`；`storefront-provider` 的 FALLBACK 用 `PLATFORM_CONTACT`。**不要塞进 features。**

### 4.2 展示点
全仓写死的微信号、二维码、服务时间改为按店面取值：
- 浮动客服、联系弹窗、页脚；
- `/support` 页面与常见问题，含 FAQ 结构化数据；
- 商品列表与详情，含 `product-intro` 服务端文案；
- 订单页；
- 隐私 / 条款页脚（`legal-page`）；
- 停业页可补客服入口。

主站 HTML 在这些点上**逐字不变**（要有测试对比）。

### 4.3 编辑入口
- 渠道后台设置中心「客服信息」卡片（OWNER，`settings.write`，暂停营业时只读）：微信号或昵称、客服邮箱、服务时间，以及二维码上传 / 清除。
  - 新增渠道接口 `PUT /api/partner/settings/contact`（JSON）、`POST /api/partner/settings/contact-qr`（multipart）、`DELETE /api/partner/settings/contact-qr`，都要登记路由总表。
  - 写审计 `settings.contact`，publicDiff 只写哪些字段变了。
- 超管渠道详情「客服信息」卡片：可改同样的字段；二维码走 `/api/upload` 新 scope `contact`（ADMIN）。PATCH 的 zod 只接受合法 qrUrl。

### 4.4 安全
- **二维码**：
  - 只收 png/jpg/webp（按文件头判断，拒绝 gif 与 SVG），≤ 2MB；
  - 存 `public/uploads/contact/`，文件名由服务端随机生成；
  - 每个渠道每小时最多 10 次；
  - 换图或清除时删除旧文件：只删 `contact/` 下、且是库里记录过的那个文件名；
  - `qrUrl` 只由服务端写入，读写两端都校验 `^/uploads/contact/[0-9a-z-]+\.(png|jpg|webp)$`，客户端不能提交 URL。
- **微信号**：`^[A-Za-z0-9_\-一-龥]{1,30}$`，不接受 URL、`@`、`<>`。
- **邮箱**：zod `email()`，≤ 120 字，且 `findBannedWord(email) === null`（避免「5 位以上数字@qq.com」进交易邮件被判违规）。
- **服务时间**：≤ 40 字，只允许数字、空格、`:`、`-`、`~`、`至`、中文。
- **渲染**：一律用 React 文本节点，不用 `dangerouslySetInnerHTML`；JSON-LD 走现有 `JsonLd` 组件转义。

### 4.5 邮件
- `MailOpts` 加 `supportEmail?`，`layout()` 页脚有值时追加「客服邮箱：xxx」。
- `src/lib/storefront/origin.ts` 新增 `tenantMailOpts(tenantId) → { origin, supportEmail }`（主站返回 undefined），渠道交易邮件的四个调用点改用它。
- **微信号与二维码永远不进邮件。** 主站邮件逐字不变。`check-transactional-mail.ts` 加渠道 supportEmail 用例。
