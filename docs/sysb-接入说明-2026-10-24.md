# sysb（HongyunAI）· 2026-10-24 按新版接入说明复核

上游停服升级约两周，10-23 发了新的《鸿运 API 接入说明》（单文件版，`api_revision 2026-10-22`）。
**Token 不变**，仍是 `.env.production` 里的 `SYSB_API_TOKEN`（`hyv2_` 开头）。
这份文件记录新说明和我们原实现的差异、这次改了什么、怎么验的。适配器文件头也有同样的摘要
（`src/lib/redeem/providers/sysb.ts`「2026-10-24」一节）。

## 1. 实测：接口都还在（2026-10-24，本机，只读）

| 请求 | 结果 |
|---|---|
| `GET /account` | 200，`enabled:true`、`integration_ready:true`、`access_profile:gpt1_ios`、`allowed_products:[chatgpt_ios, chatgpt_card]`、`service_status:operational`、`order_worker:online`；限额 `new_orders_per_minute:10`、`query_per_minute:240` |
| `GET /products` | 200，`chatgpt_ios`（ChatGPT iOS 充值）、`chatgpt_card`（ChatGPT 卡冲）都 `accepting_orders:true` |
| `GET /orders/<不存在的号>` | 404 `ORDER_NOT_FOUND`（`resubmit_allowed:false`、`next_action:check_original_order`） |

本机不带 User-Agent 也能通；接入说明说不带时可能被 Cloudflare 403（`error code: 1010`），
服务器出口 IP 更容易触发，所以照说明每次都带。

## 2. 和原实现的差异，以及改法

| # | 新说明 | 原实现 | 改法 |
|---|---|---|---|
| 1 | 每次都带 `User-Agent: HongyunAPI/1.0` | 没带（Node 默认 UA） | `call()` 加上；非 JSON 响应记一行状态码便于认出 1010 |
| 2 | 成功 = `succeeded` **且** `result_confirmed=true` | `result_confirmed !== false` 就认 | 收紧成 `=== true`（`confirmedSuccess`） |
| 3 | 明确失败 = `failed` **且** `result_confirmed=true`；其余继续查原单 | 只看 `failed` | `confirmedFailure`；未确认的 failed 归「暂时无法确认」，不出重试、也不换号重下 |
| 4 | 明确失败时显示 `data.message` | 只用我们的映射文案 | 细分原因 > 过滤后的上游 message（短、无品牌 / 链接 / 对方术语）> 错误码文案 |
| 5 | 新错误码 `SERVICE_NOT_READY`：本次没建单，等 Retry-After 原号原内容重发 | 落到「提交失败」 | 和 `ORDER_QUEUE_BUSY` / `ORDER_WORKER_OFFLINE` 一起走冷却（`COOLDOWN_ERRORS`） |
| 6 | 新错误码 `ORDER_RESULT_UNAVAILABLE`：只继续 GET 原单；「不能凭 404 认定没充值」 | `check()` 里查原单失败一律「当作没充过」出表单 | 只有 404 才继续；其它查询失败回「处理中」并按 Retry-After 冷却 |
| 7 | 信用卡 Session 须保留账号邮箱 | 只校验 accessToken | `chatgpt_card` 额外校验 `user.email`，缺了本地拦下（不扣卡、不计次） |
| 8 | 信用卡卡密为 16 位字母数字 | 只认 `PLUS-…` 形状 | 查卡顺序优化里加上这个形状（只影响先查哪条通道，不影响判定） |

没变的：order_id 规则（`BG-<卡id>-<内容指纹>`，8–64 位）、同内容重发复用原号、
`credential` 传解析后的对象、至少 15 秒轮询一次、`manual_review` 停止自动处理。

## 3. 只读查卡（`sysb-lookup.ts`）也跟着改了

上游的「卡密查询」工具升级后，`POST /api/v1/sub/queryOrder` **不带
`X-Hongyun-Query-View: card-status-v1` 头一律 503 `ORDER_QUERY_UNAVAILABLE`** ——
也就是说升级以来我们的只读查卡在卡付通道上一直是「查不到」（一律退回按商品名兜底，没有误判，
只是看不到在别处充掉的卡）。现在带上这个头。

带头之后每行多了 `card_status_query` / `order_lookup` / `order_scope_incomplete`。按上游自己的判读规则：

- `cdk_status` 是 `unknown` 时，卡的状态取 `card_status_query.status`（`state=matched` 才可信）
- 订单那一半没查全（`order_lookup=unavailable` 等）时，「未使用」**不能当真** → 当「不知道」
- 卡已核销、订单那一半又没给 → 判「上游核对中」，**不能**再说「那一笔没有成功」

站长给的测试卡 `LPGP…P6Z7（16 位，完整卡密不进仓库）` 当前返回 `backend=autosub, cdk_status=unknown, order=null,
order_lookup=unavailable`（编造的卡也一样），所以查卡给不出结论，`check()` 退回按商品名兜底：

```
SYSB_API_TOKEN=… npx tsx scripts/probe-sysb.ts check <测试卡密> "ChatGPT Plus自助充值 | 信用卡冲"
  READY / 渠道 chatgpt_card、chatgpt_ios（Claude 渠道上游已不开通，自动不出现）/ 默认 chatgpt_card / 无上游标识 ✓
```

**没有对这张卡提交充值**（站长要求）。所以真正的 `POST /orders` 在新版上游上还没跑过。

## 7. 当晚：卡#2865 本站失败、官网 66chong.com 成功 —— 卡付改走官网 V1 流程

### 7.1 现象

卡#2865（`BSB6…DYHN`，「ChatGPT Plus自助充值 | 信用卡冲」）19:14 与 19:17 在本站两次提交，
两笔 V2 单（`BG-2865-…`）都在 **1 秒内**失败：`reason_code=CDK_UNAVAILABLE`、`cdk_state=not_verified`、
「卡密暂时无法使用」。买家 19:20 转去官网 66chong.com，30 秒成功（`SUB1792840855…`，`backend=autosub`）。

### 7.2 根因：不是这一张卡，是整条卡付通道

把 10-08 以来 sysb 的单按协议分开看（线上 `redeem_logs` + 逐单 `GET /v2/orders`）：

| 时间 | 卡付走哪条 | 结果 |
|---|---|---|
| 10-08 ～ 10-14 | V1（`TASK…` 单号） | 每天 11～32 张卡充成 |
| 10-15 起 | V2 `chatgpt_card`（`BG-…`） | **一笔都没成**：BG-2256/2380/2466/2469/2525/2561/2345/2585/2586/2865…全是 `CDK_UNAVAILABLE` 秒拒 |
| 同期 | V2 `chatgpt_ios` | 正常成功（BG-2455/2471/2487/2488…） |

链条：10-15 前后上游改版，只读查卡 `queryOrder` 不带新视图头一律 503（第 3 节）→ 查卡结果为 null
→ `decideCardRoute` 把卡付全部落到 V2 → V2 卡付对我们这把 Key 从来不受理这些卡。
上游 10-23 发了新接入说明之后（今天 19:14）依旧秒拒，所以不是「升级还没完成」。
上午我按新说明建议关掉 `SYSB_CARD_V1`，方向是反的 —— 那时没有拿线上数据核对 V2 卡付的成功率。

### 7.3 官网怎么做的（逆向 66chong.com，只读）

- 66chong.com 与 hongyunai.pro 是**同一套前端换了品牌**（页面只差标题/logo，脚本文件逐字相同），后端也是同一个
  （同一张卡两站 `queryOrder` 结果一致；官网成交单的 `order_query_token` 里 `site_id=2`）。
- 区别只在路由：66chong 的 `staff-test-network-0c8fd998463440c0.js` 把 `/api/v1/sub/<x>` 改写成
  `/recharge-api/sub/<x>` 再发；直接打 `/api/v1/sub/*` 会被它的 nginx 404。
- 卡付流程看 `verifyCdk` 返回的 `backend`：
  - **gpt1**：verify → precheckAccount（建任务、预留卡，**不可逆**）→ redeem。token 发 Session 原文 —— 就是 10-09 做的那套。
  - **autosub**（这次的卡）：verify → precheckAccount（**只读核对账号**，官网源码原话 "only verifies the account"）
    → `queryOrder {cdk, activation_token}` 看本次激活下有没有单 → `verifyCdk {…, renew:true}`（**同一个 nonce**）
    → redeem（**唯一的不可逆点**）→ 轮询。token 是 `zstd64:` + base64(zstd(Session 原文))（`card-zstd.js`）。
- `request_nonce` 一张卡一个、存 24 小时（`cardFlowNonce`），renew 必须复用 —— 它是上游给卡做「预留」的钥匙。

### 7.4 改了什么

| 文件 | 改动 |
|---|---|
| `providers/sysb-card-v1.ts` | 默认发往 `https://66chong.com/recharge-api/…`（`SYSB_CARD_ORIGIN` 可切回 hongyunai.pro 原始路径）；新增 autosub 流程 `redeemAutosub`；nonce 改为按卡确定性生成（`cardNonce`）；`zstdRawFrame` / `cardToken` 生成 zstd64 token；`verifyFailure` / `precheckFailure` / `classifyAutosub` 照官网口径分类；`SYSB_CARD_V1` 默认开 |
| `providers/sysb.ts` | `decideCardRoute`：卡付除「查卡说已不可充」外一律走 V1（gpt1 / autosub 都是，查不到也是）；走 V1 前先看这张卡有没有没了结的 V2 单；把 `releaseIrreversible` 交给 V1；备用链接默认改为 66chong.com |
| `docker-compose.yml` | 加 `SYSB_CARD_ORIGIN` |

**为什么自己拼 zstd 帧**：生产镜像是 Node 20，zlib 里还没有 zstd（22.15 / 23.8 才有）。解压端只要帧合法，
不在乎压没压过，所以用 RFC 8878 的 Raw 块 + 帧头写明内容长度。本机用两个独立解码器（Node 自带 libzstd、
python-zstandard 的一次性 decompress）逐字节比对通过，含 300KB 多块的情况。

**锁的位置**：autosub 账号核对是只读的，所以核对失败**不占锁**，买家改了账号直接再交；
锁在查单之前拿，redeem 之前任何一步失败都会放掉（那时这一次请求没碰过写接口）；
redeem 之后只有上游明说「卡已退回」（`card_returned` / `cdk_status=unused`）才放。

**时间预算**：一次 HTTP 请求跑完，外面是 nginx 90 秒。总预算 80 秒，redeem 之前任何一步超预算就停下（卡没动）。

### 7.5 验证（全部没有提交充值）

- `scripts/check-redeem.ts` 581 条（新增：路由改道、别名、nonce、zstd 帧往返、verify/precheck 失败归类、
  autosub 结果判定 —— 其中「成功」那条用的是卡#2865 官网成交单的真实返回形状）。
- 模拟上游跑完整 `redeemCardV1` 10 个场景：调用顺序、请求体、上锁/放锁时机都对。
- **对上游实测（只用站长给的 sysb 测试卡，只调 verify 与只读 precheck，没调 redeem）**：
  - 66chong `verifyCdk` 认出测试卡是 autosub · ChatGPT Plus（180 秒预留，不消耗）。
  - 同一份假 Session 分别用「我们的 Raw 帧」和「真 zstd level 10」发 precheck，**上游回包逐字相同**
    （读出了邮箱和有效期，只因 accessToken 是假的而拒）；故意发坏的 token 则回「登录态数据无效」且读不出邮箱。
    → 上游能正确解我们的帧。
  - precheck 失败时上游常常只给中文不给 `error_code`（如「Token已失效…」），已按关键词归到我们的文案。

### 8.2 ECS 到上游的跨境链路丢包严重（与代码无关）

切换后从容器里实测：按正常 DNS，ECS（182.92.209.103）到 hongyunai.pro 和 66chong.com 都进 Cloudflare
**洛杉矶节点（colo=LAX）**，TCP 连接 0.2~0.3 秒就建好了，但 TLS 握手和数据传输大量丢包：

「无法连接充值服务 / 响应超时」（那时没有在构建）就是这个。66chong 和 hongyunai 一样差，换站没用。

逐个试 Cloudflare 的入口地址（`curl --resolve`，SNI 不变）：

| 入口 | colo | 结果 |
|---|---|---|
| 正常 DNS（104.21.x / 172.67.x） | LAX | 约三分之一超时，成功 3~15 秒 |
| 104.18.x / 172.64.x / 188.114.x / 104.24.x | LAX | 同上 |
