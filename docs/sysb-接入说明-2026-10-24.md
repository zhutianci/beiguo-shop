# sysb（HongyunAI）· 2026-10-24 按新版接入说明复核

上游停服升级约两周，10-23 发了新的《鸿运 API 接入说明》（单文件版，`api_revision 2026-10-22`）。
**Token 不变**，仍是 `.env.production` 里的 `SYSB_API_TOKEN`（`hyv2_` 开头）。
这份文件记录新说明和我们原实现的差异、这次改了什么、怎么验的。适配器文件头也有同样的摘要
（`src/lib/redeem/providers/sysb.ts`「2026-10-24」一节）。

## 1. 实测：接口都还在（2026-10-24，本机，只读）

| 请求 | 结果 |
|---|---|
| `GET /account` | 200，`enabled:true`、`integration_ready:true`、`access_profile:gpt1_ios`、`allowed_products:[chatgpt_ios, chatgpt_card]`、`service_status:operational`、`order_worker:online`；限额 `new_orders_per_minute:10`、`query_per_minute:240` |
| `GET /products` | 200，`chatgpt_ios`（ChatGPT iOS 充值）、`chatgpt_card`（ChatGPT 卡冲）都 `accepting_orders:true` |
| `GET /orders/<不存在的号>` | 404 `ORDER_NOT_FOUND`（`resubmit_allowed:false`、`next_action:check_original_order`） |

本机不带 User-Agent 也能通；接入说明说不带时可能被 Cloudflare 403（`error code: 1010`），
服务器出口 IP 更容易触发，所以照说明每次都带。

## 2. 和原实现的差异，以及改法

| # | 新说明 | 原实现 | 改法 |
|---|---|---|---|
| 1 | 每次都带 `User-Agent: HongyunAPI/1.0` | 没带（Node 默认 UA） | `call()` 加上；非 JSON 响应记一行状态码便于认出 1010 |
| 2 | 成功 = `succeeded` **且** `result_confirmed=true` | `result_confirmed !== false` 就认 | 收紧成 `=== true`（`confirmedSuccess`） |
| 3 | 明确失败 = `failed` **且** `result_confirmed=true`；其余继续查原单 | 只看 `failed` | `confirmedFailure`；未确认的 failed 归「暂时无法确认」，不出重试、也不换号重下 |
| 4 | 明确失败时显示 `data.message` | 只用我们的映射文案 | 细分原因 > 过滤后的上游 message（短、无品牌 / 链接 / 对方术语）> 错误码文案 |
| 5 | 新错误码 `SERVICE_NOT_READY`：本次没建单，等 Retry-After 原号原内容重发 | 落到「提交失败」 | 和 `ORDER_QUEUE_BUSY` / `ORDER_WORKER_OFFLINE` 一起走冷却（`COOLDOWN_ERRORS`） |
| 6 | 新错误码 `ORDER_RESULT_UNAVAILABLE`：只继续 GET 原单；「不能凭 404 认定没充值」 | `check()` 里查原单失败一律「当作没充过」出表单 | 只有 404 才继续；其它查询失败回「处理中」并按 Retry-After 冷却 |
| 7 | 信用卡 Session 须保留账号邮箱 | 只校验 accessToken | `chatgpt_card` 额外校验 `user.email`，缺了本地拦下（不扣卡、不计次） |
| 8 | 信用卡卡密为 16 位字母数字 | 只认 `PLUS-…` 形状 | 查卡顺序优化里加上这个形状（只影响先查哪条通道，不影响判定） |

没变的：order_id 规则（`BG-<卡id>-<内容指纹>`，8–64 位）、同内容重发复用原号、
`credential` 传解析后的对象、至少 15 秒轮询一次、`manual_review` 停止自动处理。

## 3. 只读查卡（`sysb-lookup.ts`）也跟着改了

上游的「卡密查询」工具升级后，`POST /api/v1/sub/queryOrder` **不带
`X-Hongyun-Query-View: card-status-v1` 头一律 503 `ORDER_QUERY_UNAVAILABLE`** ——
也就是说升级以来我们的只读查卡在卡付通道上一直是「查不到」（一律退回按商品名兜底，没有误判，
只是看不到在别处充掉的卡）。现在带上这个头。

带头之后每行多了 `card_status_query` / `order_lookup` / `order_scope_incomplete`。按上游自己的判读规则：

- `cdk_status` 是 `unknown` 时，卡的状态取 `card_status_query.status`（`state=matched` 才可信）
- 订单那一半没查全（`order_lookup=unavailable` 等）时，「未使用」**不能当真** → 当「不知道」
- 卡已核销、订单那一半又没给 → 判「上游核对中」，**不能**再说「那一笔没有成功」

站长给的测试卡 `LPGP…P6Z7（16 位，完整卡密不进仓库）` 当前返回 `backend=autosub, cdk_status=unknown, order=null,
order_lookup=unavailable`（编造的卡也一样），所以查卡给不出结论，`check()` 退回按商品名兜底：

```
SYSB_API_TOKEN=… npx tsx scripts/probe-sysb.ts check <测试卡密> "ChatGPT Plus自助充值 | 信用卡冲"
  READY / 渠道 chatgpt_card、chatgpt_ios（Claude 渠道上游已不开通，自动不出现）/ 默认 chatgpt_card / 无上游标识 ✓
```

**没有对这张卡提交充值**（站长要求）。所以真正的 `POST /orders` 在新版上游上还没跑过。

## 4. 卡付 V1 分叉（`SYSB_CARD_V1`）

10-09 那版为了绕过「V2 对 gpt1 卡 0 成功」走了上游面向浏览器的 V1 三段式。新说明把「SUB 信用卡」
明确放进 V2（`access_profile=gpt1_ios`），V1 那套又是非公开接口、这次升级后形状已经变了
（查卡要新头，见上一节）。**建议把 `SYSB_CARD_V1` 关掉（不设或设 0），全部走文档里的 V2。**
代码没删 V1 分支，开关打开时行为与原来一致；且按现在上游查卡的返回，未使用的卡认不出 backend，
V1 分支实际上也走不到。

## 6. 第一次真实充值要盯的

1. 提交后页面进「正在充值」，≥15 秒查一次；`redeem_logs` 里应先有 `BG-…` 订单号
2. 成功判定现在要求 `result_confirmed=true` —— 如果上游成功了却一直显示「暂时无法确认」，
   用 `probe-sysb.ts order BG-…` 看原单里有没有这个字段，再决定是否放宽
3. 服务器侧若出现 `[sysb] 非 JSON 响应 … status=403 body=error code: 1010`，说明 UA 仍被拦，联系上游
