# 集成点地图：新增「通用短信接码」板块

仓库根目录 R = `D:/selfData/code/selling system/ai-service-shop`，下文路径都相对 R，格式为 `文件:行号`。本次只读，没有改任何代码，也没有调用 hero-sms 的任何 action。

---

## 0. 先说结论：最影响设计的 6 个事实

1. **现有接码是「一个商品对应一组固定服务+国家」。** 服务、国家、成本上限三个参数挂在 Product 上（`prisma/schema.prisma:101-104`），取号时从商品读（`src/lib/vmq.ts:1456-1467`），换号时也从商品读（`src/lib/sms.ts:277-284`）。新板块要求每一单各自带服务、国家、运营商和报价快照，现有 schema 里没有地方放这些。
2. **支付不是支付宝官方接口。** 实际流程是：买家扫个人收款码并手输金额，安卓手机上的 SmsForwarder 把到账通知转发给网站，网站按「唯一金额」匹配订单。
   - 每单金额会从原价起加 0.01～0.49 来区分（`src/lib/vmq.ts:224-273`，买家界面见 `src/app/pay/[orderId]/page.tsx:148-167`）。
   - 每人最多同时挂 3 张待付款单（`vmq.ts:95`），20 分钟过期（`vmq.ts:33`）。
   - 对「几块钱一单、一次买好几个号」的接码场景，这套流程摩擦很大。
3. **没有自动退款。** 接码超时或被上游取消时，只是在订单备注里追加【待退款】（`src/lib/sms.ts:140,173`）。之后要站长手工改订单状态，再线下原路退钱（`src/app/api/admin/orders/[id]/route.ts:870`）。这个过程没有推送，后台也没有筛选入口。
4. **站内余额存在，但只能用于提现。**
   - 余额只来自推荐返现和后台手工调整，买家可以找客服提现。
   - 全站没有「用余额付款」，也没有「充值」（`src/app/api/account/wallet/route.ts:11-17`；`src/app/(shop)/wallet/page.tsx:11-13,214`）。
   - 数据库里的付款方式枚举已经有 BALANCE 这个值，但没有任何代码用它。
5. **建新订单必须挂一个商品，而现有商品机制对新板块不友好。**
   - 全仓只有 `createShopOrder` 这一个地方允许建订单，构建前的边界检查（规则 7）会拦截其他写法。订单的 productId 必填且有外键，所以新板块必须有一个「载体商品」。
   - 载体商品如果设为上架（status=1），会出现在商品列表、站点地图、落地页等所有地方；设为下架（status=0），下单和发起支付都会拒绝。
   - 发起支付时还会拿商品当前标价和下单时的标价快照比对（`src/app/api/pay/vmq/create/route.ts:99`）。接码是动态定价，走这条路必然被拒，提示「商品价格已调整」。
6. **成本数据的币种和精度有问题，而且是现存问题。**
   - hero-sms 的价格是美元（`docs/接码-国家与卡类代码.md:24-37`）。
   - 接码记录的成本列是 2 位小数（`schema.prisma:305`），存不下 $0.0189 这类价格。
   - 渠道利润计算把这个成本当成人民币元来用（`src/lib/admin/channel-profit.ts:43,83`）。
   - 主站的接码订单在后台完全没有成本和利润展示。

## 1. 现有接码全链路

### 1.1 上游客户端 `src/lib/herosms.ts`
- `:4` 上游地址可以用环境变量 HEROSMS_BASE 覆盖。集成测试就是把它指向一个不可达的本地端口来模拟上游（`scripts/itest-order-void.ts:24-25`）。
- `:6` 等码超时 HEROSMS_TIMEOUT_MIN 默认 15 分钟。
- `:12-24` 底层请求函数：GET 请求、不缓存，**但没有设置超时**。上游一旦卡住，定时轮询和买家请求都会跟着卡住。
- `:36-66` 取号函数（getNumber）：
  - 同时兼容 JSON 和纯文本两种返回。
  - 纯文本形态（`ACCESS_NUMBER:id:phone`）拿不到成本（`:62`），线上的成本多半是空的。
  - 不支持选运营商（operator）参数，而运营商很可能就是需求里说的「号码地区」。
- `:75-97` 查码只用了第一版的 getStatus 接口。
- `:100-106` 改状态只封装了 8（取消）和 6（完成），没有 3（请求再发一条短信）。
- 缺少只读接口的封装：服务列表、国家列表、价格、运营商、余额、批量查询进行中的号码（getActiveActivations）都没有。其中四个只读 action 已在 `docs/接码-国家与卡类代码.md:6-14` 实测过。

**对新设计的含义：** 这一层要扩展，包括只读的目录与价格、能拿到美元成本的第二版取号、运营商参数，并统一加请求超时。

### 1.2 核心逻辑 `src/lib/sms.ts`
- `:16-20` 备注追加函数，超过 255 字时丢掉最早的内容、保留最新的。
- `:37-95` 付款后取号（acquireForOrder）：
  - **只要这一单已有接码记录就直接返回**（`:38-39`）。
  - 未配置密钥或取号失败时，记录写成 FAILED，并在备注里写「待客服处理」（`:43-67`）。
  - 写库时撞上唯一约束，就把刚买到的号放掉，避免孤儿号（`:85-94`）。
- `:107-180` 状态轮询（pollActivation），所有写入都是条件更新（CAS），条件钉住「读到的这个号且仍在等码」：
  - 订单未付款或已取消 → 放掉号码（`:122-133`）。
  - 超时 → 记为超时、向上游取消、备注追加【待退款】（`:136-142`）。
  - 收到码 → 记为已收码、向上游确认完成、订单从待交付改为已交付、结算推荐返现（`:152-169`）。
  - 上游取消 → 记为取消、备注追加【待退款】（`:171-175`）。
- `:187-200` 后台取消或退款订单时，同步停掉还在等码的号（cancelActivationForOrder）。
- `:203-216` 定时兜底轮询（pollAllWaiting）：**逐单串行，每单调一次上游**。
- `:223` 最多换 3 次、`:226` 两次换号间隔 120 秒，都是写死的常量。
- `:261-341` 换号（retryActivation）：
  - 顺序是：先取新号 → 用条件更新把记录切到新号 → 最后放掉旧号。
  - 只有等码中可以换；已收到码后拒绝换号（`:264-266`），这正好对应需求「接码成功后不能再换号」。
  - **换号直接覆盖同一行记录，旧号的历史只留在备注里**（`:338`）。
- 收到码后立即告诉上游「完成」（`:158`），所以同一个号不能再收第二条短信。

**对新设计的含义：** 条件更新的写法、「先取新号再放旧号」的顺序、订单取消后的拦截，都应原样复用。但有三处和通用板块不兼容：「已有记录就直接返回」、「参数从商品读」、「换号覆盖同一行」。

### 1.3 买家界面 `src/components/order-sms.tsx`
- 每 5 秒请求一次状态接口（`:29,39`），状态不再是等码中就停止（`:46-51`）。
- 倒计时按「绝对时间减当前时间」每秒重算（`:53-68`），切到后台再回来不会走慢。
- 换号按钮调用换号接口（`:82`）。
- 提示文案写死了「OpenAI 等」（`:117`），通用板块要改。
- 超时或取消时显示「订单已标记退款处理，请联系客服」（`:182-187`）。
- 这个组件只挂在「我的订单」详情里（`src/app/(shop)/orders/page.tsx:1049-1054`），并且只对发货方式为 SMS 的商品显示。

### 1.4 买家接口
- `src/app/api/orders/[id]/sms/route.ts`（查询接码状态）：
  - 必须登录（`:16-17`），查询条件里带本人和本站，防止越权（`:23`）。
  - 未付款报错（`:32`），非接码商品返回「没有接码信息」（`:33`）。
  - **查询接口里会自动补取号，这是会花钱的动作**（`:38-50`）。
  - 每次查询都会调一次轮询，也就是打一次上游（`:52`）。
  - 返回可换号的绝对时间点（`:59-70`）。
- `src/app/api/orders/[id]/sms/retry/route.ts`（换号）：POST 请求，校验归属（`:34`）；进程内限流，每单 10 分钟最多 8 次（`:47`）；业务规则都在 lib 里（`:51`）。

**对新设计的含义：** 每个开着页面的买家，每 5 秒就触发一次上游查询。接码量上来后需要节流，例如记录「上次查询时间」、几秒内不重复查，或改成一次批量查询所有进行中的号。

### 1.5 定时轮询
`src/app/api/cron/sms-poll/route.ts:13-15`：先做定时任务鉴权，再调兜底轮询。`cron/crontab:32` 配置为每分钟一次，单次最长 50 秒。

### 1.6 `pay/sms-notify` 是什么
**这是收款监控，不是接码。** `src/app/api/pay/sms-notify/route.ts:7-15` 接收 SmsForwarder 转发来的支付宝到账通知，交给 `vmq.ts:1088` 的处理函数，再由 `vmq.ts:537` 按金额匹配订单。名字里的 sms 指安卓的短信/通知转发。

### 1.7 Product 上的接码字段
- `schema.prisma:101` 发货方式是字符串列（MANUAL / AUTO / SMS），不是枚举，可以加新值，但 fulfillOrder 等多处写的是「等于 'SMS'」的判断。
- `:102` 服务代码；`:103` 国家代码，留空表示随机地区；`:104` 取号最高价（美元，2 位小数）。
- 后台编辑界面在 `src/app/admin/products/page.tsx:551,578-612`。
- 公开的商品接口用字段白名单（`src/lib/product-select.ts`，理由见交接文档 2095-2105），这三列不会外泄。

### 1.8 取号的触发位置：`src/lib/vmq.ts` 的 fulfillOrder（从 `:1180` 开始）
- `:1187-1226` 付款确认：在一个事务里把订单从「待付款」改为「已付款」，同时记支付流水、加销量。只有真正完成这次状态翻转的那一次调用算「赢家」。
- `:1371-1373` 非自动发货的商品，赢家把订单置为「处理中」。
- **`:1456-1467` 只有「接码商品 且 是赢家」才取号。** 这一步必须排在「置为处理中」之后，`sms.ts:114-121` 的注释要求保持这个顺序。
- 后台手工标记已付款不走这个函数，要等买家打开订单页，由查询接口自动补取号。

### 1.9 超时与【待退款】
- 超时后订单停在「已付款 + 处理中」。
- 在站长手工取消之前，这类订单照样计入仪表盘总收入（`src/app/api/admin/stats/route.ts:24-27`）、会员等级消费额（`src/lib/vip-server.ts:41-42`）和营销「已购用户」。
- 超时没有企业微信推送，后台也没有筛选。全仓搜「待退款」，只有备注追加和注释。

### 1.10 后台如何看接码记录
**主站后台看不到号码和验证码。**
- 订单详情只在「渠道单」那一段读取接码成本和状态来算利润（`src/app/api/admin/orders/[id]/detail/route.ts:316,321`）。
- 订单列表也只给渠道单算接码成本（`src/app/api/admin/orders/route.ts:43`）。
- 主站接码单的成本和利润是空的，列表只汇总卡密的成本（同文件 `:99-101`）。
- 反倒是渠道后台能看到号码和状态（`src/lib/partner-services/selects.ts:110-117`）。
- 主站后台唯一能看到的是订单备注里的换号、超时流水。

## 2. 下单与支付

### 2.1 建单入口 `src/app/api/orders/route.ts` 的 POST（`:415`）
按执行顺序：
- 先解析店面，并且不放进 try（`:417`）。
- 强制登录（`:420-423`）。渠道站走单独的分支（`:436`）。
- 商品必须是上架状态（`:445`）。
- 每人待付款的收款单达到 3 张就拒绝（`:463`）；另有 10 分钟 20 单的下单限流（`:470`）。
- 定价走 resolveUnitPrice，其中包含推荐人专属价（`:484`）。
- 开票字段的校验和抽奖配置的读取，都必须放在锁优惠券之前（`:506`、`:523`）。
- 用条件更新锁定优惠券（`:544-`）。
- 建订单和抽奖资格在同一个事务里（`:640-661`）。
- 发企业微信「新订单」推送（`:689`）。
- 参数校验：商品 id 必填、每单最多 10 件、备注最多 200 字（`:37-73`）。

### 2.2 唯一建单函数 `src/lib/order/create-shop-order.ts`
- 全仓只有这里允许建订单（`:1-3`），构建前检查的规则 7 会拦截其他写法（`scripts/check-tenant-boundary.mjs:890`）。
- 主站订单不得带渠道快照（`:99-101`）。
- 订单金额永远不含税（`:155`）。

### 2.3 订单必填字段与载体商品
- **必填**：订单号、用户、商品 id（外键指向 Product，`schema:195,262`）、商品名（最长 100 字，`:196`）、单价、数量、金额。其余字段可空或有默认值。
- **没有「虚拟商品」先例**：Product 只有上架（1）和下架（0）两种状态，也没有「隐藏」字段。

**载体商品会撞上的问题：**
- 如果设为上架，它会出现在：
  - 商品列表页（`src/app/(shop)/products/page.tsx:46-47`）和商品接口（`src/app/api/products/route.ts:32`）
  - 站点地图（`src/app/sitemap.ts:170-171`）和落地页（`src/lib/landing/products.ts:72-73`）
  - 商品详情页、营销快照、推荐价格列表、渠道可上架的商品里
- 如果设为下架，建单（`:445`）和发起支付（`src/app/api/pay/vmq/create/route.ts:78`）都会拒绝。

### 2.4 发起支付 `src/app/api/pay/vmq/create/route.ts`
- 必须登录（`:33-34`），订单必须属于当前站点（`:44`）。
- 已有到账的收款单时拒绝重复发起（`:51-55`）。
- **新发起一张收款单时会复核三件事**：
  - 订单建单后 24 小时内（`:25,71`）
  - 商品仍在售（`:78`）
  - 商品标价没变（`:99`）
- 每人待付款上限（`:104`）；复核优惠券（`:109-128`）。
- 收款金额 = 货款 + 开票税费（`:138-146`）。
- 建单后再数一次，超过上限就作废自己这张（`:152-155`）。
- 返回收银台地址 `/pay/<收款单号>`（`:157-163`）。

**对新设计的含义：** 动态报价的订单必须绕开或改造 `:99` 的比价和 `:71` 的 24 小时窗口。报价的有效期应该不超过收款单的 20 分钟。

### 2.5 收款单与到账匹配 `src/lib/vmq.ts`
- 收款单有效期默认 20 分钟（`:33`）。
- 唯一金额分配（`:224-273`）：
  - 从原价开始每次加 1 分，最多试 50 个金额，全站共用。
  - 刚用过的金额冷却 15 分钟（`:89`）。
- 建收款单时锁住订单行、在锁内复核价格（`:289-400`）。
- 收款单只支持「订单」和「发票」两种业务类型（`schema:516-532`）。
- 到账匹配（`:537`）：
  - 按「分」精确匹配；同时命中多张时转人工（`:549-563`）。
  - 匹配不到或迟到的到账，进入「待人工核实」（`:564-604`）。
- 标记到账（`:682-735`）：用条件更新把收款单从待付改为已付，同时钉住金额，然后调 fulfillOrder。
- 履约如果抛错，不向外抛出，而是由定时对账在 3 分钟宽限期后补做（`:841,854`）。

### 2.6 幂等
- fulfillOrder 以「待付款 → 已付款」这一次条件更新为唯一赢家（`:1187-1193`）。
- 非赢家跳过发货和取号（`:1290-1307`）。
- 后台强制补单也走 fulfillOrder（`:956-972`）。
- fulfillOrder 里付款方式写死为支付宝（`:1190,1201`）。

### 2.7 超时关单
- `cron/crontab:30` 每分钟调用 `src/app/api/cron/vmq-close/route.ts`，执行 closeExpired（`vmq.ts:140`）：逐条用条件更新关闭过期收款单、删除金额锁、把未付款订单置为已取消、放回优惠券；同一个接口顺带跑到账对账。
- **从没点过「去支付」的订单不会被自动取消**（`pay/vmq/create/route.ts:64-68` 的注释）。

### 2.8 付款成功后的跳转
- 收银台 `src/app/pay/[orderId]/page.tsx` 每 3 秒查一次状态（`:81`）。
- 付款成功 2.5 秒后跳转：发票类跳 `/lookup`，其余一律跳 `/orders`（`:103-104`），**跳转目标是写死的**。
- 状态接口不要求登录（`src/app/api/pay/vmq/status/route.ts:27-28`），只返回业务类型、金额和状态，不包含订单种类。

**对新设计的含义：** 要实现「付完直接到号码页」，需要状态接口多返回一个跳转去向，或者能按订单种类推出去向，不能让前端去猜。

### 2.9 枚举
- 付款方式：ALIPAY / WECHAT / BALANCE（`schema:389-393`）
- 付款状态：UNPAID / PAID / REFUNDED（`:395-399`）
- 交付状态：PENDING / PROCESSING / DELIVERED / CANCELLED（`:401-406`）
- 按 schema 铁律，**不得往现有枚举加新值**（`docs/多渠道分销-设计.md:394`）。新状态一律用字符串列。

## 3. 用户体系与钱包

- **余额的存储**：User 表的余额列（2 位小数，`schema:19`），加余额流水表（记录变动额、变动后余额、类型 REFERRAL/ADJUST/WITHDRAW、关联订单，`schema:325-343`）。类型的中文标签在 `src/lib/balance.ts:5-11`。
- **只有两个地方会写余额**：
  - 推荐返现结算（`src/lib/referral.ts:41-`）：在事务里加余额、读回变动后余额，用返现记录的唯一约束保证不重复入账。
  - 后台手工调余额（`src/app/api/admin/referrals/balance/route.ts:60-141`）：扣减用条件更新（余额够才扣），流水和余额在同一事务；借用金额锁表里的 `bal:` 前缀键，保证同一请求号只记一次账。
- **买家侧只读**：
  - 钱包接口的注释明确写了「没有余额付款、没有自助提现」（`src/app/api/account/wallet/route.ts:11-17`），渠道站直接 404（`:33-34`）。

- **余额退款**：没有。所有退款都是线下操作（`src/app/api/admin/orders/[id]/route.ts:830-870`）。
- **匿名下单**：不允许。

- **登录门禁**：前端要先等页面水合完成再判断登录态（`src/lib/use-hydrated.ts:18-24`，用法见 `orders/page.tsx:300-304`）。购买弹窗未登录时跳转 `/login?redirect=...`（`src/components/purchase-modal.tsx:259,321`）。

## 必须避免的坑

1. **载体商品会泄漏或被拦。** 上架就会进入商品列表、站点地图、落地页、营销、推荐、渠道候选；下架就会被建单和发起支付拒绝。必须设计「上架但不在任何地方列出」的标记，并且把每一处按「上架」查询商品的地方都补上条件。
2. **动态定价会被发起支付拦下。** `pay/vmq/create:99` 的比价和 `:71` 的 24 小时支付窗口必须针对接码单特殊处理，报价有效期不超过 20 分钟。
3. **取号「已有记录就直接返回」。** 不能在下单时就预建接码记录，否则付款后根本不会取号；定时轮询也只扫「等码中」的记录。按订单的参数应该放新表。
4. **换号时的成本上限从商品读。** 新板块要改成读订单快照。
5. **币种和精度。** hero-sms 是美元，最多 4 位小数，而接码记录的成本和取号上限都是 2 位小数，渠道利润还把成本当人民币。新字段一律存美元（4 位小数或整数的「微美元」）加人民币快照。
6. **拿不到成本。** 纯文本形态的取号返回没有成本，应改用能返回 JSON 的第二版接口。这一点需要只读核对 hero-sms 文档后确认，本次没有调用。
7. **上游请求没有超时，轮询是串行的。** 买家页面每 5 秒触发一次上游查询，量大时会被上游限流，定时任务也会超过 50 秒。
8. **退号结果没有检查。** 超时时向上游取消（`sms.ts:139`），但没看上游是否真的退了。如果上游拒绝，实际已扣费，记录却是「超时」，成本按 0 计，利润就被高估了。
9. **收到码后立即告诉上游「完成」**（`sms.ts:158`）。这样同一个号收不到第二条短信；如果要支持「再次获取验证码」，要改这里。
10. **收款方式对小额单不友好。**
    - 唯一金额最多加 0.49 元，对 1～3 元的单是很高的溢价；这部分差额也不进支付流水。
    - 金额池只有 50 格、全站共用。
    - 每人最多 3 张待付款单，每次都要手输金额，到账确认要 1～30 秒。
    - 建议把「充值余额、按次扣费」作为主路径。
11. **退款全靠人工。** 【待退款】只在备注里，没有推送、没有筛选，在站长手工取消前一直计入营收、会员等级和营销。接码量一大，运营负担会失控。
12. **现有余额可以提现。** 充值和退款不能混进 User 余额。钱包页文案「余额暂不能直接用于支付订单」要同步修改；余额支付要按店面开关，渠道站拒绝。
13. **各种钩子默认都会触发**：抽奖（门槛 0）、满减券、推荐价、单笔开票、首页实时成交、企业微信推送、付款邮件。要逐项写明排除逻辑，并在服务端落实，不能只靠前端不传。
14. **schema 铁律。** 只能新增表、新增可空列或带默认值的列、新增索引。不往现有枚举加值，不从现有表建外键指向新表。上线顺序是：备份 → 预览差异（零删除）→ 过 DDL 闸门（`scripts/ops/ddl-gate.sh`）→ 执行 db push，且不带 `--accept-data-loss` → 再换镜像。`scripts/deploy.sh` 已停用。
15. **构建前检查。** 不能在别处建订单、后台接口必须有守卫、接口里不能用不分店面的取用户函数、页面不能设为静态生成。
16. **主站后台看不到号码和验证码。** 新增后台接码记录页时要注意：接码表没有站点 id 列，归属要通过订单判断。
17. **导航太挤。** 768～900px 已经放了 8 项，标签只能用两个字。
18. **定时任务的运维细节。** 改任务表后要带 `--no-deps` 重建 cron 容器；启动命令里不能有反斜杠；文件必须是 LF 换行。
19. **备注最长 255 字。** 追加一律走截断函数。
20. **服务条款里没有接码的退款规则。** 服务条款第四节只写了订阅和卡密（`src/app/(shop)/terms/page.tsx:98-108`），需要补充。另外按交接文档 1816 的教训，所有面向买家的说明都要能在代码里找到出处。
21. **合规风险。** 《反电信网络诈骗法》严查接码和替他人做实名核验。建议后台可配置服务和国家黑名单，默认屏蔽中国境内的平台（微信、QQ、支付宝、淘宝、抖音等）以及中国号段（国家编号 3）。
22. **迟到的付款。** 超过 20 分钟才到账的付款会进入「待人工核实」，此时报价可能已经过时。取号时必须带上限价（等于报价成本），不能按实时价格无上限地取号。

## 需要新增的 schema 候选（全部遵守铁律）

1. **服务目录** `sms_services`：服务代码（唯一）、中英文名、图标路径（可空）、排序、是否热门、是否启用（兼做黑名单）、同步时间。
   - 用于服务搜索；搜不到时推荐「Any other」。它在 SMS-Activate 协议里通常是 `ot`，需要用服务列表接口只读核对确认。
2. **国家目录** `sms_countries`：hero-sms 国家编号（唯一）、中英文名、两位国家代码（用于国旗）、是否启用、排序。
3. **价格缓存** `sms_prices`：以「服务 + 国家 + 运营商」唯一；美元成本（4 位小数，或整数的微美元）、库存、同步时间。由定时任务同步，页面只读库、不直接打上游。
4. **接码订单快照** `sms_orders`：
   - 字段：订单 id（唯一）、用户 id、服务、国家、运营商、报价时的美元成本、汇率、加价（分）、单价（分）、美元上限价、报价过期时间、退款状态（字符串，如 NONE / PENDING / DONE）、退款金额（分）、退款时间、最终美元成本、最终成本（分）、利润（分）。
   - 与建订单在同一个事务里写入，做法同抽奖资格。
5. **取号尝试明细** `sms_activation_attempts`：订单 id、第几次、上游号码 id、手机号、美元成本、状态、取号时间、结束时间、结束原因。
   - 换号不再覆盖历史，方便核算成本和售后举证。
   - 另外可以给现有接码记录表加几个可空列：运营商、美元成本（4 位小数）、上次查询上游的时间（用于节流）。
6. **载体商品的标记**：给 Product 加一个带默认值的列，例如「是否在列表展示」（默认是）或「商品种类」。或者给发货方式启用一个新值（例如 SMS_ANY）；但 fulfillOrder、查询接口、后台取消、落地页介绍、付款邮件等多处写的是「等于 'SMS'」，用新值就要逐处决定走哪条逻辑。
7. **定价配置**：Setting 表的 `sms_pricing`，存一段 JSON，包含汇率、加价（分）、最低价、取整方式、最大换号次数、冷却秒数、超时分钟、服务和国家黑名单。这个方案不需要改表结构。如果要按服务或国家单独设置加价并审计，再建 `sms_price_rules` 表。
8. **钱包**（如果采纳）：
   - 两张表：余额表 `sms_wallets`（用户 id 唯一、余额（分）、版本号）；流水表 `sms_wallet_logs`（用户 id、变动额（分）、变动后余额（分）、类型 TOPUP / SPEND / REFUND / ADJUST、关联订单、幂等键（唯一）、备注、时间）。
   - 充值：直接复用订单加一个「接码余额充值」载体商品走现有收款流程，不必给收款单新增业务类型；付款后在 fulfillOrder 里按商品种类入账。
   - 扣款和退款：分别用 `spend:<订单id>`、`refund:<订单id>` 作幂等键，扣减用「余额够才扣」的条件更新。
9. **订单种类列**（可选）：给 Order 加一列订单种类，默认 `SHOP`，接码单写 `SMS`。好处是后台和买家订单列表可以直接筛选，收银台的跳转去向、各个钩子的排除都不用再关联商品表判断。
