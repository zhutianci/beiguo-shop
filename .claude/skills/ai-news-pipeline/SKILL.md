# 【AI圈大事记】内容管线规范

这份文档是这个模块的**契约**。代码可以重写，契约不能随手改——尤其是第 1 节的法律定性和第 6 节的标识义务，它们决定的是站点的合规底线，不是产品偏好。

---

## 1. 法律定性：这是「信息聚合工具」，不是新闻站

这条决定了其他所有设计。

**为什么**：《互联网新闻信息服务管理规定》第二条把「新闻信息」限定为「有关政治、经济、军事、外交等社会公共事务的报道、评论，以及有关社会突发事件的报道、评论」；第五条要求提供此类服务须取得许可，第十一条要求设总编辑、采编人员持新闻记者证。这个许可对本站不现实。**正确策略是让内容不落入该定义，而不是想办法拿证。**

### 1.1 硬性禁止（写进代码，不留后台开关）

| 禁止 | 原因 |
|---|---|
| 页面出现「记者」「编辑部」「独家」「爆料」「本站原创」「本网讯」 | 自证在做采编发布 |
| 给条目署任何真人姓名 | 同上。作者字段硬编码为 `贝果科技 AI 资讯助手`，后台不可改 |
| 整段复制原文正文 | 第十五条转载须来自中央/省级直属新闻单位，我们的信源都不在名单内。只能自写摘要 |
| 使用原文配图 | 媒体配图多为视觉中国/Getty 授权，单张索赔 2000–8000 元且有成熟维权产业链 |
| 页面提供任何用户可输入的 AI 入口（「让 AI 解读这条」） | 一旦提供即落入《生成式人工智能服务管理暂行办法》，需要上线备案 |
| 新闻页开放评论 | 本站论坛已落入《安全评估规定》范围；新闻页加文本 UGC 会触发重新自评估。讨论一律用按钮导流到论坛 |

### 1.2 选题黑名单（命中即 `BLOCKED`，不进队列，不入库正文）

以下**看起来是 AI 垂类、实际属于「社会公共事务」**，必须在分诊阶段就拦掉：

```
AI 监管立法、AI 法案、算法备案与行政处罚
芯片出口管制、实体清单、制裁、贸易战
国家级 AI 战略、政府采购、军事与国防应用
大规模裁员、罢工、集体诉讼
数据泄露的监管处罚、平台被约谈/下架
涉及具体政治人物、地缘冲突、领土主权的表述
```

判断从严：**拿不准就归入黑名单**。漏发一条产业动态的成本，远低于一条政策解读带来的定性风险。

### 1.3 允许的选题（企业经营动态与技术事实）

模型发布与版本更新 / 产品功能上线 / 开源项目与工具 / 论文与技术方法 / 融资并购与公司动态 / 基准测试与评测 / 开发者实践与教程 / 从业者公开观点。

## 2. 信源

### 2.1 分级

| tier | 含义 | 例子 | 默认权重 |
|---|---|---|---|
| 1 | 一手官方 | OpenAI/Anthropic 官方博客与官方账号、模型厂商 release notes、arXiv | 1.5 |
| 2 | 专业媒体 | 机器之心、量子位、InfoQ、TechCrunch、The Verge、Ars Technica、MIT TechReview | 1.0 |
| 3 | 从业者与社区 | Simon Willison、HN、GitHub Trending、X 上的研究者账号 | 0.7 |

`role` 字段区分用途：
- `feed`：产出时间轴条目
- `signal`：**只给已有事件加热度，不自己产条目**（HN、GitHub 属于这类，否则时间轴会被英文技术贴稀释）
- `both`：两者都做

### 2.1.1 线索源（第三方选题发现渠道）

与上面三种角色正交的一类源：它本身不是媒体，只告诉我们「**去哪儿看**」。
当前只有 AIHOT 一个（`kind='AIHOT'`，见 `docs/AIHOT线索接入.md`）。三条约束是硬的：

1. **只取选题发现信号**：标题 / 原文链接 / 原发布者名 / 发布时间。
   对方写的摘要、推荐理由、重要性评分、分类，一律不取 —— 取了既超授权范围，
   也违反 §1.1「只能自写摘要」。边界靠 zod 白名单 shape + 类型系统守，不靠注释提醒。
2. **原文抓不到就丢弃，不入库**。没有素材就写不出自写摘要，留着只会产生空壳条目。
3. **页面必须标注并回链**，且不计入 `sourceCount`——
   线索中介不是一家独立报道的媒体，计进去会让 §7 的「单源 tier3 → 待复核」闸门永不触发。

新增任何线索源都要走同样三条，并在 `docs/` 下留一份授权边界的书面对照表。

### 2.2 已实测的可达性（2026-09-04，从阿里云北京 ECS）

**直连可用**：机器之心 RSS、量子位、36氪、InfoQ、少数派、开源中国、掘金、AIbase、通义博客、hnrss.org、TechCrunch、The Verge、Ars Technica、MIT TechReview、微软研究院、OpenAI RSS、Anthropic News、GitHub API、arXiv API、Simon Willison。

**直连不可用**：X/Twitter、Reddit、HuggingFace（含 hf-mirror）、DeepMind、Meta AI、Mistral、Google News、V2EX、RSSHub 公共实例、CSDN、知乎热榜（需登录态）。

**新增信源前必须先实测**，不要凭印象加：

```bash
curl -sL -o /dev/null -w "%{http_code} %{time_total}s %{size_download}B\n" -m 12 \
  -A "Mozilla/5.0 (compatible; BigoLabBot/1.0)" "<FEED_URL>"
```

### 2.3 境外源中继（X / Reddit / HuggingFace 等）

大陆 ECS 直连不通的源，统一走 **Cloudflare Worker 中继**（免费档 10 万请求/天，转发是 I/O 等待不吃 CPU 配额）：

- Worker 必须做 **URL 域名白名单**。不做白名单等于在自己域名下开了一个公开 SSRF 代理。
- Worker 用 `Promise.all` 一次并发抓完全部境外源，把跨境往返从 N 次压到 1 次。
- 中继挂掉时所有一手源同时失联。必须有降级：中文源照常产出，`tier1Count` 与 HN 热度计 0，并在后台状态页标红。

X 账号的取数不要依赖非官方镜像（nitter 类实例已基本全部关停），要么走官方 API，要么在 Worker 里抓账号页。**无论哪种，抓到的推文必须标注为 `X：<显示名>（<身份>）(@<handle>)` 的完整形态**，不能只写「推特」。

## 3. 管线：五段，各自可独立重入

每一段都是独立的 cron 任务，**任何一段失败都不能影响其他段**。

```
① collect  每小时   抓 feed → 原始条目入 news_items（零 LLM、零依赖）
② triage   每小时   新条目分诊：是否 AI 相关、是否命中黑名单、归类（小模型）
③ cluster  每小时   同事件聚合：实体指纹召回 + 小模型判定 → news_events
④ compose  每小时   为够格的事件写摘要与推荐理由（大模型，唯一的写作题）
⑤ rank     每小时   重算热度分；每日 21:00 生成日报，每周一 09:00 生成周报
```

### 3.1 collect

- 单源超时 8s，**单源失败必须熔断隔离**，不能拖垮整批
- 限制单个响应体大小（建议 2MB）：2MB XML 的同步解析会阻塞 Node 事件循环几百毫秒，前台会卡
- 源与源之间主动让出事件循环（`await new Promise(r => setImmediate(r))`）
- RSS/Atom 解析用零依赖实现，与 `lib/aliyun.ts` 手搓签名的风格一致，**不要为此引入新 npm 依赖**
- 去重键：`[sourceId, urlHash]`。**urlHash 不能设全局唯一**——同一篇原文会同时出现在 TechCrunch 的 RSS 和 HN 的返回里
- 只取 feed 提供的标题 + description，**不抓原文正文**。这一个决定同时解掉三件事：不需要 jsdom/Readability（省 100MB+ 内存）、不需要 robots.txt 解析器（feed 本就是站点主动发布供订阅的）、规避整篇转载的著作权风险

### 3.2 triage（判断题，用便宜模型）

输入：标题 + description（截断到 500 字）。
**线索源条目没有 description**（对方的摘要不在授权范围内），改为先抓原文正文当输入，
抓不到就判 `SKIP`。只拿标题分诊会让 §1.2 黑名单判定明显变松，而判错的代价是合规风险。

**能力边界（必须知道）**：分诊看到的只是标题 + 一段摘要，**它没看过原文正文**。
一篇标题看着是「某公司发布新模型」的稿子，正文里完全可能带出出口管制、监管处罚、
大规模裁员。而 compose 会去抓正文、`detail` 更是直接从正文扩写 ——
那部分内容分诊从来没有过目。所以 compose 落库前必须再跑一道关键词兜底
（`score.ts` 的 `blocklistHit` / `forbiddenHit`），这不是冗余。
输出：

```jsonc
{
  "isAiRelated": true,
  "blocked": false,          // 命中 1.2 黑名单
  "blockReason": null,       // blocked 时必填，中文，用于后台复核
  "category": "ai-models",   // 见 §4
  "entities": ["OpenAI", "GPT-6"],  // 用于聚类指纹
  "confidence": 0.9
}
```

`blocked=true` 的条目**不进入后续任何环节**，但要保留原始记录供后台审计。

### 3.3 cluster

**不用向量检索**。MySQL 8 没有向量索引，而「实体指纹召回 + 一次约 300 token 的小模型判定」成本更低（约 0.6 元/月）且判定理由可审计。

流程：用 `entities` 交集 + 时间窗（48h）召回候选事件 → 小模型判定「是否同一事件」→ 合并或新建。

`sourceCount` 的统计口径必须是**先按 urlHash 去重、再数 distinct sourceId**，否则两家媒体转载同一篇原文会把跨源交叉验证信号刷成假的 2。

### 3.4 compose（唯一的写作题，用好一点的模型）

输入：该事件下所有信源条目的标题 + description + 来源名。
输出：

```jsonc
{
  "headline": "……",        // ≤ 40 字，事件级描述，不做标题党
  "summary": "……",         // 80–200 字。材料不足就写短，不许扩写
  "whyItMatters": "……",    // ≤ 60 字「推荐理由」，说明为什么值得看
  "aiScore": 81,           // 0–100，模型对重要性的判断，会展示给用户
  "facts": [               // 每个关键事实标注来自第几个信源，供人工一键复核
    { "text": "……", "sourceIndex": 0 }
  ],
  "detail": [              // 全文层：详情页用，2-4 段带小标题，总计 600-1200 字
    { "heading": "……", "body": "……" }
  ]
}
```

**summary 与 detail 的分工**：summary 是「一句话讲清发生了什么」（列表卡片用），
detail 是「把材料里的细节按逻辑铺开」（详情页用）。detail **不是把 summary 拉长**。

**detail 是可丢弃区块**：任何校验不过（段数/字数/连续 18 字重合/数字回查/禁词/黑名单）
就只丢这一块，事件本身照常发布 —— 页面退回「只有摘要」，那是完全合规的状态，
没有需要人工确认的残留。所以 **detail 的问题不进 `needsReview` 队列**，
只有 summary 层的问题才进（否则会用一个未标定的长文阈值挤占那 20 条的人工审核名额）。

**没有窗口，但有双车道**：compose 不再限定「只处理 7 天内的事件」——
那会让超期事件永远轮不到，表现为「只有最近一批」。改成固定名额的两条车道：
新鲜（3 天内，3 条/轮）+ 积压（更老，2 条/轮）。名额是**固定切分**而不是
「优先新鲜、有剩再给积压」：后者在信源稳定产出时永远剩不下名额。

**单轮墙钟 7 分钟**。crontab 的 `--max-time 540` 是硬上限，到点 curl 就断开、
服务端却还在跑并占着锁。**锁 TTL 永远不能大于 540s**，正确做法是让 compose
自己提前收工。任何「加长锁 TTL / 加大 --max-time」的改法都是错的。

**提示词必须明确写入的约束**：
- 「材料不足就写短，宁可 80 字也不要补充材料里没有的信息」
- 「不得出现材料中没有的数字、版本号、日期、人名、公司名」
- 「不得使用『据悉』『业内人士称』『有消息表示』等无主语转述」
- 「与原文连续 20 字不得重合」

### 3.5 rank —— 热度分

必须**可解释、可复现**。每个加分项拆成独立计数列并把明细落 `scoreDebug` JSON，后台能看到分是怎么来的。

```
score = (
    sourceCount * 2.0            // 跨源交叉验证，最强信号
  + tier1Count * 1.5             // 一手官方源
  + log10(1 + hnPoints) * 1.2    // HN 讨论度
  + log10(1 + githubStars) * 0.8
  + log10(1 + siteViews) * 0.6   // 站内浏览（去重后）
  + shareCount * 1.0
  + aiScore / 100 * 1.5          // 模型的重要性判断
) * timeDecay
```

`timeDecay = 0.5 ^ (ageHours / 36)`（36 小时半衰期）。

**分层重算，不扫全表**。去掉时间窗口后如果每 15 分钟把全部事件重算一遍，
`scoreDebug`（TEXT 列）的无谓写入会直接变成 binlog 与磁盘压力。按衰减曲线的形状分三层：
热层（72h 内）每轮算、温层（72h–14d）每小时算一次、冷层（14d 以上）只补 `baseScore` 为空的。

**`baseScore` 是不含衰减的原始分，必须单独落一列**。`score` 是 `Decimal(8,3)`，
约三周后所有老事件都 round 成 `0.000`，归档页要按热度排就再也排不出先后。
`baseScore` 不随时间变，是老事件唯一稳定的排序键。历史行为 NULL，由冷层每轮补 200 条自愈。

**读热度分的 select 必须含 `baseScore`**：漏了它，「分数没变就不写」那道护栏会恒判为脏，
于是每一轮都在全量 UPDATE 带 TEXT 列的行 —— 而这件事不报错，只是磁盘悄悄涨。

**站内浏览必须去重**：论坛现有的 `views: { increment: 1 }` 裸自增无去重无限流，直接拿来当讨论度会被爬虫刷榜。改为前端停留 3 秒后 `sendBeacon` 上报 + `(eventId, viewerKey, hourBucket)` 唯一约束去重——爬虫不执行 JS，天然被排除。

**冷启动**：前 4 周站内没有浏览/分享数据，排序几乎完全由 `sourceCount` 决定，会偏向「被中文媒体集体转载的事件」，漏掉重要但小众的一手发布。靠 `tier1Count` 加成缓解，仍需人工置顶兜底。

## 4. 分类（固定 6 类，不要随意增改）

分类一旦定下会影响 og 底图、URL、订阅，改动成本高。

| slug | 中文 |
|---|---|
| `ai-models` | 模型 |
| `ai-products` | 产品 |
| `industry` | 行业 |
| `paper` | 论文 |
| `tool` | 工具 |
| `opinion` | 观点 |

标签用 **60–80 个白名单词表**约束，AI 只能从表里选。允许自由生成标签会在三个月内长出几千个只有 1 条内容的话题页，对 SEO 是负资产。

## 5. LLM 供应商接入

### 5.1 抽象层

所有模型调用走 `src/lib/llm.ts` 的统一接口，**供应商可替换**：

```ts
interface LlmProvider {
  name: string
  chat(opts: {
    system: string
    user: string
    schema?: object      // JSON Schema，供应商支持则用结构化输出
    maxTokens?: number
    temperature?: number
  }): Promise<{ text: string; promptTokens: number; completionTokens: number }>
}
```

供应商由环境变量 `LLM_PROVIDER` 选择：`dashscope` | `deepseek` | `glm`。三家都兼容 OpenAI Chat Completions 格式，**换供应商只需要换 baseURL、apiKey、model 名**。

| 供应商 | baseURL | 大陆直连实测 |
|---|---|---|
| 阿里云百炼 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | ✅ 401 / 34ms |
| DeepSeek | `https://api.deepseek.com/v1` | ✅ 401 / 87ms |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | 需实测 |

`api.openai.com` 超时不可用，`api.anthropic.com` 返回 403，**均不可作为生产选项**。

### 5.2 结构化输出的两级降级

不同供应商对 JSON 输出的支持不一致，客户端必须写死这个降级链：

1. 先试 `response_format: { type: "json_schema", ... }`
2. 收到 400 就降级 `response_format: { type: "json_object" }`——**注意此模式要求 messages 里必须出现 "json" 字样**，否则服务端直接 400
3. 再失败就纯文本 + 正则提取首个 `{...}` 块
4. 无论哪条路径，最终都要用 **zod 校验**（项目已装 `zod ^3.23.8`，不需要新依赖）

### 5.3 成本控制

- **数据库级保证**：只对 `summaryState = 'RAW'` 的新条目调用大模型。成本失控的唯一现实路径是代码 bug（例如每小时把近 7 天条目全部重新摘要）
- **每日硬闸**：`news_daily_budget_cents`（默认 300 分/天）。超预算当天自动降级为「只去重、不写摘要」的简讯站，而不是继续烧钱
- **每次调用记账**：写 `news_llm_calls`（模型、tokens、耗时、估算成本、成功与否）。
  两个容易写错、且写错了不会报错的地方：
  ① 三级降级是**三次真实的、会计费的调用**，token 要 `+=` 累加而不是覆盖；
  ② **失败调用也要按真实 token 计费**。记 0 的后果是失败率一升高，
  真实花费涨、账面花费不动，`budgetExhausted()` 这道最后兜底永远不会触发。
- **单价必须到控制台核对**（`LLM_IN_PRICE` / `LLM_OUT_PRICE`）。它不影响调用本身，
  只影响记账 —— 而记账是预算闸门的唯一依据。填小 50 倍，闸门就形同虚设。
- **日界用固定 +8 偏移算术**，不要用 `new Date(y, m, d)`：那取的是进程本地时区的零点，
  而 alpine 不装 tzdata 时 `TZ` 会被静默忽略、进程仍跑 UTC，日界会偏 8 小时。
- **已发布事件不重写摘要**。只在 `sourceCount` 从 1 涨到 ≥3、或首次出现一手源时重写一次，且**一条事件终身最多重写 1 次**
- 把固定的 system prompt 逐字放在 messages 最前——多数供应商有隐式上下文缓存，命中部分按输入价约 20% 计费

### 5.3.1 思考（推理链）档位 —— 比换模型更影响成本

新一代模型默认带推理链，而推理链是按**输出 token** 计费的。必须显式控制，
不能靠默认值。2026-09-07 从生产 ECS 实测（同一条 compose 任务，各跑 3 次）：

| 模型 | 档位 | 耗时 | 输出 token | JSON 可解析 | detail 字数 |
|---|---|---|---|---|---|
| glm-4.7 | `disabled` | 9.5s | **476** | 3/3 | 518 |
| glm-4.7 | 默认（开） | 54s | **2534**（含 3626 字推理链） | 3/3 | 744 |
| glm-5.3-flash | `low` | 18.9s | 676 | 3/3 | 851 |
| glm-5.3-flash | 不传参数 | 48s | **2200（烧穿）** | **0/3** | 0 |
| glm-4-plus（旧） | 不支持 | 7.7s | 473 | 3/3 | 540 |
| glm-4-flash（旧） | 不支持 | 9.1s | 283 | 3/3 | **259（低于下限，会被丢弃）** |

三条结论：

1. **glm-5.3 / glm-5.3-flash 强制思考，关不掉**（错误码 1210「该模型始终思考，
   不支持关闭思考；请使用 low、high 或 max」）。不传控制参数会把 `max_tokens` 烧穿、
   返回截断的 JSON，三级降级全废 —— **等于管线瘫痪**。用它必须配 `reasoning_effort`。
2. **两种模型两套参数名**（实测得出，不是抄文档）：
   关思考用 `thinking: { type: 'disabled' }`，调档位用 `reasoning_effort: 'low'|'high'|'max'`。
   给强制思考的模型传 `thinking:{type:'low'}` 会被 400 拒绝。
3. **flash 不等于省钱**。glm-4-flash 写出来的 detail 只有 259 字，达不到下限会被整块丢弃 ——
   花了钱没拿到东西才是最贵的。而 glm-5.3-flash 因为强制思考，输出 token 比
   glm-4.7 关思考多 42%，耗时多一倍。

配置项 `LLM_THINKING`（disabled | low | high | max | off）。填错不会挂：
代码遇到「始终思考」的 400 会自动降到 `low` 重试并打警告。

### 5.4 模型别名会被重指

`qwen-flash`、`deepseek-chat` 这类是**别名不是快照**，供应商可以把它重新指向新版本并静默涨价。生产配置里写死具体版本号，并在后台状态页显示当前实际使用的模型名。

## 6. AI 生成内容标识（法定义务，不可省）

《人工智能生成合成内容标识办法》第四条要求文本在「起始、末尾或中间适当位置添加文字提示」，第五条要求文件元数据加隐式标识，且**覆盖下载/复制/导出场景**。

必须出现在**全部 6 处**：

1. 列表卡片上的「AI 摘要」徽章
2. 详情页正文开头的提示条
3. 详情页正文末尾的免责声明
4. 页面 HTML 的 `<meta name="ai-generated" content="true">`
5. **一键复制的分享文案里**（带「AI 摘要」字样）
6. **生成的分享海报上**（顶部徽章 + 底部脚注两处）

来源标注同样是硬要求：每条事件必须展示**全部信源的媒体名 + 可点击的原文外链**，且外链带 `rel="noopener noreferrer nofollow"`（`lib/markdown.ts` 已有此行为）。

## 7. 自动发布与人工干预

按用户决定：**全自动发布**，可疑条目在后台标注后人工确认。

```
新事件 → 自动发布到列表页与时间流
      ↘ 命中「可疑」条件 → 标记 needsReview=true，仍然发布，但：
                          · 不进首页热点位
                          · 不进「今日重点」「本周重点」
                          · 后台待办列表高亮
```

**统一口径：只有 summary 层的问题才进 `needsReview`。** detail 校验不过 → 丢弃这一块，不标；
线索素材不足 → 保持 DRAFT 不发布，也不标。队列上限是 20 条，
把不需要人看的东西灌进去，等于把这个机制变成摆设。

**「可疑」条件**（任一命中）：
- `triage.confidence < 0.7`
- 摘要与原文重合率落在健康带 `0.15–0.55` 之外（过低=可能编造，过高=可能抄袭）
- 摘要中出现材料里不存在的数字、版本号或实体（**数字回查**）
- 单源事件（`sourceCount = 1`）且信源为 tier 3
- LLM 返回被安全护栏拦截

**数字回查的能力边界**：它只能证明「摘要里的数字和实体出现在原材料里」，证明不了「材料本身是对的」，也拦不住实体关系颠倒（把「A 收购 B」写成「B 收购 A」时两个实体都在材料里，回查全部通过）。这类错误只能靠 `facts[].sourceIndex` 让人工一键跳转复核。**不能对外宣称零幻觉。**

**队列上限是必需项不是优化项**：待审队列一旦堆到三位数，管理员会直接放弃审核并把开关调成全自动——这是所有人工审核机制的真实死法。设 `news_pending_cap = 20`，溢出按热度自动降级处理。

## 8. 失败模式与兜底

| 失败 | 兜底 |
|---|---|
| 单个信源挂掉 | 熔断隔离，连续失败 3 次自动禁用并在后台标红，不影响其他源 |
| 境外中继挂掉 | 中文源照常，tier1/HN 信号计 0，后台状态页标红 |
| LLM 超时/额度耗尽 | 条目停在 `RAW` 状态，下一轮重试；连续失败则降级为「来源摘要」（直接用 feed 的 description，标注「未经 AI 摘要」） |
| LLM 返回格式非法 | 三级降级（§5.2），最终失败则记 `news_llm_calls` 并跳过该条 |
| cron 重叠执行 | 用 `VmqLock` 同款的唯一约束抢锁（`lib/vmq.ts:84-95` 有现成范式），本轮没抢到就直接退出 |
| 抓取任务变慢 | crontab 的 curl **必须带 `--max-time`**（**现已全部带上**：分钟级任务 50s、新闻管线 540s）。宁可漏一小时也不拖长任务，靠 guid 去重不会丢。注意这是**硬上限**：到点 curl 就断，服务端却还在跑并占着锁，所以各段要自带墙钟提前收工，且锁 TTL 不能大于它 |
| 内存打满 | app 容器已设 `mem_limit: 1024m`，爆炸限制在自己的 cgroup 内，不会波及 MySQL |
| 时区 | app 容器已设 `TZ=Asia/Shanghai`。但涉及「今日/本周」日切的计算仍应用固定 +8 偏移算术，不依赖进程 TZ（参考 `api/admin/analytics/cardkeys/route.ts` 的 `dayStartUtc` / `dayKey`） |
| 磁盘 | `news_items` 保留 30 天，`news_events` 保留 1 年。InnoDB 删行不释放文件空间，每天把表体积写入 Setting 供后台告警，需人工择时 `OPTIMIZE TABLE` |

## 9. 后台必备能力

- 事件列表：按状态/分类/热度/是否待审筛选
- 单条：改标题、改摘要、改分类标签、置顶、下线（`UNLISTED` 而非物理删除，保留证据）
- **拆分事件 / 从事件中移除某个信源**（聚类判错时的补救，前者更伤——用户会在信源列表里看到明显不相关的原文）
- 信源管理：启停、改 tier/role/权重、查看最近抓取状态与失败原因
- 手动触发某一段管线
- 抓取日志与 LLM 调用记账（含当日花费与预算余量）
- 侵权投诉入口：按《信息网络传播权保护条例》第十四条收集三要件（权利人姓名/联系方式、要求删除的作品名称与网址、构成侵权的初步证明），第十五条要求接到通知后**立即删除**
